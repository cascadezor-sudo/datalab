# Backup & recovery, фаза 1.1

Пользовательская страница: `storage-recovery.html` (на Pages — `/datalab/storage-recovery.html`). Все действия локальны, без загрузки файлов на сервер. Реальные данные пользователя не использовались при разработке и проверках.

## Пользовательский сценарий

1. Закрыть старые вкладки DataLab. Нажать «Скачать текущую копию» и убедиться, что файл сохранён браузером. Файл содержит личные учебные данные и не зашифрован.
2. Выбрать файл. Проверяются формат, версия, размер, структура и SHA-256. Предпросмотр показывает пути добавляемых, заменяемых и удаляемых полей DB/KV без вывода их значений. Для более 250 отличий выводятся первые 250 и полный счётчик с предупреждением; полный локальный diff можно сделать по двум экспортам.
3. Проверить source/target origin. Подтвердить замену: это полная замена DB/KV, включая удаления отсутствующих полей, а не автоматическое доменное объединение.
4. Применение использует ожидаемую ревизию предпросмотра. В одной readwrite-транзакции IndexedDB сохраняется предыдущее состояние в recovery store и применяется новое. Успех показывается после commit. Ошибка/новая ревизия не уничтожает текущее состояние; нужно повторить просмотр.
5. «Отменить последний импорт» работает только пока ревизия совпадает с результатом импорта. После любой новой записи отмена отклоняется, чтобы сохранить новые изменения. Предыдущие состояния доступны для скачивания в разделе истории.

Копия legacy внутри импортируемого файла — provenance, а не инструкция перезаписать живой localStorage или локальный неизменяемый архив миграции. Основные данные и оба маркера anonymous import хранятся в DB/KV и архиве; старый anonymous snapshot не запускает повторный импорт после активации IDB.

## Схема

Основной конверт:

```
format: "datalab-local-backup"
version: 1
createdAt: ISO timestamp
source: { origin, basePath }
snapshot: {
  schemaVersion: 1,
  state: { db: JSON object, kv: { audited-key: raw-string }, revision: integer },
  legacy: { rawEntries: { audited-key: exact-original-string }, checksum, ... }
}
integrity: { algorithm: "SHA-256", canonicalization: "sorted-json-v1", digest: hex }
```

SHA-256 вычисляется по UTF-8 JSON всего конверта, кроме `integrity`. Ключи объектов рекурсивно сортируются сравнением строк JS `.sort()`, порядок элементов массивов сохраняется, пробелы отсутствуют, примитивы кодируются `JSON.stringify`. Это проверка случайного повреждения, не подпись автора. Хеш проверяется повторно перед применением.

Пределы: файл не более 20 МиБ, глубина до 64 уровней, до 200000 элементов/полей; только JSON, без `__proto__`, `constructor`, `prototype`. Поддерживается только версия 1. Неизвестные DB-поля сохраняются; неоднозначные legacy ID не переименовываются. KV/legacy содержат только явно аудированные семейства ключей. Сессии, `auth_token`, `auth_user` и неизвестные ключи localStorage не включаются. Кеши роли/формата навигации и выбор ученика явно включены в whitelist новой полной копии IDB. Их строки не являются аутентификационными токенами.

Потенциальные секреты по известным именам полей и форматам токенов блокируют экспорт целиком без скрытого удаления частей. Структурированные JSON внутри raw-строк также проверяются. Эта эвристика не доказывает отсутствие любых секретов в произвольном тексте черновика; перед передачей файла другому человеку его нужно проверить. Секретные значения, намеренно спрятанные под произвольными именами, автоматически распознать невозможно.

## Старые клиенты и неудачная миграция

Изменения старой вкладки не объединяются автоматически. Сервис сохраняет источник legacy отдельно, блокирует обычные записи при расхождении и предлагает на recovery-странице скачать текущие raw-значения, посмотреть отличия и явно принять legacy. Проверяются одновременно ревизия IDB и SHA-256 просмотренного legacy-источника. Принятие заменяет DB/KV, сохраняет предыдущее состояние и обновляет baseline. Это контролируемый переход, а не абсолютная синхронизация с JavaScript старой версии.

Если исходная legacy DB повреждена, активация IDB не выполняется. Неизменяемый `legacy-original` уже сохранён и доступен в истории. Страница позволяет скачать точные raw-строки даже при отклонённой ready. После осознанного исправления исходного legacy-формата доступен отдельный предпросмотр «новая миграция». Подтверждение вызывает проверяемый retry: новая raw-копия фиксируется и проверяется до переноса, исходный архив остаётся, активация происходит только при отсутствии готовой DB и совпадении просмотренного источника. После commit страница перезагружается. Повторная загрузка не повторяет миграцию; нормальные startup-транзакции приложения могут увеличивать ревизию без изменения содержимого.

Вместо ручного исправления legacy можно выбрать исправную основную резервную копию прямо на странице после ошибки миграции. Предпросмотр явно сообщает об отсутствии действующей DB и независимом сохранении raw-источника. `bootstrapRestore` проверяет отсутствие активной DB, SHA-256 просмотренного legacy, валидность schema 1, фиксирует и проверяет исходные архивы и входящий снимок до активации. Затем одной транзакцией активирует DB/KV из копии с revision 0 и текущим legacy baseline. Исходные `datalab_offline_db`/anonymous raw не перезаписываются. При уже активной или несовместимой DB bootstrap запрещён; обычное восстановление требует её текущую ревизию. Успех приводит к reload. Этот сценарий проверен в реальном Chromium на повреждённом синтетическом исходнике.

Снимки без DB (исходные повреждённые raw, расхождения legacy) скачиваются в отдельном формате `datalab-legacy-archive`, version 1, с `archive` и тем же SHA-256-конвертом. Это диагностический lossless архив; обычный импорт DB его намеренно не принимает. Он не обозначается как готовое пользовательское состояние. Восстановление старой программы в исходный v1 localStorage автоматически не выполняется: оба источника нужно сначала сохранить и согласовать отдельно.

## Проверки

- `node --test tests/storage-recovery.test.cjs`: 5 проверок, round-trip неизвестных полей/пустых строк/маркеров, corrupt/version/secret/prototype/size rejection, nested deletion preview, truthful truncation.
- `node tests/browser/storage-recovery.cjs` с изолированным Playwright и Chromium: UI download/preview/restore/undo, stale revision, новые записи перед отменой, повреждённая копия без мутаций, история, old-client divergence, download/preview/adoption, reload, неудачная миграция и явный идемпотентный retry. Только fresh nonpersistent contexts и синтетические данные.

Recovery-снимки занимают квоту origin и автоматически не удаляются: это сохраняет возможность восстановления, но архив требует места. При нехватке квоты операция отклоняется, исходные данные не подменяются пустыми. Не обещается защита от ручного удаления origin, повреждения диска, внешнего удаления IndexedDB или враждебного JavaScript того же origin.
