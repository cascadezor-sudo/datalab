## До и после

До реализации изолированный `tests/browser/storage-multitab.cjs` снова завершился FAIL: 50 операций разрешились, отсутствовали 25 значений. После реализации исходные утверждения о всех 50 значениях и постороннем поле сохранены и проходят при повторном запуске. Наблюдатель читает актуальный источник через сервис: native JSON теперь намеренно заморожен и не является текущей БД. Это изменение места наблюдения не снижает требование сохранности данных.

Подтверждённый класс ошибки — read-modify-write всего дерева через отдельные localStorage-снимки не был общей транзакцией. Наблюдались последовательные записи устаревших снимков разными вкладками даже с Web Locks. Внутренний механизм кеширования Chromium не инструментировался, поэтому объяснение конкретным renderer cache остаётся интерпретацией наблюдений. Исправление устраняет необходимость в согласованности этих кешей: чтение и изменение актуального дерева выполняются в одной IDB readwrite-транзакции.

## Выбор архитектуры

| Вариант | Целостность / вкладки | Совместимость и сбои | Решение |
|---|---|---|---|
| IndexedDB с транзакцией | Атомарный read-modify-write; транзакции общего store упорядочены; успех после `oncomplete` | Сохраняется v1 JSON-дерево; отдельная схема физического хранилища; abort не активирует частичное состояние | Выбран после настоящего прототипа: исходные 50 значений прошли, затем расширенная матрица |

| Журнал операций | Может хранить независимые операции и давать replay | Нужны атомарный append, deduplication, конфликтная семантика и compaction; localStorage не решает их автоматически | Не добавлен: сложнее текущей задачи и требует отдельного протокола |

GitHub Pages не требует серверной БД: IndexedDB работает в браузере на HTTPS. Localhost и Pages имеют разные origin и разные состояния; `/datalab/` сам по себе origin не меняет.

## Новый слой хранения

`storage-service.js`: IDB database `datalab-state-v2`, физическая schema 1, stores `records` и `recovery`. Единственная активная запись `records/state` содержит `{schemaVersion, db, kv, revision, legacyBaseline, ...}`. `db` сохраняет существующее дерево v1 и обычные неизвестные поля; `kv` содержит аудированные raw-значения пользовательских ключей. Новые произвольные native-ключи не принимаются автоматически: они могут принадлежать сторонним приложениям или содержать секреты.

Основные операции: readiness/configure, `read`, `mutate`, `getKV/setKV/removeKV`, адресные Firebase-подобные операции через адаптер, подписка, recovery snapshots, restore/undo, просмотр и явное принятие legacy, bootstrap после неудачной миграции. `storage-recovery.js` добавляет проверяемый экспорт, разбор файла и предпросмотр поверх того же источника истины. Полная карта писателей: [storage-writers.md](storage-writers.md).

`mutate` получает свежий state внутри readwrite-транзакции, выполняет синхронный callback и сохраняет результат. Асинхронный callback отклоняется, транзакция прерывается. Promise разрешается только после `oncomplete`; throw/quota/abort отклоняются. Полученный snapshot изолирован от последующих мутаций. Обычные неизвестные поля сохраняются, опасные prototype-ключи и неподдерживаемые схемы отклоняются до активации. Cache ревизии не регрессирует при поздних уведомлениях.

Для независимых путей сохраняются все подтверждённые изменения. Для одного значения действует последний порядок commit; для read-modify-write используется callback внутри транзакции. Повтор одинакового `set` безопасен. Автоматическая deduplication произвольного повторно отправленного mutator по operationId не реализована и не обещается.

`BroadcastChannel` — только уведомление с последующим чтением IDB. При его отсутствии данные читаются актуально через API, но мгновенное межвкладочное обновление UI не гарантируется. Web Locks не требуется. Фиксация браузером не является доказательством сохранности при отключении питания или полном удалении origin пользователем.

## Интеграция

`firebase-mock.js` синхронно определяет совместимый API, а операции и auth callback ожидают готовность сервиса. Динамический loader сохраняет `/datalab/` и cache version исходного mock-скрипта. Init/seed, достижения, quiz repair, staff-писатели и обычные ref проходят через тот же механизм; `loadDb/saveDb` не могут писать вне транзакции. Достижения уведомляют после подтверждённого commit.

Активные JS-писатели черновиков и настроек переведены на managed service facade. Native setter fallback удалён. Исправлена отдельная inline-запись role cache в `main.html`; analytics interactive получил отсутствовавший bootstrap. До readiness native чтения допускаются для раннего оформления; `theme/palette/lang` имеют display-only native проекцию после commit, чтобы старый inline boot корректно рисовал тему и выбирал язык. Эта проекция не может перезаписать IDB. Наблюдённые чужие изменения проекции архивируются; возможно архивирование безвредного запоздавшего события.

Tracker подписан на подтверждённое состояние: отметки и очистка видны в другой вкладке. Одиночные и пакетные изменения не показывают успешную запись при отказе. Повторения рассчитывают расписание из актуального состояния в транзакции и продвигают карточку после commit, сохраняя неизвестные поля карточки. Исправлена асинхронная загрузка Python-черновика: она ожидает storage/auth, сохраняет пустую строку и не заменяет уже введённый пользователем текст поздним ответом. Цели, оформление, язык и demo milestones ожидают подтверждение перед соответствующим успехом/переходом. Autosave текста может оставаться неподтверждённым при внезапном закрытии; это не объявляется успешным сохранением.

## Миграция и старые вкладки

1. Native значения аудированных ключей читаются без удаления. Приоритет основной v1 DB сохранён; несколько старых кандидатов или некорректный JSON не заменяются пустой базой.
2. Исходные raw-строки и SHA-256 сохраняются как immutable `legacy-original` в IDB recovery store. Архив читается обратно и проверяется до преобразования.
3. Подготавливается v1-дерево, перенос legacy reports, одноразовый anonymous import и оба маркера: внешний managed `datalab_anonymous_import_v1` и внутренний `datalab_migrations.anonymous_progress_v1`. Исходные строки, черновики, тесты, повторения и обычные неизвестные поля сохраняются. Неоднозначные ID не переименовываются.
4. Активация нового state происходит атомарно только при его отсутствии. Повторный запуск использует активный IDB, а не повторяет старый импорт. Native DB и anonymous остаются исходной копией.
5. Ошибка не стирает источник. Если источник исправлен после неудачной попытки, автоматическая замена original-архива запрещена: используется явный предпросмотр/checksum и повторный перенос. Исправный backup можно импортировать без ручной правки native JSON через контролируемый bootstrap: архив исходника и входящего файла проверяется до активации. Ошибка активации оставляет активный state отсутствующим и позволяет повторить операцию.

Старый JS не соблюдает IDB-протокол. При наблюдаемом изменении защищённых native legacy-данных сервис атомарно архивирует расхождение и устанавливает сохраняемую блокировку `legacyConflict`. Даже возврат native raw к исходному виду сам не снимает блокировку. Новые операции отклоняются с указанием закрыть старые вкладки и открыть восстановление. Явное принятие требует актуальную revision и checksum просмотренного source и сохраняет предыдущую IDB-версию. Обе ветви остаются доступными для восстановления.

**Это контролируемый переход, а не абсолютная защита от старого произвольного JavaScript.** Старую вкладку невозможно заставить сообщать правду о её native-записи. Совместная работа старого и нового кода не поддерживается: старые вкладки нужно закрыть. Изменение старым клиентом сразу после проверки не входит в IDB-транзакцию; оно сохраняется в legacy-ветви и при обнаружении вызывает блокировку, а не скрытое объединение. Автоматическое принятие старого целого дерева не выполняется.

## Backup / restore / откат

Пользовательский путь: меню аккаунта → **«Резервная копия и восстановление»**, `storage-recovery.html`. Полная инструкция: [storage-recovery.md](storage-recovery.md).

Экспорт — `datalab-local-backup`, version 1, source origin/basePath, DB/KV, legacy raw, оба anonymous-маркера и SHA-256 canonical JSON. Есть ограничения размера 20 МиБ, глубины/сложности, схемы и опасных ключей. Известные секретные ветви/форматы блокируют весь экспорт, не вырезаются молча; auth/session не включаются. Поиск секретов эвристический: произвольный секрет в пользовательском коде нельзя гарантированно распознать. Файл не шифруется и не подписывается; SHA-256 проверяет целостность, не авторство.

Импорт проверяет файл до записи, показывает вложенные добавления/замены/удаления без значений и явно требует подтверждение полной замены. Для больших diff показывается ограниченный список с полным счётчиком. Если состояние изменилось после preview, expected revision не совпадёт и операция отклонится. До применения в той же IDB-транзакции создаётся копия текущего состояния; abort не оставляет частично применённую DB. Undo требует ревизию сразу после импорта: новые правки блокируют отмену, а не исчезают. История доступна для скачивания. После failed migration доступны сырой архив и импорт исправного файла с архивированием старого источника.

Откат к прежнему JavaScript не переносит новый IDB-прогресс обратно в замороженный native JSON. Поэтому простой возврат старых assets **не является откатом данных**. Перед сменой версии нужен внешний экспорт, закрытие старых вкладок и проверенный импорт через совместимый новый recovery UI. Автоматического обратного экспорта в старые native writers нет: он вернул бы исходную гонку. Очистка браузером всех данных origin уничтожит также внутренние архивы; необходим скачанный файл. Автоматическая чистка recovery history не реализована, архивы занимают квоту.

## Council

Роли: Storage Architect, QA Engineer, Compatibility & Security Engineer. Независимо сравнены варианты, затем проверены реальные изменения, обмен возражениями и финальные позиции. Первоначальное предпочтение IDB стало окончательным только после успешного настоящего прототипа.

QA возразил против вывода только по API-тестам: UI обнаружил native role-cache обход в `main.html` и гонку загрузки Python draft. Оба исправлены; соответствующие и полные клиентские проверки прошли. Архитектор потребовал убрать native setter fallbacks, не объявлять успех до commit, блокировать derived KV-writes и сохранять legacy-conflict latch; это реализовано. Security review обнаружил trap после failed migration и отсутствие bootstrap из исправного backup; добавлены контролируемый retry и bootstrap с failure/retry-проверкой.

Итог всех трёх позиций: открытых P0 в проверенных операциях новых клиентов не обнаружено; **критическая часть Фазы 1 закрыта**. Уверенность высокая для перечисленных Chromium-сценариев, ограниченная для других браузеров/больших реальных DB/аппаратных сбоев. Нет консенсуса в пользу абсолютной защиты от старого произвольного JS — такой гарантии реализация не даёт. Сильнейший контрпример для пересмотра — потеря подтверждённого независимого ключа в той же реальной матрице или успешный stale restore, удаливший более свежую запись.
