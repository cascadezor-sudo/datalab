# Контракты пользовательского хранилища: baseline

> Фаза 1.1: новый источник истины — IndexedDB `datalab-state-v2`, schema 1, stores `records`/`recovery`. В `records/state` остаётся дерево DB v1 вместе с managed KV, ревизией и метаданными перехода. Native legacy DB не обновляется: это сохранённый источник для восстановления. Все текущие writers основной БД используют транзакционный адаптер; JS-настройки и черновики — service facade. Три native ключа `theme`/`palette`/`lang` служат только проекцией раннего оформления/маршрутизации. Актуальная семантика, исключения и ограничения — в [phase-1.1-report.md](phase-1.1-report.md).

> Фаза 1: этот документ ниже фиксирует состояние до изменений. Новые правила, результаты и оставшиеся критические ограничения описаны в [отчёте Фазы 1](phase-1-report.md). В частности, Web Locks не обеспечил сохранность в проверке двух вкладок; не считайте параллельную запись безопасной.

Снимок кода: `95682d2e3aedaa4d0fa70ce009b899f68fba2cdd`, ветка `refactor/phase-0-baseline`. Статический анализ, без доступа к реальному browser storage. Ключи, raw-значения, идентификаторы и неизвестные поля — контракты совместимости; переименование и нормализация требуют отдельной проверенной миграции. LocalStorage принадлежит origin (scheme, host, port), а не пути: localhost и GitHub Pages имеют независимые данные; путь `/datalab/` сам по себе не создаёт отдельное хранилище.

Канбан и roadmap могут обновляться отдельными операциями; сохранение одной не гарантирует вторую. `kanban-board.js` и `course-roadmap.js` — клиенты; персональные настройки могут также быть в пользовательском объекте, поэтому нельзя экспортировать только перечисленные поля DB.

## Подтверждённые различия и риски

* `evaluateAchievementsOffline` берёт целую DB :541, ожидает сетевой fetch :605, при новом достижении сохраняет прежний объект :675–676. Запись другим действием/вкладкой в промежутке может исчезнуть. `repairOfflineQuizResults` :1073–1092 аналогично удерживает снимок через `await scoreOfflineQuizAttempt`; потеря возможна при `changed` и конкурирующей записи. Это доказательство последовательности кода, а не наблюдение потери реальных данных. Обычные отдельные read-modify-write также не имеют межвкладочной блокировки.
* Оба файла делают `Object.assign(window.achievementApi || {}, …)` (`achievement-api.js:510`, `firebase-mock.js:1284`): последняя реализация одноимённых методов побеждает. `main.html:1158,1404` и `achievements.html:623,771`: mock позже; `spaced-repetition.html:233,328`: component позже. Mock `submitQuizAttempt` :1060–1068 рассчитывает результат и сохраняет по quizId/attemptId, component :328–333 делает flat push исходной попытки. Реальный эффект зависит от вызывающего сценария и порядка загрузки; не утверждается, что каждый сценарий сейчас ломается.
* `progress-tracker-questions.js:296–298` требует truthy `.completed`; mock :559 принимает `true` или любое truthy значение, у которого `.completed !== false`; `spaced-repetition.js:262,288` использует разные условия (`status === completed` в одном месте и строго `completed === true` в другом). Например `{}` или `true` учитывается достижениями, но не как завершение tracker; `{status:"completed"}` не проходит строгую проверку карточки. Не унифицировать без решения по legacy-данным.
* Tracker берёт `.name.id` без namespace пути (:346–360). `python_versions` существует в `site/python/base.html:438` и `site/en/python/base.html:433`; общая запись доказана, намеренное ли это соответствие переводов — не установлено. Совпадение идентификатора разных учебных единиц приведёт к общей отметке; отдельный полный семантический аудит коллизий нужен до переименования. Ключ draft также включает qid без пути.
* `node tools/audits/storage-regressions.cjs` воспроизводит два дефекта на синтетическом Map в изолированном Node VM: очищенная отметка возвращается при повторной загрузке и обновление, записанное во время ожидания каталога достижений, исчезает после сохранения старого снимка. Команда сейчас возвращает код 1 и два `FAIL` — это известные дефекты, а не обращение к пользовательским данным. Конкуренция двух настоящих вкладок не проверялась; частота дефектов на реальных данных неизвестна.

В качестве следующего шага нужны атомарная или сериализованная модель записи, однократная отслеживаемая миграция с tombstones, единый контракт API и явное сопоставление ID. До реализации — резервная копия по соседнему плану; данные автоматически не очищать.

## Машинный указатель обращений

[storage-access-inventory.json](storage-access-inventory.json) содержит статические кандидаты в `site/**/*.js` и `site/**/*.html`: только путь, строка и тип операции. Перестроить: `python tools/audits/storage_inventory.py --write`; проверить актуальность без записи: `python tools/audits/storage_inventory.py --check`. Без аргументов команда только выводит количество. Прямые операции browser storage классифицированы по типу; `storage.alias.dynamic.*`, `storage.computed.dynamic` и `firebase.ref.dynamic` — кандидаты с неустановленным получателем. Обобщённое `.ref` может относиться к не-Firebase объекту. Регулярные выражения могут захватить комментарии и пропустить многострочные выражения, другие алиасы, вычисляемые имена, косвенные вызовы, сгенерированный или загруженный извне код. Список не доказывает полного покрытия и не заменяет ручную проверку семантики, зависимостей и runtime. Данные браузера генератор не читает.
