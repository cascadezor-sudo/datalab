# Фаза 1: отчёт об изменениях и проверках

Дата: 2026-11-14. **Статус: частично завершена. Критический блокер — воспроизводимая потеря записей в двух вкладках.** Изменения не следует считать доказанной защитой пользовательского прогресса или публиковать как законченное исправление.

## Исходное состояние

Работа начата на `refactor/phase-0-baseline`, HEAD `95682d2e3aedaa4d0fa70ce009b899f68fba2cdd`. Уже имелись незакоммиченные результаты Фазы 0, пользовательское изменение `site/profile.html` и неотслеживаемый `LEARNING_PROGRESS.md`. Для сохранения существующего набора изменений новая ветка не создавалась. SHA-256 обоих пользовательских файлов совпадает с исходным; staging, commit, push, публикация и доступ к реальному браузерному профилю не выполнялись.

## Что изменено

- `firebase-mock.js`: чтение каталога достижений до получения состояния, актуальное чтение/обновление под Web Locks для ref, оценки, исправления результатов и ряда бывших прямых писателей; прежний асинхронный снимок evaluator больше не сохраняется в протестированном сценарии. Два исходных диагностических сценария возвращают PASS. **Это не защищает все межвкладочные записи**, см. ниже.
- Одноразовый импорт `anonymous_progress` не заменяет уже существующие записи основной БД; источник сохраняется, маркеры хранятся внутри БД и в `datalab_anonymous_import_v1`. После удаления БД внешний маркер препятствует повторному импорту. При сбое миграции операции через lock отклоняются. `progress-tracker-questions.js` для offline-пользователя не примешивает старое зеркало обратно и не дублирует сохранение после API. Тесты охватывают старый импорт, повторный запуск, удаление и сохранение посторонних ветвей.
- Offline-адаптер является владельцем пересекающихся методов `achievementApi`; компонент заполняет отсутствующие методы. Оба порядка загрузки проверены в VM. Неизвестный вызов `achievementApi.call` теперь возвращает ошибку, а не фиктивный успех; существующие непредоставляемые offline-операции могут перейти в свои обработчики ошибок. Это заметное изменение поведения. Не все потребители проверены; `staffApi.call` для неизвестных методов всё ещё может возвращать успех.
- `DataLabProgress.isCompleted` трактует `true`, `{completed:true}`, `{status:'completed'}` и legacy-объект без этих полей как завершение; `false`, `null`, отсутствующее значение и `{completed:false}` — как незавершение. Компоненты тем, roadmap, quiz, повторения и главной используют предикат для соответствующих проверок. Данные массово не преобразуются; историческая запись завершения страницы не удаляется при изменении текущего списка. Семантика старых неоднозначных записей требует дополнительной проверки на реальных совместимых примерах без доступа к пользовательским данным.
- При ошибке одиночной отметки tracker перечитывает фактическое состояние БД, а если чтение не удалось — восстанавливает предыдущее отображение. Обработчики кнопок используют фактическое состояние; исключение по-прежнему отображает предупреждение. Это не гарантирует атомарность БД и зеркала.
- `exercise-checker.js` отправляет заголовок `X-DataLab-Local: 1` только для HTTP loopback, оставляет серверные проверки и авторизацию удалённого API, сообщает о недоступности runner на GitHub Pages. Сохраняемые результат и попытка относятся к фактически отправленному снимку кода; изменённый при выполнении черновик не удаляется.
- `tools/build-pages.mjs` копирует разрешённые форматы, исключает скрытые, резервные, временные, служебные и явно секретные имена и ссылки, проверяет результат. Он **отказывается перезаписывать любой непустой `.local/pages`**, поэтому повторный локальный запуск требует предварительно вручную разобрать старый результат. Исходные `.bak` не удаляются. Фильтр имён не обнаруживает секрет в содержимом разрешённого файла.

## Критический остаточный риск

`tests/browser/storage-multitab.cjs` создаёт новый непостоянный контекст Chromium с двумя вкладками одного origin, последовательно инициализирует на пустых страницах только `firebase-mock.js`, затем каждая вкладка делает по 25 разных `ref.set`. Все вызовы разрешились; третья вкладка обнаружила отсутствие одной полной серии из 25 записей. Тест многократно завершился с ошибкой, последний запуск — отсутствуют `a0…a24`. Синтетические данные; реальные профили не использованы. Фоновые компоненты страницы исключены. Наблюдались устаревшие снимки между контекстами при последовательном владении lock; внутренний механизм Chromium не установлен. Web Locks и успешный `setItem`/read-back не дают оснований утверждать надёжность данной схемы.

Инициализация, seed и некоторые legacy-миграции остаются вне общей блокировки; старые вкладки и браузеры без Web Locks тоже не участвуют в протоколе. Запись БД и `anonymous_progress` в отдельных ключах неатомарна: ошибка второй записи может последовать после успешной первой, поэтому UI предупреждает о частичном результате. Без безопасного межвкладочного протокола не выполнены критерии сохранности всех успешных записей и единого механизма.

## Проверки

- `node --test`: **22/22**. Python 3.12 из локального окружения добавлен в PATH текущего процесса, чтобы серверные тесты не пропускались.
- `python -m unittest discover -s tests -p 'test_*inventory.py' -v`: **6/6**. Обновлён статический `storage-access-inventory.json`: 669 кандидатов, `--check` exit 0. Это перечень кандидатов, не доказательство полноты всех runtime-писателей.
- `node tools/audits/storage-regressions.cjs`: **2/2 PASS** для исходных синтетических воспроизведений очистки и stale evaluator. Эти случаи не заменяют проваленный браузерный тест двух вкладок.
- `tests/browser/storage-multitab.cjs`: **FAIL**, 25/50 успешных записей отсутствуют; критический P0. Тест специально оставлен воспроизводимым и не входит в автоматический `node --test`.
- `tests/browser/storage-quota.cjs`: в изолированном Chromium искусственный отказ записи показывает предупреждение; отметка отражает сохранённое состояние до и после reload. Проверена одна ошибка quota в одном UI-сценарии.
- `tests/browser/python-checker.cjs`: реальный интерфейс с локальными Node и Python серверами; запросы без заголовка и с неверным Origin отклонены, проверены ошибка сервера, редактирование во время исполнения, сохранение отправленной версии и имитация GitHub Pages. Серверы по-прежнему работают на loopback; выполнение Python с правами пользователя не является полноценной песочницей.
- Изолированная сборка текущего сайта сохранила 189 HTML из 189 и исключила 12 `.bak`; имена 1843 остальных файлов совпали. Встроенная проверка префикса `/datalab/` прошла. Эта проверка сделана до последнего ужесточения отказа для непустого output, которое отдельно покрыто тестом. Реальный Pages не публиковался и не проверялся.
- Browser smoke: шесть страниц на 320/375/390/768/1440 px — HTTP 200, нет наблюдённых `pageerror` в коротком окне. Сценарии повторно показали результат quiz, математическую задачу и сохранение одной оценки карточки. Загрузка Pyodide в этом запуске не удалась из-за `net::ERR_NETWORK_ACCESS_DENIED`; выполнение Python-примера не подтверждено повторно. Запросы локального checker проверены отдельным тестом выше.

## Откат и совместимость

Ключ и дерево `datalab_offline_db` остаются v1, неизвестные поля при адресных операциях сохраняются в покрытых тестах. Новые маркеры миграции и сохранённое зеркало требуют согласованного восстановления вместе с основной БД. Откат к старому JS может снова включить импорт зеркала при каждом запуске и восстановить удалённые отметки; восстановление только старой БД рядом с новым внешним маркером может пропустить импорт. Старые и новые вкладки на одном origin одновременно дополнительно опасны. Готового пользовательского backup/restore и проверенного бесконфликтного пути отката нет; не выполнять его автоматически. [План восстановления](backup-recovery-plan.md) описывает необходимые условия.

Инженер безопасности подтвердил защиту пустого/непустого output и отметил ограниченность фильтра имён. Общий вердикт: **фаза частична, P0 не закрыт**. Нет доказательства, что редизайн модели хранения или конкретный механизм синхронизации уже безопасны.

## Оставшиеся задачи и готовность к Фазе 2

1. Спроектировать совместимую транзакционную модель с сохранением v1-данных, неизвестных полей, отказов, межвкладочного взаимодействия и старых вкладок; отдельно определить безопасный миграционный и обратный путь. Не считать задержку или Web Locks поверх текущего localStorage достаточным исправлением без доказательств.
2. Устранить потерю в `storage-multitab.cjs` и проверить настоящий браузер: разные ветви БД, сбои, инициализация, фоновые и старые писатели, закрытие вкладки и отключение/отсутствие Web Locks. Зелёная VM-имитация недостаточна.
3. Реализовать и испытать согласованный backup/restore, включающий оба маркера, БД, зеркало, неизвестные поля и изменения после снимка. Проверить непроверенные ошибки и потребителей API, в том числе `staffApi.call`.
4. Проверить Python UI на фактической конфигурации Pages/локального сервера; ограничения сетевой песочницы в этом запуске сохранились. Провести повторные сквозные сценарии и оценку безопасности разрешённых файлов артефакта.
5. В backlog без изменений в текущей фазе: пять отсутствующих иконок, ссылки `news.html`, переполнение roadmap при 320 px, аудит неоднозначных ID.

К Фазе 2 переходить только после устранения P0 и успешных проверок целостности и восстановления, согласования обратной совместимости и повторного Council review.
