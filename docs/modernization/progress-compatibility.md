# Совместимость каталога с прогрессом — Фаза 2

## Граница безопасности

Новый каталог — отдельная модель контента; он не является форматом пользовательского состояния. Production `storage-service.js` и schema IndexedDB не изменяются этой фазой. Основной контракт Фазы 1.1 остаётся: IndexedDB `datalab-state-v2`, версия 1, stores `records` и `recovery`; `records/state` содержит дерево `db`, managed строки `kv`, `revision` и метаданные. Legacy native localStorage остаётся источником восстановления, а не каталогом. Никакого чтения реальных пользовательских значений при этом аудите нет.

Read-only прототип `tools/content/progress-compatibility.cjs` принимает уже переданные вызывающей стороной synthetic records, mapping, registry и необязательный explicit review overlay. В Фазе 3 отсутствие registry всегда запрещает resolved result. Он не открывает IndexedDB/localStorage, не выполняет миграцию, запись, сетевые запросы, выдачу достижений или пересчёт результатов. Подключение его к production отсутствует. Авторизовать массовую миграцию этим прототипом нельзя.

## Правила разрешения

Mapping использует `{namespace, legacyId, source, canonicalId, status, candidates}`. `source` — точный путь исходника относительно `site/` из mapping (например `python/base.html`), либо `null` для глобального legacy ID. Возврат всегда содержит `status`: `resolved`, `ambiguous`, `deprecated`, `orphaned`, `pending_review` или `unresolved` (неизвестный/невалидируемый lookup). Разрешение возможно только при одном target, статусе resolved всех найденных строк и существующем target в переданном registry. Верифицирующие вызовы обязаны передавать registry; без него ни одна запись не может получить resolved; target обязан иметь active binding. Явные решения проверяются по сохранённым исходным candidates и review evidence, см. [id-resolution-report.md](id-resolution-report.md).

Resolver не выбирает scoped mapping вместо отсутствующего global mapping. Две страницы с одним `python_versions` (русская/английская Python Base) — подтверждённый пример необходимости выбора политики. Совпадение строк не доказывает переводческую эквивалентность. Если source известен из доверенного источника самой записи, можно передать scope явно; текущий URL пользователя не является таким доказательством для старой глобальной отметки. При ambiguous raw запись остаётся одной записью, без размножения completion в несколько canonical сущностей.

Независимый HTMLParser scan всех HTML обнаружил 1638 разных `.name[id]`, 1763 пары ID/страница и 124 ID, повторяющихся на нескольких страницах. Это не только переводы: `median` находится в `site/ai/ml/classic-cv.html` и `site/math/probability.html`; `typing_annotations` — в theory Python Base, его переводе и practice Python Base; `ce-interview`/`overfitting-interview` — в банках Classic ML и DL; `masked-attn-interview` — в DL и NLP. Без source глобальная запись не позволяет выбрать объект. Подсчёт включает `.name[id]` как статические кандидаты и не доказывает, что каждый из них активирован tracker в runtime.

Aliases должны быть явными отдельными строками mapping. Сам resolver не делает URL-нормализацию, decode URI, lowercase, split ID, удаление query или догадки по basename. Это позволяет не скрывать коллизии. Неизвестный ID или неподдержанный namespace остаётся unresolved. Если для удалённого source сохранён binding с aliases, mapping явно возвращает orphaned с прежними candidates; target не активируется.

`projectRecords` выдаёт ровно одну строку на входную запись: identity, resolution и независимую копию полного raw record. Не агрегирует два результата с одним canonical ID, не выбирает «последний», не склеивает пользователей/попытки/локали. Исходные unknown fields, awards, code, drafts и отрицательные/противоречивые результаты не теряются. Прототип предназначен для JSON-подобных данных без побочных getter; чтение private DB и дальнейшая редакция результата — ответственность будущего интеграционного слоя.

## Проверка и ограничения

`node --test tests/content-progress-compatibility.test.cjs` — 12 проверок после Фазы 3 (исходные сценарии и дополнительно active target, lifecycle decisions, все progress families): global ambiguity, точный scope, разделение namespace, отсутствие target, конфликт mapping, сохранность unknown historical award/fields, попыток теста и math draft identity. Интеграционная проверка читает persisted mapping/registry: `median` и `python_versions` глобально ambiguous, scoped `median` в probability/CV разрешается в разные существующие canonical ID; полный math draft ID разрешается, unknown award остаётся unresolved. Пользовательские записи исключительно synthetic; это не доказательство совместимости каждого существующего пользовательского состояния. Реальные данные не загружались и не мигрировались.

`python -m unittest discover -s tests -p 'test_content_progress_coverage.py' -v` — 2 независимые проверки покрытия фактического HTML, без повторного вызова генератора: каждый `.name[id]` присутствует в scoped/global topic mapping и нормализованных difficulty/review mappings; каждый `li.question[data-tests]` имеет exercise mapping; все 19 `data-answers` сохраняют math exercise и полный draft ID. Scoped candidates обязаны быть подмножеством global candidates. Это ловит пропущенные алиасы, но не доказывает идентичность содержимого совпавших ID.

Полнота извлечения ID проверяется отдельно валидатором контентного каталога. Даже полный статический source inventory не доказывает наличие всех исторических пользовательских IDs: каталог должен оставлять unknown/unresolved видимыми. До любой будущей миграции нужны экспорт и preview по контракту Фазы 1.1, решение по переводам/коллизиям, сохранение source metadata и отдельная проверка всех namespace. Это не разрешение проводить такую миграцию в Фазе 2.

Конфликт карточек подтверждён сравнением источников: runtime data содержит 5638 записей с 5628 уникальными ID, config snapshot — 4867 записей с 4857 уникальными ID. Все 4857 уникальных config ID встречаются в runtime data; внутри каждого источника также есть повторяющиеся ID. Сведение записей в словарь с выбором последнего дубликата скрывает различия отдельных occurrences, поэтому оно не доказывает эквивалентность карточек. Это разные snapshot с общими ID. Глобальное сопоставление должно явно ссылаться на обоснованный runtime authority либо оставаться ambiguous; происхождение, дубликаты и расхождения сохраняются. Каталог не переносит расписание повторений на дополнительную версию автоматически.
