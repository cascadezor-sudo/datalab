  1. Рабочий процесс в Jupyter Notebook

    Собеседование (Product Analyst / Data Scientist): Практический вопрос по культуре разработки: «Как вы организуете воспроизводимый исследовательский анализ (EDA) в Jupyter Notebook? Как бороться с проблемой скрытого состояния (Hidden State), версионированием в Git и как эффективно переносить прототипы из ноутбуков в продакшен-пайплайны?»

    Если совсем простыми словами: Jupyter — это лабораторный журнал, а не склад готового ПО. Он идеален для интерактивных графиков и гипотез, но без дисциплины быстро превращается в свалку ячеек, запущенных в случайном порядке, которые невозможно повторить через неделю.

    Стандарты зрелого рабочего процесса в Jupyter Notebook:

    1. Проблема скрытого состояния (Hidden State): Если запустить ячейку 10, затем изменить переменную в ячейке 2 и не перезапустить ядро, ноутбук находится в недокументированном состоянии. Золотое правило: Перед коммитом всегда выполнять Restart Kernel and Run All Cells. Ноутбук должен стабильно проходить сквозной запуск от начала до конца.
    2. Магические команды IPython (Magics): - `%load_ext autoreload` / `%autoreload 2`: Автоматическая перезагрузка внешних Python-модулей при их изменении на диске без рестарта ядра. - `%timeit -n 100 -r 5`: Прецизионный замер времени выполнения кода. - `%%prun`: Профилирование вызовов функций внутри ячейки.
    3. Версионирование в Git и Jupytext: Формат `.ipynb` — это тяжелый JSON, содержащий бинарные base64-картинки графиков. Коммитить сырые аутпуты — плохая практика. Решения: Использование `nbstripout` (очистка вывода перед коммитом) или `jupytext` (двусторонняя синхронизация ноутбука с чистым `.py` файлом в формате percent-script `# %%`).
    4. Структура аналитического ноутбука: 1. Назначение и контекст задачи (Markdown). 2. Импорты и фиксация seed. 3. Загрузка и валидация схемы данных. 4. Очистка и EDA. 5. Проверка статистических гипотез. 6. Бизнес-выводы и рекомендации.

    Кейс из продакшена: Аналитик презентовал результаты A/B теста руководству: эффект $+12\%$. При повторном открытии ноутбука разработчиком результат не сошелся (эффект $+1\%$). Причина: аналитик выполнил фильтрацию выбросов в отдельной ячейке, затем стер ее, сохранив измененную переменную в оперативной памяти. Внедрение pre-commit хука `nbstripout` и обязательного сквозного прогона исключило подобные инциденты в команде.

      Ситуация, когда переменные в памяти ядра не соответствуют текущему тексту ячеек из-за их выполнения не по порядку.

      Связывает `.ipynb` с обычным `.py` скриптом, позволяя редактировать код в IDE и хранить в Git чистый текстовый дифф без артефактов вывода.

    5. Какое правило является обязательным перед отправкой ноутбука коллегам?

      Выполнить Restart Kernel & Run All Cells и убедиться в отсутствии ошибок от начала до конца.

  2. NumPy и векторизация

    Собеседование (Data Analyst / Python Core): Фундаментальный технический вопрос: «Что такое векторизация и механизм Broadcasting в NumPy? Почему векторизованные операции на порядки быстрее циклов for в чистом Python и как устроено размещение массива ndarray в оперативной памяти?»

    Если совсем простыми словами: чистый Python — это медленный курьер, который носит по одному яблоку в коробке, а NumPy — железнодорожный состав. Вместо интерпретации типа каждой отдельной переменной в цикле процессору скармливается непрерывный блок памяти на языке Си, обрабатываемый за считанные такты через SIMD-инструкции.

    Низкоуровневое устройство массивов и правила векторизации:

    1. Анатомия объекта ndarray: - Непрерывный блок памяти (C-contiguous buffer) фиксированного типа (homogeneous dtype, например `float64`). - Метаданные: `shape` (размерности), `dtype` (размер элемента в байтах), `strides` (шаг в байтах при переходе к следующему элементу вдоль каждой оси). - В отличие от списка Python `list[float]`, где хранятся указатели на разрозненные объекты в куче (Pointer Indirection), NumPy размещает числа вплотную друг к другу в L1/L2 кэше процессора.
    2. Правила согласования размерностей (Broadcasting Rules): Две размерности совместимы, если: 1. Они равны ($d_1 = d_2$), ИЛИ 2. Одна из них равна единице ($d_1 = 1$ или $d_2 = 1$). NumPy виртуально растягивает единичную ось без физического дублирования данных в памяти (stride по этой оси устанавливается в $0$ байт!).
    3. Сравнение вычислительной сложности: Поэлементное умножение двух массивов длины $N$: - Python `for x, y in zip(a, b)`: $O(N)$ с колоссальными накладными расходами на проверку типов (dynamic dispatch) и распаковку объектов. - NumPy `a * b`: $O(N)$ на чистом C с оптимизацией векторизации AVX-512 (до 16 чисел `float32` за 1 процессорный такт!).

    Практический бенчмарк: Расчет евклидовых расстояний: Вычисление попарных расстояний между $1000$ точками и $1000$ центроидами ($1\,000\,000$ пар): - Вложенный цикл Python: $\approx 2.45$ секунды. - Векторизованный Broadcasting `np.linalg.norm(A[:, None, :] - B[None, :, :], axis=-1)`: $\approx 0.015$ секунды (ускорение в $160$ раз!).

    # Демонстрация векторизации и механизма Broadcasting в NumPy
import numpy as np
import time

n_points = 5000000

# Создаем два массива случайных величин
a = np.random.randn(n_points).astype(np.float64)
b = np.random.randn(n_points).astype(np.float64)

# 1. Медленный подход: цикл Python
t0 = time.perf_counter()
res_loop = [x * y + 2.0 for x, y in zip(a[:100000], b[:100000])] # замеряем только 100k, иначе слишком долго
t_loop_scaled = (time.perf_counter() - t0) * 50 # экстраполяция на 5 млн

# 2. Быстрый подход: векторизация NumPy (SIMD)
t0 = time.perf_counter()
res_vectorized = a * b + 2.0
t_numpy = time.perf_counter() - t0

print(f"Размер данных: 5,000,000 элементов")
print(f"Время цикла Python (оценка): {t_loop_scaled:6.3f} сек.")
print(f"Время NumPy векторизации:    {t_numpy:6.3f} сек.")
print(f"Ускорение вычислений:        в {t_loop_scaled / t_numpy:6.1f} раз!")
    • Использование цикла for для обхода элементов массива ndarray. Полностью нивелирует преимущества NumPy и работает медленнее стандартных списков Python.
    • Создание огромных промежуточных тензоров при Broadcasting. Выражение `A[:, None] - B[None, :]` для $100\,000$ элементов создаст матрицу $100\,000 \times 100\,000$, вызвав падение по Out Of Memory (OOM).
    • Ошибочное предположение о копировании данных при сглаживании или срезах. Срезы `arr[1:5]` создают View (представление), а не копию. Изменение среза меняет исходный массив!
    • Непреднамеренное повышение типов (Type Upcasting). Сложение `float32` и `float64` неявно удваивает потребление памяти массивом.

    На собеседовании: объясните механизм Strides (шагов смещения по памяти). Упоминание того, что при Broadcasting размерность 1 имеет шаг `stride = 0`, производит сильное впечатление на интервьюера.

    1. Что такое Broadcasting в NumPy?

      Механизм автоматического виртуального согласования массивов разной формы для выполнения поэлементных операций без физического копирования данных.

    2. Почему векторизация работает быстрее циклов Python?

      Благодаря непрерывному размещению в памяти, отсутствию динамической проверки типов на каждой итерации и задействованию SIMD-инструкций CPU.

    3. Что такое Strides (шаги) в ndarray?

      Кортеж чисел, показывающий, на сколько байт нужно сместиться в памяти, чтобы перейти к следующему элементу вдоль соответствующей оси.

    4. Создает ли срез `a[::2]` копию массива?

      Нет, срез возвращает View (представление), ссылающееся на тот же буфер памяти с измененным stride.

    5. Когда две размерности совместимы по правилам Broadcasting?

      Когда они строго равны либо когда одна из них равна 1.

  3. Основы Pandas: DataFrame и Series

    Собеседование (Data Analyst): Базовый архитектурный вопрос: «Как устроены структуры данных Series и DataFrame в Pandas? Как оптимизировать потребление оперативной памяти датафреймом в 3-5 раз при работе с большими датасетами?»

    Если совсем простыми словами: Series — это именованный одномерный массив с индексами, а DataFrame — двумерная таблица из таких колонок. По умолчанию Pandas выделяет память с огромным запасом (64-битные типы и строки-указатели), из-за чего таблица на 500 МБ на диске может раздуться до 5 ГБ в RAM.

    Внутреннее устройство и техники оптимизации памяти (Memory Optimization):

    1. BlockManager в архитектуре Pandas: - Внутри DataFrame колонки одинакового типа группируются в многомерные блоки (`FloatBlock`, `IntBlock`, `ObjectBlock`). - Тип `object` хранит не сами строки, а 64-битные указатели на Python-объекты `PyObject` в куче, порождая колоссальный оверхед памяти и кэш-промахи CPU.
    2. Понижение числовых типов (Downcasting): - По умолчанию целые числа читаются как `int64` (8 байт на число). Если значения лежат в диапазоне $0-100$, достаточно `uint8` (1 байт) — экономия $87.5\%$. - Дробные числа: перевод `float64` в `float32` экономит ровно $50\%$ памяти.
    3. Категориальный тип данных (Categorical dtype): - Для строковых полей с повторяющимися значениями (статусы, города, категории, пол) тип `category` заменяет строки на словарь целых чисел (`codes` + `categories`). - Снижает потребление памяти строковой колонки в $5-10$ раз и многократно ускоряет операции `groupby`.
    4. Глубокий аудит памяти: Вызов `df.info()` показывает поверхностный размер. Реальное потребление с учетом строковых объектов показывает строго `df.info(memory_usage='deep')`.

    Кейс оптимизации памяти на 5 млн строк: Датасет логов пользователей: - До оптимизации: все числовые поля `int64`/`float64`, строки `object`. Общий объем RAM: $2\,450$ МБ. - Применение `downcast='integer'` + `category` для полей `country` и `device`: - После оптимизации: $410$ МБ (сокращение потребления памяти на $83\%$!). Ноутбук перестал падать в OOM при построении отчетов.

    # Универсальная функция оптимизации памяти Pandas DataFrame
import pandas as pd
import numpy as np

def optimize_dataframe_memory(df):
    start_mem = df.memory_usage(deep=True).sum() / (1024**2)
    
    for col in df.columns:
        col_type = df[col].dtype
        
        # Оптимизация целых чисел
        if np.issubdtype(col_type, np.integer):
            df[col] = pd.to_numeric(df[col], downcast='integer')
            
        # Оптимизация вещественных чисел
        elif np.issubdtype(col_type, np.floating):
            df[col] = pd.to_numeric(df[col], downcast='float')
            
        # Оптимизация строковых объектов с низкой кардинальностью
        elif col_type == 'object':
            num_unique = df[col].nunique()
            num_total = len(df[col])
            if num_unique / num_total < 0.5: # если уникальных значений меньше 50%
                df[col] = df[col].astype('category')
                
    end_mem = df.memory_usage(deep=True).sum() / (1024**2)
    reduction = 100 * (start_mem - end_mem) / start_mem
    print(f"Память ДО: {start_mem:.2f} МБ | Память ПОСЛЕ: {end_mem:.2f} МБ | Снижение: {reduction:.1f}%")
    return df

    • Перевод в тип category колонок с высокой кардинальностью (High-cardinality strings, например уникальные ID или UUID). Только увеличит расход памяти из-за накладных расходов на поддержание словаря.
    • Забывание о том, что операции над category могут неявно возвращать object. Некоторые строковые методы `.str` сбрасывают тип категории обратно в object.
    • Хранение дат в виде строк object вместо типа datetime64[ns]. Строковые даты занимают в 4 раза больше памяти и не поддерживают временные выборки.

    1. Чем Series отличается от DataFrame?

      Series — это одномерный массив с индексными метками; DataFrame — двумерная табличная структура, состоящая из столбцов Series с общим индексом.

    2. Зачем использовать dtype='category'?

    4. Как безопасно понизить разрядность целочисленных колонок в Pandas?

    5. Что такое BlockManager в архитектуре Pandas?

  4. Выборка и фильтрация в Pandas (loc, iloc, query)

    Собеседование (Data Analyst): Каверзный вопрос по индексации: «В чем принципиальная разница между .loc, .iloc и методом .query()? Почему возникает предупреждение SettingWithCopyWarning, чем оно опасно и как гарантировать корректное изменение данных в датафрейме?»

    Если совсем простыми словами: .loc ищет по именам и подписям, а .iloc — по физическим порядковым номерам строк и столбцов. Цепочечная фильтрация `df[mask]['col'] = val` — главная причина скрытых багов в Python: вы можете случайно модифицировать временную копию в воздухе, оставив исходный датафрейм нетронутым.

    Сравнительный анализ методов доступа и фильтрации:

    МетодТип адресацииГраницы диапазона (Slicing)Пример
    .loc[rows, cols]По меткам индекса и именам колонок (Labels)Включая обе границы $[start, stop]$df.loc['2026-01-01':'2026-01-05', 'revenue']

    Механика SettingWithCopyWarning: Когда вы пишете `df[df['a'] > 0]['b'] = 10`, операция делится на два шага: 1. `__getitem__`: возвращает результат фильтрации (неизвестно: срез памяти или новая копия). 2. `__setitem__`: пытается записать значение `10`. Если `__getitem__` вернул копию, значение запишется во временный объект, который тут же уничтожится сборщиком мусора, а исходный `df` не изменится! Правильное решение: Всегда использовать единый метод `.loc`: `df.loc[df['a'] > 0, 'b'] = 10`.

    Практический пример лаконичного кода с .query(): Вместо громоздких скобок и битовых операторов: `df[(df['country'] == 'RU') & (df['age'] >= 18) & (df['spend'] > 1000)]` Используется читаемый синтаксис: `min_spend = 1000` `df.query("country == 'RU' and age >= 18 and spend > @min_spend")`

    • Забывание о том, что срез .loc включает правую границу диапазона. `df.loc[0:5]` вернет 6 строк (с 0 по 5 включительно), тогда как `df.iloc[0:5]` вернет 5 строк.

      .loc адресует строки и столбцы по их меткам/именам; .iloc адресует строго по целочисленным позициям от 0 до N-1.

    2. Включает ли срез .loc правую границу диапазона?

      Да, в отличие от стандартных срезов Python, срез `.loc['a':'c']` включает элемент `'c'`.

    3. Почему возникает предупреждение SettingWithCopyWarning?

      Когда Pandas не может гарантировать, выполняется ли присваивание в исходный датафрейм (View) или во временную копию (Copy).

    4. Как обратиться к внешней Python-переменной внутри метода .query()?

      Через префикс `@` (например, `df.query('col > @my_var')`).

    5. Почему нельзя использовать `and` при фильтрации через булевы маски Series?

      Потому что `and` пытается вычислить единую булеву истинность всего массива, что неоднозначно; нужно использовать побитовое `&`.

  5. Группировка данных (groupby) и агрегации

    Собеседование (Data / Product Analyst): Один из главных вопросов на лайвкодинге: «Как работает парадигма Split-Apply-Combine в Pandas? Чем принципиально отличаются методы .agg(), .transform(), .filter() и .apply()? Почему злоупотребление .apply() драматически замедляет выполнение кода?»

    Если совсем простыми словами: .agg() сжимает каждую группу в одну строчку (агрегация), а .transform() считает статистику группы и размножает ее обратно на все строки исходного размера. Метод `.apply()` — это медленный универсальный молоток, который вызывает интерпретатор Python построчно, игнорируя быстрые C-оптимизации.

    Анатомия Split-Apply-Combine и методов агрегации:

    1. Парадигма Хэдли Уикхема (Split-Apply-Combine): - Split: Разбиение датафрейма на группы по значениям ключей. - Apply: Применение вычислений к каждой группе автономно. - Combine: Сборка результатов в единую результирующую структуру данных.
    2. Различия между методами обработки групп:
      • .agg() (Aggregate): Уменьшает размерность. Возвращает по 1 значению на группу. Поддерживает оптимизированные функции Cython: `'mean'`, `'sum'`, `'count'`, `'std'`.
      • .transform(): Сохраняет исходную размерность. Результат имеет точно такое же число строк, как исходный датафрейм. Идеально для нормализации признаков (Z-score внутри когорты) и расчета доли строки от общего объема группы.
      • .filter(): Фильтрует целые группы по предикату (например, оставить только категории, где суммарная выручка превысила 1 млн рублей).
      • .apply(): Универсальная функция обратного вызова (Python callback). Вызывает функцию на каждом под-датафрейме. В 20-100 раз медленнее .agg() из-за невозможности векторизации.
    3. Именованная агрегация (Named Aggregation): Современный стандарт читаемого синтаксиса без создания запутанных MultiIndex-колонок: `df.groupby('dept').agg(avg_salary=('salary', 'mean'), max_age=('age', 'max'))`.

    Практический пример применения .transform(): Задача: рассчитать отклонение чека конкретной покупки от среднего чека в данном городе: `df['city_avg_spend'] = df.groupby('city')['spend'].transform('mean')` `df['spend_diff'] = df['spend'] - df['city_avg_spend']` Без джойнов и промежуточных таблиц — в одну строчку с сохранением индексов!

    # Сравнение .agg(), .transform() и Named Aggregation в Pandas
import pandas as pd
import numpy as np

df = pd.DataFrame({
    'category': ['Electronics', 'Electronics', 'Electronics', 'Clothing', 'Clothing'],
    'item': ['Phone', 'Laptop', 'Headphones', 'Shirt', 'Jeans'],
    'price': [50000, 120000, 8000, 3000, 6000]
})

# 1. Named Aggregation через .agg(): компактные плоские колонки
summary = df.groupby('category').agg(
    total_revenue=('price', 'sum'),
    avg_price=('price', 'mean'),
    item_count=('item', 'count')
).reset_index()

# 2. Использование .transform() для расчета доли товара внутри его категории
df['category_total'] = df.groupby('category')['price'].transform('sum')
df['category_share_pct'] = (df['price'] / df['category_total']) * 100.0

print("Сводная аналитика по категориям (.agg):")
print(summary)
print("\nИсходный датафрейм с долями категорий (.transform):")
print(df[['category', 'item', 'price', 'category_share_pct']])
    • Использование .apply() для стандартных математических агрегаций. Вызов `df.groupby('x').apply(lambda g: g['y'].sum())` работает в десятки раз медленнее нативного `.agg('sum')`.
    • Забывание reset_index() или as_index=False. Группировка по умолчанию превращает ключи группировки в индекс, что создает неудобства при последующих операциях слияния.
    • Работа с категориальными переменными без observed=True. При группировке по категориальным колонкам Pandas по умолчанию создает декартово произведение всех возможных категорий, включая пустые комбинации.
    • Случайная мутация глобальных переменных внутри функций для .apply(). Функция в .apply() вызывается на первой группе дважды (для проверки возвращаемого типа), что может исказить сайд-эффекты.

    На собеседовании: продемонстрируйте знание Named Aggregation (синтаксис `new_col=('source_col', 'agg_func')`) и мощь .transform(). Это сразу отличает опытного практика от новичка.

    1. В чем различие между .agg() и .transform()?

      .agg() сворачивает каждую группу в одно итоговое значение; .transform() возвращает массив той же длины, что и исходная группа, транслируя результат на каждую строку.

    2. Что такое Named Aggregation в Pandas?

      Синтаксис `.agg(col_name=('orig_col', 'func'))`, позволяющий задавать имена колонок и типы агрегаций без появления сложного двухуровневого MultiIndex.

    3. Почему метод .apply() работает медленнее векторизованных агрегаций?

      Потому что он выполняет итеративный вызов пользовательской Python-функции на уровне каждой подгруппы без низкоуровневых оптимизаций C/Cython.

    4. Что делает метод .filter() у объекта groupby?

      Фильтрует и возвращает строки тех групп целиком, для которых пользовательское условие вернуло True.

    5. Зачем использовать параметр `as_index=False` в groupby?

      Чтобы ключи группировки оставались обычными столбцами датафрейма, а не перемещались в индекс.

  6. Слияние таблиц: merge, join, concat

    Собеседование (Data Analyst): Стандартный блок задач по манипуляции данными: «В чем различия между pd.merge(), df.join() и pd.concat()? Как работает валидация кардинальности связей (параметр validate), почему при Left Join целочисленные колонки могут неявно превратиться во float и как отладить пропущенные ключи с помощью indicator=True?»

    Если совсем простыми словами: merge — это SQL-джойны по колонкам, join — быстрое соединение по индексам строк, а concat — склеивание таблиц стопкой (друг под другом или бок о бок). Неявные дубликаты ключей в джойнах — скрытый кошмар аналитика, раздувающий размер таблицы в миллионы строк из-за эффекта декартова произведения.

    Методология и правила объединения данных в Pandas:

    1. Типы операций соединения: - `pd.merge(df1, df2, on='key', how='inner|left|right|outer|cross')`: Полный аналог реляционного SQL JOIN по любым совпадающим столбцам. - `df1.join(df2, on='key')`: Соединение, оптимизированное для объединения по индексам строк (Index-based join). - `pd.concat([df1, df2], axis=0|1)`: Физическое конкатенирование вдоль оси: `axis=0` (добавление новых строк снизу), `axis=1` (приклеивание новых колонок справа).
    2. Защита от декартова взрыва (Параметр `validate`): Параметр `validate` гарантирует соответствие кардинальности связей: - `'one_to_one'` (1:1): Ключи уникальны в обеих таблицах. - `'one_to_many'` (1:N): Ключ уникален в левой таблице. - `'many_to_one'` (N:1): Ключ уникален в правой таблице. Если в таблице окажутся неожиданные дубликаты, Pandas мгновенно выбросит исключение `MergeError`, предотвратив искажение бизнес-метрик.
    3. Аудит джойнов через `indicator=True`: Создает служебную колонку `_merge` со значениями `'left_only'`, `'right_only'`, `'both'`, позволяя мгновенно изолировать несошедшиеся записи.
    4. Проблема Int $\to$ Float в классическом Pandas: В старых версиях NumPy стандартный `int64` не поддерживал `NaN`. Если при `left join` ключ не находился, вся целочисленная колонка неявно приводилась к `float64`. В современном Pandas это решается использованием расширенного типа `Int64` (Nullable Integer) или PyArrow backend.

    Кейс из продакшена: Потеря денег из-за дубликата ключей: Таблица заказов ($10\,000$ строк) объединялась с таблицей скидок по `user_id`. В таблице скидок для одного пользователя было две активные записи. Джойн размножил строки, сумма выручки задвоилась, и отчет завысил продажи на $3.5$ млн рублей. Использование `validate='many_to_one'` выбросило бы ошибку на этапе выполнения и предотвратило выпуск ошибочного отчета.

import pandas as pd

orders = pd.DataFrame({

# Слияние с проверкой Many-to-One и индикатором сопоставления
merged_df = pd.merge(
    orders,
    customers,
    on='customer_id',
    how='left',
    validate='many_to_one', # выбросит ошибку, если в customers найдутся дубли customer_id!
    indicator=True

print("Результат объединения с аудитом _merge:")
print(merged_df)

# Изоляция заказов с потерянными клиентами:
unmatched = merged_df[merged_df['_merge'] == 'left_only']
print(f"\nЗаказов без найденного профиля клиента: {len(unmatched)}")

    • Конкатенация таблиц pd.concat([df1, df2]) без ignore_index=True. Приводит к дублированию индексных меток, что вызывает трудноуловимые баги при последующей выборке `.loc`.
    • Несовпадение типов ключей объединения (например, str '123' и int 123). Pandas вернет пустой результат объединения без предупреждений.
    • Забывание суффиксов (suffixes) при совпадении имен колонок. Приводит к автоматическому созданию колонок `col_x` и `col_y`, ломающим дальнейший код обработки.

    На собеседовании: всегда упоминайте аргумент validate='many_to_one' и флаг indicator=True. Это визитная карточка инженера, знающего цену качеству данных.

    1. Чем pd.merge() отличается от pd.concat()?

      merge соединяет таблицы горизонтально по совпадающим ключам (как SQL JOIN); concat склеивает массивы вдоль заданной оси (по строкам или колонкам).

    2. Зачем использовать параметр `validate` в pd.merge()?

      Для автоматической проверки ожидаемой кардинальности связи (1:1, 1:N, N:1) и защиты от появления дубликатов.

    3. Что показывает колонка `_merge` при включенном `indicator=True`?

      Источники строки: 'both' (ключ найден в обеих), 'left_only' (только в левой), 'right_only' (только в правой).

    4. Почему в классическом Pandas целочисленные колонки при Left Join превращаются в float?

      Потому что стандартные целочисленные типы NumPy не поддерживают значение NaN; пропуски кодируются через float64.

      Использовать Nullable integer тип Pandas (`Int64` с большой буквы) или типы PyArrow.

  7. Решейпинг данных: pivot_table и melt

    Собеседование (Product Analyst / BI): Практическая трансформация матриц: «В чем разница между широким (Wide) и длинным (Long / Tidy) форматами данных? Как трансформировать данные между ними с помощью pivot_table() и melt(), чем pivot отличается от pivot_table и как расплющить (flatten) составной MultiIndex колонок после сведения?»

    Если совсем простыми словами: melt плавит широкую сводную таблицу в длинный столбик наблюдений, а pivot_table кристаллизует длинные факты в двумерную матрицу с подсчетом итогов. Для визуализаций в Seaborn и баз данных нужен узкий длинный формат (Tidy Data), а для отчетов в Excel — широкий.

    Принципы Tidy Data и механика решейпинга:

    1. Концепция аккуратных данных (Tidy Data): 1. Каждая переменная образует отдельный столбец. 2. Каждое наблюдение образует отдельную строку. 3. Каждый тип наблюдаемой единицы образует отдельную таблицу.
    2. Метод melt() (Wide $\to$ Long / Unpivot): - Принимает фиксированные столбцы-идентификаторы (`id_vars`) и столбцы-значения (`value_vars`). - Схлопывает десятки горизонтальных столбцов (например, `sales_jan`, `sales_feb`, `sales_mar`) в две строгие колонки: имя переменной (`variable`) и ее значение (`value`).
    3. Методы pivot() и pivot_table() (Long $\to$ Wide): - `df.pivot()`: Требует строгой уникальности комбинации индексов и колонок. Если есть дубликаты — падает с ошибкой `ValueError: Index contains duplicate entries`. - `df.pivot_table()`: Поддерживает агрегацию при совпадении ключей (`aggfunc='mean|sum|count'`) и подсчет общих итогов (`margins=True`).
    4. Схлопывание иерархического MultiIndex: После применения `pivot_table` колонки часто становятся двухуровневыми. Техника расплющивания: `df.columns = ['_'.join(col).strip() for col in df.columns.values]`.

    Практический сценарий: Подготовка когортной матрицы: Сырые логи содержат строки: `(cohort, month_offset, active_users)`. Аналитик применяет: `matrix = df.pivot_table(index='cohort', columns='month_offset', values='active_users', aggfunc='sum')` Получается идеальная треугольная матрица удержания, готовая для экспорта в дашборд или отрисовки тепловой карты (Heatmap).

    # Полный цикл трансформации: Wide -> Long (melt) -> Wide (pivot_table)
import pandas as pd

# 1. Исходная широкая таблица (Wide format)
wide_df = pd.DataFrame({
    'branch': ['Москва', 'СПб'],
    'q1_sales': [150000, 90000],
    'q2_sales': [180000, 110000],
    'q3_sales': [210000, 125000]
})

# 2. Перевод в длинный формат Tidy Data через melt()
long_df = pd.melt(
    wide_df,
    id_vars=['branch'],
    value_vars=['q1_sales', 'q2_sales', 'q3_sales'],
    var_name='quarter',
    value_name='revenue'
)
# Очистка названий кварталов
long_df['quarter'] = long_df['quarter'].str.replace('_sales', '').str.upper()

# 3. Обратное сведение через pivot_table с подсчетом итогов
pivot_result = pd.pivot_table(
    long_df,
    index='branch',
    columns='quarter',
    values='revenue',
    aggfunc='sum',
    margins=True,       # итоговые суммы
    margins_name='ИТОГО'
)

print("Длинный формат (Long / Tidy):")
print(long_df)
print("\nСводная таблица с итогами (pivot_table):")
print(pivot_result)
    • Попытка использовать pivot() вместо pivot_table() на данных с дубликатами ключей. Запрос немедленно завершится ошибкой ValueError; при наличии дубликатов всегда используйте pivot_table().
    • Оставление двухуровневого MultiIndex в колонках после сведения. Создает проблемы при последующей сериализации в CSV/Parquet или переименовании столбцов.
    • Потеря идентификаторов строк при вызове melt() из-за пропуска аргумента id_vars. Все столбцы схлопнутся в одну плоскую пару колонок, потеряв связь с контекстом строки.

  8. Работа со временем: DatetimeIndex и resample

    Собеседование (Data / Time-Series Analyst): Практическая работа с временными рядами: «Как устроены типы Timestamp, DatetimeIndex и Timedelta в Pandas? Чем .resample() отличается от скользящего окна .rolling(), почему важно явно передавать параметр format в pd.to_datetime() и как корректно работать с таймзонами?»

    Если совсем простыми словами: resample — это GROUP BY по календарным корзинам времени (например, сжать секунды в часы), а rolling — это скользящее окно фиксированной ширины (например, среднее за последние 7 дней на каждую дату). Парсинг дат без явного формата — главная причина замедления пайплайнов в десятки раз.

    Архитектура временных рядов в Pandas:

    1. Оптимизация парсинга через `pd.to_datetime(format=...)`: - Без указания формата Pandas запускает эвристический перебор регулярных выражений для каждой строки, что занимает минуты на больших данных. - Передача точной маски (например, `format='%Y-%m-%d %H:%M:%S'`) ускоряет парсинг в 20-50 раз.
    2. Группировка по времени: `.resample()` vs `.rolling()`: - **.resample('1D' / '1h'):** Меняет частоту дискретизации (Downsampling или Upsampling). Уменьшает число строк датасета, схлопывая события внутри дискретных отрезков времени. - **.rolling(window='7D'):** Скользящее окно. Сохраняет исходное количество строк, вычисляя метрику по окну предшествующих наблюдений.
    3. Работа с часовыми поясами (Timezones): - Наивные метки (Timezone-naive) не привязаны к поясу. Сравнение naive и aware меток вызывает ошибку `TypeError`. - Метод `.dt.tz_localize('UTC')`: привязка временного пояса. - Метод `.dt.tz_convert('Europe/Moscow')`: перевод меток в локальное время с учетом переходов на сезонное время.
    4. Новые строгие частоты в Pandas 2.2+: Устаревшие суффиксы `M` (Month End) и `Q` (Quarter End) заменены на эксплицитные `ME` и `QE` во избежание неоднозначностей.

import pandas as pd
import numpy as np

# Генерация минутных временных меток за 3 дня
date_rng = pd.date_range(start='2026-10-01', periods=4320, freq='min')
ts_df = pd.DataFrame({
    'timestamp_str': date_rng.strftime('%Y-%m-%d %H:%M:%S'),
    'transactions': np.random.poisson(lam=5, size=len(date_rng))
})

# 1. Быстрый прецизионный парсинг с явным форматом
ts_df['dt'] = pd.to_datetime(ts_df['timestamp_str'], format='%Y-%m-%d %H:%M:%S')

# 2. Локализация часового пояса в UTC и конвертация в МСК (+3)
ts_df['dt_msk'] = ts_df['dt'].dt.tz_localize('UTC').dt.tz_convert('Europe/Moscow')

# 3. Агрегация по часам через resample()
hourly_summary = (
    ts_df.set_index('dt_msk')
    .resample('1h')['transactions']
    .sum()
    .to_frame(name='hourly_total')
)

# 4. Скользящее среднее за 24 часа для сглаживания суточных колебаний
hourly_summary['rolling_24h_avg'] = hourly_summary['hourly_total'].rolling(window=24, min_periods=1).mean()

print("Часовая агрегация с 24-часовым скользящим трендом:")
print(hourly_summary.head(10))

    • Сравнение дат с часовым поясом (tz-aware) и без пояса (tz-naive). Приводит к фатальной ошибке TypeError: Cannot compare tz-naive and tz-aware timestamps.
    • Путаница между .resample() и .rolling(). resample агрегирует данные в дискретные корзины, уменьшая число строк; rolling вычисляет окно по каждой строке без изменения их числа.
    • Неучет нерегулярных временных рядов при использовании целочисленного окна rolling(window=7). Если в данных есть пропуски дней, окно из 7 строк охватит не 7 дней, а произвольный диапазон. Используйте строковое окно `window='7D'`.

    На собеседовании: обратите внимание на разницу между строковым окном по времени (`rolling('7D')`) и окном по количеству строк (`rolling(7)`). Это классическая ловушка на практических секциях.

    1. Почему передача параметра format критична при вызове pd.to_datetime()?

      Она исключает долгий эвристический перебор регулярок и ускоряет парсинг строковых дат в 20-50 раз.

    2. В чем различие между методами .resample() и .rolling()?

      .resample() группирует данные по временным интервалам со сжатием строк; .rolling() вычисляет статистику в скользящем окне без сжатия числа строк.

    3. Чем отличаются методы tz_localize() и tz_convert()?

      tz_localize() привязывает исходно наивную метку к часовому поясу; tz_convert() переводит метку из одного пояса в другой со сдвигом часов.

    4. Какая опасность возникает при использовании целочисленного окна `rolling(N)` на нерегулярных рядах?

      Окно N строк не соответствует N календарным дням, если в ряде присутствуют пропущенные даты.

    5. Что означает аргумент `min_periods` в методе .rolling()?

      Минимальное количество непустых наблюдений в окне, необходимое для расчета значения (иначе возвращается NaN).

  9. Очистка данных: пропуски и дубликаты

    Собеседование (Data Analyst): Фундаментальный этап подготовки данных: «Какие механизмы образования пропусков существуют (MCAR, MAR, MNAR) и как выбирать между удалением (dropna), заполнением средним/медианой и интерполяцией? Как устроена логика поиска дубликатов с параметром keep и почему проверка `np.nan == np.nan` возвращает False?»

    Если совсем простыми словами: пропуск — это не просто пустая клетка, это информация о сбое или поведении клиента. Если пользователь скрыл свой доход, заполнение пропуска средней зарплатой исказит портрет аудитории, а слепое удаление строк через `dropna()` может уничтожить половину выборки.

    Классификация природы пропусков и стратегии обработки:

    1. Типология пропущенных значений (Donald Rubin): - **MCAR (Missing Completely at Random):** Пропуск случаен и никак не зависит от данных (например, случайный сбой датчика). Безопасно удалять строки или заполнять медианой. - **MAR (Missing at Random):** Вероятность пропуска зависит от других наблюдаемых полей (например, молодые пользователи реже указывают домашний телефон). Заполняется моделями на основе других признаков. - **MNAR (Missing Not at Random):** Вероятность пропуска напрямую связана со скрытым значением (люди с огромным доходом отказываются его называть). Заполнение средним категорически запрещено; требуется отдельный флаг `is_missing = 1`.
    2. Математическая специфика NaN в стандарте IEEE 754: По определению стандарта число с плавающей точкой NaN не равно ничему, включая себя самого: `np.nan == np.nan` возвращает `False`. Проверку необходимо выполнять строго через `pd.isna(x)` или `np.isnan(x)`.
    3. Стратегии заполнения: - Численные признаки с выбросами: строго медианой (`df['val'].fillna(df['val'].median())`). - Временные ряды: прямое распространение (`ffill` — forward fill) или линейная интерполяция (`interpolate()`). - Категории: отдельная категория `'Unknown'` во избежание потери паттерна отсутствия ответа.
    4. Дедупликация и параметр `keep`: Метод `df.drop_duplicates(subset=['user_id', 'date'], keep='first|last|False')`: - `'first'`: сохранить первое вхождение (требует предварительной сортировки!). - `'last'`: сохранить последнее вхождение. - `False`: удалить все дублирующиеся строки целиком.

    Кейс из продакшена: Ошибка заполнения пропусков чека: В чеках интернет-магазина для части заказов не проставилась сумма доставки. Джуниор заполнил пропуски средней стоимостью доставки ($350$ руб.). В результате заказы самовывозом (где доставка была бесплатной и логично отсутствовала) получили искусственную наценку, а юнит-экономика самовывоза оказалась искажена.

      Согласно стандарту IEEE 754 для чисел с плавающей точкой, значение NaN (Not a Number) не равно ничему, включая само себя.

      MCAR — пропуски полностью случайны; MNAR — вероятность пропуска напрямую зависит от скрытого истинного значения пропущенного признака.

      Медиана робастна (устойчива) к асимметрии распределения и экстремальным выбросам.

    4. Что делает параметр `keep='last'` в методе drop_duplicates()?

      Сохраняет последнее встреченное вхождение дублирующейся строки, удаляя все предшествующие.

    5. Зачем при заполнении пропусков создавать дополнительный флаг `is_missing`?

      Чтобы сохранить информацию о факте пропуска, которая сама по себе может быть сильным предиктивным сигналом.

    1. В чем различие между Figure и Axes в Matplotlib?

      Figure — это общее окно или полотно графической области; Axes — это конкретный подграфик с осями координат, шкалами и графическими элементами.

    2. Почему ось Y столбчатой диаграммы обязана начинаться с нуля?

      Потому что зритель подсознательно сравнивает площади и высоты столбиков, и усечение оси создает иллюзию колоссальной разницы там, где ее нет.

    3. Как создать вторую независимую ось Y для отображения разных метрик?

      С помощью метода `ax2 = ax1.twinx()`.

    4. Когда линейный график предпочтительнее столбчатой диаграммы?

      Когда данные представляют собой непрерывную временную последовательность и важно передать темп (производную) изменений.

    5. Что такое Chartjunk?

      Визуальные элементы оформления диаграммы (3D объемы, пестрые текстуры, тяжелые сетки), не несущие полезной информации и мешающие чтению данных.

  11. Анализ распределений в Seaborn

    Собеседование (Data / Product Analyst): Статистическая визуализация: «Как исследовать распределение продуктовой метрики с помощью Seaborn? В чем различия и ограничения Histplot, KDE, Boxplot, Violinplot и ECDF? Почему ящичковая диаграмма (Boxplot) и график средней могут скрывать мультимодальность данных?»

    Если совсем простыми словами: одно число (среднее или медиана) скрывает реальность. Если у вас половина пользователей платит 100 рублей, а половина — 10 000 рублей, среднее покажет 5050 рублей, хотя таких клиентов в природе не существует. Графики распределений показывают истинный рельеф ваших данных.

    Сравнительный анализ инструментов исследования распределений в Seaborn:

    1. Гистограмма (Histplot): - Разбивает непрерывный диапазон на равные корзины (Bins). - Ограничение: Форма распределения сильно зависит от выбранного числа корзин (`bins`). Слишком мало — потеря деталей; слишком много — шум и гребенка.
    2. Оценка плотности ядра (KDE — Kernel Density Estimation): - Строит сглаженную кривую плотности вероятности методом ядерного сглаживания. - Ловушка KDE: Параметр сглаживания (`bw_adjust`). При избыточном сглаживании два отдельных пика сливаются в один; кроме того, KDE может «размазать» плотность в отрицательную область для строго положительных метрик (например, времени ответа).
    3. Эмпирическая функция распределения (ECDF — Empirical Cumulative Distribution): - `sns.ecdfplot(x)`: Золотой стандарт строгого анализа. - Не требует подбора параметров (нет корзин и сглаживания). - Позволяет мгновенно находить любые перцентили: $y = 0.90 \implies$ 90-й перцентиль задержки или чека.
    4. Ящик с усами (Boxplot) vs Скрипичная диаграмма (Violinplot): - *Boxplot:* Показывает квартили ($Q_1, \text{Median}, Q_3$) и усы Тьюки ($1.5 \times IQR$). - *Опасность Boxplot:* Скрывает бимодальность! Бимодальное распределение (два пика) и равномерное распределение могут иметь абсолютно идентичный Boxplot. - *Violinplot:* Совмещает Boxplot внутри с симметричной KDE снаружи, наглядно показывая бимодальность и форму распределения.

    # Исследование скошенного продуктового распределения через Seaborn
import seaborn as sns
import matplotlib.pyplot as plt
import numpy as np

np.random.seed(42)
# Симуляция чеков: логнормальное тяжелое распределение с выбросами
spends = np.random.lognormal(mean=4.5, sigma=0.8, size=2000)

fig, axes = plt.subplots(1, 3, figsize=(15, 4.5), dpi=100)

# 1. Histplot с логарифмической шкалой и KDE
sns.histplot(spends, kde=True, log_scale=True, ax=axes[0], color='#2b5c8f')
axes[0].set_title('Histplot с лог-шкалой (Сумма чека)')
axes[0].set_xlabel('Чек, руб. (log-scale)')

# 2. Boxplot: демонстрация квартилей и выбросов (усы Тьюки)
sns.boxplot(x=spends, ax=axes[1], color='#41b6c4')
axes[1].set_title('Boxplot (Усы: 1.5 * IQR)')
axes[1].set_xlabel('Чек, руб.')

# 3. ECDFplot: накопленная вероятность (точный поиск перцентилей)
sns.ecdfplot(spends, ax=axes[2], color='#d95f02', linewidth=2)
axes[2].axhline(0.90, color='gray', linestyle='--', alpha=0.7)
p90 = np.percentile(spends, 90)
axes[2].axvline(p90, color='gray', linestyle='--', alpha=0.7)
axes[2].set_title(f'ECDF (90-й перцентиль = {p90:.0f} руб.)')
axes[2].set_xlabel('Чек, руб.')
axes[2].set_ylabel('Кумулятивная доля')

plt.tight_layout()
plt.show()

    • Использование KDE с параметрами по умолчанию для строго неотрицательных величин. KDE может нарисовать ложную ненулевую плотность вероятности в области отрицательных чисел.
    • Забывание о том, что Boxplot не показывает количество наблюдений. Boxplot по 10 наблюдениям выглядит так же солидно, как по 100 000, создавая ложную уверенность.
    • Неучет влияния размера корзины (binwidth) в гистограммах. Слишком широкий bin скрывает выбросы и пики распределения.

    На собеседовании: назовите ECDF как самый надежный инструмент анализа перцентилей без артефактов сглаживания. Это сразу выделяет сильного прикладного статистика.

    1. В чем ключевое преимущество ECDF перед гистограммой и KDE?

      ECDF не требует подбора гиперпараметров (числа корзин или ширины окна сглаживания) и отображает реальные перцентили выборки без искажений.

    2. Что обозначают границы коробки в Boxplot?

      Первый квартиль $Q_1$ (25%), медиану (50%) и третий квартиль $Q_3$ (75%); расстояние между ними — интерквартильный размах $IQR$.

    3. Как определяются усы Тьюки в стандартном Boxplot?

      Они простираются до крайних точек данных в пределах $1.5 imes IQR$ от квартилей; все точки за ними считаются потенциальными выбросами.

    4. Какую опасность несет слепое доверие графику Boxplot?

      Он скрывает форму распределения: равномерное и бимодальное распределения могут иметь одинаковый Boxplot.

    5. Что показывает Violinplot?

      Комбинацию Boxplot и зеркальной оценки плотности ядра (KDE), позволяющую наглядно видеть мультимодальность и форму распределения.
