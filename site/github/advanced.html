  1. Восстановление потерянных коммитов

    git reflog хранит историю перемещений HEAD и позволяет вернуть коммиты, которые больше не видны в обычной истории.

    После случайного reset --hard или переписывания истории, чтобы восстановить потерянную работу.

    git reflog # Найдите нужный hash git checkout <hash> # или верните ветку на него git reset --hard <hash>

    1. Что записывает git reflog?

      Журнал перемещений HEAD и checkout — даже если коммит «исчез» из git log.

    2. Поможет ли reflog после git reset --hard?

      Да — можно найти hash до сброса и вернуться git reset --hard <hash>.

    3. Хранится ли reflog вечно?

      Нет — записи со временем истекают (по умолчанию ~90 дней для unreachable).

    4. Чем reflog отличается от обычной истории ветки?

      Reflog локальный для вашего репозитория; на remote его нет — коллеги не восстановят ваш reset через reflog.

  2. Перенос отдельных коммитов

    git cherry-pick копирует конкретные коммиты в текущую ветку без слияния всей истории.

    Когда нужно забрать конкретную правку из другой ветки или PR.

    # Добавить один коммит git cherry-pick <hash> # Несколько коммитов git cherry-pick <hash1> <hash2>

    1. Чем cherry-pick отличается от merge?

      Берёт один или несколько конкретных коммитов, а не всю историю ветки.

    2. Почему после cherry-pick hash коммита другой?

      Создаётся новый коммит с тем же diff, но другим родителем и контекстом.

    3. Когда cherry-pick уместен для hotfix?

      Нужно перенести уже готовый фикс из main в release/1.2 без слияния всей ветки.

    4. Что делать при конфликте в cherry-pick?

      Исправить файлы, git add, git cherry-pick --continue или --abort.

  3. Squash

    Squash объединяет несколько коммитов в один, упрощая историю перед merge.

    Перед отправкой PR, чтобы убрать "шум" из истории разработки.

    git rebase -i HEAD~5 # В интерактивном режиме пометьте коммиты как 'squash' (s) # Объедините сообщения, сохраните и закройте

    1. Что делает squash коммитов?

      Объединяет несколько коммитов в один с общим итоговым diff.

    2. Зачем squash перед merge PR?

      Убрать «WIP», «fix typo» и оставить в main одну осмысленную единицу изменений.

    3. Как сделать интерактивный squash локально?

      git rebase -i HEAD~N и пометить коммиты как squash / fixup.

    4. Теряется ли содержимое правок при squash?

      Нет — меняется только структура истории, итоговый код тот же (если конфликтов не было).

  4. Удаление файлов из истории

    git filter-repo позволяет полностью удалить файлы из истории Git.

    Когда случайно закоммилили большие файлы или секреты.

    pip install git-filter-repo git filter-repo --path секретный_файл.txt --invert-paths

    1. Чем git filter-repo отличается от удаления файла в новом коммите?

      Переписывает всю историю — файл исчезает из старых коммитов, а не только из HEAD.

    2. Когда это нужно для секретов?

      Если ключ уже попал в Git — одного .gitignore мало, секрет остаётся в старых коммитах.

    3. Почему после filter-repo всем нужен fresh clone или force-push?

      Hash всех затронутых коммитов меняется — история несовместима со старыми клонами.

    4. Что делать после вычищения секрета из истории?

      Ротировать сам секрет — он мог быть скопирован до очистки.

  5. Protected branches

    Protected Branches запрещают прямые пуши и требуют прохождения проверок перед merge.

    Для защиты основной ветки от случайных или небезопасных изменений.

    В GitHub $\to$ Settings $\to$ Branches $\to$ Branch protection rules $\to$ запретить force-push, требовать review и успешные CI.

    1. Что блокирует protected branch на GitHub?

      Прямой push (и часто force-push) в ветку без PR и прохождения правил.

    2. Зачем требовать approving review?

      Чтобы в main попадал код, который хотя бы один человек осознанно проверил.

    3. Что даёт требование «passing CI» перед merge?

      Нельзя слить PR, пока тесты workflow не зелёные.

    4. Можно ли обойти protection без прав администратора?

      Обычно нет — это организационная гарантия качества, а не подсказка Git.
