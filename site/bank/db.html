  1. Собеседование: Все типы JOIN

    Собеседование (Middle/Senior Data Analyst & Backend): Классический фундамент реляционных баз данных: «Перечислите все типы JOIN в стандарте SQL. Чем отличаются SEMI-JOIN и ANTI-JOIN, как оптимизатор СУБД физически выполняет соединения (Nested Loop, Hash Join, Merge Join) и почему соединение по полям со значением NULL возвращает пустой результат?»

    Если совсем простыми словами: JOIN — это операция сопоставления строк двух таблиц по заданному логическому условию. Но на уровне процессора СУБД не просто перебирает строки: она строит хеш-таблицы в оперативной памяти или сортирует массивы на диске, чтобы объединить миллионы записей за доли секунды.

    Классификация типов JOIN и физические алгоритмы выполнения:

    1. Логические типы JOIN в SQL:
      • INNER JOIN: Возвращает только те строки, для которых условие соединения истинно в обеих таблицах ($A \cap B$).
      • LEFT / RIGHT OUTER JOIN: Возвращает все строки одной таблицы и совпадающие строки второй. Если совпадений нет — заполняет поля `NULL`.
      • FULL OUTER JOIN: Объединение ($A \cup B$): все строки из обеих таблиц, дополненные `NULL` при отсутствии пары.
      • CROSS JOIN: Декартово произведение ($A \times B$). Каждая строка левой таблицы соединяется с каждой строкой правой. Размер: $|A| \times |B|$ строк.
      • SEMI-JOIN (Полусоединение): Возвращает строки левой таблицы, для которых есть хотя бы одно совпадение в правой, но без размножения строк и без добавления колонок правой таблицы (`EXISTS`).
      • ANTI-JOIN (Антисоединение): Возвращает строки левой таблицы, для которых нет ни одного совпадения в правой (`NOT EXISTS` или `LEFT JOIN ... WHERE right.key IS NULL`).
    2. Физические алгоритмы выполнения в оптимизаторе (Execution Engines):
      АлгоритмСложностьКогда выбирается оптимизатором
      Nested Loop Join$O(N \times M)$ или $O(N \log M)$Одна таблица крошечная, а вторая имеет индекс B-Tree по ключу джойна.
      Hash Join$O(N + M)$Большие несортированные таблицы. По меньшей таблице строится хеш-таблица в RAM (`work_mem`), большая таблица сканируется построчно.
      Merge Join (Sort-Merge)$O(N \log N + M \log M)$Обе таблицы уже отсортированы по ключу соединения (например, через B-Tree индекс). Сканирование в один проход.
    3. Ловушка NULL в условиях соединения: Поскольку в трехуровневой логике SQL `NULL = NULL` вычисляется как `UNKNOWN`, условие `ON a.id = b.id` никогда не сопоставит строки с NULL. Строки с NULL выпадают из INNER JOIN и уходят в правую часть с NULL при LEFT JOIN.

    Кейс из продакшена: Размножение строк при Left Join: Финансовый отчет считал выручку: `orders LEFT JOIN payments ON orders.id = payments.order_id`. Если заказ оплачивался двумя частями (аванс + доплата), в таблице `payments` было 2 строки. Left Join удвоил строку заказа, и сумма `SUM(orders.total_amount)` завысила выручку на $40\%$. Решение: Предварительная агрегация `payments` до уровня 1:1 перед джойном либо использование SEMI-JOIN.

    -- 1. Эффективный ANTI-JOIN через NOT EXISTS (быстрее, чем NOT IN при наличии NULL)
SELECT c.customer_id, c.email
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 
    FROM orders o 
    WHERE o.customer_id = c.customer_id
);

-- 2. Эквивалентный ANTI-JOIN через LEFT JOIN ... IS NULL
SELECT c.customer_id, c.email
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.customer_id IS NULL;

-- 3. Безопасный SEMI-JOIN: извлечь клиентов, купивших товар из категории 'VIP', без размножения строк
SELECT c.customer_id, c.full_name
FROM customers c
WHERE EXISTS (
    SELECT 1 
    FROM orders o
    JOIN order_items oi ON o.order_id = oi.order_id
    WHERE o.customer_id = c.customer_id AND oi.category = 'VIP'
);
    • Непреднамеренное размножение строк при связи 1:N в LEFT JOIN. Суммирование метрик левой таблицы после джойна с таблицей отношений 'многие' приводит к фатальному задвоению сумм.
    • Использование конструкции `WHERE col NOT IN (SELECT ...)` при наличии NULL. Если подзапрос вернет хотя бы один `NULL`, весь предикат `NOT IN` вернет пустой результат (0 строк) из-за трехзначной логики SQL!
    • Отсутствие индексов на внешних ключах при Nested Loop Join. Приводит к катастрофическому последовательному сканированию (`Seq Scan`) на каждую строку внешней таблицы.
    • Случайный CROSS JOIN из-за опечатки в условии ON. Создает декартово произведение, исчерпывает оперативную память сервера и роняет базу данных.

    На собеседовании: всегда объясняйте физические движки выполнения — Hash Join, Merge Join, Nested Loop. Понимание того, как `work_mem` влияет на выбор Hash Join, отличает Senior инженера.

    1. Чем SEMI-JOIN отличается от обычного INNER JOIN?

      SEMI-JOIN только проверяет наличие совпадения в правой таблице, не возвращая ее колонок и не размножая строки левой таблицы при множественных совпадениях.

    2. Как оптимизатор СУБД выполняет Hash Join?

      Строит хеш-таблицу по ключам меньшей таблицы в оперативной памяти, затем последовательно сканирует вторую таблицу, вычисляя хеш ключа.

    3. Почему условие `ON a.key = b.key` не соединяет строки, где `key IS NULL`?

      Потому что в стандарте SQL операция `NULL = NULL` вычисляется как UNKNOWN (ложно для предикатов соединения).

    4. Когда оптимизатор предпочтет Merge Join вместо Hash Join?

      Когда обе соединяемые таблицы уже отсортированы по ключу джойна (например, через индекс B-Tree) или таблицы слишком велики для RAM.

    5. В чем опасность использования NOT IN со значением NULL?

      Если в списке значений присутствует NULL, выражение `x NOT IN (..., NULL)` всегда возвращает UNKNOWN, что отсекает вообще все строки.

  2. Собеседование: WHERE против HAVING

    Собеседование (Data Analyst): Классический проверочный вопрос: «В чем принципиальная разница между предложениями WHERE и HAVING в SQL? В каком строгом порядке СУБД выполняет этапы SQL-запроса и почему фильтрация строк в HAVING вместо WHERE может замедлить запрос в сотни раз?»

    Если совсем простыми словами: WHERE отсекает отдельные сырые строки ДО группировки, а HAVING фильтрует уже свернутые группы ПОСЛЕ выполнения агрегатных функций. Фильтровать в HAVING то, что можно отсечь в WHERE — это как нарезать гнилые яблоки в салат, а потом выковыривать их вилкой.

    Канонический порядок выполнения фаз SQL-запроса (SQL Order of Execution):

    1. 1. FROM & JOIN: Определение таблиц источников, вычисление декартовых произведений и соединений `ON`.
    2. 2. WHERE: Фильтрация отдельных атомарных строк по предикатам. На этом этапе агрегатные функции (SUM, AVG) еще недоступны!
    3. 3. GROUP BY: Сворачивание строк в группы по заданным ключам.
    4. 4. HAVING: Фильтрация полученных групп на основе условий, включающих агрегатные функции (`COUNT(*) > 5`).
    5. 5. SELECT: Вычисление выражений выборки, проекция столбцов.
    6. 6. DISTINCT: Удаление дубликатов строк.
    7. 7. ORDER BY: Сортировка финального результата.
    8. 8. LIMIT / OFFSET: Пагинация и отсечение числа выводимых строк.

    Почему WHERE критически быстрее HAVING: Если таблица содержит $10\,000\,000$ строк, а нам нужны только активные пользователи за текущий год ($100\,000$ строк): - Предикат `WHERE status = 'active'` отсечет $9.9$ млн строк сразу (используя индекс), и `GROUP BY` обработает всего $100$ тысяч записей. - Предикат `HAVING status = 'active'` заставит базу сгруппировать все $10$ миллионов строк в оперативной памяти, потратив гигабайты RAM и минуты CPU, и только потом отфильтрует группы!

    Практический пример: Задача: найти отделы с более чем 10 сотрудниками, средняя зарплата которых превышает 150 000 руб., рассматривая только штатных сотрудников (`is_contractor = FALSE`). - `is_contractor = FALSE` $\to$ строго в **WHERE** (атомарное свойство сотрудника). - `COUNT(*) > 10` и `AVG(salary) > 150000` $\to$ строго в **HAVING** (агрегаты группы).

    -- Корректное разделение предикатов между WHERE и HAVING
SELECT
    department_id,
    COUNT(*) AS total_employees,
    ROUND(AVG(salary), 2) AS avg_salary
FROM employees
-- WHERE: фильтрация сырых строк ДО группировки (использует индекс по is_active и hire_date)
WHERE is_active = TRUE
  AND hire_date >= '2020-01-01'
-- GROUP BY: агрегация только валидных строк
GROUP BY department_id
-- HAVING: фильтрация агрегированных групп ПОСЛЕ свертки
HAVING COUNT(*) >= 5 
   AND AVG(salary) > 120000.00
ORDER BY avg_salary DESC;
    • Помещение условий на обычные столбцы в блок HAVING вместо WHERE. Заставляет СУБД группировать гигантские объемы мусорных данных в оперативной памяти вместо использования индексов в WHERE.
    • Попытка использовать агрегатные функции (SUM, COUNT) в блоке WHERE. Вызовет синтаксическую ошибку `aggregate functions are not allowed in WHERE`, так как строки еще не сгруппированы.
    • Использование алиасов из SELECT в блоке WHERE. Поскольку WHERE выполняется раньше SELECT, алиасы колонок еще не существуют и вызовут ошибку `column does not exist`.
    • Забывание о том, что HAVING без GROUP BY превращает всю таблицу в единую группу. Конструкция `SELECT SUM(x) FROM t HAVING SUM(x) > 0` валидна, но работает на уровне всей таблицы.

    На собеседовании: перечислите этапы выполнения SQL по порядку (FROM $\to$ WHERE $\to$ GROUP BY $\to$ HAVING $\to$ SELECT $\to$ ORDER BY $\to$ LIMIT). Это фундаментальный маркер технической грамотности.

    1. В чем главное функциональное различие WHERE и HAVING?

      WHERE фильтрует индивидуальные строки до группировки; HAVING фильтрует сформированные группы на основе агрегатных функций.

    2. Можно ли использовать агрегатные функции в блоке WHERE?

      Нет, на этапе WHERE группировка еще не выполнена, поэтому агрегаты вычислять невозможно.

    3. Почему фильтрация неагрегированных колонок в HAVING снижает производительность?

      Потому что база данных тратит ресурсы на группировку всех строк таблицы вместо быстрой фильтрации по индексу в WHERE.

    4. На каком этапе выполнения SQL создаются алиасы из блока SELECT?

      На этапе SELECT, который выполняется строго ПОСЛЕ WHERE, GROUP BY и HAVING.

    5. Можно ли использовать условие HAVING без явного указания GROUP BY?

      Да, в этом случае вся таблица неявно считается единой агрегированной группой.

  3. Собеседование: Поведение NULL в SQL

    Собеседование (Database Specialist / Senior Analyst): Тонкости стандарта SQL: «Как работает трехзначная логика (Three-Valued Logic, 3VL) при наличии значений NULL? В чем различия между COUNT(*), COUNT(1), COUNT(column) и COUNT(DISTINCT column)? Почему функция AVG() может возвращать смещенную оценку при наличии NULL?»

    Если совсем простыми словами: NULL — это не ноль и не пустая строка, это признак неизвестности (Unknown). Любое сравнение с неизвестностью дает неизвестность: если у Васи неизвестна зарплата, и у Пети неизвестна зарплата, мы не можем сказать, равны ли они — поэтому `NULL = NULL` вычисляется как UNKNOWN, а не TRUE.

    Трехзначная логика (3VL) и семантика агрегатных функций:

    1. Таблица истинности трехзначной логики (3VL):
      ВыражениеРезультатПояснение
      TRUE AND UNKNOWNUNKNOWNИстинность зависит от неизвестного значения.
      FALSE AND UNKNOWNFALSEЛожь при любых обстоятельствах (короткое замыкание).
      TRUE OR UNKNOWNTRUEИстина при любых обстоятельствах.
      NOT UNKNOWNUNKNOWNОтрицание неизвестности остается неизвестностью.
      x = NULL / x <> NULLUNKNOWNСравнение строго через операторы IS NULL / IS NOT NULL!
    2. Различия семейства COUNT: - `COUNT(*)`: Считает все физические строки таблицы, включая строки, целиком состоящие из NULL. - `COUNT(1)`: Абсолютно идентичен `COUNT(*)` в современных СУБД (оптимизатор транслирует их в один и тот же план). - `COUNT(column)`: Считает строки, где значение в данном столбце НЕ равно NULL (`NOT NULL`). - `COUNT(DISTINCT column)`: Считает число уникальных значений, полностью игнорируя NULL.
    3. Искажение средних в AVG(): Функция `AVG(col)` математически рассчитывается как: $$\text{AVG}(col) = \frac{\sum_{i \in \text{not null}} col_i}{\text{COUNT}(col)}$$ Знаменатель — это `COUNT(col)`, а не `COUNT(*)`. Если у 10 пользователей зарплата 100 000, а у 90 пользователей она `NULL`, `AVG()` вернет $100\,000$ рублей, а не реальные $10\,000$ на человека!

    Кейс: Ловушка функции COALESCE в среднем чеке: Таблица пользователей: 100 человек. 20 человек потратили по $1\,000$ руб., у 80 покупок не было (`NULL`). - `SELECT AVG(spend) FROM users;` $\to$ вернет **$1\,000$ руб.** (средний чек среди платящих). - `SELECT AVG(COALESCE(spend, 0)) FROM users;` $\to$ вернет **$200$ руб.** (ARPU на всю базу). Путаница этих двух формул в бизнес-отчетах приводит к завышению ARPU в 5 раз!

    -- Демонстрация поведения NULL в агрегатных функциях
WITH user_data AS (
    SELECT 1 AS id, 100.0 AS amount UNION ALL
    SELECT 2 AS id, 200.0 AS amount UNION ALL
    SELECT 3 AS id, NULL  AS amount
)
SELECT
    COUNT(*) AS cnt_star,                       -- 3 (все строки)
    COUNT(amount) AS cnt_amount,               -- 2 (только NOT NULL)
    AVG(amount) AS avg_ignoring_null,          -- (100 + 200) / 2 = 150.0
    AVG(COALESCE(amount, 0.0)) AS avg_with_zero -- (100 + 200 + 0) / 3 = 100.0
FROM user_data;

-- Безопасное сравнение с учетом NULL: оператор IS DISTINCT FROM
-- В отличие от '=', 'a IS NOT DISTINCT FROM b' вернет TRUE, если оба значения NULL!
SELECT *
FROM employees
WHERE manager_id IS DISTINCT FROM 42;
    • Использование конструкции `WHERE col = NULL` вместо `WHERE col IS NULL`. Предикат всегда вернет UNKNOWN, и запрос вернет 0 строк.
    • Забывание о том, что `NOT IN` ломается при наличии хотя бы одного NULL в подзапросе. Конструкция `WHERE id NOT IN (1, 2, NULL)` эквивалентна `id != 1 AND id != 2 AND id != NULL`, что дает UNKNOWN и уничтожает весь результат.
    • Расчет ARPU через AVG(revenue) без замены NULL на 0 через COALESCE. Игнорирует неплатящую аудиторию и превращает ARPU в ARPPU.
    • Сортировка ORDER BY без явного указания NULLS FIRST / NULLS LAST. По умолчанию в PostgreSQL NULL сортируются в конец при ASC и в начало при DESC, что может скрыть важные данные при пагинации.

    На собеседовании: расскажите про оператор стандарта SQL IS DISTINCT FROM (null-safe equality). Это маркер того, что кандидат виртуозно владеет стандартом ANSI SQL.

    1. Что такое трехзначная логика (3VL) в SQL?

      Логическая система, оперирующая тремя истинностными значениями: TRUE, FALSE и UNKNOWN.

    2. Чем `COUNT(*)` отличается от `COUNT(column)`?

      `COUNT(*)` считает общее количество физических строк; `COUNT(column)` считает только те строки, где значение в указанной колонке не равно NULL.

    3. Почему выражение `NULL = NULL` не равно TRUE?

      Потому что NULL означает неизвестное значение, а равенство двух неизвестных величин невозможно подтвердить достоверно (результат UNKNOWN).

    4. Как функция AVG() обрабатывает значения NULL?

      Она полностью игнорирует строки со значением NULL как при подсчете числителя (суммы), так и знаменателя (числа строк).

    5. Как работает оператор `IS NOT DISTINCT FROM`?

      Он выполняет null-safe сравнение: возвращает TRUE, если оба операнда имеют одинаковые значения либо если оба операнда равны NULL.

  4. Собеседование: UNION vs UNION ALL

    Собеседование (Data Engineer / Analyst): Базовый, но критический вопрос оптимизации: «В чем физическая и алгоритмическая разница между операторами UNION и UNION ALL? Почему замена UNION на UNION ALL может ускорить выполнение запроса в 50 раз и когда применение обычного UNION оправдано?»

    Если совсем простыми словами: UNION ALL просто склеивает две таблицы стопкой как есть, а UNION дополнительно запускает тяжелую операцию поиска и удаления дубликатов. Если дубликатов в данных заведомо нет (или они допустимы), использование UNION впустую сжигает память и процессорное время сервера.

    Алгоритмическое устройство и физический план выполнения:

    1. Механика UNION ALL: - Операция потокового объединения (Append node в плане запроса). - Не требует синхронизации, сортировки или сохранения промежуточных строк в буфер памяти. - Вычислительная сложность: $O(N + M)$. Данные начинают отдаваться клиенту мгновенно (Streaming).
    2. Механика UNION: - Выполняет UNION ALL, а затем накладывает неявный DISTINCT. - Способ 1 (Sort-Unique): Все строки обеих выборок выгружаются во временный буфер, сортируются на диске/RAM ($O(K \log K)$), и соседние дубликаты схлопываются. - Способ 2 (HashAggregate): Строится огромная хеш-таблица в `work_mem` для дедупликации записей. Если память переполняется — данные сбрасываются во временные файлы на диск (Spill to disk).
    3. Требования стандарта к объединяемым выборкам: 1. Одинаковое количество столбцов. 2. Совместимые типы данных соответствующих колонок. 3. Имена колонок в результирующем наборе определяются строго первой выборкой.

    Кейс из продакшена: Оптимизация ETL-пайплайна логов: Ежесуточный джоб собирал данные за прошлый день из 10 региональных партиций: `SELECT ... FROM reg1 UNION SELECT ... FROM reg2 UNION ...` Запрос выполнялся $42$ минуты и периодически падал с ошибкой нехватки диска под временные файлы сортировки. Поскольку ключи записей в разных регионах физически уникальны, инженер заменил `UNION` на `UNION ALL`. Время выполнения упало с 42 минут до 18 секунд!

SELECT

    event_timestamp

SELECT

    • Использование UNION по умолчанию вместо UNION ALL. Главная анти-паттерн привычка начинающих: создание скрытой тяжелой дедупликации там, где она не требуется.
    • Несовпадение порядков колонок в объединяемых SELECT. SQL сопоставляет столбцы по их позиции (1-й с 1-м, 2-й со 2-м), а не по именам! Если перепутать порядок, данные запишутся в чужие поля.
    • Попытка задать алиасы колонок во втором подзапросе. Алиасы результирующего набора определяются исключительно первым SELECT; имена во втором просто игнорируются.
    • Размещение ORDER BY внутри каждого подзапроса без ограничения LIMIT. В большинстве СУБД ORDER BY внутри отдельных веток UNION без LIMIT игнорируется или вызывает синтаксическую ошибку.

    На собеседовании: золотое правило — «Всегда используйте UNION ALL по умолчанию. Применяйте UNION только тогда, когда удаление дубликатов является строгим бизнес-требованием и не может быть решено иначе».

    1. В чем ключевое отличие UNION от UNION ALL?

      UNION ALL просто объединяет строки без изменений; UNION выполняет объединение с последующим ресурсоемким удалением дубликатов (DISTINCT).

    2. Какой узел (Node) создает UNION ALL в плане выполнения запроса?

      Узел Append, выполняющий потоковое чтение результатов без промежуточных буферов.

    3. Как СУБД физически удаляет дубликаты при операции UNION?

      Через сортировку всех строк во временной памяти (Sort Unique) либо через построение хеш-таблицы (Hash Aggregate).

    4. Какая из выборок определяет имена столбцов в результирующем наборе UNION?

      Исключительно первая выборка (самый первый оператор SELECT).

    5. Почему UNION ALL работает быстрее при передаче данных клиенту?

      Потому что он может стримить первые строки клиенту немедленно, не дожидаясь окончания чтения всех объединяемых таблиц.

  5. Собеседование: DELETE vs TRUNCATE vs DROP

    Собеседование (Database Administrator / Analyst): Эксплуатационный вопрос по DDL и DML: «В чем принципиальная разница между командами DELETE, TRUNCATE и DROP? Что происходит с логом транзакций (WAL), счетчиками автоинкремента, триггерами и дисковым пространством при выполнении каждой из них? Можно ли откатить (ROLLBACK) TRUNCATE в транзакции?»

    Если совсем простыми словами: DELETE выносит жильцов из комнат по одному, составляя опись каждого чемодана; TRUNCATE сносит все внутренние перегородки здания за одну секунду; а DROP сносит сам дом вместе с фундаментом. DELETE работает аккуратно, но медленно; TRUNCATE очищает миллионы строк мгновенно.

    Миф про невозможность отката TRUNCATE: Многие начинающие разработчики считают, что TRUNCATE нельзя откатить. В СУБД PostgreSQL DDL-команды полностью транзакционны! Если выполнить `BEGIN; TRUNCATE table; ROLLBACK;`, таблица и все ее данные останутся нетронутыми!

    Кейс из продакшена: Зависание базы от массового DELETE: Аналитик попытался очистить историческую таблицу логов на $50$ млн строк: `DELETE FROM raw_logs;`. Сервер завис: PostgreSQL начал генерировать гигабайты WAL-логов, заблокировал таблицу эксклюзивными блокировками и заполнил диск. Правильное решение: `TRUNCATE TABLE raw_logs;` очистил таблицу за $0.05$ секунды без раздувания WAL.

    -- Демонстрация транзакционности TRUNCATE в PostgreSQL
BEGIN;

-- Мгновенная очистка таблицы со сбросом автоинкремента
TRUNCATE TABLE staging_events RESTART IDENTITY;

-- Проверка: таблица пуста
SELECT count(*) FROM staging_events; -- вернет 0

-- Если произошла ошибка, операция откатывается на 100%!
ROLLBACK;

-- Данные снова на месте в целости и сохранности:
SELECT count(*) FROM staging_events;
    • Удаление всей таблицы через DELETE без условий вместо TRUNCATE. Порождает колоссальный объем журналов транзакций (WAL) и приводит к 'раздуванию' (Table Bloat), не возвращая место операционной системе.
    • Забывание о блокировках при TRUNCATE. TRUNCATE берет тяжелую исключительную блокировку `ACCESS EXCLUSIVE`, блокируя даже чтение из таблицы до завершения транзакции.
    • Попытка TRUNCATE таблицы, на которую ссылается Foreign Key. Завершится ошибкой, если не указать каскадное удаление `TRUNCATE ... CASCADE`.
    • Ошибочная вера в то, что TRUNCATE в MySQL можно откатить. В MySQL DDL-команды вызывают неявный авто-коммит (`implicit commit`), и откат становится невозможным.

    На собеседовании: обязательно подчеркните транзакционность TRUNCATE в PostgreSQL и разницу в логировании WAL (построчное логирование кортежей vs деаллокация страниц на диске).

    1. К какой категории команд SQL относится TRUNCATE?

      К командам DDL (Data Definition Language), так как она манипулирует объектами схемы и экстентами хранения.

    2. Можно ли откатить операцию TRUNCATE внутри транзакции в PostgreSQL?

      Да, в PostgreSQL транзакции поддерживают DDL, поэтому после ROLLBACK все строки будут восстановлены.

    3. Почему TRUNCATE выполняется быстрее, чем DELETE без предложения WHERE?

      Потому что TRUNCATE освобождает страницы памяти целиком и пишет минимальный лог, а DELETE построчно блокирует и логирует каждую запись.

    4. Что происходит с дисковым пространством после выполнения массового DELETE в PostgreSQL?

      Место физически не возвращается операционной системе и помечается как свободное для повторного использования внутри таблицы (требуется VACUUM FULL).

    5. Вызываются ли построчные триггеры FOR EACH ROW при выполнении TRUNCATE?

      Нет, построчные триггеры DELETE игнорируются при операции TRUNCATE.

  6. Собеседование: Первичные и внешние ключи

    Собеседование (Database Architect / Backend): Проектирование реляционных схем: «В чем разница между Primary Key, Unique Key и Foreign Key? Что выбрать в качестве первичного ключа: естественный бизнес-ключ (Natural Key), автоинкрементный ID (Surrogate Key) или UUID (v4 vs v7)? Почему случайные UUIDv4 разрушают производительность B-Tree индексов?»

    Если совсем простыми словами: Первичный ключ — это паспорт строки (уникален и никогда не пуст), Внешний ключ — поводок, связывающий строку с другой таблицей, а Уникальный ключ запрещает дубликаты, но допускает отсутствие данных (NULL).

    Сравнительный анализ ключей и стратегий идентификации:

    1. Ограничения целостности ключей: - Primary Key (PK): `UNIQUE` + `NOT NULL`. В таблице может быть строго один первичный ключ (простой или составной). Автоматически создает уникальный B-Tree индекс. - Unique Key: Гарантирует уникальность значений. В таблице может быть сколько угодно Unique ключей. В большинстве СУБД разрешает хранение значений NULL (и даже нескольких NULL, так как `NULL <> NULL`). - Foreign Key (FK): Ссылается на Primary Key или Unique Key другой таблицы, гарантируя ссылочную целостность (Referential Integrity).
    2. Баттл первичных ключей: BIGINT IDENTITY vs UUIDv4 vs UUIDv7:
      Тип ключаРазмерСортируемостьПоведение B-Tree индекса
      BIGINT (Sequence)8 байтМонотонно растетИдеальное: запись строго в правый лист B-Tree, отсутствие фрагментации.
      UUIDv4 (Случайный)16 байтХаотичныйКатастрофа: случайная вставка в середину B-Tree, расщепление страниц (Page Splits), кэш вымывается из RAM.
      UUIDv7 (Time-ordered)16 байтСортируется по времениИдеальное: глобальная уникальность без координации + монотонный рост для быстрого B-Tree.

    Кейс из продакшена: Просадка скорости записи на 90% из-за UUIDv4: Высоконагруженный сервис платежей использовал `uuid_generate_v4()` в качестве Primary Key. При объеме таблицы $200$ млн строк скорость вставки упала с $5\,000$ RPS до $250$ RPS. Причина: размер индекса B-Tree вырос до $45$ ГБ и перестал помещаться в RAM (`shared_buffers`). Каждая новая случайная вставка требовала медленного чтения случайной страницы с SSD. Миграция на UUIDv7 вернула производительность до $6\,500$ RPS.

    -- Создание таблицы с правильной организацией первичных, внешних и уникальных ключей
CREATE TABLE user_accounts (
    account_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- Компактный монотонный PK (8 байт)
    account_uuid UUID NOT NULL DEFAULT gen_random_uuid(),       -- Публичный идентификатор для API
    email VARCHAR(255) NOT NULL,
    phone VARCHAR(32),
    created_at TIMESTAMPTZ DEFAULT NOW(),
    
    -- Уникальный бизнес-ключ
    CONSTRAINT uq_user_email UNIQUE (email),
    -- Уникальный ключ, допускающий NULL (несколько клиентов могут не иметь телефона)
    CONSTRAINT uq_user_phone UNIQUE (phone)
);

CREATE TABLE user_cards (
    card_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    account_id BIGINT NOT NULL,
    card_token VARCHAR(128) NOT NULL UNIQUE,
    is_active BOOLEAN DEFAULT TRUE,
    
    -- Внешний ключ со строгим контролем ссылочной целостности
    CONSTRAINT fk_cards_account 
        FOREIGN KEY (account_id) 
        REFERENCES user_accounts(account_id) 
        ON DELETE RESTRICT
);

-- КРИТИЧЕСКИ ВАЖНО: Внешние ключи в PostgreSQL не индексируются автоматически!
CREATE INDEX idx_user_cards_account_id ON user_cards(account_id);
    • Использование изменяемых естественных ключей (email, телефон, номер паспорта) в качестве PK. При смене email придется обновлять записи в миллионах связанных таблиц через каскадный апдейт.
    • Забывание создания индексов на столбцы Foreign Key в PostgreSQL. Без индекса удаление строки в родительской таблице вызывает полное последовательное сканирование (`Seq Scan`) всей дочерней таблицы.
    • Использование чисто случайных UUIDv4 для таблиц с сотнями миллионов записей. Вызывает тяжелую фрагментацию B-Tree и деградацию дискового ввода-вывода.
    • Использование составных первичных ключей из 5+ колонок во взаимосвязанных таблицах. Раздувает размер внешних ключей и таблиц фактов в разы.

    На собеседовании: если встает выбор между BIGINT и UUID для распределенной системы, рекомендуйте UUIDv7. Это показывает глубокое понимание устройства дисковых структур данных B-Tree.

    1. Может ли Primary Key содержать значение NULL?

      Нет, стандарт SQL категорически запрещает значение NULL в столбцах первичного ключа.

    2. Разрешает ли Unique Key хранение значений NULL?

      Да, в стандарте SQL ограничение UNIQUE допускает значения NULL (и даже несколько строк с NULL, если не задано NOT NULL).

    3. Почему случайные UUIDv4 вызывают деградацию производительности B-Tree индексов?

      Из-за хаотичности значений вставки происходят в случайные страницы дерева, вызывая частое расщепление страниц (Page Splits) и вымывание кэша.

    4. В чем преимущество UUIDv7 перед UUIDv4?

      UUIDv7 содержит временную метку (timestamp) в старших битах, что делает его хронологически сортируемым и дружественным к индексам B-Tree.

    5. Индексируются ли Foreign Keys автоматически в PostgreSQL?

      Нет, в PostgreSQL индексы на внешние ключи должны создаваться разработчиком явно.

  7. Собеседование: Оконные функции ранжирования

    Собеседование (Product Analyst / Data Engineer): Топовый вопрос технического интервью: «В чем математическая разница между оконными функциями ранжирования ROW_NUMBER(), RANK(), DENSE_RANK() и NTILE()? Что вернет каждая из них на наборе значений с дубликатами [100, 100, 80, 50]?»

    Если совсем простыми словами: ROW_NUMBER нумерует строки тупо по порядку без оглядки на совпадения, RANK дает одинаковым числам одинаковое место, но пропускает следующие номера (как в спорте), а DENSE_RANK дает одинаковые места без пропусков. NTILE делит выборку на равные корзины (квантили).

    Сравнительный расчет функций ранжирования на реальных данных:

    ScoreROW_NUMBER()RANK()DENSE_RANK()NTILE(2)Логика и механика
    1001111Первое вхождение лидера
    1002111Дубликат: ROW_NUMBER инкрементирует, остальные сохраняют ранг
    8033 (пропустил 2!)2 (без пропуска)2RANK пропустил номер 2 из-за двух лидеров
    504432Четвертое значение

    Сферы применения каждой функции: - **ROW_NUMBER():** Дедупликация данных (выборка строго 1 самой свежей записи `WHERE rn = 1`) и пагинация страниц. - **DENSE_RANK():** Топ-3 зарплаты в отделе (если три человека получают максимум, они все на 1 месте, а человек со второй зарплатой будет строго на 2 месте). - **RANK():** Олимпийские соревнования и расчет центилей. - **NTILE(N):** Разбиение пользователей на когорты равного размера: терцили ($N=3$), квартили ($N=4$), децили ($N=10$).

    Практическая задача: Топ-3 максимальные зарплаты в отделе: Если использовать `ROW_NUMBER() <= 3` при наличии 3 человек с зарплатой 200 000 руб., мы потеряем сотрудника с реальной второй зарплатой (180 000 руб.). Использование `DENSE_RANK() <= 3` корректно выберет все три уровня самых высоких окладов компании.

    -- Сравнение всех функций ранжирования в одном запросе
WITH sales_leaders AS (
    SELECT 'Алиса' AS rep, 'Электроника' AS dept, 500000 AS revenue UNION ALL
    SELECT 'Борис',       'Электроника',        500000 UNION ALL
    SELECT 'Влад',        'Электроника',        350000 UNION ALL
    SELECT 'Дарья',       'Электроника',        200000 UNION ALL
    SELECT 'Елена',       'Одежда',             400000 UNION ALL
    SELECT 'Федор',       'Одежда',             400000
)
SELECT
    dept,
    rep,
    revenue,
    ROW_NUMBER() OVER (PARTITION BY dept ORDER BY revenue DESC) AS row_num,
    RANK()       OVER (PARTITION BY dept ORDER BY revenue DESC) AS rnk,
    DENSE_RANK() OVER (PARTITION BY dept ORDER BY revenue DESC) AS dense_rnk,
    NTILE(2)     OVER (PARTITION BY dept ORDER BY revenue DESC) AS quartile_bucket
FROM sales_leaders;
    • Использование функции RANK() для дедупликации данных. Если есть дубликаты, условие `WHERE rnk = 1` вернет несколько строк вместо одной уникальной записи (нужно использовать ROW_NUMBER).
    • Забывание предложения ORDER BY внутри конструкции OVER(). Функции ранжирования без явной сортировки теряют детерминированность и возвращают случайные результаты.
    • Использование ROW_NUMBER() для поиска топ-N значений при наличии дубликатов окладов. Приведет к потере сотрудников с одинаковыми максимальными баллами.
    • Попытка фильтрации по оконной функции прямо в блоке WHERE. Оконные функции выполняются после WHERE; фильтровать по ним можно строго через CTE или подзапрос.

    На собеседовании: мгновенно нарисуйте таблицу с числами [100, 100, 80] и покажите значения (1,2,3 vs 1,1,3 vs 1,1,2). Это гарантирует максимальный балл за секцию SQL.

    1. Что вернет RANK() для элементов [100, 100, 80]?

      Значения: 1, 1, 3 (ранг 2 пропускается из-за связки на первом месте).

    2. Что вернет DENSE_RANK() для тех же элементов [100, 100, 80]?

      Значения: 1, 1, 2 (ранжирование продолжается без пропусков номеров).

    3. Какую функцию ранжирования следует использовать для гарантированного удаления дубликатов?

      `ROW_NUMBER()`, так как она всегда присваивает абсолютно уникальный номер каждой строке.

    4. Для чего используется функция NTILE(K)?

      Для разбиения отсортированного набора строк на K равных по количеству групп (корзин / бакетов).

    5. Почему нельзя написать `WHERE ROW_NUMBER() OVER (...) = 1`?

      Потому что оконные функции вычисляются на этапе SELECT, который выполняется строго ПОСЛЕ этапа фильтрации WHERE.

  8. Собеседование: Оконные функции LAG и LEAD

    Собеседование (Data / Product Analyst): Оконные смещения во времени: «Как работают оконные функции LAG(), LEAD(), FIRST_VALUE() и LAST_VALUE()? Как рассчитать время между соседними событиями пользователя и в чем заключается знаменитая ловушка функции LAST_VALUE() с рамкой окна (Window Frame)?»

    Если совсем простыми словами: LAG смотрит в зеркало заднего вида (на предыдущую строку), а LEAD заглядывает вперед (в будущую строку). Без них аналитику пришлось бы делать медленный self-join таблицы самой на себя со смещением по дате.

    Синтаксис и механика функций смещения:

    1. Функции LAG и LEAD: $$\text{LAG}(column, [offset=1], [default=NULL]) \text{ OVER } (\text{PARTITION BY } ... \text{ ORDER BY } ...)$$ - `offset`: Смещение на сколько строк назад/вперед смотреть (по умолчанию 1). - `default`: Значение для первой/последней строки, у которой нет соседа (вместо NULL можно подставить 0).
    2. Ловушка рамки окна в функции `LAST_VALUE()`: Если написать `LAST_VALUE(val) OVER (PARTITION BY u ORDER BY date)`, функция вернет... значение текущей строки, а не последнее значение партиции! Причина: Стандартная рамка окна по умолчанию при наличии `ORDER BY` — это: `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Окно расширяется построчно и заканчивается на текущей строке, поэтому текущая строка и оказывается «последней»! Правильное решение: Явно указывать рамку до конца партиции: `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.

    Практический кейс: Расчет времени бездействия между сессиями (Inactivity Time): Логи приложения содержат клики пользователя. Задача: выделить сессии, если пауза между действиями превысила 30 минут: `diff_minutes = (event_time - LAG(event_time) OVER (PARTITION BY user_id ORDER BY event_time))` Если `diff_minutes > 30` или `diff_minutes IS NULL`, мы ставим флаг `new_session_flag = 1` и затем через кумулятивную сумму нумеруем сессии пользователя!

    -- Расчет дельты выручки к предыдущему месяцу и решение ловушки LAST_VALUE
WITH monthly_revenue AS (
    SELECT '2026-01-01'::DATE AS month_date, 100000 AS revenue UNION ALL
    SELECT '2026-02-01'::DATE, 125000 UNION ALL
    SELECT '2026-03-01'::DATE, 110000 UNION ALL
    SELECT '2026-04-01'::DATE, 150000
)
SELECT
    month_date,
    revenue,
    -- 1. Значение прошлого месяца
    LAG(revenue, 1) OVER (ORDER BY month_date) AS prev_month_rev,
    -- 2. Абсолютный и процентный прирост (MoM Growth)
    revenue - LAG(revenue, 1) OVER (ORDER BY month_date) AS mom_diff,
    ROUND(
        (revenue - LAG(revenue, 1) OVER (ORDER BY month_date)) * 100.0 / 
        NULLIF(LAG(revenue, 1) OVER (ORDER BY month_date), 0), 
        1
    ) AS mom_growth_pct,
    -- 3. Корректное использование LAST_VALUE с явным фреймом до конца окна:
    LAST_VALUE(revenue) OVER (
        ORDER BY month_date 
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    ) AS final_month_revenue
FROM monthly_revenue;
    • Использование LAST_VALUE() без явного указания фрейма ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING. Функция будет возвращать значение текущей строки, вводя аналитика в заблуждение.
    • Забывание о NULL в первой строке при использовании LAG(). Арифметические операции с NULL возвращают NULL, поэтому деление `rev / LAG(rev)` в первой строке требует обработки через COALESCE или NULLIF.
    • Использование LAG без предложения ORDER BY. Оконные смещения не имеют физического смысла без строгой детерминированной сортировки.
    • Путаница между LAG и LEAD при обратной сортировке DESC. При `ORDER BY date DESC` функция LAG() начинает возвращать хронологически следующее событие!

    На собеседовании: обязательно упомяните дефолтный фрейм окна в стандарте SQL (RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) при объяснении поведения LAST_VALUE. Это высший пилотаж.

    1. Что делают функции LAG() и LEAD()?

      LAG() возвращает значение из строки, находящейся на N позиций позади текущей; LEAD() — из строки на N позиций впереди.

    2. Что вернет LAG() для самой первой строки партиции?

      Значение NULL (или заданное значение по умолчанию, если передан третий аргумент).

    3. В чем заключается ловушка функции LAST_VALUE()?

      По умолчанию рамка окна ограничена текущей строкой (CURRENT ROW), поэтому LAST_VALUE() возвращает саму текущую строку вместо последнего значения группы.

    4. Как исправить поведение функции LAST_VALUE()?

      Явно указать границы фрейма: `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.

    5. Как рассчитать Month-over-Month (MoM) прирост с помощью LAG?

      Как разность текущего значения и `LAG(revenue) OVER (ORDER BY month)`.

  9. Собеседование: Накопительный итог (Running Total)

    Собеседование (Middle/Senior Analyst): Практическая задача на окна: «Как написать SQL-запрос для расчета накопительного итога (Running Total) и скользящего среднего (Moving Average)? В чем фундаментальная разница между рамками окон ROWS и RANGE при наличии одинаковых дат?»

    Если совсем простыми словами: накопительный итог — это копилка. Каждая новая строка добавляет свои деньги к сумме всех предыдущих строк. Но если у вас две покупки совершены в один день, ключевое слово `RANGE` объединит их и покажет одинаковую сумму сразу в обеих строках, а `ROWS` прибавит честно по очереди.

    Устройство оконных рамок (Window Frames): ROWS против RANGE:

    1. Синтаксис накопительного итога: $$\text{SUM}(amount) \text{ OVER } (\text{PARTITION BY } ... \text{ ORDER BY date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW})$$
    2. Разница между ROWS и RANGE: - **ROWS:** Работает строго с физическими строками таблицы. Обрабатывает записи строго по одной: текущая строка берет ровно строки от начала до себя. - **RANGE:** Работает с логическим диапазоном значений ключа сортировки `ORDER BY`. Опасность RANGE: Если несколько строк имеют одинаковое значение даты (Tie), `RANGE` суммирует все эти строки целиком и выдает одинаковый суммарный итог для всех дубликатов сразу!
    3. Скользящее среднее (Moving Average): $$\text{AVG}(metric) \text{ OVER } (\text{ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW})$$ Окно охватывает ровно текущую строку и 6 предшествующих (7-дневное сглаживание недельной сезонности).

    Сравнение ROWS и RANGE при совпадении дат: Транзакции в один день 2026-10-01: заказ 1 ($100$ руб.) и заказ 2 ($200$ руб.). - `SUM(amount) OVER (ORDER BY date ROWS ...)`: - Заказ 1: **$100$ руб.** - Заказ 2: **$300$ руб.** (строго накопительно). - `SUM(amount) OVER (ORDER BY date RANGE ...)`: - Заказ 1: **$300$ руб.** (схлопнулись вместе!) - Заказ 2: **$300$ руб.**

    -- Накопительный итог и 7-дневное скользящее среднее в одном запросе
WITH daily_sales AS (
    SELECT '2026-10-01'::DATE AS sale_date, 10000 AS amount UNION ALL
    SELECT '2026-10-02'::DATE, 15000 UNION ALL
    SELECT '2026-10-03'::DATE, 12000 UNION ALL
    SELECT '2026-10-04'::DATE, 18000 UNION ALL
    SELECT '2026-10-05'::DATE, 25000 UNION ALL
    SELECT '2026-10-06'::DATE, 20000 UNION ALL
    SELECT '2026-10-07'::DATE, 30000
)
SELECT
    sale_date,
    amount,
    -- 1. Накопительный итог с начала времен (Cumulative Sum)
    SUM(amount) OVER (
        ORDER BY sale_date 
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total_revenue,
    
    -- 2. Скользящее среднее за 3 дня (текущий + 2 предшествующих)
    ROUND(
        AVG(amount) OVER (
            ORDER BY sale_date 
            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
        ), 
        2
    ) AS moving_avg_3d
FROM daily_sales
ORDER BY sale_date;
    • Использование краткой записи `SUM(x) OVER (ORDER BY d)` без указания ROWS. По умолчанию стандарт SQL использует RANGE, что приводит к некорректным скачкам сумм при наличии дублирующихся дат.
    • Попытка посчитать накопительный итог через треугольный SELF-JOIN (a.date >= b.date). Имеет квадратичную сложность $O(N^2)$, которая на 100 000 строк подвесит сервер на часы (оконная функция считает за $O(N \log N)$).
    • Забывание min_periods при расчете скользящих средних на первых строках. Первые N строк окна усредняют меньшее число наблюдений, что может создать ложное впечатление просадки.
    • Использование фрейма ROWS на временных рядах с пропусками дней. Окно из 7 строк не будет равно 7 дням, если в ряде пропущены выходные дни.

    На собеседовании: всегда явно пишите ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW вместо краткой формы `OVER (ORDER BY date)`. Это подчеркивает знание тонкостей фрейма ROWS/RANGE.

    1. Что такое накопительный итог (Running Total)?

      Последовательное суммирование значений текущей и всех предшествующих строк внутри упорядоченного набора данных.

    2. В чем различие между ROWS и RANGE во фрейме окна?

      ROWS считает физические строки независимо от значений; RANGE объединяет строки с совпадающими значениями ключа сортировки в одну общую группу.

    3. Какое поведение оконного фрейма задано по умолчанию при наличии ORDER BY?

      `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

    4. Как рассчитать 7-дневное скользящее среднее на непрерывном ежедневном ряде?

      `AVG(val) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)`.

    5. Какова вычислительная сложность расчета накопительного итога оконной функцией?

      $O(N \log N)$ на этапе сортировки и $O(N)$ на этапе одного прохода оконного аккумулятора.

  10. Собеседование: Common Table Expressions (CTE) vs Subqueries

    Собеседование (Data Engineer / Senior Analyst): Структурирование сложного SQL: «В чем разница между CTE (WITH), подзапросами (Subqueries) и временными таблицами? Как оптимизатор PostgreSQL 12+ обрабатывает CTE (Inlining vs Materialization Fence) и как работают рекурсивные CTE (WITH RECURSIVE)?»

    Если совсем простыми словами: CTE — это временные именованные переменные в начале запроса, делающие SQL похожим на понятную поэтапную программу сверху вниз. Без них сложный аналитический запрос превращается в нечитаемую «матрешку» из пяти вложенных подзапросов.

    Сравнительный анализ и поведение оптимизатора:

    1. Читаемость и декомпозиция (Code Structure): - Подзапросы (`FROM (SELECT ...)`) читаются изнутри наружу (снизу вверх), усложняя отладку. - CTE (`WITH step1 AS (...), step2 AS (...)`) читаются последовательно от источника к результату.
    2. Поведение оптимизатора (Optimization Fence в PostgreSQL 12+): - До PostgreSQL 12: CTE всегда материализовался принудительно (Optimization Fence). СУБД вычисляла CTE целиком и складывала во временный буфер памяти, даже если внешний запрос брал только `LIMIT 1`. - Начиная с PostgreSQL 12: Оптимизатор по умолчанию **встраивает (inline)** нерекурсивные CTE без побочных эффектов прямо во внешний запрос, проталкивая предикаты `WHERE` и индексы внутрь. - Управление материализацией: `WITH my_cte AS MATERIALIZED (...)` (принудительно изолировать расчет) или `NOT MATERIALIZED` (принудительно встроить в план).
    3. Рекурсивные CTE (Recursive CTE): Синтаксис `WITH RECURSIVE cte AS (Anchor query UNION ALL Recursive query)`: - Anchor: Базовый шаг (корень иерархии или начальное число). - Recursive: Итеративный шаг, ссылающийся на саму CTE, пока результирующий набор не станет пустым. - Незаменимы для обхода графов, деревьев категорий и генерации дат.

    Практический пример: Обход организационной структуры компании: Задача: найти всех подчиненных генерального директора на всех уровнях иерархии: Anchor: `SELECT emp_id, manager_id, 1 AS level FROM employees WHERE manager_id IS NULL` Recursive: `SELECT e.emp_id, e.manager_id, c.level + 1 FROM employees e JOIN org_tree c ON e.manager_id = c.emp_id` Рекурсивный CTE обходит дерево произвольной глубины за один элегантный SQL-запрос.

    -- 1. Пример рекурсивного CTE для генерации непрерывного календаря дат
WITH RECURSIVE calendar AS (
    -- Anchor member (начало диапазона)
    SELECT '2026-10-01'::DATE AS cal_date
    UNION ALL
    -- Recursive member (итерация +1 день до условия остановки)
    SELECT (cal_date + INTERVAL '1 day')::DATE
    FROM calendar
    WHERE cal_date < '2026-10-07'::DATE
)
SELECT cal_date FROM calendar;

-- 2. Использование явной подсказки MATERIALIZED для тяжелого общего расчета
WITH expensive_stats AS MATERIALIZED (
    SELECT
        user_id,
        COUNT(*) AS total_tx,
        SUM(amount) AS total_spent
    FROM transactions
    WHERE event_date >= CURRENT_DATE - INTERVAL '90 days'
    GROUP BY user_id
)
SELECT u.email, s.total_spent
FROM users u
JOIN expensive_stats s ON u.user_id = s.user_id
WHERE s.total_spent > 100000;
    • Бесконечный цикл в рекурсивном CTE из-за циклов в данных (A ссылается на B, B ссылается на A). Запрос зависнет навсегда; для защиты используйте лимит глубины `WHERE level < 50` или отслеживание пути через массив `ARRAY[id]`.
    • Использование десятков вложенных CTE там, где достаточно простой временной таблицы. При очень сложных многостадийных ETL-скриптах временная таблица (`CREATE TEMP TABLE`) с созданием индексов работает быстрее огромного монолитного WITH.
    • Забывание о том, что CTE не сохраняется между запросами. Область видимости CTE ограничена строго одним единственным SQL-запросом.
    • Неучет того, что до Postgres 12 CTE блокировал проталкивание предикатов (Predicate Pushdown). Если в старых версиях к CTE применялся внешний WHERE, база все равно сканировала таблицу целиком.

    На собеседовании: расскажите про ключевое изменение в PostgreSQL 12 относительно inline-оптимизации CTE и синтаксис MATERIALIZED / NOT MATERIALIZED. Это признак глубокой экспертизы.

    1. Что такое CTE (Common Table Expression)?

      Временный именованный результирующий набор данных, определенный с помощью оператора WITH и доступный в рамках одного SQL-запроса.

    2. Как изменилась оптимизация CTE в PostgreSQL начиная с версии 12?

      Нерекурсивные CTE стали по умолчанию встраиваться (inline) в общий план запроса, как обычные подзапросы, с проталкиванием предикатов WHERE.

    3. Из каких двух обязательных частей состоит рекурсивный CTE?

      Из якорного запроса (Anchor member) и рекурсивного запроса (Recursive member), объединенных через UNION ALL.

    4. Как предотвратить зацикливание рекурсивного CTE при обходе графов с циклами?

      Добавлением ограничения максимального уровня глубины (`level < MAX`) или отслеживанием массива посещенных вершин (`NOT id = ANY(path)`).

    5. Зачем использовать явную директиву WITH ... AS MATERIALIZED?

      Чтобы принудительно заставить СУБД выполнить расчет CTE один раз и сохранить его в буфер памяти, предотвращая повторное вычисление при многократном обращении.

  11. Собеседование: Топ-N записей в каждой группе

    Собеседование (Senior Data Analyst / Backend): Классический хит технических секций: «Как эффективно выбрать Топ-N записей в каждой группе (например, 3 самых дорогих товара в каждой категории или последний заказ каждого клиента)? Почему на огромных таблицах оконная функция ROW_NUMBER() проигрывает соединению LATERAL и специфической конструкции PostgreSQL DISTINCT ON?»

    Если совсем простыми словами: ROW_NUMBER() честно перебирает и нумерует абсолютно все миллионы строк таблицы, даже если вам нужны только 3 штуки из каждой папки. Конструкция LATERAL с правильным индексом прыгает сразу к верхушке каждой группы (Index Skip Scan), выполняя запрос в тысячи раз быстрее.

    Три паттерна решения задачи Топ-N в каждой группе:

    1. Паттерн 1: Оконная функция ROW_NUMBER() (Стандарт ANSI SQL): Универсальный переносимый подход. `WITH ranked AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY cat_id ORDER BY price DESC) AS rn FROM products) SELECT * FROM ranked WHERE rn <= 3;` - Плюс: Работает в любых СУБД (Postgres, MySQL, Oracle, ClickHouse). - Минус: Сканирует и сортирует всю таблицу целиком ($100$ млн строк), даже если категорий всего 10.
    2. Паттерн 2: PostgreSQL DISTINCT ON (Топ-1 в каждой группе): Специфический сверхбыстрый синтаксис для выбора ровно одной записи: `SELECT DISTINCT ON (customer_id) * FROM orders ORDER BY customer_id, order_date DESC;` Возвращает строго первую строку для каждого уникального значения `customer_id`.
    3. Паттерн 3: CROSS JOIN LATERAL (High-Performance Top-N): Соединение таблицы категорий с подзапросом, содержащим `LIMIT N`: `SELECT c.cat_name, p.* FROM categories c CROSS JOIN LATERAL (SELECT * FROM products WHERE cat_id = c.id ORDER BY price DESC LIMIT 3) p;` - Магия: При наличии индекса `(cat_id, price DESC)` база делает ровно 3 точечных чтения индекса на каждую категорию ($O(K \times N)$ вместо $O(\text{Все строки})$)!

    Сравнение производительности на 10 млн товаров (50 категорий): - ROW_NUMBER(): Читает 10 млн строк, сортирует в памяти: $4.8$ секунды. - LATERAL + B-Tree индекс: Делает $50 \times 3 = 150$ чтений по индексу: $0.002$ секунды (ускорение в $2400$ раз!).

    -- 1. Классический переносимый подход через ROW_NUMBER() (Топ-3 товара в категории)
WITH ranked_products AS (
    SELECT
        category_id,
        product_name,
        price,
        ROW_NUMBER() OVER (
            PARTITION BY category_id 
            ORDER BY price DESC
        ) AS ranking
    FROM products
)
SELECT category_id, product_name, price, ranking
FROM ranked_products
WHERE ranking <= 3
ORDER BY category_id, ranking;

-- 2. Высокопроизводительный подход через LATERAL JOIN для больших таблиц
-- Требует индекса: CREATE INDEX idx_products_cat_price ON products(category_id, price DESC);
SELECT
    c.category_id,
    c.category_name,
    top_p.product_name,
    top_p.price
FROM categories c
CROSS JOIN LATERAL (
    SELECT product_name, price
    FROM products p
    WHERE p.category_id = c.category_id
    ORDER BY p.price DESC
    LIMIT 3
) top_p
ORDER BY c.category_id, top_p.price DESC;
    • Использование ROW_NUMBER() без покрытия составным индексом на больших таблицах. Приводит к тяжелой дисковой сортировке всей таблицы при выборке всего нескольких строк.
    • Забывание о том, что порядок колонок в ORDER BY при DISTINCT ON должен начинаться с полей DISTINCT ON. В PostgreSQL синтаксис `DISTINCT ON (a) ... ORDER BY b` выбросит ошибку; порядок обязан быть `ORDER BY a, b`.

    Методология физической дедупликации данных:

    1. Понятие системного атрибута `ctid` в PostgreSQL: - Каждая физическая строка (кортеж / tuple) в таблице PostgreSQL имеет невидимый системный идентификатор `ctid` вида `(page_number, tuple_offset)` (например, `(0, 1)` — первая страница, первая строка). - `ctid` уникален для каждой строки в данный момент времени и идеально подходит для точечного удаления дубликатов, когда у таблицы нет первичного ключа.
    2. Стратегия 1: DELETE через CTE и оконную функцию (Рекомендуемый стандарт): Группируем строки по бизнес-ключам, нумеруем через `ROW_NUMBER()` и удаляем строки с `rn > 1`.
    3. Стратегия 2: DELETE через ctid и подзапрос: `DELETE FROM users WHERE ctid NOT IN (SELECT MIN(ctid) FROM users GROUP BY email);` Удаляет все физические строки, кроме кортежей с минимальным адресом блока.
    4. Стратегия 3: Пересоздание таблицы (Table Swap для огромных данных): Если дубликатов более $30\%$ в таблице на 100 млн строк, DELETE вызовет гигантский Table Bloat и блокировки. Быстрее создать новую таблицу через `INSERT INTO new_table SELECT DISTINCT ON ...`, создать индексы и сделать `ALTER TABLE RENAME`.

    -- 1. Эталонное удаление дубликатов в PostgreSQL через CTE и ctid
WITH ranked_duplicates AS (
    SELECT
        ctid,
        ROW_NUMBER() OVER (
            PARTITION BY client_id, email 
            ORDER BY created_at ASC -- сохраняем самую раннюю запись
        ) AS duplicate_rank
    FROM client_applications
)
DELETE FROM client_applications
WHERE ctid IN (
    SELECT ctid 
    FROM ranked_duplicates 
    WHERE duplicate_rank > 1
);

    Собеседование (Lead Product Analyst): Высший пилотаж аналитического SQL: «Напишите сквозной SQL-запрос для построения треугольной матрицы месячного когортного удержания (Monthly Cohort Retention Rate) по таблице пользовательской активности user_events(user_id, event_date). Как избежать смещения дат и корректно развернуть матрицу?»

    Если совсем простыми словами: когортный анализ — это отслеживание судьбы людей, пришедших в один месяц. Мы группируем людей по месяцу их «рождения» и смотрим, какой процент из них вернулся в магазин через 1 месяц, через 2 месяца и через полгода.

    Математический и технический алгоритм расчета когортной матрицы:

    1. Шаг 1: Определение даты когорты для каждого пользователя: Используем оконную функцию `MIN(event_date) OVER (PARTITION BY user_id)` или группировку, усекая дату до месяца через `DATE_TRUNC('month', ...)`.
    2. Шаг 2: Расчет индекса периода жизни (Cohort Index / Month Offset): Вычисляем разницу в полных месяцах между датой текущего события и датой когорты: $$\Delta M = (\text{Year}_{\text{event}} - \text{Year}_{\text{cohort}}) \times 12 + (\text{Month}_{\text{event}} - \text{Month}_{\text{cohort}})$$
    3. Шаг 3: Агрегация уникальных пользователей (Active Users): Группируем по `(cohort_month, month_offset)` и считаем `COUNT(DISTINCT user_id)`. Базовый размер когорты — это число пользователей на смещении $0$ ($M_0$).
    4. Шаг 4: Разворачивание (Pivot) в треугольную матрицу: Используем условную фильтрацию `100.0 * COUNT(DISTINCT CASE WHEN month_offset = K THEN user_id END) / cohort_size`.

    -- Сквозной расчет когортного удержания в PostgreSQL
WITH user_cohorts AS (
    -- 1. Месяц первого действия (когорта) каждого клиента
    SELECT
        user_id,
        DATE_TRUNC('month', MIN(event_date))::DATE AS cohort_month
    FROM user_events
    GROUP BY user_id
),
activity_with_offsets AS (
    -- 2. Связываем каждое последующее событие с когортой и вычисляем смещение
    SELECT DISTINCT
        e.user_id,
        c.cohort_month,
        -- Формула точного смещения в месяцах
        (EXTRACT(YEAR FROM e.event_date) - EXTRACT(YEAR FROM c.cohort_month)) * 12 +
        (EXTRACT(MONTH FROM e.event_date) - EXTRACT(MONTH FROM c.cohort_month)) AS month_offset
    FROM user_events e
    JOIN user_cohorts c ON e.user_id = c.user_id
),
cohort_sizes AS (
    -- 3. Базовый размер когорты на нулевом месяце
    SELECT
        cohort_month,
        COUNT(DISTINCT user_id) AS total_users
    FROM user_cohorts
    GROUP BY cohort_month
)
-- 4. Сборка треугольной матрицы Retention Rate (%)
SELECT
    TO_CHAR(cs.cohort_month, 'YYYY-MM') AS cohort,
    cs.total_users AS cohort_size,
    100.0 AS m0,
    ROUND(100.0 * COUNT(DISTINCT CASE WHEN a.month_offset = 1 THEN a.user_id END) / cs.total_users, 1) AS m1,
    ROUND(100.0 * COUNT(DISTINCT CASE WHEN a.month_offset = 2 THEN a.user_id END) / cs.total_users, 1) AS m2,
    ROUND(100.0 * COUNT(DISTINCT CASE WHEN a.month_offset = 3 THEN a.user_id END) / cs.total_users, 1) AS m3,
    ROUND(100.0 * COUNT(DISTINCT CASE WHEN a.month_offset = 6 THEN a.user_id END) / cs.total_users, 1) AS m6
FROM cohort_sizes cs
LEFT JOIN activity_with_offsets a ON cs.cohort_month = a.cohort_month
GROUP BY cs.cohort_month, cs.total_users
ORDER BY cs.cohort_month ASC;
    • Расчет разницы месяцев через простое деление дней на 30 `(date2 - date1) / 30`. Длина месяцев колеблется от 28 до 31 дня; деление на 30 приводит к хаотичным ошибкам смещения когорт.
    • Забывание DISTINCT при подсчете активных пользователей месяца. Пользователь с 50 событиями в месяце будет посчитан 50 раз, раздув Retention свыше 100%.
    • Неучет того, что размер когорты должен определяться строго по месяцу 0. Использование текущего числа активных исказит знаменатель расчета долей.
    • Жесткий JOIN вместо LEFT JOIN при сведении матрицы. Если в каком-то месяце вернулось 0 человек, строка когорты может полностью выпасть из отчета.

    На собеседовании: четко структурируйте код на 3 CTE: **определение когорт $\to$ расчет смещения $\to$ сводная матрица**. Читаемость и архитектурная чистота решения оцениваются в первую очередь.

    1. Что является базой (размером) когорты при расчете Retention Rate?

      Количество уникальных пользователей, совершивших первое ключевое действие в период формирования данной когорты (месяц 0).

    2. Как рассчитать целочисленную разницу в месяцах между двумя датами в SQL?

      `((EXTRACT(YEAR FROM d2) - EXTRACT(YEAR FROM d1)) * 12 + EXTRACT(MONTH FROM d2) - EXTRACT(MONTH FROM d1))`.

    3. Почему нулевой месяц (m0) в когортном анализе всегда строго равен 100%?

      Потому что все пользователи когорты по определению проявили активность в месяц своего привлечения ($N_0 / N_0 = 100\%$).

    4. Какую роль играет функция DATE_TRUNC('month', date)?

      Она усекает дату до первого числа соответствующего месяца со временем 00:00:00.

    5. Как развернуть строки смещений в столбцы без сторонних модулей?

      Через условную агрегацию с конструкцией `COUNT(DISTINCT CASE WHEN month_offset = K THEN user_id END)`.

  14. Собеседование: Задача Gaps and Islands (Острова и пропуски)

    Собеседование (Lead Analyst / Senior SQL): Легендарная олимпиадная задача на собеседованиях: «Дана таблица посещений пользователем приложения по дням user_logins(user_id, login_date). Как найти непрерывные последовательности дней активности (Острова / Islands), максимальный непрерывный стрик (Streak) каждого пользователя и интервалы пропусков (Пропуски / Gaps)? В чем заключается математический фокус разности двух последовательностей?»

    Если совсем простыми словами: трюк 'Gaps and Islands' — это чистая математическая магия. Если из непрерывно растущей даты вычесть непрерывно растущий номер строки ($1, 2, 3$), их разность останется абсолютной константой! Как только в датах случается пропуск (дыра), эта разность мгновенно перескакивает на новое число, автоматически создавая идеальный ключ группы.

    Математическое доказательство трюка Difference of Row Numbers:

    1. Идея константной разности: Пусть у нас есть непрерывная последовательность дат $D_i$ и их порядковые номера $R_i$: $$D_i = D_0 + i \cdot \text{1 day}, \quad R_i = R_0 + i$$ Вычтем номер строки (умноженный на 1 день) из даты: $$D_i - R_i \cdot \text{1 day} = (D_0 + i) - (R_0 + i) = D_0 - R_0 = \text{const}$$ Пока дни идут подряд без пропусков, разность $(D_i - R_i)$ строго постоянна!
    2. Что происходит при пропуске (Gap): Если пользователь пропустил 3 дня, дата перескакивает на $+4$, а номер строки увеличивается только на $+1$. Разность $(D_{i+1} - R_{i+1})$ скачкообразно меняется, образуя идентификатор нового острова!
    3. Группировка: Группируя по полученной константной разности `grp`, мы мгновенно находим: - Начало острова: `MIN(login_date)`. - Конец острова: `MAX(login_date)`. - Длину непрерывной серии (Streak): `COUNT(*)`.

    Демонстрация трюка на числах: Даты: 01-е, 02-е, 03-е (пропуск!) 07-е, 08-е число. - День 1: 01.10 - 1 = **30.09** (Группа A) - День 2: 02.10 - 2 = **30.09** (Группа A) - День 3: 03.10 - 3 = **30.09** (Группа A) $\to$ Стрик = 3 дня! - Пропуск 3 дня - День 4: 07.10 - 4 = **03.10** (Группа B) - День 5: 08.10 - 5 = **03.10** (Группа B) $\to$ Стрик = 2 дня!

    -- Решение классической задачи Gaps and Islands (поиск непрерывных серий входов)
WITH distinct_logins AS (
    -- Шаг 1: Дедупликация (пользователь мог войти 5 раз за один день)
    SELECT DISTINCT
        user_id,
        login_date
    FROM user_logins
),
numbered_logins AS (
    -- Шаг 2: Вычисление порядкового номера дня активности
    SELECT
        user_id,
        login_date,
        ROW_NUMBER() OVER (
            PARTITION BY user_id 
            ORDER BY login_date ASC
        ) AS row_num
    FROM distinct_logins
),
islands AS (
    -- Шаг 3: Математический фокус вычитания номера строки из даты
    SELECT
        user_id,
        login_date,
        -- Разность образует уникальный групповой маркер непрерывного острова
        (login_date - (row_num * INTERVAL '1 day'))::DATE AS island_group
    FROM numbered_logins
),
streak_summary AS (
    -- Шаг 4: Агрегация непрерывных серий
    SELECT
        user_id,
        MIN(login_date) AS streak_start,
        MAX(login_date) AS streak_end,
        COUNT(*) AS streak_length_days
    FROM islands
    GROUP BY user_id, island_group
)
-- Шаг 5: Нахождение максимального стрика для каждого пользователя
SELECT
    user_id,
    streak_start,
    streak_end,
    streak_length_days
FROM (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY user_id 
            ORDER BY streak_length_days DESC, streak_start DESC
        ) AS rn
    FROM streak_summary
)
WHERE rn = 1;
    • Забывание предварительной дедупликации дат на шаге 1. Если в один день было 2 входа, номер строки увеличится на 2 при одинаковой дате, сломав разность констант.
    • Попытка решения задачи через рекурсивный CTE на миллионах строк. Рекурсивный CTE имеет сложность $O(N^2)$ и упадет по памяти, в то время как трюк с ROW_NUMBER() работает за $O(N \log N)$.
    • Неучет нерегулярных временных меток со временем (TIMESTAMP вместо DATE). Метки времени необходимо обязательно приводить к типу DATE, иначе миллисекунды уничтожат равенство.
    • Путаница в нахождении пропусков (Gaps). Для поиска самих пропусков проще использовать функцию `LEAD(date) OVER ()` и условие `next_date - date > 1`.

    На собеседовании: мгновенно произнесите фразу «Разность даты и номера строки постоянна для непрерывных последовательностей». Это классический маркер эрудиции и высокого ранга в SQL.

    1. В чем суть задачи Gaps and Islands (Острова и пропуски)?

      В разбиении дискретных упорядоченных последовательностей на непрерывные непрерывающиеся диапазоны (острова) и изолировании промежутков между ними (пропуски).

    2. Почему выражение `date - ROW_NUMBER() * INTERVAL '1 day'` является константой внутри острова?

      Потому что для последовательных дней и дата, и номер строки прирастают ровно на 1 единицу на каждом шаге.

    3. Зачем необходима предварительная дедупликация дат перед расчетом островов?

      Чтобы один календарный день соответствовал строго одному номеру строки.

    4. Как найти сами пропуски (Gaps) между событиями?

      С помощью функции `LEAD(event_date)`: условие `LEAD(event_date) - event_date > 1` указывает на наличие разрыва.

    5. Какова вычислительная сложность алгоритма поиска островов через ROW_NUMBER()?

      $O(N \log N)$ на этапе сортировки оконной функции, что делает его масштабируемым на миллиарды строк.

    Собеседование (Senior Database / Analytics Engineer): Глубокое понимание структур данных: «Как устроено сбалансированное дерево B-Tree в индексах реляционных баз данных? Как работает правило левого префикса (Leftmost Prefix Rule) для составных индексов, что такое Index-Only Scan с предложением INCLUDE и в каких случаях индекс BRIN превосходит B-Tree?»

    Если совсем простыми словами: B-Tree индекс — это алфавитный указатель в конце толстой энциклопедии. Вместо листания всех 1000 страниц подряд вы за 3 шага находите нужную фамилию и сразу открываете конкретную страницу. Составной индекс — как телефонная книга, отсортированная строго по 'Фамилия $\to$ Имя $\to$ Отчество'.

    Анатомия индексов и физические механизмы поиска:

    1. Устройство B+Tree (Balanced Tree) индекса: - Корень (Root) $\to$ Промежуточные узлы (Internal Nodes) $\to$ Листовые страницы (Leaf Pages). - Листовые страницы связаны двусвязным списком (Doubly Linked List), обеспечивая мгновенный диапазонный поиск (`BETWEEN`, `>`, `<`). - Лист содержит: `(Ключ, TID / ItemPointer)` — физический адрес строки на диске `(block, offset)`. - Сложность поиска: $O(\log N)$. При 100 млн строк высота дерева составляет всего 3-4 уровня!
    2. Правило левого префикса (Leftmost Prefix Rule): Индекс создан по полям `(A, B, C)`: - Запросы `WHERE A = 1` $\to$ Использует индекс. - Запросы `WHERE A = 1 AND B = 2` $\to$ Использует индекс. - Запросы `WHERE B = 2 AND C = 3` $\to$ НЕ МОЖЕТ использовать индекс (первое поле пропущено, как поиск по имени 'Иван' в телефонной книге без знания фамилии!).
    3. Покрывающие индексы (Covering Index / Index-Only Scan): Индекс с дополнительными неключевыми полями: `CREATE INDEX ... ON orders(customer_id) INCLUDE (total_amount)`. - Поле `total_amount` хранится только в листьях дерева и не участвует в сортировке. - Запрос `SELECT total_amount FROM orders WHERE customer_id = 42` получает данные строго из индекса, вообще не обращаясь к таблице на диске (Zero Heap Fetches)!
    4. Индексы BRIN (Block Range Index): - Хранит только диапазон `[MIN, MAX]` для блока из 128 страниц. - Размер: в 1000 раз меньше B-Tree! - Идеален для монотонно растущих временных рядов и логов событий.

    Кейс из продакшена: Ускорение аналитического запроса в 300 раз: Запрос: `SELECT user_id, sum(spent) FROM orders WHERE status = 'paid' GROUP BY user_id;` Таблица: $50$ млн строк. Обычный B-Tree на `(status)` требовал чтения миллионов страниц таблицы из Heap. Создание покрывающего индекса `CREATE INDEX idx ON orders(status, user_id) INCLUDE (spent);` перевело план в **Index Only Scan**, сократив время с $14$ секунд до $0.04$ секунды!

    -- 1. Создание композитного B-Tree индекса с учетом селективности (слева направо)
CREATE INDEX idx_orders_customer_date 
ON orders (customer_id, order_date DESC);

-- 2. Создание покрывающего индекса с предложением INCLUDE для Index-Only Scan
CREATE INDEX idx_orders_covering_report 
ON orders (customer_id) 
INCLUDE (total_amount, status);

-- 3. Частичный индекс (Partial Index) для экономии 95% памяти RAM
-- Индексирует только активные заказы (не раздувает B-Tree завершенными архивами)
CREATE INDEX idx_orders_active_only 
ON orders (created_at) 
WHERE status IN ('processing', 'delivering');

-- 4. BRIN-индекс для гигантской таблицы аналитических логов (терабайты данных)
CREATE INDEX idx_events_timestamp_brin 
ON app_event_logs USING BRIN (event_timestamp);
    • Применение функций к индексированным колонкам в блоке WHERE. Выражение `WHERE DATE(created_at) = '2026-10-01'` ослепляет индекс B-Tree! Нужно писать диапазон `WHERE created_at >= '2026-10-01' AND created_at < '2026-10-02'`.
    • Создание индексов на низкоселективные колонки (например, пол M/F или булев флаг is_active). Оптимизатор проигнорирует такой индекс и выберет последовательное сканирование Seq Scan; используйте частичные индексы (Partial Indexes).
    • Чрезмерная индексация всех подряд колонок (Over-indexing). Каждый дополнительный индекс драматически замедляет операции INSERT, UPDATE и DELETE, так как требует обновления деревьев.
    • Неучет неявного приведения типов (Type Coercion). Если колонка `phone` имеет тип VARCHAR, а запрос ищет `WHERE phone = 79991234567` (число), индекс не применится.

    На собеседовании: обязательно объясните разницу между B-Tree, BRIN (для временных рядов) и концепцией Index-Only Scan с INCLUDE. Это признак элитного разработчика.

    1. Какова вычислительная сложность поиска по B-Tree индексу?

      $O(\log N)$ благодаря сбалансированной древовидной структуре страниц.

    2. В чем суть правила левого префикса (Leftmost Prefix Rule)?

      Составной индекс может использоваться только в том случае, если предикаты запроса фильтруют по начальным (левым) столбцам определения индекса без пропусков.

    3. Что такое Index-Only Scan?

      Режим выполнения запроса, при котором все запрашиваемые данные извлекаются напрямую из листьев индекса без обращения к страницам самой таблицы на диске.

    4. Чем полезно предложение INCLUDE при создании индекса?

      Оно включает дополнительные столбцы в листовые узлы индекса для поддержки Index-Only Scan, не утяжеляя дерево сортировкой по ним.

    5. В чем специфика индекса BRIN (Block Range Index)?

      Он хранит только минимальные и максимальные значения для блоков страниц, занимая в сотни раз меньше места и эффективно работая на физически отсортированных данных.

  16. Собеседование: Чтение плана запроса EXPLAIN

    Собеседование (Database Performance Tuning): Экспертный навык оптимизации: «Как читать и анализировать план выполнения запроса EXPLAIN (ANALYZE, BUFFERS)? Чем отличаются оценки планировщика (Cost) от реального времени (Actual Time), как трактовать узлы Seq Scan, Index Scan, Bitmap Scan и о чем сигнализирует метрика Buffers: shared read?»

    Если совсем простыми словами: EXPLAIN — это рентгеновский снимок работы базы данных. Он показывает, какую стратегию выбрал планировщик, сколько страниц он прочитал из оперативной памяти, а сколько пришлось мучительно считывать с медленного диска.

    Анатомия вывода EXPLAIN (ANALYZE, BUFFERS):

    1. EXPLAIN vs EXPLAIN ANALYZE: - `EXPLAIN`: Показывает гипотетический план и оценку стоимости (Cost) на основе статистики `pg_statistic` без реального запуска запроса. - `EXPLAIN ANALYZE`: Реально выполняет запрос на сервере, замеряет фактическое время в миллисекундах и сравнивает прогноз с фактом. Осторожно с DELETE/UPDATE!
    2. Ключевые метрики в строке плана: `cost=0.42..8.45 rows=10 width=64 (actual time=0.015..0.030 rows=8 loops=1)` - `cost=0.42..8.45`: Условные единицы дискового I/O. Первое число — стоимость получения первой строки (Startup cost), второе — общая стоимость (Total cost). - `rows=10 vs actual rows=8`: Если оценка планировщика расходится с фактом в $10-1000$ раз — статистика устарела, требуется `ANALYZE table`. - `loops=N`: Количество повторений узла (например, во внешнем цикле Nested Loop). Общее реальное время = `actual time * loops`!
    3. Типы узлов сканирования таблицы: - **Seq Scan:** Полное последовательное сканирование таблицы. Нормально для чтения $>20\%$ строк, катастрофа для точечных поисков. - **Index Scan:** Поиск в B-Tree $\to$ точечный переход в страницу таблицы (Heap Fetch) за каждой строкой. - **Index Only Scan:** Данные прочитаны строго из индекса без перехода в таблицу. - **Bitmap Index Scan + Bitmap Heap Scan:** Индекс сканируется целиком, строится битовая карта страниц в памяти, затем страницы таблицы читаются последовательно.
    4. Анализ дискового ввода-вывода (Buffers): - `shared hit`: Страницы найдены в оперативной памяти (`shared_buffers` RAM) — мгновенно. - `shared read`: Страницы прочитаны с диска/SSD — главный источник задержек.

    Кейс оптимизации по EXPLAIN: Запрос выполнялся за $12.4$ секунды. План показал: `Seq Scan on large_orders (cost=0.00..894520.00 rows=5) (Buffers: shared read=450000)`. Аналитик обнаружил, что база прочитала $450\,000$ блоков ($3.5$ ГБ) с диска ради 5 строк! После добавления индекса план переключился на `Index Scan (Buffers: shared hit=4)`, время выполнения упало до 0.8 миллисекунды.

    -- Запуск детального профилирования запроса с замером буферов
EXPLAIN (ANALYZE, BUFFERS, TIMING, COSTS, VERBOSE)
SELECT 
    c.customer_id, 
    c.email, 
    o.order_id, 
    o.total_amount
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_date >= '2026-10-01'
  AND o.status = 'completed';

/* Пример интерпретации реального вывода:
-> Nested Loop (cost=0.56..32.40 rows=5 width=48) (actual time=0.045..0.120 rows=4 loops=1)
     Buffers: shared hit=12 read=0
     -> Index Scan using idx_orders_date on orders o (actual time=0.025..0.040 rows=4 loops=1)
          Index Cond: (order_date >= '2026-10-01'::date)
          Filter: (status = 'completed')
          Buffers: shared hit=4
     -> Index Scan using customers_pkey on customers c (actual time=0.012..0.015 rows=1 loops=4)
          Index Cond: (customer_id = o.customer_id)
          Buffers: shared hit=8
Planning Time: 0.180 ms
Execution Time: 0.165 ms
*/
    • Запуск EXPLAIN ANALYZE для команд DELETE или DROP на боевой базе. EXPLAIN ANALYZE физически выполняет команду, что приведет к реальному удалению данных! Оборачивайте вызов в транзакцию с последующим ROLLBACK.
    • Путаница между единицами Cost и миллисекундами времени. Cost — это абстрактная математическая оценка планировщика, а не секунды.
    • Забывание умножения времени на счетчик loops. Если узел выполнялся со значением `loops=1000`, суммарное затраченное время равно `actual time * 1000`.
    • Игнорирование расхождения оценочного и фактического числа строк (Rows estimate discrepancy). Если оптимизатор ожидает 1 строку, а получает 1 млн, он выберет заведомо неверный план (Nested Loop вместо Hash Join).

    На собеседовании: всегда предлагайте добавить флаг BUFFERS к `EXPLAIN ANALYZE`. Умение анализировать `shared hit` против `shared read` — знак высочайшего класса инженера баз данных.

    1. В чем принципиальная разница между EXPLAIN и EXPLAIN ANALYZE?

      EXPLAIN строит прогнозный план на основе статистики без выполнения запроса; EXPLAIN ANALYZE реально выполняет запрос и фиксирует точные тайминги и фактическое число строк.

    2. Что означает метрика loops в выводе EXPLAIN ANALYZE?

      Количество итераций выполнения данного узла плана во внутреннем цикле соединения.

    3. Когда планировщик выбирает Bitmap Index Scan вместо обычного Index Scan?

      Когда строк много, и чтобы избежать хаотичных случайных чтений диска, база сначала формирует упорядоченную битовую карту блоков в памяти.

    4. О чем свидетельствует показатель `shared read` в отчете BUFFERS?

      О количестве страниц данных размером 8 КБ, которые пришлось физически считывать с дискового накопителя из-за их отсутствия в кэше RAM.

    5. Что делать, если прогнозируемое число строк (estimated rows) сильно расходится с фактическим?

      Выполнить команду `ANALYZE table_name` для обновления статистики распределения данных в системном каталоге.

  17. Собеседование: Принципы ACID

    Собеседование (Backend Architect / Senior Data Engineer): Канонический фундамент транзакционных систем: «Как детально расшифровываются принципы ACID (Atomicity, Consistency, Isolation, Durability)? Какими низкоуровневыми механизмами СУБД гарантирует каждый из этих четырех принципов (WAL, MVCC, 2PL, fsync)?»

    Если совсем простыми словами: ACID — это четыре нерушимые заповеди надежности банка. Деньги либо перевелись полностью, либо не тронуты вообще (Атомарность); сумма на счетах всегда сходится с математикой (Согласованность); параллельные переводы не путаются между собой (Изоляция); и если вам выдали чек, запись не сотрется даже при ударе молнии в серверную (Долговечность).

    Низкоуровневые механизмы реализации каждого принципа ACID:

    1. Atomicity (Атомарность — «Все или ничего»): - Транзакция не может выполниться частично. При любом сбое все промежуточные шаги откатываются. - Реализация: Журнал упреждающей записи WAL (Write-Ahead Log) или Undo-логи. При падении система накатывает успешные и откатывает незавершенные транзакции.
    2. Consistency (Согласованность / Непротиворечивость): - Перевод системы из одного валидного состояния в другое. Все ограничения схемы данных (`NOT NULL`, `CHECK`, `UNIQUE`, `FOREIGN KEY`) и триггеры остаются нерушимыми. - Реализация: Валидация констрейнтов на уровне ядра СУБД перед коммитом.
    3. Isolation (Изоляция): - Параллельно выполняющиеся транзакции не должны влиять на результат работы друг друга. - Реализация: Механизм многоверсионности MVCC (Multi-Version Concurrency Control) и блокировки (Shared / Exclusive Locks).
    4. Durability (Долговечность / Надежность): - Если транзакция зафиксирована (`COMMIT`), ее результаты гарантированно сохранятся даже при внезапном отключении электричества. - Реализация: Синхронный сброс буфера WAL на энергонезависимый диск через системный вызов fsync() до отправки клиенту подтверждения об успехе.

    Кейс из продакшена: Цена отключения fsync: Команда настроила параметр PostgreSQL `fsync = off` ради ускорения тестов в 10 раз, но случайно раскатала этот конфиг на боевой сервер. При кратковременном сбое питания в ЦОД база данных поднялась в поврежденном состоянии с битыми страницами диска (Data Corruption). Восстановление из бэкапов заняло $14$ часов. Durability нельзя приносить в жертву производительности.

    -- Классическая банковская транзакция с гарантией ACID
BEGIN;

-- Проверка и списание баланса отправителя
UPDATE accounts
SET balance = balance - 5000.00
WHERE account_id = 101 AND balance >= 5000.00;

-- Зачисление на счет получателя
UPDATE accounts
SET balance = balance + 5000.00
WHERE account_id = 202;

-- Запись в аудит-лог транзакций
INSERT INTO transaction_audit (from_acc, to_acc, amount, created_at)
VALUES (101, 202, 5000.00, NOW());

-- Если все 3 шага успешны — фиксируем (Durability + Atomicity)
COMMIT;

-- В случае любой ошибки (например, сработал CHECK balance >= 0) — полный откат:
-- ROLLBACK;
    • Путаница между понятием Consistency в ACID и понятием Consistency в CAP-теореме. В ACID это соблюдение инвариантов схемы данных; в CAP — это линеаризуемость и одинаковое чтение на всех репликах.
    • Отключение параметра fsync или synchronous_commit на боевых базах данных. Уничтожает гарантию Durability: при падении сервера зафиксированные транзакции будут безвозвратно утеряны.
    • Выполнение длинных многоминутных транзакций. Удерживает блокировки, раздувает таблицы версиями строк (MVCC Bloat) и препятствует очистке VACUUM.
    • Ожидание, что изоляция по умолчанию защитит от всех конфликтов. По умолчанию уровень Read Committed допускает неповторяющееся чтение и фантомы.

    На собеседовании: четко разграничьте Consistency в ACID (бизнес-инварианты и ограничения целостности) и Consistency в CAP (согласованность распределенных реплик). Это классическая ловушка для синьоров.

    1. Что означает Атомарность (Atomicity) в транзакциях?

      Гарантию неделимости транзакции: либо все операции фиксируются успешно, либо ни одна операция не применяется к базе.

    2. Какой системный компонент обеспечивает Долговечность (Durability)?

      Журнал предзаписи WAL (Write-Ahead Log) совместно с системным вызовом `fsync`, принудительно сбрасывающим буферы диска.

    3. В чем отличие понятия Consistency в ACID от Consistency в теореме CAP?

      В ACID это соблюдение правил схемы (FK, CHECK, UNIQUE); в CAP — это гарантия того, что все узлы распределенной системы видят одинаковые актуальные данные.

    4. С помощью каких двух технологий обычно реализуется Изоляция (Isolation)?

      С помощью MVCC (многоверсионного контроля параллелизма) и механизма блокировок (2-Phase Locking).

    5. Что произойдет с транзакцией при падении сервера до выполнения команды COMMIT?

      При перезапуске СУБД процесс восстановления WAL обнаружит незавершенную транзакцию и полностью откатит все ее изменения.

  18. Собеседование: Уровни изоляции транзакций

    Анатомия MVCC в PostgreSQL: - Каждая строка в таблице содержит скрытые служебные поля: `xmin` (ID транзакции, создавшей строку) и `xmax` (ID транзакции, удалившей/обновившей строку). - Обновление строки `UPDATE` не перезаписывает байты на месте: оно проставляет `xmax` старой строке и вставляет новую строку с новым `xmin`. - Снимок данных (Snapshot): - В `Read Committed`: снимок создается заново перед каждым отдельным SQL-выражением внутри транзакции. - В `Repeatable Read`: единый неизменяемый снимок фиксируется один раз в момент старта транзакции.

    Аномалия Write Skew (Перекос записи): Два дежурных врача в больнице одновременно запрашивают: `SELECT count(*) FROM on_call WHERE active = true`. Оба видят, что дежурят двое. Каждый решает снять себя с дежурства (`UPDATE ... SET active = false`) и коммитит транзакцию. В результате в больнице не осталось ни одного дежурного врача! Эта аномалия лечится только уровнем Serializable или явной блокировкой `FOR UPDATE`.

    Кейс: Предотвращение Write Skew через SELECT FOR UPDATE: Вместо изменения уровня изоляции на Serializable разработчик заблокировал строки: `SELECT * FROM on_call WHERE active = true FOR UPDATE;` Вторая транзакция встала в очередь и увидела изменения первого врача после коммита, предотвратив инцидент.

-- ERROR: could not serialize access due to concurrent update

    • Уверенность в том, что Repeatable Read защищает от аномалии Write Skew. Write Skew возникает, когда транзакции модифицируют непересекающиеся множества строк; спасает только Serializable или блокировка `FOR UPDATE`.
    • Отсутствие логики повтора (Retry Loop) при работе с уровнем Serializable. Уровень Serializable гарантирует целостность ценой частых ошибок `could not serialize access` (код 40001), которые приложение должно автоматически перезапускать.
    • Использование Read Uncommitted в PostgreSQL. В PostgreSQL уровень Read Uncommitted физически транслируется в Read Committed, так как движок MVCC не умеет читать грязные незакоммиченные версии строк.
    • Длительное удержание транзакций в Repeatable Read. Старый снимок мешает фоновому процессу VACUUM удалять мертвые строки (Dead Tuples), вызывая лавинообразное раздувание таблиц.

    1. Что такое грязное чтение (Dirty Read)?

      Чтение данных, измененных параллельной транзакцией, которая еще не была зафиксирована (COMMIT) и впоследствии может быть откатана (ROLLBACK).

    2. Чем неповторяющееся чтение отличается от фантомного чтения?

      Неповторяющееся чтение — изменение или удаление уже прочитанных строк; фантомное чтение — появление новых строк, подходящих под предикат диапазонного запроса.

    3. В чем различие между снимками данных в Read Committed и Repeatable Read в Postgres?

      В Read Committed снимок пересоздается перед каждой инструкцией; в Repeatable Read фиксируется один снимок на всю транзакцию.

    4. Что такое аномалия Write Skew (Перекос записи)?

      Аномалия, при которой две параллельные транзакции на основе одинакового состояния данных модифицируют разные строки, приводя к нарушению общего бизнес-инварианта системы.

    5. Как приложение должно обрабатывать ошибку 40001 (Serialization Failure)?

      Приложение обязано перехватить исключение и заново повторить всю транзакцию целиком с начального шага (Retry pattern).

  19. Собеседование: Нормальные формы БД и денормализация

    Собеседование (Database Modeler / Analyst): Теория реляционного проектирования: «В чем суть первых трех нормальных форм (1NF, 2NF, 3NF) и нормальной формы Бойса-Кодда (BCNF)? Какие аномалии модификации данных решает нормализация и когда осознанная денормализация является лучшим инженерным решением?»

    Если совсем простыми словами: каждый факт должен храниться строго в одном месте. Нормализация исключает бардак, при котором для смены фамилии клиента вам нужно обновить 100 000 строк в разных таблицах. Денормализация — осознанный шаг назад ради скорости чтения в отчетах.

    Иерархия нормальных форм (Эдгар Кодд):

    1. 1-я Нормальная Форма (1NF — Атомарность): - Каждая ячейка содержит строго атомарное (неделимое) значение. - Нет повторяющихся групп и массивов (например, строка `'телефон1, телефон2'` нарушает 1NF). - У таблицы есть уникальный первичный ключ.
    2. 2-я Нормальная Форма (2NF — Полная функциональная зависимость): - Таблица находится в 1NF. - Каждый неключевой атрибут функционально зависит от всего первичного ключа целиком, а не от его части (актуально для составных ключей `(A, B)`). - Пример нарушения: В таблице `(order_id, product_id, product_name)` название товара `product_name` зависит только от `product_id`, а не от заказа.
    3. 3-я Нормальная Форма (3NF — Отсутствие транзитивных зависимостей): - Таблица находится в 2NF. - Нет транзитивных зависимостей неключевых полей: $A \to B \to C$ (неключевой атрибут не должен зависеть от другого неключевого атрибута). - Классическая фраза: «Every attribute must depend on the key, the whole key, and nothing but the key, so help me Codd».
    4. Когда денормализация оправдана: 1. Аналитические хранилища (DWH / Схема «Звезда»): объединение измерений ускоряет джойны в разы. 2. Горячие счетчики и агрегаты: хранение `total_orders_count` прямо в профиле пользователя во избежание тяжелого `COUNT(*)` при каждом входе в приложение.

    Практический пример приведения к 3NF: Исходная таблица: `Orders(order_id, user_id, user_city, city_delivery_cost)`. Здесь `order_id $\to$ user_id $\to$ user_city $\to$ city_delivery_cost`. При изменении тарифа доставки по городу пришлось бы обновлять миллионы исторических заказов (Аномалия обновления!). Приведение к 3NF: Вынесение `cities(city_id, delivery_cost)` и `users(user_id, city_id)` в отдельные таблицы.

    -- 1. Пример нормализованной структуры (3NF): отсутствие дублирования и транзитивности
CREATE TABLE cities (
    city_id SERIAL PRIMARY KEY,
    city_name VARCHAR(100) UNIQUE NOT NULL,
    delivery_base_cost NUMERIC(10, 2) NOT NULL
);

CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    full_name VARCHAR(255) NOT NULL,
    city_id INT NOT NULL REFERENCES cities(city_id)
);

CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INT NOT NULL REFERENCES customers(customer_id),
    order_date TIMESTAMPTZ DEFAULT NOW(),
    order_amount NUMERIC(12, 2) NOT NULL
);

-- 2. Осознанная денормализация для ускорения чтения дашборда:
-- Добавление предрассчитанных агрегатов с обновлением через триггер
ALTER TABLE customers ADD COLUMN total_spent NUMERIC(12, 2) DEFAULT 0.00;
    • Преждевременная денормализация на этапе проектирования транзакционной OLTP системы. Приводит к расхождениям данных, когда в одной таблице статус обновился, а в другой остался старым.
    • Чрезмерная нормализация в аналитических базах данных. Требование соединить 12 таблиц ради построения простого отчета продаж делает аналитику неповоротливой.
    • Забывание о синхронизации денормализованных полей. Если поле `total_spent` хранится в профиле, разработчик обязан гарантировать его актуальность через транзакции или триггеры.
    • Хранение списков через запятую в текстовом поле VARCHAR. Грубейшее нарушение 1NF, блокирующее индексацию, проверку типов и быстрый поиск.

    На собеседовании: процитируйте знаменитую фразу: «Каждое неключевое поле должно зависеть от ключа, всего ключа и ни от чего, кроме ключа (so help me Codd)». Это гарантирует признание интервьюера.

    1. Что требует первая нормальная форма (1NF)?

      Атомарности всех атрибутов (отсутствие списков/массивов в ячейках) и наличия уникального первичного ключа.

    2. В чем суть второй нормальной формы (2NF)?

      В отсутствии частичных функциональных зависимостей: каждый неключевой атрибут должен зависеть от составного ключа целиком.

    3. Что устраняет третья нормальная форма (3NF)?

      Транзитивные зависимости между неключевыми атрибутами ($A o B o C$).

    4. Какие аномалии предотвращает нормализация данных?

      Аномалии вставки (Insertion anomaly), обновления (Update anomaly) и удаления (Deletion anomaly).

    5. В каких сценариях осознанная денормализация приносит пользу?

      В аналитических хранилищах данных (DWH) и для кэширования агрегированных счетчиков в высоконагруженных интерфейсах.

    Собеседование (Lead Data Architect): Системный дизайн корпоративных данных: «Как спроектировать надежный пайплайн передачи данных между транзакционным бэкендом (OLTP) и аналитическим хранилищем (OLAP)? Боевая база уходила в перегрузку, транзакции пользователей завершались по таймауту. Внедрение связки PostgreSQL WAL $\to$ Debezium $\to$ Kafka $\to$ ClickHouse снизило нагрузку на боевую базу до нуля и обеспечило появление свежих транзакций на дашбордах через $500$ миллисекунд после их совершения.

-- 1. Создание публикации для изменений таблицы заказов
CREATE PUBLICATION orders_cdc_publication FOR TABLE orders;

-- В ClickHouse: Создание витрины с движком ReplacingMergeTree для приема CDC потока
CREATE TABLE analytics.orders_stream (
    order_id UInt64,
    customer_id UInt64,
    order_amount Decimal(10, 2),
    status LowCardinality(String),
    cdc_op LowCardinality(String), -- 'c' (create), 'u' (update), 'd' (delete)
    cdc_timestamp DateTime64(3),
    version UInt64
)
ENGINE = ReplacingMergeTree(version)
ORDER BY order_id;

-- Аналитический запрос к свежим данным: мгновенная агрегация с дедупликацией
SELECT
    status,
    count() AS total_orders,
    sum(order_amount) AS total_revenue
FROM analytics.orders_stream FINAL
WHERE cdc_op != 'd' -- исключение удаленных записей
GROUP BY status;

    • Опрос базы данных частыми запросами polling (SELECT WHERE updated_at > last_sync). Создает постоянную нагрузку на индексы и не может отследить физически удаленные строки (`DELETE`).
    • Отсутствие контроля версий при записи CDC-потока в OLAP. События в распределенных очередях могут приходить не по порядку (Out-of-order delivery); в OLAP требуется сохранять поле версии (`version`).
    • Использование единой базы данных и для транзакций, и для Big Data аналитики. Архитектурный тупик, неизбежно приводящий к деградации бизнеса при росте аудитории.

    1. Что такое Change Data Capture (CDC)?

      Технология отслеживания и захвата изменений данных на уровне журнала транзакций (WAL/binlog) СУБД для их потоковой репликации в другие системы без нагрузки на SQL-движок.

    2. В чем преимущество CDC перед периодическими SQL-выгрузками?

      CDC не нагружает боевую базу, гарантирует фиксацию всех промежуточных состояний и физических удалений, обеспечивая околонулевую задержку репликации.

    3. Почему OLTP базы используют нормализованную модель (3NF), а OLAP — денормализованную?

      OLTP минимизирует избыточность для быстрых и безопасных транзакций записи; OLAP минимизирует количество JOIN для скоростной аналитики больших объемов.

    4. Как ClickHouse справляется с обновлениями, приходящими из CDC потока?

      Через движок `ReplacingMergeTree(version)`, схлопывающий устаревшие версии строк во время фонового слияния или по модификатору FINAL.

    5. Что произойдет, если запустить тяжелый OLAP-запрос на реплике PostgreSQL?

      Запрос может заблокировать применение WAL-логов репликации, вызвав критическое отставание реплики от мастера (Replication Lag).
