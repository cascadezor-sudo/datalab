  1. Какие типы данных есть в Python?

    Встроенные типы удобно перечислять группами — так ответ звучит структурно, а не как случайный список.

    • Числовые: int (произвольной точности — переполнения нет), float (двойная точность IEEE 754), complex.
    • Логический: bool. Формально подкласс int, поэтому True == 1 и sum([True, True]) даёт 2.
    • Последовательности: str (неизменяемая последовательность кодпоинтов Unicode), list (изменяемая), tuple (неизменяемая), range (ленивая арифметическая прогрессия, не хранит элементы).
    • Множества: set (изменяемое), frozenset (неизменяемое и хешируемое).
    • Отображения: dict — сопоставление ключ → значение; с Python 3.7 порядок вставки гарантирован спецификацией.
    • Двоичные: bytes (неизменяемая), bytearray (изменяемая), memoryview (представление чужого буфера без копирования).
    • Особые: NoneType с единственным значением None, Ellipsis (...), NotImplemented.

    Поперёк этой классификации идёт вторая, не менее важная: деление на изменяемые и неизменяемые — именно оно определяет, что может быть ключом словаря и что произойдёт при передаче объекта в функцию. См. изменяемые и неизменяемые типы и типы данных.

    И третья особенность, которую стоит назвать: в Python всё — объект, включая функции, классы, модули и сами типы. int — это объект класса type, у функции есть атрибуты, класс можно положить в список. См. в Python всё — объект.

    print(type(42), type(3.14), type("s"), type(None)) print(isinstance(True, int)) # True — bool наследует int print(2 ** 200) # int неограничен print(0.1 + 0.2 == 0.3) # False — двоичная плавающая точка print(range(10**9)[:5]) # range ленив: срез — снова range, элементы не создаются

    Часто вопрос продолжается: «а какие структуры используете на практике?». Полезные ответы:

    • collections.Counter — подсчёт частот, most_common(k);
    • collections.defaultdict — словарь с фабрикой значений, избавляет от if key not in d;
    • collections.deque — очередь с $\mathcal{O}(1)$ на обоих концах (у списка pop(0) — $\mathcal{O}(n)$);
    • heapq — приоритетная очередь на списке, top-$k$ за $\mathcal{O}(n \log k)$;
    • array.array — компактный массив чисел одного типа, когда NumPy избыточен;
    • decimal.Decimal и fractions.Fraction — точная арифметика для денег и дробей;
    • datetime, pathlib.Path, enum.Enum, typing.NamedTuple, dataclasses.dataclass.

    Это переводит ответ из «перечислил встроенные типы» в «понимаю, чем пользоваться в задаче».

    float и точность. 0.1 + 0.2 != 0.3, потому что десятичные дроби не представимы точно в двоичной системе. Сравнивать вещественные числа надо через math.isclose, а деньги считать в Decimal или в целых копейках.

    bool — это int. isinstance(True, int) истинно, True + True == 2, и {1: "a", True: "b"} — словарь из одного элемента.

    Изменяемое как значение по умолчанию — def f(x=[]); см. отдельный разбор.

    str — это не байты. str хранит кодпоинты Unicode, bytes — байты; преобразование всегда требует явного указания кодировки (s.encode("utf-8")). Ошибка UnicodeDecodeError при чтении файла почти всегда означает, что кодировку угадали неправильно, а не что «файл битый».

    Аннотации типов не проверяются в рантайме. def f(x: int) спокойно примет строку — типы нужны статическому анализатору и людям; см. typing, аннотации.

  2. Какие типы изменяемые / неизменяемые?

    Изменяемые (mutable): list, dict, set, bytearray, а также экземпляры обычных пользовательских классов (у них можно менять атрибуты). Их состояние меняется «на месте», id() при этом не меняется.

    Неизменяемые (immutable): int, float, complex, bool, str, bytes, tuple, frozenset, range, None. Любая «модификация» на деле создаёт новый объект; старый остаётся нетронутым.

    Проверить различие проще всего через id():

    lst = [1, 2]; before = id(lst) lst.append(3); print(id(lst) == before) # True — тот же объект s = "ab"; before = id(s) s += "c"; print(id(s) == before) # False — новый объект

    Почему это важно на практике — три следствия:

    1. Хешируемость. Ключами словаря и элементами множества могут быть только неизменяемые (точнее — хешируемые) объекты. Подробнее — что может быть ключом словаря.
    2. Разделяемое состояние. Изменяемый объект, переданный в функцию или сохранённый в двух местах, меняется для всех владельцев сразу. Это же лежит в основе проблемы изменяемого аргумента по умолчанию.
    3. Копирование. Для неизменяемых копия не нужна вовсе; для изменяемых приходится выбирать между поверхностным и глубоким копированием.

    См. типы данных: изменяемые и неизменяемые.

    a = "qwerty" # a[1] = "o" # TypeError: 'str' object does not support item assignment b = a[:1] + "o" + a[2:] # создаётся новая строка print(a, b) # qwerty qowrty

    Кортеж нельзя изменить, но объекты внутри него — можно, если они изменяемы:

    t = ([1, 2], "x") t[0].append(3) # разрешено: меняем список, а не кортеж print(t) # ([1, 2, 3], 'x') # hash(t) # TypeError: unhashable type: 'list'

    Отсюда следствие: кортеж хешируем только если хешируемы все его элементы. Ровно поэтому frozenset требует, чтобы элементы были хешируемыми, а @dataclass(frozen=True) не спасает от мутации вложенного списка.

    Ещё коварный случай — t[0] += [3]: он одновременно изменит список и бросит TypeError, потому что += сначала мутирует объект через __iadd__, а затем пытается присвоить результат обратно в кортеж.

    «Строка меняется, потому что s += "c" работает». Нет: создаётся новый объект и имя перепривязывается. Практическое следствие — склейка строк в цикле квадратична; используйте "".join(parts).

    «Неизменяемость означает потокобезопасность». Для самого объекта — да, но перепривязка имени и составные операции безопасности не дают.

    is вместо == для неизменяемых. Кеширование малых int и интернирование строк делают is случайно истинным; полагаться на это нельзя, см. is против ==.

    Изменяемый объект как атрибут класса. class A: items = [] — список общий для всех экземпляров, ровно та же ловушка, что с аргументом по умолчанию. Инициализировать нужно в __init__ или через field(default_factory=list).

  3. В чём отличие is от ==?

    == сравнивает значения и вызывает метод __eq__, который класс может переопределить. is сравнивает идентичность — совпадают ли id() объектов, то есть один ли это объект в памяти. is нельзя переопределить, и он всегда работает за константное время.

    Отсюда правило употребления:

    • == — для содержательного сравнения: числа, строки, коллекции, доменные объекты.
    • is — только для синглтонов: x is None, x is True, x is False, x is NotImplemented, а также для проверок вроде «это тот же самый объект, что я положил в кэш».

    Два объекта могут быть равны, но не идентичны (два одинаковых списка) — и наоборот, идентичный объект почти всегда равен сам себе, кроме float("nan"), для которого x == x ложно, а x is x истинно.

    Подробнее — ==, !=, is и None: почему проверять через is.

    a = [1, 2, 3] b = [1, 2, 3] c = a print(a == b, a is b) # True False — равны, но это разные объекты print(a == c, a is c) # True True — одно и то же имя объекта nan = float("nan") print(nan == nan, nan is nan) # False True

    CPython кеширует некоторые неизменяемые объекты, и из-за этого is порой совпадает с == — но полагаться на это нельзя, это деталь реализации:

    a, b = 256, 256 print(a is b) # True — малые int (-5..256) закешированы a, b = 257, 257 print(a is b) # True в одной строке REPL/скрипта, False при раздельном создании s1, s2 = "hello", "hello" print(s1 is s2) # True — интернирование строк-идентификаторов s3 = "hello world!" s4 = "hello world!" print(s3 is s4) # может быть False — строка с пробелами не интернируется автоматически

    Небольшие целые от −5 до 256 создаются при старте интерпретатора и переиспользуются; короткие строки, похожие на идентификаторы, интернируются; литералы внутри одного блока кода схлопываются компилятором в одну константу. Всё это оптимизации, которые различаются между версиями и реализациями Python.

    if x is 5 вместо if x == 5. Работает случайно на малых числах и ломается на больших. С Python 3.8 интерпретатор выдаёт SyntaxWarning: "is" with a literal; линтеры (ruff, правило F632) ловят это же.

    if x == None. Формально работает, но None — синглтон, и правильная проверка x is None: она быстрее и не может быть перехвачена чужим __eq__. Особенно важно с numpy и pandas, где arr == None вернёт массив булей, а не один булев, и if упадёт с ValueError: truth value of an array is ambiguous.

    if flag is True. Избыточно и опасно: значение 1 равно True, но не идентично ему. Пишут просто if flag.

    is для проверки типа. Для сравнения типов используют isinstance(x, T), а не type(x) is T, — иначе перестанут работать наследники; см. isinstance.

  4. Список Python vs массив NumPy

    Различия идут от устройства памяти и определяют всё остальное.

    Как лежат данные. list — массив указателей на разбросанные по куче Python-объекты. np.ndarray — непрерывный блок «сырых» чисел одного dtype плюс метаданные shape и strides. Отсюда разница в памяти: миллион int в списке — примерно 36 МБ (8 байт указателя + 28 байт объекта), в np.int64 — 8 МБ.

    Как выполняются операции. [x * 10 for x in a] — это Python-цикл: на каждый элемент интерпретатор разыменовывает указатель, определяет тип, ищет метод __mul__, создаёт новый объект. arr * 10 — один вызов в C, который проходит непрерывный блок памяти, часто с использованием SIMD-инструкций процессора. Типичное ускорение — 10–100 раз.

    Что умеет сверх этого NumPy. Broadcasting (операции над массивами разной формы без явных циклов), многомерность и reshape/transpose без копирования данных, срезы как представления, а не копии, булеву и fancy-индексацию, линейную алгебру, статистику, FFT, генераторы случайных чисел.

    В чём выигрывает список. Гетерогенность (разные типы в одной коллекции), дешёвое добавление и удаление с конца, отсутствие фиксированного dtype и переполнения, работа с произвольными объектами. Подробнее — разница массивов numpy и list и numpy.

    import numpy as np x = np.array([1, 2, 3]) print(x * 10) # [10 20 30] — векторизация print(x[x > 1]) # [2 3] — булева маска print(np.arange(6).reshape(2, 3) + np.array([10, 20, 30])) # broadcasting a = np.arange(10) view = a[2:5] # представление, не копия view[0] = 99 print(a[2]) # 99 — изменился исходный массив

    Обычный срез NumPy (a[2:5], a[::2], a.T, a.reshape(...)) возвращает view: новый объект с другими strides, но с тем же буфером данных. Запись в него меняет исходный массив. Это сделано ради скорости — копирование гигабайтного массива при каждом срезе было бы неприемлемо.

    Копию возвращают fancy-индексация (a[[1, 3, 5]]), булева маска (a[a > 0]) и явный a.copy(). Проверить принадлежность буфера можно через arr.base is not None.

    Со списками всё наоборот и проще: lst[2:5] — всегда новый список (правда, поверхностный: вложенные объекты общие, см. shallow и deep copy).

    Практическое правило: если функция получает массив и не должна менять аргумент, делайте arr = np.asarray(arr).copy() либо явно документируйте, что работаете на месте.

    Переполнение. Python-int неограничен, а np.int32/np.int64 — нет: np.array([2**31 - 1], dtype=np.int32) + 1 даст отрицательное число. В NumPy 2.x такие переполнения при скалярных операциях стали ошибкой, но внутри массивов молчаливое обёртывание остаётся.

    Апкаст к object. np.array([1, "a"]) создаст массив строк, а np.array([1, [2, 3]]) — массив объектов, где вся векторизация теряется и скорость падает до уровня списка. Всегда проверяйте arr.dtype.

    Рост массива в цикле. У ndarray нет append в смысле списка: np.append каждый раз создаёт новый массив и копирует всё — цикл превращается в $\mathcal{O}(n^2)$. Правильно: накопить в списке и один раз сделать np.array(...), либо заранее выделить np.empty(n) и заполнять по индексу.

    Смешивание циклов и NumPy. for i in range(len(arr)): arr[i] += 1 медленнее, чем чистый список: к затратам Python-цикла добавляется упаковка каждого элемента в объект. Если появился цикл по элементам массива — почти наверняка есть векторная запись.

  5. Какие есть способы установки пакетов в Python?

    pip — стандартный установщик. Ставит пакеты с PyPI, из git-репозитория, из локального каталога, из wheel-файла. Умеет разрешать зависимости, но не управляет окружениями и не фиксирует их состояние сам по себе — для этого нужен requirements.txt или lock-файл.

    conda / mamba — менеджер пакетов и окружений, который ставит не только Python-библиотеки, но и системные зависимости: CUDA toolkit, MKL, компиляторы, GDAL. Именно поэтому он до сих пор популярен в ML: не нужно отдельно решать вопрос с драйверами и нативными библиотеками. Минус — тяжеловесность и медленное разрешение зависимостей (ускоряется переходом на mamba или micromamba).

    uv — современный установщик и менеджер проектов на Rust, совместимый с pip по интерфейсу. Работает на порядок быстрее за счёт параллельной загрузки и глобального кэша с жёсткими ссылками, ставит и сам интерпретатор Python, генерирует uv.lock и работает с pyproject.toml как источником истины. Сейчас это дефолтный выбор для нового проекта.

    poetry / pdm / pipenv — менеджеры проектов предыдущего поколения: pyproject.toml плюс собственный lock-файл и виртуальное окружение.

    Отдельно: pipx — для установки CLI-утилит (ruff, black, dvc) в изолированные окружения, чтобы они не смешивались с зависимостями проекта.

    Подробнее — виртуальные окружения и pyproject.toml для uv.

    python -m venv .venv && source .venv/bin/activate pip install -r requirements.txt uv venv && uv pip install -r requirements.txt # то же самое, быстрее uv add torch # добавит в pyproject.toml + uv.lock uv sync # воспроизвести окружение из lock conda create -n ml python=3.11 && conda activate ml conda install -c conda-forge numpy pandas

    requirements.txt с незакреплёнными версиями (torch, pandas>=2.0) описывает намерение, а не состояние: через месяц та же команда установит другие версии, и эксперимент перестанет воспроизводиться. Транзитивные зависимости он не фиксирует вовсе.

    Промышленный подход — разделять два файла:

    • что нужно проекту — pyproject.toml (или requirements.in) с широкими ограничениями;
    • что именно установлено — lock-файл (uv.lock, poetry.lock, requirements.txt, сгенерированный uv pip compile / pip-compile) с точными версиями и хешами всех зависимостей, включая транзитивные.

    В образ и в CI ставится строго из lock-файла. Это же требование лежит в основе воспроизводимости ML-экспериментов: код, данные и окружение должны быть зафиксированы одинаково строго.

    PyTorch и CUDA. pip install torch с PyPI тянет сборку под определённую версию CUDA. Если на машине другой драйвер, всё установится и упадёт только в рантайме на torch.cuda.is_available() == False. Правильно — ставить с индекса, соответствующего версии CUDA: pip install torch --index-url https://download.pytorch.org/whl/cu121.

    Смешивание pip и conda. Установка pip-пакета поверх conda-окружения ломает учёт зависимостей: conda не видит того, что поставил pip, и при следующем conda install может перезаписать файлы. Правило — сначала всё, что можно, через conda, pip только в конце и одним проходом.

    Размер образа. Слой с torch и CUDA-библиотеками легко занимает 5–8 ГБ. Помогают CPU-only сборки для сервисов инференса, multi-stage build и --no-cache-dir у pip.

    pip install без версии в Dockerfile сводит на нет весь кэш сборки и делает образ невоспроизводимым — сегодня и через полгода соберутся разные образы из одного и того же Dockerfile.

  6. Чем отличаются list, numpy.ndarray, torch.Tensor?

    Три контейнера с разным устройством памяти и разным набором возможностей.

    list — динамический массив указателей на Python-объекты. Элементы могут быть разных типов, каждый — полноценный объект с заголовком (для int это 28 байт против 8 у C-шного int64). Данные разбросаны по куче, поэтому обход плохо ложится в кэш процессора, а любая арифметика идёт через Python-цикл с диспетчеризацией на каждый элемент. Гибко, но медленно и расточительно по памяти.

    numpy.ndarray — непрерывный блок памяти с единым dtype плюс метаданные (shape, strides). Все операции выполняются в скомпилированном C-коде над всем массивом сразу — это векторизация; на типовых задачах выигрыш в 10–100 раз. Дают broadcasting, срезы без копирования (view), линейную алгебру, статистику, свёртки FFT. Работает на CPU. См. разница массивов numpy и list.

    torch.Tensor — то же непрерывное хранилище, но с двумя добавками: устройство (cpu / cuda / mps), то есть данные могут лежать в видеопамяти, и автоматическое дифференцирование — при requires_grad=True тензор запоминает граф операций, и loss.backward() считает градиенты по всем участвовавшим тензорам.

    Правило выбора: list — гетерогенные коллекции и логика на уровне Python; numpy — численные расчёты на CPU и весь научный стек; torch — обучение моделей, GPU, автодифф.

    # list: поэлементно в Python a = [1, 2, 3] b = [x * 10 for x in a] # numpy: векторизация import numpy as np x = np.array([1, 2, 3], dtype=np.float32) y = x * 10 # [10. 20. 30.] — цикл внутри C # torch: устройство + автодифф import torch t = torch.tensor([1., 2., 3.], requires_grad=True) loss = (t * 10).sum() loss.backward() print(t.grad) # tensor([10., 10., 10.])

    torch.from_numpy(arr) и tensor.numpy() разделяют одну и ту же память — изменение одного объекта видно в другом. Это удобно (нулевая стоимость) и опасно (неожиданные мутации). torch.tensor(arr), наоборот, всегда копирует.

    Совместное использование памяти работает только для CPU-тензоров: для тензора на GPU .numpy() бросит ошибку, нужно сначала .cpu(). Полный безопасный путь из графа в NumPy — t.detach().cpu().numpy(): detach отцепляет от графа вычислений, cpu переносит из видеопамяти.

    Внутри NumPy тоже важно различать view и copy: срез a[1:5] — представление (изменение отразится на исходном массиве), а a[[1,2,3]] (fancy indexing) и a.copy() — копия. Непонимание этого — источник трудноуловимых багов в препроцессинге.

    .item() в цикле обучения. Обращение к элементу GPU-тензора синхронизирует CPU и GPU; вызов loss.item() на каждом шаге ради логирования заметно замедляет обучение. Накапливайте на GPU и снимайте значение раз в N шагов.

    Утечка графа. total_loss += loss вместо total_loss += loss.item() удерживает весь граф вычислений всех батчей — память растёт до OOM. Классическая ошибка.

    dtype. NumPy по умолчанию делает float64, PyTorch — float32. При смешивании легко получить молчаливый апкаст и удвоенное потребление памяти или, наоборот, ошибку несовпадения типов в слое.

    Смешивание Python-цикла и тензоров. Обход for i in range(len(t)) по тензору убивает всю выгоду: каждая итерация — вызов ядра и синхронизация. Почти всегда есть векторная альтернатива.

  7. В чем отличия потоков и процессов?

    Процесс — исполняемая программа со своим изолированным адресным пространством, таблицей файловых дескрипторов и набором ресурсов, выданных операционной системой. Процессы не видят память друг друга: чтобы обменяться данными, нужен IPC — пайпы, сокеты, разделяемая память, очереди.

    Поток — единица планирования внутри процесса. Потоки одного процесса делят кучу, глобальные переменные, открытые файлы и загруженные библиотеки; у каждого своё только: стек, регистры и счётчик команд.

    Сравнение по существенным осям:

    ПотокиПроцессы
    Памятьобщаяизолированная
    Стоимость созданиянизкая (~МБ стека)высокая (копия/новое адресное пространство)
    Переключение контекстадешевледороже (смена таблиц страниц, промах TLB)
    Обмен данныминапрямую по ссылкечерез IPC с сериализацией
    Отказоустойчивостьпадение потока обычно валит весь процесспадение процесса изолировано
    Отладкасложнее (гонки, дедлоки)проще, состояние изолировано

    Одной фразой: потоки дешевле и удобнее для обмена данными, процессы безопаснее и по-настоящему параллельны. В Python к этому добавляется GIL, из-за которого выбор смещается в сторону процессов для CPU-bound задач.

    Ядро Linux не различает потоки и процессы принципиально: и то и другое — задачи (task_struct), созданные системным вызовом clone с разным набором флагов. Флаг CLONE_VM означает «делить адресное пространство» и превращает новую задачу в поток; без него получается процесс. Поэтому ps -eLf показывает потоки как строки с общим PID и разными LWP.

    fork() создаёт процесс копированием, но с copy-on-write: страницы физически не дублируются, пока кто-то в них не запишет. Отсюда практическое следствие — дочерний процесс стартует быстро, но память начинает расти по мере записи. В Python это особенно заметно из-за счётчиков ссылок: даже простое чтение объекта меняет ob_refcnt, то есть трогает страницу и вызывает её копирование. Именно поэтому «форкнуть процесс с большим датасетом и ничего не тратить» не работает так хорошо, как хотелось бы.

    Промежуточные модели, о которых полезно знать: зелёные потоки / корутины (планируются в user space самим приложением, ещё дешевле ОС-потоков — это asyncio) и пул процессов с общей памятью (multiprocessing.shared_memory, mmap), когда данные большие, а копировать их нельзя.

    Практическая иллюстрация лучше определения. Например: браузер использует процесс на вкладку именно ради изоляции — упавшая страница не должна ронять весь браузер; внутри вкладки работают потоки, потому что им нужно быстро обмениваться данными с общим DOM.

    Второе: «потоки легче» — верно про создание, но не про сопровождение. Разделяемая память означает гонки данных, которые воспроизводятся через раз и ловятся тяжело; изолированные процессы этой категории багов лишены в принципе.

    Третье, специфичное для Python: не путайте уровни. GIL — ограничение интерпретатора CPython, а не операционной системы; потоки Python — настоящие ОС-потоки, просто исполнение байткода между ними сериализовано. Формулировка «в Python нет настоящих потоков» неверна.

  8. Что такое асинхронные запросы?

    Асинхронные запросы — это неблокирующие операции ввода-вывода, выполняемые конкурентно в одном потоке с помощью событийного цикла (event loop) и корутин.

    Идея: обычный синхронный вызов requests.get(url) останавливает поток до прихода ответа — всё это время процессор простаивает. В асинхронной модели корутина на await отдаёт управление event loop, который тут же запускает другую готовую задачу; когда ядро ОС сообщает, что данные пришли (через epoll/kqueue/IOCP), loop возобновляет корутину с того же места.

    Что важно понимать про модель:

    • Это конкурентность, а не параллелизм: в каждый момент исполняется ровно один кусок Python-кода. Ускорение берётся из того, что ожидание перестало быть простоем, а не из использования нескольких ядер.
    • Переключение задач стоит доли микросекунды против десятков микросекунд у потоков ОС, а задача не требует мегабайта стека. Поэтому десятки тысяч одновременных операций — норма.
    • Планирование кооперативное: задача уступает управление только на await. Один синхронный вызов (тяжёлый расчёт, time.sleep, requests) блокирует весь loop и все остальные задачи.

    В Python это asyncio плюс синтаксис async def / await. См. асинхронные функции.

    import asyncio, aiohttp, time async def fetch(session, url): async with session.get(url) as resp: return await resp.text() async def main(urls): async with aiohttp.ClientSession() as s: return await asyncio.gather(*(fetch(s, u) for u in urls)) # 100 запросов по 1 секунде выполнятся примерно за 1 секунду, а не за 100 # asyncio.run(main(urls))

    Асинхронность окупается там, где время ожидания много больше времени счёта и одновременных ожиданий много: HTTP-клиенты и API-шлюзы, запросы к БД и Redis, чтение из очередей, WebSocket-соединения, прокси и веб-сервисы (FastAPI, aiohttp).

    Численный ориентир: 100 запросов по 1 секунде синхронно займут 100 секунд, в 10 потоках — около 10, асинхронно — около 1. При этом 10 000 одновременных соединений в потоках невозможны (10 ГБ стеков), а в asyncio — рядовая нагрузка.

    Полезные инструменты: asyncio.gather — запустить и дождаться всех; asyncio.Semaphore — ограничить конкурентность; asyncio.TaskGroup (3.11+) — структурная конкурентность с корректной отменой при ошибке; asyncio.timeout — дедлайн на блок кода; asyncio.to_thread — вынести синхронный вызов в поток, не блокируя loop.

    Не ускоряет вычисления. CPU-bound задача внутри корутины блокирует event loop целиком: пока считается, ни одна другая задача не выполнится. Для счёта нужны процессы; см. сравнение подходов к конкурентности.

    Один синхронный вызов отравляет весь сервис. requests, psycopg2 без async-режима, time.sleep, чтение большого файла через обычный open — всё это останавливает loop. Либо берите асинхронный аналог (httpx, asyncpg, aiofiles), либо оборачивайте в await asyncio.to_thread(...).

    Асинхронность заразна. await можно писать только внутри async def; чтобы вызвать корутину из синхронного кода, нужен asyncio.run. Поэтому переход на async обычно затрагивает всю цепочку вызовов, а не одну функцию.

    Забытый await. Вызов fetch(url) без await создаёт объект корутины и ничего не выполняет; Python выдаст RuntimeWarning: coroutine was never awaited — но только в конце, и причину придётся искать. Отдельно: asyncio.create_task(...) нужно сохранять в переменную, иначе задачу может собрать сборщик мусора.

  9. Что такое корутины?

    Корутина — функция, исполнение которой можно приостановить и возобновить с сохранением состояния: локальных переменных и точки, где остановились. В отличие от обычной функции, у которой один вход и один выход, у корутины точек приостановки может быть много.

    В Python корутина объявляется как async def, а точка приостановки обозначается await. Важная деталь: вызов корутины не выполняет её тело — он создаёт объект корутины, который потом нужно передать event loop (через asyncio.run, await, asyncio.create_task или gather).

    Механически это надстройка над генераторами: приостановка реализована тем же способом — кадр функции не уничтожается, а замораживается. Разница в назначении: генератор отдаёт значения наружу, корутина отдаёт управление планировщику.

    Зачем это нужно: пока корутина ждёт ответа сети или диска, поток не простаивает — event loop исполняет другие готовые корутины. Так один поток обслуживает тысячи одновременных операций ввода-вывода без затрат на потоки ОС. См. асинхронные функции и что такое асинхронные запросы.

    import asyncio async def work(name, delay): print(f"{name}: старт") await asyncio.sleep(delay) # отдаём управление loop, поток не блокируется print(f"{name}: готово") return name async def main(): coro = work("a", 1) # тело ещё НЕ выполнено — это объект корутины print(type(coro)) # <class 'coroutine'> results = await asyncio.gather(coro, work("b", 1), work("c", 1)) return results # asyncio.run(main()) # три задачи по секунде завершатся примерно за 1 секунду

    Три понятия, которые постоянно путают:

    • Корутина — объект, описывающий что нужно сделать. Сама по себе она пассивна.
    • Task — корутина, отданная event loop на исполнение (asyncio.create_task). Она начинает выполняться сразу, параллельно с текущим кодом, и её можно отменить (task.cancel()).
    • Future — низкоуровневый объект-обещание результата; Task является его подклассом.

    Отсюда практическое различие: await work() — «выполнить и дождаться» (последовательно), а t = asyncio.create_task(work()); ...; await t — «запустить в фоне и забрать результат позже» (конкурентно). Написать три await подряд и удивляться, что нет ускорения, — типичная ошибка новичка; нужен gather или TaskGroup.

    Историческая справка, которую иногда спрашивают: до Python 3.5 корутины писали на генераторах — @asyncio.coroutine плюс yield from. Синтаксис async/await появился именно как явная замена этой конструкции, чтобы отличать «генератор значений» от «корутины».

    Не блокируйте loop. Любой синхронный вызов внутри корутины останавливает все задачи: time.sleep вместо asyncio.sleep, requests вместо httpx, тяжёлый numpy-расчёт. Для синхронного кода есть await asyncio.to_thread(f, ...), для CPU-bound — пул процессов через loop.run_in_executor.

    Сохраняйте ссылку на Task. asyncio.create_task(...) без присваивания может быть собран сборщиком мусора до завершения — задача просто исчезнет. Держите ссылку или используйте asyncio.TaskGroup (3.11+), который вдобавок корректно отменяет остальные задачи при ошибке в одной.

    Обрабатывайте отмену. CancelledError — это BaseException; голый except Exception его не поймает (и хорошо), но try/finally для освобождения ресурсов нужен.

    gather(..., return_exceptions=True), если нужно получить результаты остальных задач, когда одна упала; по умолчанию исключение всплывает сразу.

  10. Что выбрать: асинхронные запросы, multiprocessing или threading?

    Выбор определяется одним вопросом: на что уходит время — на ожидание или на вычисления.

    • asyncio — I/O-bound задачи с большим числом одновременных ожиданий: HTTP-запросы, БД, брокеры очередей, сокеты. Всё живёт в одном потоке, переключение между задачами стоит доли микросекунды, поэтому десятки тысяч одновременных операций — норма. Требование: вся библиотека должна быть асинхронной; один синхронный вызов блокирует весь event loop.
    • threading — тот же I/O-bound, но когда асинхронного API нет (requests, драйверы БД, boto3) или нужен фоновый воркер/таймер. Поток стоит около мегабайта стека, поэтому счёт идёт на десятки-сотни, а не на тысячи. Из-за GIL CPU-bound код потоки не ускоряют.
    • multiprocessing — CPU-bound: numpy-вычисления в чистом Python, обработка изображений и аудио, парсинг, тяжёлый препроцессинг. Каждый процесс имеет свой интерпретатор и свой GIL, поэтому параллелизм настоящий. Плата — накладные расходы: старт процесса, сериализация аргументов и результатов через pickle, отдельная память под каждую копию данных.

    Соответствующие разделы теории: threading, multiprocessing, async/await.

    • Сеть и диск $\to$ сначала asyncio; если библиотека синхронная — ThreadPoolExecutor.
    • Тяжёлая CPU-работа на чистом Python $\to$ ProcessPoolExecutor.
    • Смешанная нагрузка $\to$ event loop для I/O плюс loop.run_in_executor(process_pool, ...) для CPU-частей: так тяжёлый расчёт не блокирует цикл.
    • Числодробилка через NumPy/PyTorch/scikit-learn $\to$ часто вообще не нужен параллелизм на уровне Python: эти библиотеки отпускают GIL внутри C-кода и сами используют несколько ядер через BLAS/OpenMP. Прежде чем городить пул процессов, стоит проверить, не проще ли векторизовать вычисление.
    # ThreadPoolExecutor — I/O через синхронное API from concurrent.futures import ThreadPoolExecutor import requests def get(url): return requests.get(url, timeout=10).text with ThreadPoolExecutor(max_workers=32) as ex: pages = list(ex.map(get, urls)) # ProcessPoolExecutor — CPU-bound from concurrent.futures import ProcessPoolExecutor def heavy(x): return sum(i * i for i in range(x)) with ProcessPoolExecutor() as ex: results = list(ex.map(heavy, [10_000_000] * 8))

    На macOS и Windows по умолчанию используется метод старта spawn: дочерний процесс импортирует модуль заново. Поэтому код запуска обязан быть под if __name__ == "__main__":, иначе получится бесконечное порождение процессов. Все аргументы и результаты должны быть picklable — лямбды, локальные функции и открытые соединения не пройдут.

    Ещё два практических момента: число процессов имеет смысл брать по числу физических ядер (os.cpu_count()), а не «побольше» — лишние процессы только конкурируют за кэш; и если каждый воркер поднимает NumPy/PyTorch с многопоточным BLAS, произойдёт oversubscription (8 процессов × 8 потоков = 64 потока на 8 ядрах), из-за чего всё станет медленнее. Лечится переменными OMP_NUM_THREADS=1 / torch.set_num_threads(1) внутри воркеров.

  11. Задача по "двойным указателям" (two pointers) с решением

    Дан отсортированный по неубыванию массив целых чисел $A$ длины $n$ и число $T$. Требуется найти пару индексов $(i, j)$, $i < j$, такую что $A_i + A_j = T$, или сообщить, что такой пары нет. Ограничения: $\mathcal{O}(n)$ по времени и $\mathcal{O}(1)$ по дополнительной памяти.

    Ставим два указателя на концы: $L = 0$, $R = n - 1$, и сравниваем сумму $s = A_L + A_R$ с целью $T$:

    • $s = T$ — ответ найден;
    • $s < T$ — сумму нужно увеличить; единственный способ, не теряя решений, — сдвинуть левый указатель вправо ($A_L$ минимален среди оставшихся);
    • $s > T$ — сумму нужно уменьшить, сдвигаем правый указатель влево.

    Цикл идёт, пока $L < R$. За каждую итерацию расстояние между указателями сокращается на единицу, значит итераций не больше $n$ — отсюда $\mathcal{O}(n)$ и $\mathcal{O}(1)$ памяти.

    Почему это корректно. Ключевой аргумент, который и хочет услышать интервьюер: сдвигая $L$ при $s < T$, мы отбрасываем все пары вида $(L, k)$ для $k \le R$. Но $A_L + A_k \le A_L + A_R = s < T$ для любого такого $k$ (массив отсортирован), то есть ни одна из отброшенных пар не могла быть ответом. Симметрично для правого указателя. Значит, никакое решение не теряется.

    См. два указателя.

    def two_sum_sorted(A, T): L, R = 0, len(A) - 1 while L < R: s = A[L] + A[R] if s == T: return L, R if s < T: L += 1 else: R -= 1 return None A = [-5, -2, 0, 3, 4, 9, 11] print(two_sum_sorted(A, 7)) # (1, 5): -2 + 9 print(two_sum_sorted(A, 100)) # None

    Тогда два указателя неприменимы напрямую, и есть два пути:

    • Отсортировать — $\mathcal{O}(n \log n)$ по времени, $\mathcal{O}(1)$ дополнительной памяти (или $\mathcal{O}(n)$, если исходные индексы важны и приходится сортировать пары (значение, индекс)).
    • Хеш-множество — один проход: для каждого $x$ проверяем, встречался ли уже $T - x$. Это $\mathcal{O}(n)$ по времени, но $\mathcal{O}(n)$ по памяти, зато возвращает индексы в исходном порядке.
    def two_sum_hash(A, T): seen = {} for i, x in enumerate(A): if T - x in seen: return seen[T - x], i seen[x] = i return None

    Выбор — классический размен «время против памяти». Если массив уже отсортирован, два указателя строго лучше: та же линейность без затрат памяти.

    Two pointers — это семейство приёмов, и интервьюер часто просит соседнюю задачу:

    • 3Sum — зафиксировать первый элемент и запустить два указателя на остатке: $\mathcal{O}(n^2)$;
    • Удаление дубликатов in-place и перенос нулей в конец — вариант «медленный/быстрый указатель» (slow/fast);
    • Слияние двух отсортированных массивов — по указателю на каждый;
    • Container With Most Water — та же схема сжатия с концов, но с другим критерием сдвига;
    • Скользящее окно — родственный приём, где оба указателя идут в одну сторону; см. скользящее окно;
    • Обнаружение цикла в связном списке (алгоритм Флойда «заяц и черепаха») — два указателя с разной скоростью.

    Граничные случаи, которые стоит проговорить: пустой массив и массив из одного элемента (цикл просто не выполнится), дубликаты (условие $i < j$ соблюдается автоматически, потому что $L < R$), переполнение при сложении — в Python неактуально, но в C++/Java об этом спросят.

  12. Где поиск быстрее: словарь или список?

    В словаре — в среднем $\mathcal{O}(1)$, в списке — $\mathcal{O}(n)$.

    x in list выполняет линейный перебор со сравнением == на каждом шаге: в худшем случае (элемента нет) просматриваются все $n$ элементов. x in dict (и x in set) вычисляет хеш ключа, сразу переходит в нужный слот хеш-таблицы и делает обычно одно сравнение. Время не зависит от размера коллекции: поиск в словаре на миллион элементов стоит столько же, сколько на десяти.

    Цена — память и требования к элементам: словарь и множество занимают в несколько раз больше места (таблица держится заполненной не более чем на 2/3) и требуют, чтобы ключи были хешируемыми.

    Практическое следствие, которое и проверяет вопрос: проверка вхождения в список внутри цикла — это скрытый $\mathcal{O}(n \cdot m)$. Замена списка на множество в такой конструкции — самая дешёвая и самая частая оптимизация в Python-коде; на десятках тысяч элементов она даёт ускорение в сотни раз. См. хеш-таблица: dict и set.

    import timeit items = list(range(100_000)) s = set(items) d = {x: True for x in items} # элемента нет — худший случай для списка print(timeit.timeit("99_999_999 in items", globals=globals(), number=100)) # ~0.9 c print(timeit.timeit("99_999_999 in s", globals=globals(), number=100)) # ~0.00002 c
    # антипаттерн: O(n*m) bad = [x for x in big_list if x in other_list] # правильно: O(n+m) other = set(other_list) good = [x for x in big_list if x in other]

    Разница проявляется на размере. На 5–20 элементах линейный поиск обычно быстрее: нет затрат на хеширование и на построение таблицы, а данные лежат подряд и попадают в кэш процессора. Если коллекция маленькая и создаётся заново на каждой итерации, кортеж или список выигрывают.

    Список незаменим, когда важен порядок и нужны дубликаты, когда элементы нехешируемы (списки, словари, numpy-массивы), а также когда нужен доступ по индексу — в словаре его нет.

    Отдельный случай — отсортированный список: bisect даёт поиск за $\mathcal{O}(\log n)$ без затрат памяти на хеш-таблицу и вдобавок отвечает на вопросы «ближайший меньший/больший», на которые словарь ответить не может.

    Ещё нюанс: если проверок будет всего одна-две, а список большой, построение множества ($\mathcal{O}(n)$ плюс аллокации) может не окупиться. Множество строят, когда проверок много.

    set и dict по скорости поиска эквивалентны — это одна и та же хеш-таблица. Если значения не нужны, берите set: он экономит память. Конструкция {x: True for x in items} вместо set(items) — распространённая избыточность.

    x in dict проверяет вхождение среди ключей, а не значений. x in dict.values() — это снова линейный поиск $\mathcal{O}(n)$; если нужен обратный поиск, стройте обратный словарь.

    list.index(x) и list.count(x) тоже линейны, а list.remove(x) — линеен вдвойне (поиск плюс сдвиг).

    И про худший случай: у словаря он теоретически $\mathcal{O}(n)$ — при массовых коллизиях. Для встроенных типов это практически недостижимо, но с плохим пользовательским __hash__ вполне реально; подробнее — когда dict деградирует.

  13. Разница между loc и iloc в pandas

    loc работает с метками — значениями индекса и именами столбцов. iloc работает с целочисленными позициями, как обычный список Python.

    Разница не только в том, что подставлять, но и в семантике среза:

    • df.loc["b":"d"] включает обе границы — это диапазон меток.
    • df.iloc[1:4] исключает правую границу — это обычный Python-срез.

    Эта асимметрия смущает, но логична: у меток нет понятия «следующая после последней», поэтому включающий срез — единственный осмысленный вариант.

    Обе индексации принимают одинаковые формы: скаляр, список, срез, булеву маску, а также пару [строки, столбцы]. Дополнительно loc понимает callable: df.loc[lambda d: d.age > 30, ["name"]] — удобно в цепочках методов, где промежуточный DataFrame не имеет имени.

    Отдельно стоят at и iat — быстрые версии для доступа к одной ячейке: df.at["y", "a"], df.iat[1, 0]. Они заметно быстрее в циклах, потому что не строят промежуточных объектов.

    import pandas as pd df = pd.DataFrame({"a": [10, 20, 30], "b": [1, 2, 3]}, index=["x", "y", "z"]) print(df.loc["y", "a"]) # 20 — по метке print(df.iloc[1, 0]) # 20 — по позиции print(df.loc["x":"y"]) # обе границы включены print(df.iloc[0:2]) # правая граница исключена print(df.loc[df.a > 15]) # булева маска работает только в loc

    Если индекс сам состоит из чисел, метка и позиция перестают совпадать, и код начинает молча возвращать не то:

    df = pd.DataFrame({"a": [10, 20, 30]}, index=[3, 1, 2]) print(df.loc[1]) # строка с меткой 1 -> a = 20 print(df.iloc[1]) # вторая строка по счёту -> a = 20 (совпало случайно) print(df.loc[3]) # a = 10 print(df.iloc[0]) # a = 10

    После df = df[df.x > 0] или df.sort_values(...) индекс остаётся «дырявым» ([0, 3, 7, ...]), и df.loc[1] бросит KeyError, хотя строк много. Практическое правило: после фильтрации или сортировки, если индекс не несёт смысла, делайте reset_index(drop=True). И никогда не полагайтесь на то, что метки совпадают с позициями.

    Голое df[...] — третий, самый неоднозначный способ: df["a"] берёт столбец, df[0:2] берёт строки по позиции, df[df.a > 0] берёт строки по маске. Именно из-за этой неоднозначности в рабочем коде предпочитают явные loc/iloc.

    Классическая ошибка — присваивание через две индексации подряд:

    df[df.a > 15]["b"] = 0 # SettingWithCopyWarning; исходный df может не измениться df.loc[df.a > 15, "b"] = 0 # правильно: одна операция, гарантированная запись

    Причина в том, что df[df.a > 15] возвращает объект, который может быть копией, а может — представлением; присваивание в него не обязано попасть в исходный DataFrame. Единственный надёжный способ — одна операция loc с указанием и строк, и столбцов.

    В pandas 3.0 включён Copy-on-Write, где семантика стала строгой: chained assignment просто не действует на исходный объект (без предупреждения о неопределённости). Тем более стоит писать через loc сразу.

    И про производительность: for i in range(len(df)): df.iloc[i, 0] ... — антипаттерн. Векторизованная операция над столбцом на два-три порядка быстрее; см. pandas.

  14. Зачем нужен контекстный менеджер?

    Контекстный менеджер решает одну задачу: гарантировать, что парное действие выполнится обязательно — открыли/закрыли, захватили/освободили, включили/выключили, — даже если внутри блока произошло исключение или сработал return.

    Механика: объект реализует два метода. __enter__ вызывается на входе в блок with и возвращает то, что попадает в переменную после as; __exit__(exc_type, exc_value, traceback) вызывается на выходе в любом случае — при нормальном завершении, при исключении, при return, break и continue. Это ровно то же, что try/finally, но короче, невозможно забыть и переиспользуемо.

    Если __exit__ вернёт истинное значение, исключение считается обработанным и подавляется; обычно возвращают None, чтобы исключение всплывало дальше.

    Типичные применения: файлы, сетевые соединения и курсоры БД, блокировки (threading.Lock), транзакции, временные каталоги, замер времени, временное изменение глобального состояния. Подробнее — контекстный менеджер with.

    # файл закроется гарантированно, даже если внутри исключение with open("file.txt", "r") as f: data = f.read() # инференс без построения графа градиентов import torch with torch.no_grad(): preds = model(x) # несколько менеджеров сразу with open("in.txt") as src, open("out.txt", "w") as dst: dst.write(src.read())

    Полный вариант — класс с __enter__/__exit__. Короткий — декоратор contextlib.contextmanager над функцией-генератором: всё до yield выполняется на входе, всё после — на выходе. Чтобы выходная часть отработала и при исключении, тело оборачивают в try/finally.

    from contextlib import contextmanager import time @contextmanager def timer(name): t0 = time.perf_counter() try: yield finally: print(f"{name}: {time.perf_counter() - t0:.3f}s") with timer("train epoch"): ...

    Полезное из contextlib: suppress(FileNotFoundError) вместо пустого except, ExitStack для динамического числа менеджеров (например, открыть список файлов), closing(obj) для объектов, у которых есть только .close().

    torch.no_grad() — не просто «чтобы не считать градиенты»: без него на валидации и инференсе PyTorch строит граф вычислений и удерживает промежуточные активации, из-за чего видеопамять растёт с каждым батчем и прогон падает с OOM. Это одна из самых частых ошибок новичков.

    Второй момент: with не проглатывает исключение сам по себе. Формулировка «with нужен, чтобы код не падал» неверна — он нужен, чтобы ресурс освободился, когда код падает. Исключение по-прежнему всплывёт наверх.

    Третий: в асинхронном коде нужен async with и методы __aenter__/__aexit__ — обычный with на асинхронном ресурсе (например, aiohttp.ClientSession) работать не будет.

  15. Многопоточность vs мультипроцессинг

    threading. Потоки живут внутри одного процесса и делят адресное пространство: любой объект доступен всем потокам без сериализации. Создание потока дёшево (доли миллисекунды, около мегабайта стека), переключение — тоже. Но в CPython исполнение байткода сериализуется GIL, поэтому CPU-bound код потоки не ускоряют. Зато GIL отпускается на время ввода-вывода и внутри C-расширений — значит, для I/O-bound и для NumPy/PyTorch потоки работают полноценно.

    multiprocessing. Каждый процесс — отдельный интерпретатор со своей памятью и своим GIL, поэтому параллелизм настоящий и упирается только в число ядер. Плата: старт процесса стоит десятки-сотни миллисекунд, аргументы и результаты передаются через pickle (это и время, и ограничение на то, что вообще можно передать), а общая память требует явных средств — multiprocessing.shared_memory, Value, Array, Manager.

    Короткое правило: ждём — потоки, считаем — процессы. Более точное: если горячий участок отпускает GIL (сеть, диск, C-код), берите потоки; если он крутится в чистом Python — процессы.

    См. threading, multiprocessing, сравнение подходов к конкурентности.

    # CPU-bound -> процессы from multiprocessing import Pool def f(x): return sum(i * i for i in range(x)) if __name__ == "__main__": # обязательно при spawn (macOS, Windows) with Pool() as p: print(p.map(f, [10**6] * 8)) # I/O-bound -> потоки from concurrent.futures import ThreadPoolExecutor import requests with ThreadPoolExecutor(max_workers=32) as ex: pages = list(ex.map(lambda u: requests.get(u, timeout=10).text, urls))

    torch.utils.data.DataLoader(num_workers=N) использует процессы — потому что декодирование JPEG, аугментации на PIL и парсинг на чистом Python упирались бы в GIL. Цена — каждый воркер держит свою копию датасета; если в __init__ лежит большой Python-объект (список из миллионов словарей), память умножается на N. Обходят это через numpy-массивы, memory-mapped файлы или IterableDataset.

    Обратный случай: копирование тензоров на GPU, pin_memory, вызовы cuDNN и BLAS — всё это C-код, отпускающий GIL, поэтому здесь потоки работают, а процессы были бы избыточны.

    Частая ошибка — oversubscription: 8 процессов, в каждом NumPy с 8 потоками OpenMP на 8-ядерной машине даёт 64 потока, которые дерутся за кэш, и всё становится медленнее однопоточного варианта. Лечится OMP_NUM_THREADS=1 / torch.set_num_threads(1) внутри воркеров.

    Процессы. Метод старта spawn (по умолчанию на macOS и Windows, а с Python 3.14 — и на Linux) заново импортирует модуль, поэтому код запуска обязан быть под if __name__ == "__main__", иначе получится бесконечное порождение процессов. Всё передаваемое должно быть picklable: лямбды, локальные функции, открытые файлы и соединения не пройдут. Метод fork дешевле, но небезопасен в связке с потоками и может приводить к дедлокам в CUDA и в некоторых C-библиотеках.

    Потоки. Разделяемая память означает гонки: counter += 1 из нескольких потоков теряет инкременты, потому что это не атомарная операция. Нужны Lock, Queue или атомарные структуры. Отладка таких багов тяжела — они воспроизводятся не всегда.

    Общее. Ни та, ни другая модель не ускорит задачу, узкое место которой — диск или сеть провайдера. Прежде чем распараллеливать, профилируйте: см. профилирование.

  16. Что такое GIL?

    GIL (Global Interpreter Lock) — глобальный мьютекс в CPython, который позволяет исполнять байткод только одному потоку одновременно. Даже на 16-ядерной машине чистый Python-код в 8 потоках будет выполняться по сути последовательно, с накладными расходами на переключение.

    Зачем он нужен: управление памятью в CPython построено на подсчёте ссылок, и счётчик ob_refcnt есть у каждого объекта. Без глобальной блокировки каждое изменение счётчика пришлось бы делать атомарно, что замедлило бы однопоточный код (а это подавляющее большинство программ) и потребовало бы блокировок на уровне отдельных объектов — с риском дедлоков. GIL — размен: простая и быстрая однопоточность и простой C-API взамен параллелизма потоков.

    Важно: GIL отпускается во время блокирующих операций — сетевого и файлового ввода-вывода, time.sleep, а также внутри C-расширений, которые явно это делают (NumPy, PyTorch, lxml, сжатие, хеширование). Поэтому:

    • I/O-bound код потоки ускоряют нормально: пока один поток ждёт ответа сети, GIL держит другой.
    • CPU-bound код на чистом Python потоки не ускоряют; нужен multiprocessing, векторизация через NumPy или вынос горячего участка в C/Cython/Numba.

    Подробнее — GIL и сравнение подходов к конкурентности.

    Практически весь тяжёлый счёт в ML-коде происходит внутри C/CUDA-ядер NumPy, PyTorch и scikit-learn, а они отпускают GIL на время вычисления. Матричное умножение на 8 ядрах через BLAS работает параллельно независимо от GIL — интерпретатор в этот момент простаивает и никому не мешает.

    Именно поэтому DataLoader в PyTorch по умолчанию использует процессы (num_workers), а не потоки: аугментации и парсинг на чистом Python и PIL — как раз тот случай, когда GIL был бы узким местом. А вот pin_memory и копирование на GPU выполняются в потоке — там GIL отпущен.

    Практический вывод: прежде чем бороться с GIL, стоит профилировать (профилирование). Часто окажется, что горячий участок — это Python-цикл, который правильнее векторизовать, а не распараллелить.

    С Python 3.13 существует официальная free-threaded сборка (PEP 703, флаг --disable-gil, интерпретатор python3.13t), где GIL отсутствует. Это экспериментальная опция: однопоточный код в ней немного медленнее, а C-расширения должны быть явно помечены как совместимые — экосистема ещё догоняет. В обычной сборке CPython GIL на месте.

    Параллельно в 3.12+ развиваются субинтерпретаторы с собственным GIL (PEP 684, PEP 734) — промежуточный вариант между потоками и процессами.

    Два частых заблуждения: «GIL есть в языке Python» — нет, это деталь реализации CPython; в Jython и IronPython его нет, в PyPy есть. И «GIL делает Python однопоточным» — нет, потоки создаются настоящие, ОС-ные, и для I/O работают полноценно; ограничена лишь одновременность исполнения байткода.

  17. Отсортировать подсписок по порядку из внешнего списка

    Даны массивы $N$ и $K$ без повторов, причём $K \subseteq N$. Нужно упорядочить элементы $K$ в том же порядке, в каком они идут в $N$.

    Ключевая идея: «порядок как в $N$» — это не сортировка по значению, а сортировка по позиции в другом списке. Отсюда два эквивалентных по сложности решения; выбор между ними определяется соотношением размеров.

    Решение 1 — один проход по $N$ с фильтром. Превращаем $K$ во множество (проверка вхождения за $\mathcal{O}(1)$) и идём по $N$, забирая элементы, которые есть в $K$. Порядок получается автоматически, потому что мы идём в порядке $N$. Сложность $\mathcal{O}(|N| + |K|)$ по времени, $\mathcal{O}(|K|)$ по памяти.

    Решение 2 — сортировка $K$ по ключу-позиции. Строим словарь pos = {v: i for i, v in enumerate(N)} и сортируем $K$ по pos[x]. Сложность $\mathcal{O}(|N| + |K|\log|K|)$.

    Первое асимптотически лучше и его стоит назвать основным. Второе полезно, когда $K$ сильно меньше $N$ и словарь позиций уже построен заранее (например, переиспользуется для многих запросов): тогда каждый запрос стоит $\mathcal{O}(|K|\log|K|)$ без прохода по всему $N$.

    Наивное решение sorted(K, key=N.index) формально верно, но даёт $\mathcal{O}(|N| \cdot |K|)$ — list.index каждый раз выполняет линейный поиск. Это ровно та ошибка, ради которой задачу и дают.

    def order_by_reference(N, K): k_set = set(K) return [x for x in N if x in k_set] # O(|N| + |K|) def order_by_position(N, K): pos = {v: i for i, v in enumerate(N)} return sorted(K, key=pos.__getitem__) # O(|N| + |K| log |K|) N = [5, 3, 8, 1, 2] K = [1, 8, 5] print(order_by_reference(N, K)) # [5, 8, 1] print(order_by_position(N, K)) # [5, 8, 1]

    Повторы в $N$. Словарь pos при построении оставит последнюю позицию; если нужна первая — стройте его как pos.setdefault(v, i). Решение с фильтром выдаст элемент столько раз, сколько он встречается в $N$.

    Повторы в $K$. Первое решение их потеряет (множество схлопнет дубли). Тогда берут Counter(K) и выводят каждый элемент нужное число раз.

    $K \not\subseteq N$. Элементы, которых нет в $N$, первое решение молча выбросит, второе упадёт с KeyError. Обычно их договариваются складывать в конец: key=lambda x: pos.get(x, len(N)).

    Элементы нехешируемы (например, списки). Тогда словарь и множество не построить: остаётся сортировка по ключу из внешнего индекса или приведение к хешируемому виду (кортежи).

    Задача проверяет не знание синтаксиса, а рефлекс «линейный поиск внутри цикла — это квадрат». Хорошая структура ответа: (1) назвать наивное решение и его сложность, (2) объяснить, что именно в нём дорого, (3) предложить замену поиска на хеш-структуру, (4) уточнить граничные случаи — повторы, элементы вне $N$, пустые входы.

    Полезно также спросить, что важнее: время или память. Если $N$ огромен, а $K$ мал и это единственный запрос, второе решение выигрывает по памяти лишь при уже готовом индексе — иначе словарь на весь $N$ дороже множества на $K$.

    Связанная теория: хеш-таблица, алгоритмическая сложность.

  18. Что может быть ключом словаря в Python?

    Ключом может быть любой хешируемый объект. Хешируемый — значит, у него есть __hash__, возвращающий целое число, которое не меняется за время жизни объекта, и есть __eq__, согласованный с хешем.

    Формально требований два, и оба обязательны:

    1. hash(obj) не должен меняться (иначе объект «потеряется»: словарь будет искать его в другом слоте, чем тот, куда положил).
    2. Если a == b, то обязательно hash(a) == hash(b). Обратное не требуется — разные объекты могут иметь одинаковый хеш, это коллизия, и она разрешается автоматически.

    Можно: int, float, bool, str, bytes, tuple (если все элементы хешируемы), frozenset, None, функции, классы, модули и экземпляры обычных пользовательских классов (по умолчанию хешируются по id).

    Нельзя: list, dict, set, bytearray — у них __hash__ = None, попытка даёт TypeError: unhashable type. Причина не в «изменяемости как таковой», а в том, что их __eq__ сравнивает содержимое: хеш пришлось бы менять вместе с содержимым, что нарушило бы требование (1).

    Подробнее — хеш-таблица: dict и set.

    d = { "x": 1, (1, 2): "кортеж из неизменяемых — ок", frozenset({1, 2}): "ок", 3.0: "внимание: 3.0 == 3, поэтому перезапишет ключ 3", } # d[[1, 2]] = 3 # TypeError: unhashable type: 'list' # d[(1, [2])] = 3 # TypeError: кортеж хешируем только если хешируемы элементы

    По умолчанию экземпляры пользовательского класса хешируются по адресу в памяти, а сравниваются по идентичности — то есть два «одинаковых по содержимому» объекта будут разными ключами. Если это не то, что нужно, определяют __eq__ и __hash__ вместе и по одному и тому же набору полей:

    class Point: def __init__(self, x, y): self.x, self.y = x, y def __eq__(self, other): return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y) def __hash__(self): return hash((self.x, self.y))

    Важная деталь: если определить только __eq__, Python автоматически выставит __hash__ = None, и объект перестанет быть хешируемым. Это сделано намеренно — чтобы нельзя было случайно получить пару методов, нарушающую инвариант.

    Готовое решение — @dataclass(frozen=True): он сгенерирует согласованные __eq__ и __hash__ и запретит изменение полей.

    True == 1 == 1.0 — все три дают один и тот же хеш, поэтому {1: "a", True: "b", 1.0: "c"} превращается в словарь из одного элемента {1: 'c'}: ключ остаётся первым, а значение перезаписывается последним.

    Кортеж хешируем только если хешируемы все его элементы: (1, [2]) использовать нельзя.

    Мутировать объект, уже лежащий в словаре как ключ (например, менять поле, участвующее в __hash__), — способ навсегда потерять запись: она останется в памяти, но d[key] её не найдёт.

    float('nan') как ключ ведёт себя странно: nan != nan, поэтому один и тот же объект найдётся (сравнение по is идёт первым), а новый такой же — нет.

  19. Какова алгоритмическая сложность append() в списке?

    list.append(x) работает за амортизированное $\mathcal{O}(1)$. Слово «амортизированное» здесь ключевое, и именно его ждёт интервьюер.

    list в CPython — динамический массив указателей. Он хранит два числа: len (сколько элементов занято) и allocated (сколько ячеек выделено под буфер). Пока len < allocated, append просто записывает указатель в свободную ячейку и увеличивает счётчик — это несколько машинных инструкций, честное $\mathcal{O}(1)$.

    Когда буфер закончился, происходит realloc: выделяется буфер большего размера, и старые указатели копируются — это $\mathcal{O}(n)$ для конкретного вызова. Но растёт буфер не на единицу, а пропорционально текущему размеру (в CPython примерно на 12,5 %, формула new_allocated = len + (len >> 3) + 6). Из-за геометрического роста дорогие перевыделения случаются всё реже: суммарная стоимость $n$ вызовов append есть $\mathcal{O}(n)$, то есть в среднем $\mathcal{O}(1)$ на вызов.

    Подробнее про оценки сложности — алгоритмическая сложность.

    Если бы буфер расширялся на фиксированное число ячеек (скажем, на 1 или на 10), перевыделение случалось бы каждые $k$ вставок, и суммарная стоимость $n$ вставок стала бы $\mathcal{O}(n^2)$ — построение списка из миллиона элементов заняло бы минуты вместо миллисекунд. Умножение размера на константу $> 1$ — единственный способ получить амортизированное $\mathcal{O}(1)$; это общий приём, он же используется в std::vector в C++ и в ArrayList в Java.

    Обратная сторона — перерасход памяти: список почти всегда занимает больше, чем нужно под его элементы. Проверить это можно через sys.getsizeof — размер прыгает ступеньками, а не растёт на 8 байт с каждым append.

    list.insert(0, x) и list.pop(0) — это $\mathcal{O}(n)$: все элементы сдвигаются. Если нужна очередь с быстрыми операциями с обоих концов, берут collections.deque, у которого appendleft/popleft — $\mathcal{O}(1)$.

    list.pop() (с конца) — $\mathcal{O}(1)$, а list.remove(value) — $\mathcal{O}(n)$, потому что сначала выполняется линейный поиск.

    И ещё: a += [x] и a.append(x) эквивалентны по сложности, а вот a = a + [x] в цикле — это $\mathcal{O}(n^2)$, потому что каждый раз создаётся новый список.

  20. Что быстрее — список или кортеж?

    Кортеж немного быстрее и заметно компактнее, но разница невелика, и на собеседовании важнее объяснить почему, а не назвать «кортеж».

    Память. У списка есть запас ёмкости под будущие append и отдельное поле allocated, поэтому он занимает больше: sys.getsizeof([1,2,3]) — 88 байт против 64 у (1,2,3). Разница растёт с числом элементов из-за over-allocation.

    Создание. Литерал кортежа из констант вычисляется на этапе компиляции и складывается в константы кода (LOAD_CONST), тогда как литерал списка каждый раз собирается инструкциями BUILD_LIST. Плюс CPython держит пул переиспользуемых кортежей малого размера. Отсюда основной выигрыш — на создании, а не на чтении.

    Доступ и итерация. Здесь разница минимальна: и там, и там — индексация в массив указателей. На микробенчмарках кортеж выигрывает единицы процентов.

    Функциональные различия важнее скорости. Кортеж хешируем (если хешируемы элементы), поэтому годится в качестве ключа словаря и элемента множества; список — нет. Кортеж безопасно передавать как значение по умолчанию и хранить как константу — он не изменится незаметно.

    import sys, timeit print(sys.getsizeof([1, 2, 3]), sys.getsizeof((1, 2, 3))) # 88 64 print(timeit.timeit("(1, 2, 3, 4, 5)")) # ~0.01 c — LOAD_CONST print(timeit.timeit("[1, 2, 3, 4, 5]")) # ~0.04 c — BUILD_LIST t, l = (1, 2, 3), [1, 2, 3] print(timeit.timeit("t[1]", globals=globals())) # разница на доступе минимальна print(timeit.timeit("l[1]", globals=globals()))

    Если в ответе приводите бенчмарк, важно сравнивать одно и то же. Типичная ошибка — сравнить итерацию по генератору и по списку (setup="t=(i for i in range(1000))" создаёт генератор, а не кортеж, и после первого прохода он исчерпан) — тогда цифры получаются абсурдными.

    Правильный setup для кортежа — t=tuple(range(1000)). И измерять надо с timeit в несколько повторов, беря минимум: разброс из-за планировщика ОС и turbo-boost легко превышает измеряемый эффект.

    Общий совет: не выбирайте между list и tuple по скорости. Разница в единицы процентов на реальном коде не видна, а вот случайно изменённый список, переданный в чужую функцию, — вполне.

    Ключ словаря и элемент множества: d[(user_id, date)] — стандартный приём, со списком он невозможен.

    Неизменяемость как контракт: возвращая кортеж, вы сообщаете вызывающему, что структура не предназначена для модификации. namedtuple и @dataclass(frozen=True) развивают эту идею с именованным доступом — см. NamedTuple.

    Оговорка: неизменяемость кортежа поверхностная. t = ([1, 2], 3) — сам кортеж менять нельзя, но вложенный список можно, и hash(t) при этом упадёт с TypeError. Соответственно, кортеж со списком внутри ключом словаря быть не может.

  21. Как в Python передаются аргументы: по ссылке или по значению?

    Ни то, ни другое в классическом смысле. Правильная формулировка — pass by object reference (иногда говорят «call by sharing»): в функцию передаётся ссылка на объект, но сама ссылка передаётся по значению.

    Что это означает на практике:

    • Имя параметра внутри функции — новая локальная переменная, изначально указывающая на тот же объект, что и аргумент снаружи.
    • Если внутри функции объект мутируют (list.append, dict[key] = ..., изменение атрибута), изменения видны снаружи — объект-то один.
    • Если внутри функции параметру присваивают новое значение (b = 10, b += 10 для числа), локальное имя просто перепривязывается к другому объекту; переменная снаружи продолжает указывать на старый. Никакого эффекта наружу нет.

    Поэтому наблюдаемое поведение полностью определяется не механизмом передачи, а изменяемостью типа: list, dict, set, экземпляры классов — изменяемые; int, float, str, tuple, frozenset — нет. Подробнее — передача аргументов в функции и изменяемые и неизменяемые типы.

    def f(a, b): a.append(10) # мутация -> видна снаружи b += 10 # перепривязка имени -> не видна снаружи L, x = [1, 2], 5 f(L, x) print(L, x) # [1, 2, 10] 5

    b += 10 для числа — это перепривязка, а a += [10] для списка — это мутация на месте: список реализует __iadd__, который эквивалентен a.extend([10]). То есть один и тот же оператор += ведёт себя по-разному в зависимости от типа, и именно на этом строят каверзные вопросы.

    Отсюда же известная ловушка с кортежем: t = ([1], 2); t[0] += [3] одновременно изменит вложенный список и бросит TypeError — потому что += сначала успешно мутирует список, а потом пытается присвоить результат обратно в неизменяемый кортеж.

    Слабый ответ — «по ссылке». Он неверен: при передаче по ссылке присваивание b = 10 внутри функции меняло бы переменную снаружи (как & в C++), а в Python не меняет.

    Сильный ответ строится в три шага: (1) назвать модель — object reference; (2) провести границу между мутацией и присваиванием; (3) привести пример с изменяемым и неизменяемым аргументом. Полезно сразу упомянуть связанную практическую проблему — изменяемый аргумент по умолчанию: это прямое следствие той же модели.

  22. Есть ли в Python конструкторы и деструкторы?

    Да, но устроены они иначе, чем в C++ или Java.

    Создание объекта разделено на два шага. __new__(cls, ...) — статический метод, который создаёт и возвращает объект; __init__(self, ...) — метод, который инициализирует уже созданный объект и обязан вернуть None. Вызов Demo("obj") разворачивается в type.__call__, который выполняет obj = Demo.__new__(Demo, "obj") и затем, если obj является экземпляром Demo, вызывает obj.__init__("obj").

    В 99 % случаев переопределяют только __init__. __new__ нужен, когда объект должен быть создан особым образом: наследование от неизменяемых типов (int, str, tuple — там менять уже поздно в __init__), синглтоны, пулы объектов, кастомные метаклассы.

    Деструктора в привычном смысле нет. __del__ вызывается не в момент выхода из области видимости, а когда сборщик мусора освобождает объект. CPython использует подсчёт ссылок, поэтому обычно это происходит сразу после исчезновения последней ссылки, — но это деталь реализации, а не гарантия языка. Подробнее — конструкторы и деструкторы и сборщик мусора.

    class Demo: def __new__(cls, *args): print("__new__: создаётся объект") return super().__new__(cls) def __init__(self, name): print(f"__init__: инициализация {name}") def __del__(self): print("__del__: объект освобождён") x = Demo("obj") del x # __del__ отработает здесь — но только потому, что ссылок больше нет

    Момент вызова __del__ не определён: объект может попасть в цикл ссылок и дожить до срабатывания generational GC, а при завершении интерпретатора __del__ может не быть вызван вовсе. Исключение, брошенное внутри __del__, не всплывает наружу — оно печатается в stderr и игнорируется, что превращает отладку в мучение.

    Правильный инструмент для освобождения ресурсов — контекстный менеджер (__enter__/__exit__) или try/finally: они дают детерминированный момент закрытия. Именно поэтому файлы открывают через with open(...), а не полагаются на то, что объект файла когда-нибудь соберётся. См. контекстный менеджер with.

    «Что будет, если __new__ вернёт объект другого класса?» — __init__ не вызовется вовсе, потому что возвращённый объект не является экземпляром cls. Это регулярный источник багов при попытке сделать синглтон.

    «Зачем __init__ возвращает None?» — если вернуть что-то другое, type.__call__ бросит TypeError. Инициализатор не создаёт объект, он его настраивает.

    «Как сделать альтернативный конструктор?» — не через __new__, а через @classmethod: Point.from_string("1,2"). Это идиоматичный способ, см. альтернативные конструкторы.

  23. Что такое хэш-функция и где она используется?

    Хеш-функция — детерминированное отображение объекта произвольного размера в число фиксированной длины. Ключевые свойства: одинаковый вход всегда даёт одинаковый выход; разные входы могут дать одинаковый выход (коллизия) — это неизбежно, потому что входов бесконечно много, а выходов конечное число; хорошая функция распределяет значения равномерно, так что коллизии редки и не образуют кластеров.

    В Python это протокол __hash__, вызываемый встроенной hash(). Именно на нём построены dict и set: индекс слота вычисляется из хеша, поэтому поиск, вставка и удаление стоят в среднем $\mathcal{O}(1)$ вместо $\mathcal{O}(n)$ линейного перебора.

    Требование согласованности: если a == b, то hash(a) == hash(b). Обратное неверно. Нарушение этого правила ломает dict не по скорости, а по корректности.

    Где применяются хеши за пределами словарей:

    • Проверка целостности и дедупликация — SHA-256 файла как его отпечаток; так работают Docker-слои, git-объекты, кэши датасетов.
    • Шардирование — hash(user_id) % n_shards определяет, на какой сервер идёт запрос; consistent hashing уменьшает переезды при изменении числа шардов.
    • Вероятностные структуры — Bloom filter, HyperLogLog, MinHash / LSH для быстрого поиска похожих документов.
    • ML: hashing trick — sklearn.feature_extraction.FeatureHasher отображает признаки произвольной кардинальности в фиксированное число колонок без хранения словаря; так обрабатывают категории, которых заранее не знаешь.
    • Криптография — подписи, пароли (там нужны специальные медленные функции: bcrypt, argon2, а не SHA).

    Подробнее — хеш-таблица: dict и set.

    print(hash(42), hash("abc")) # хеш строки меняется между запусками print(hash((1, 2))) # кортеж хешируем # print(hash([1, 2])) # TypeError: unhashable type: 'list' import hashlib print(hashlib.sha256(b"data").hexdigest()[:16]) # стабильно всегда и везде

    Это разные инструменты, и путать их — типичная ошибка.

    hash() оптимизирован под скорость и используется только внутри процесса. Для str и bytes он рандомизирован: соль генерируется при старте интерпретатора (управляется PYTHONHASHSEED), поэтому hash("abc") различается между запусками. Это защита от hash-flooding — атаки, при которой злоумышленник шлёт заранее подобранные коллизии и превращает $O(1)$ в $O(n)$.

    Отсюда правило: никогда не сохраняйте hash() за пределы процесса — в файл, в БД, в имя кэш-файла, в ключ Redis. После рестарта значение будет другим, и кэш «протухнет» молча. Для стабильного отпечатка берут hashlib.sha256 / md5 (для некриптографических задач подойдут и быстрые xxhash, blake3).

    Hashing trick удобен, но у него есть цена: коллизии складывают разные категории в одну колонку. При 2^18 колонок и миллионе уникальных значений коллизии неизбежны, и модель теряет часть сигнала. Размер пространства подбирается по кривой качества, а не «на глаз»; в CTR-задачах типичны 2^20–2^24.

    Второе: если для сплита train/test используется хеширование идентификатора (hash(user_id) % 10 < 8), берите стабильную функцию из hashlib. С встроенным hash() сплит развалится при следующем запуске, и одни и те же пользователи окажутся то в train, то в test — это прямая утечка.

  24. Как решаются коллизии в словарях Python?

    Коллизия — ситуация, когда два разных ключа претендуют на один слот хэш-таблицы. Это неизбежно: хэш — большое число, а слотов конечное количество, и индекс берётся как hash(key) & (size - 1), то есть по младшим битам.

    CPython решает коллизии открытой адресацией (open addressing), а не цепочками списков, как учат в классических курсах. Если слот занят, интерпретатор пробует следующий по псевдослучайной последовательности проб; она использует все биты хэша, а не только младшие, поэтому ключи, совпавшие по младшим битам, быстро расходятся:

    perturb = hash j = hash & mask пока слот занят: j = (5 * j + 1 + perturb) & mask perturb >>= 5

    При каждой пробе сравнивается сначала сохранённый хэш (дешёвое сравнение целых), и только при совпадении хэшей — сами ключи через __eq__. Именно поэтому коллизия хэша обычно стоит одно лишнее сравнение int, а не вызов дорогого __eq__.

    Таблица никогда не заполняется полностью: при заполнении примерно на 2/3 происходит resize с перехэшированием всех элементов. Свободное место — то, что удерживает среднее число проб близким к единице, а сложность операций — в $\mathcal{O}(1)$ в среднем ($\mathcal{O}(n)$ в худшем случае). Подробнее — хеш-таблица: dict и set.

    Цепочки требуют отдельного объекта-списка на каждый занятый слот: это лишние аллокации и, главное, прыжки по памяти — каждый переход по указателю с высокой вероятностью промахивается мимо кэша процессора. Открытая адресация держит данные в одном непрерывном массиве, поэтому пробы попадают в уже загруженную кэш-линию и работают заметно быстрее.

    С Python 3.7 dict вдобавок разделён на две части: компактный массив записей (hash, key, value) в порядке вставки и отдельный индексный массив слотов. Это экономит память (индексы занимают 1–4 байта вместо 24) и попутно даёт гарантированное сохранение порядка вставки — то самое свойство, которое стало частью спецификации языка.

    Удаление реализуется не обнулением слота, а установкой маркера-«надгробия» (DUMMY): иначе цепочка проб оборвалась бы и следующий за удалённым элемент стал бы недоступен.

    Практический риск коллизий возникает не со встроенными типами, а с собственными классами. Если __hash__ возвращает константу или значение с плохим распределением (например, hash(self.category) для поля с тремя значениями), все объекты сваливаются в одну область проб, и dict деградирует до линейного поиска с дорогими __eq__.

    Правило: реализуйте __hash__ как hash((self.a, self.b)) — по тому же набору полей, что участвует в __eq__. Нарушение инварианта «a == b $\Rightarrow$ hash(a) == hash(b)» ломает словарь не по производительности, а по корректности: объект «теряется» в нём.

    Отдельно: строки в Python хэшируются с hash randomization (соль задаётся при старте процесса, PYTHONHASHSEED) — это защита от DoS-атак подобранными коллизиями. Следствие — hash("abc") различается между запусками, поэтому его нельзя использовать как стабильный идентификатор в файлах и БД; для этого берут hashlib.sha256.

  25. Отличие генераторов и итераторов

    Полезно развести три понятия, которые часто смешивают.

    Итерируемый объект (iterable) — тот, у которого есть __iter__. По нему можно пройти циклом for. Списки, строки, словари, файлы — итерируемые.

    Итератор (iterator) — объект с __next__ и __iter__ (возвращающим самого себя). Он хранит позицию обхода и выдаёт элементы по одному, а закончив — бросает StopIteration. Итератор всегда итерируемый, обратное неверно: iter([1,2,3]) даёт итератор, сам список — нет.

    Генератор (generator) — частный случай итератора, созданный функцией с yield или генераторным выражением. Python сам генерирует для него __iter__, __next__ и логику StopIteration, а состояние (локальные переменные и точка исполнения) сохраняется между вызовами автоматически.

    То есть: каждый генератор — итератор, но не каждый итератор — генератор. Разница не в возможностях, а в способе записи: класс на 12 строк против функции на 3. Подробнее — итераторы и генераторы, примеры кода — здесь.

    lst = [1, 2, 3] it = iter(lst) # итератор поверх списка print(hasattr(lst, "__next__")) # False — список не итератор print(hasattr(it, "__next__")) # True def gen(): # генератор yield 1; yield 2 import types, collections.abc as abc print(isinstance(gen(), abc.Iterator)) # True print(isinstance(gen(), types.GeneratorType)) # True print(isinstance(it, types.GeneratorType)) # False — итератор, но не генератор

    У генератора есть двусторонний интерфейс, которого нет у произвольного итератора:

    • gen.send(value) — возобновить исполнение, передав значение внутрь: выражение x = yield вернёт его. На этом механизме исторически строились корутины до async/await.
    • gen.throw(exc) — возбудить исключение в точке yield.
    • gen.close() — бросить GeneratorExit, чтобы генератор корректно освободил ресурсы (именно так работает contextlib.contextmanager).
    • yield from other — делегировать другому генератору с корректной передачей значений и исключений.

    Это и есть содержательный ответ на «зачем нужен генератор, если есть итератор»: не только краткость записи, но и управляемая двусторонняя связь.

    Итератор (и генератор) одноразовый: после исчерпания повторный обход даёт пустоту. Классическая ошибка — сохранить zip(a, b) или map(f, xs) в переменную и пройти по ней дважды; во второй раз результат пуст. Если нужен многократный обход, материализуйте в список или сделайте объект, чей __iter__ возвращает новый итератор при каждом вызове.

    У итератора нет len() и индексации. Для взятия среза используют itertools.islice, для «заглянуть на элемент вперёд» — next(it) с сохранением значения или itertools.tee (осторожно: он буферизует).

    И частая ловушка: класс, чей __iter__ возвращает self, нельзя вложенно обходить — два вложенных цикла for разделят одну позицию. Правильный паттерн для коллекции — __iter__, возвращающий свежий объект-итератор.

  26. Примеры итераторов и генераторов

    Есть три уровня, и на собеседовании полезно показать все три — от самого явного к самому идиоматичному.

    1. Итератор «руками». Класс реализует протокол итератора: __iter__ возвращает сам объект, __next__ отдаёт следующий элемент и бросает StopIteration, когда элементы кончились. Именно это исполняет цикл for под капотом.

    2. Генератор через yield. Функция с yield при вызове не выполняется, а возвращает объект-генератор. Каждый next() исполняет тело до следующего yield и замораживает состояние — локальные переменные, позицию исполнения. StopIteration возбуждается автоматически при выходе из функции. Это те же 15 строк класса, записанные в три.

    3. Генераторное выражение. Синтаксис списочного включения в круглых скобках: ничего не вычисляется заранее, элементы производятся по требованию.

    Ключевое отличие от списка — ленивость и память: генератор хранит только текущее состояние, а не все элементы, поэтому им можно обрабатывать поток любого размера. Подробнее — итераторы и генераторы.

    # 1. Итератор вручную class Counter: def __init__(self, n): self.i, self.n = 0, n def __iter__(self): return self def __next__(self): if self.i >= self.n: raise StopIteration self.i += 1 return self.i print(list(Counter(3))) # [1, 2, 3] # 2. Генератор через yield — то же самое def counter(n): for i in range(1, n + 1): yield i print(list(counter(3))) # [1, 2, 3] # 3. Генераторное выражение gen = (i * i for i in range(5)) print(next(gen), next(gen)) # 0 1

    Именно ленивость делает генераторы рабочим инструментом, а не синтаксическим украшением. Конвейер из генераторов обрабатывает файл в сотни гигабайт при постоянном потреблении памяти — данные текут через него по одной строке:

    def read_lines(path): with open(path) as f: for line in f: # файловый объект сам по себе итератор yield line.rstrip("\n") def parse(lines): for line in lines: if line and not line.startswith("#"): yield line.split("\t") def only_positive(rows): for row in rows: if float(row[2]) > 0: yield row for row in only_positive(parse(read_lines("huge.tsv"))): ... # ни на одном шаге в памяти нет всего файла

    Такой же принцип лежит в основе torch.utils.data.IterableDataset и потоковых режимов Hugging Face datasets.

    Генератор одноразовый: после полного прохода он исчерпан, повторный for по нему не даст ничего. Список можно обходить сколько угодно раз. Это ловушка при отладке — напечатали list(gen), а следующий цикл получил пустоту.

    У генератора нет len() и нет индексации: gen[3] — TypeError. Если нужен $k$-й элемент, берут itertools.islice.

    yield from subgen делегирует другому генератору (и корректно пробрасывает значения и исключения), а gen.send(value), gen.throw() и gen.close() превращают генератор в корутину — исторически именно на этом механизме были построены корутины до появления async/await.

  27. Что такое вложенный декоратор и зачем он нужен?

    «Вложенный декоратор» (он же декоратор с аргументами) — это функция, которая принимает параметры и возвращает декоратор. То есть добавляется ещё один уровень вложенности по сравнению с обычным декоратором.

    Разница видна в синтаксисе применения:

    • Обычный декоратор: @log — здесь log получает функцию и возвращает обёртку. Один уровень.
    • Декоратор с аргументами: @repeat(3) — сначала вызывается repeat(3), он возвращает декоратор, и уже тот применяется к функции. Три уровня: repeat → decorator → wrapper.

    Зачем это нужно: параметризовать поведение обёртки. Число повторов, таймаут, уровень логирования, TTL кэша, требуемая роль пользователя, имя метрики — всё это параметры, которые хочется задавать в точке применения, а не хардкодить в декораторе.

    Отдельно: термином «вложенные декораторы» иногда называют стек декораторов — несколько подряд над одной функцией. Они применяются снизу вверх: при @a над @b над def f получится a(b(f)). Подробнее — вложенные декораторы и декораторы.

    import functools, time def repeat(n): # 1: принимает параметр def decorator(func): # 2: принимает функцию @functools.wraps(func) # сохраняет __name__, __doc__, сигнатуру def wrapper(*args, **kwargs): # 3: подменяет вызов for _ in range(n): result = func(*args, **kwargs) return result return wrapper return decorator @repeat(3) def hi(name): print("hi", name) hi("Ann") # напечатает трижды print(hi.__name__) # 'hi' — благодаря functools.wraps

    Самый частый реальный случай — параметризованный повтор при сетевой ошибке. Обратите внимание, что все настройки живут в замыкании и не засоряют сигнатуру самой функции:

    def retry(attempts=3, delay=1.0, exceptions=(Exception,)): def decorator(func): @functools.wraps(func) def wrapper(*args, **kwargs): for i in range(attempts): try: return func(*args, **kwargs) except exceptions: if i == attempts - 1: raise time.sleep(delay * 2 ** i) return wrapper return decorator @retry(attempts=5, delay=0.5, exceptions=(TimeoutError,)) def fetch(url): ...

    Тот же приём — за декораторами @app.route("/predict") во Flask, @pytest.mark.parametrize(...), @lru_cache(maxsize=128), @task(retries=3) в оркестраторах.

    Забыть functools.wraps. Без него обёртка «съедает» __name__, __doc__, аннотации и __wrapped__. Ломаются help(), отладка, автодокументация, а фреймворки вроде FastAPI и pytest, читающие сигнатуру, начинают вести себя неправильно.

    Перепутать @repeat и @repeat(). Если декоратор написан с параметрами, применять его без скобок нельзя: @repeat передаст саму функцию в качестве n, и ошибка вылезет далеко от места причины. Универсальный декоратор, работающий и так и так, пишут через проверку if func is None плюс functools.partial — но проще завести чёткое соглашение.

    Порядок в стеке. @timing над @cache и @cache над @timing дают разный результат: в первом случае измеряется в том числе попадание в кэш, во втором — только реальные вычисления. Для декораторов авторизации и логирования порядок тоже критичен.

    Состояние в замыкании общее для всех вызовов. Если внутри decorator завести счётчик, он будет один на функцию, а не на вызов — иногда это то, что нужно, иногда источник гонок в многопоточном коде.

  28. Зачем нужны абстрактные классы?

    Абстрактный класс — базовый класс, который задаёт контракт: список методов, обязательных для всех наследников, но не реализует их (или реализует лишь частично). В Python он делается через модуль abc: класс наследуется от ABC, а обязательные методы помечаются декоратором @abstractmethod.

    Ключевое свойство: класс с хотя бы одним нереализованным абстрактным методом нельзя инстанцировать — попытка создать объект падает с TypeError: Can't instantiate abstract class ... with abstract method area. Ошибка возникает в момент создания объекта, а не когда до недостающего метода дойдёт исполнение, — то есть проблема обнаруживается раньше и в понятном месте.

    Зачем это нужно на практике: когда в проекте есть несколько взаимозаменяемых реализаций одной идеи (несколько источников данных, несколько бэкендов хранилища, несколько стратегий предобработки), абстрактный класс фиксирует общий интерфейс в одном месте. Новый разработчик, добавляя реализацию, сразу видит, что обязан реализовать, а вызывающий код может работать с любой реализацией, не зная её конкретного типа. Подробнее — абстрактные классы (abc) и принципы ООП.

    from abc import ABC, abstractmethod class Shape(ABC): @abstractmethod def area(self) -> float: ... class Circle(Shape): def __init__(self, r): self.r = r def area(self) -> float: return 3.14159 * self.r ** 2 # Shape() # TypeError: Can't instantiate abstract class Shape print(Circle(2).area()) # 12.56636

    ABC — это номинальная типизация: наследник обязан явно унаследоваться от базового класса. typing.Protocol — структурная («утиная»): подходит любой класс с нужными методами, наследование не требуется, а проверка выполняется статически (mypy), а не в рантайме.

    Практическое правило: ABC берут, когда реализации пишутся внутри вашего проекта и есть общий код, который хочется положить в базовый класс. Protocol — когда нужно описать интерфейс для чужих классов, которые вы не контролируете (например, «объект, у которого есть .predict()»), или когда не хочется навязывать иерархию наследования.

    @abstractmethod работает только в связке с метаклассом ABCMeta — то есть при наследовании от ABC (или явном metaclass=ABCMeta). Если просто написать декоратор в обычном классе, он не даст никакого эффекта: объект создастся, и метод вернёт None.

    Второе: @abstractmethod должен быть самым нижним декоратором. Правильный порядок — @property (или @classmethod, @staticmethod) сверху, @abstractmethod под ним; наоборот работать не будет.

    Третье: абстрактный класс может иметь реализацию по умолчанию и вызываться через super(). Утверждение «абстрактный метод обязан быть пустым» — распространённое заблуждение.

  29. Зачем нужны dataclass и Pydantic BaseModel?

    Оба инструмента избавляют от шаблонного кода при описании «класса данных», но решают разные задачи.

    @dataclass (stdlib) по аннотациям полей генерирует __init__, __repr__, __eq__, при order=True — операторы сравнения, при frozen=True — неизменяемость и __hash__. Аннотации типов при этом не проверяются: UserDC("Ann", "30") спокойно создаст объект со строкой в поле age: int. Типы здесь — контракт для разработчика и статического анализатора (mypy), а не для рантайма.

    pydantic.BaseModel делает то же самое плюс валидацию и приведение типов во время выполнения: UserPM(name="Ann", age="30") вернёт объект с age=30 (int), а age="abc" бросит ValidationError с точным указанием поля и причины. Сверху — сериализация (model_dump(), model_dump_json()), разбор вложенных структур, кастомные валидаторы (@field_validator), генерация JSON Schema и настройки через Field(ge=0, max_length=64).

    Правило выбора: dataclass — для внутренних структур, где данные вы формируете сами и уже уверены в их типах (конфиги в коде, промежуточные записи, ключи кэша). BaseModel — на границе доверия: HTTP-запросы, ответы внешних API, YAML/JSON-конфиги, сообщения из очереди, аргументы CLI. Подробнее — @dataclass и Pydantic BaseModel.

    from dataclasses import dataclass from pydantic import BaseModel, Field, ValidationError @dataclass class UserDC: name: str age: int class UserPM(BaseModel): name: str age: int = Field(ge=0, le=150) print(UserDC("Ann", "30")) # UserDC(name='Ann', age='30') — типы не проверены print(UserPM(name="Ann", age="30")) # name='Ann' age=30 — строка приведена к int try: UserPM(name="Ann", age=-5) except ValidationError as e: print(e) # Input should be greater than or equal to 0

    Создание объекта Pydantic дороже, чем dataclass: даже в Pydantic v2, где ядро переписано на Rust, это десятки-сотни наносекунд против единиц. На границе сервиса это ничто по сравнению с сетью. А вот внутри горячего цикла — например, если оборачивать в модель каждую строку датасета на миллион записей — валидация станет заметной статьёй расхода. Там берут dataclass со __slots__ либо NamedTuple.

    Отсюда практический паттерн: валидировать один раз на входе, дальше внутри системы передавать уже проверенные объекты и не перепроверять их на каждом слое.

    Промежуточный вариант — pydantic.dataclasses.dataclass: синтаксис dataclass с валидацией Pydantic, удобно когда не хочется менять существующие сигнатуры.

    Изменяемое значение по умолчанию в dataclass запрещено: tags: list = [] бросит ValueError ещё при определении класса. Нужно field(default_factory=list) — это защита ровно от той же проблемы, что с mutable default argument.

    Pydantic v1 и v2 несовместимы по API: .dict() → .model_dump(), .parse_obj() → .model_validate(), @validator → @field_validator, class Config → model_config. На собеседовании стоит уточнить версию, а в проекте — не смешивать их.

    По умолчанию Pydantic v2 в «умном» режиме приводит "30" к 30, но не приведёт "abc". Если нужна строгая проверка без приведения, задаётся model_config = ConfigDict(strict=True). Также по умолчанию лишние поля во входных данных молча игнорируются — если важно ловить опечатки в конфигах, ставьте extra="forbid".

  30. Как эффективно скачать 100 тысяч файлов по URL?

    Задача I/O-bound: почти всё время процесс ждёт сеть, а не считает. Значит, нужен не пул процессов, а конкурентность — асинхронный HTTP-клиент (aiohttp, httpx) либо пул потоков, если библиотека синхронная. Подробнее про выбор — сравнение подходов к конкурентности.

    Каркас решения:

    1. Одна сессия на весь прогон. aiohttp.ClientSession переиспользует TCP-соединения и TLS-хендшейки; создание клиента на каждый запрос — самая частая причина, почему «асинхронно» получается медленнее синхронного варианта.
    2. Ограниченная конкурентность. asyncio.Semaphore(N) или фиксированный пул воркеров. Запустить 100 000 корутин разом нельзя: кончатся файловые дескрипторы и память, а сервер начнёт отдавать 429.
    3. Потоковая подача URL и потоковая запись. URL читаются из файла построчно, тело ответа пишется на диск чанками (async for chunk in resp.content.iter_chunked(...)), а не через await resp.read() — иначе большие файлы съедят память.
    4. Таймауты, retry, backoff. У каждого запроса ClientTimeout (отдельно на соединение и на чтение); повтор только для сетевых ошибок и 5xx/429, с экспоненциальной задержкой и jitter.
    5. Идемпотентное возобновление. Имя файла детерминированно выводится из URL (например, хеш), уже скачанные пропускаются. Прогон на 100 тысяч файлов обязательно упадёт хотя бы раз — он должен продолжаться, а не начинаться заново.
    6. Проверка результата. Статус-код, Content-Length/размер на диске, при наличии — контрольная сумма. Запись сначала во временный файл и os.replace в конце, чтобы не оставлять обрезанных файлов.
    import asyncio, aiohttp, hashlib, os from pathlib import Path async def fetch_one(session, sem, url, out_dir: Path): name = hashlib.sha256(url.encode()).hexdigest() dst = out_dir / name if dst.exists(): # идемпотентное возобновление return async with sem: # ограничение конкурентности for attempt in range(4): try: async with session.get(url) as r: r.raise_for_status() tmp = dst.with_suffix(".part") with tmp.open("wb") as f: async for chunk in r.content.iter_chunked(1 << 16): f.write(chunk) os.replace(tmp, dst) # атомарная публикация return except (aiohttp.ClientError, asyncio.TimeoutError): await asyncio.sleep(2 ** attempt + os.urandom(1)[0] / 255) async def main(urls, out_dir=Path("data"), limit=64): out_dir.mkdir(exist_ok=True) sem = asyncio.Semaphore(limit) timeout = aiohttp.ClientTimeout(total=None, sock_connect=10, sock_read=60) conn = aiohttp.TCPConnector(limit=limit, ttl_dns_cache=300) async with aiohttp.ClientSession(timeout=timeout, connector=conn) as s: await asyncio.gather(*(fetch_one(s, sem, u, out_dir) for u in urls))

    Оптимальное limit не выводится из формулы — оно упирается в самое узкое место: лимиты сервера (429, бан по IP), полосу канала, число файловых дескрипторов (ulimit -n), IOPS диска и — на большом числе мелких файлов — скорость DNS-резолвинга.

    Практический подход: замерить пропускную способность на 1000 URL при limit 16, 64, 256 и взять точку, после которой скорость перестаёт расти, а доля ошибок начинает. Обычно это десятки, а не тысячи. Для мелких файлов узким местом часто оказывается создание файлов на диске, а не сеть, — тогда выгоднее складывать результаты в один архив или в формат вроде WebDataset, чем в 100 тысяч отдельных файлов.

    Скачивание 100 тысяч файлов с одного домена без ограничения скорости — это фактически нагрузочный тест чужого сервиса. Нужен rate limit (запросов в секунду), уважение к Retry-After в ответе 429, осмысленный User-Agent и проверка robots.txt, если это публичный веб.

    И обязательно логирование по каждому URL: статус, размер, число попыток. Без него после прогона невозможно ответить на вопрос «а всё ли скачалось» — а он всегда возникает. Прогресс удобно показывать через tqdm, но считать надо завершённые задачи, а не запущенные.

  31. Как защищать batch inference сервис от перегрузки?

    Базовая идея: сервис должен отказывать быстро и предсказуемо, а не накапливать работу, которую всё равно не успеет сделать. Слои защиты выстраиваются от входа к вычислениям.

    Bounded queue. Очередь входящих запросов имеет фиксированный максимум. Когда он достигнут, новый запрос получает 429 Too Many Requests или 503 с Retry-After — сразу, а не через минуту ожидания. Безразмерная очередь превращает перегрузку в рост latency и в конечном счёте в OOM.

    Ограничение конкурентности и параметров батча. Одновременно обрабатывается не более $N$ батчей; у динамического батчинга задаются max_batch_size и max_wait_ms — иначе под нагрузкой батчи разрастаются и p99 взлетает.

    Дедлайны. Запрос несёт бюджет времени. Перед постановкой в очередь и перед запуском инференса проверяется, не истёк ли он: считать батч, результат которого клиент уже не ждёт, — чистая потеря GPU.

    Backpressure наружу. Если сервис читает из очереди (Kafka, SQS), он просто перестаёт забирать новые сообщения — нагрузка копится в брокере, который для этого и предназначен. Для синхронного HTTP аналог — rate limit на уровне gateway.

    Timeouts, retry с jitter, circuit breaker на вызовах зависимостей (feature store, БД), чтобы медленная зависимость не выела все воркеры.

    Приоритеты и graceful degradation. Пользовательский трафик обслуживается раньше фонового; при перегрузке допустим упрощённый ответ — кэш, лёгкая модель, дефолтное значение.

    Autoscaling по правильной метрике. Масштабировать по глубине очереди и p95 latency, а не по CPU: GPU-сервис может быть загружен на 100 % при 20 % CPU. И помнить, что GPU-реплика поднимается минуты, поэтому load shedding — не запасной вариант, а обязательный.

    Минимальный набор дашбордов: p50/p95/p99 latency отдельно для времени в очереди и времени инференса (иначе непонятно, где узкое место), throughput в запросах и в примерах в секунду, текущая длина очереди и возраст самого старого элемента, средний фактический размер батча, доля отклонённых запросов, GPU utilization и потребление видеопамяти, число OOM и рестартов пода.

    Возраст головы очереди — самая ранняя метрика перегрузки: он начинает расти задолго до того, как вырастет p99, и до того, как что-то упадёт.

    Повторы увеличивают нагрузку ровно тогда, когда система уже не справляется, — это положительная обратная связь. Особенно опасны retry на нескольких уровнях сразу: клиент повторяет 3 раза, gateway 3 раза, сервис 3 раза — до 27 запросов на один пользовательский.

    Правила: retry делается на одном уровне, с ограниченным бюджетом (не более 10 % от основного трафика), с экспоненциальной задержкой и обязательным jitter, и никогда — для запроса, у которого уже истёк общий дедлайн. Ответ 429 от перегруженного сервиса нужно уважать, а не ретраить немедленно.

  32. Как передавать секреты в Docker и Kubernetes?

    Главный принцип: секрет попадает в контейнер в момент запуска, а не в момент сборки, и никогда не оказывается внутри образа или в git.

    Куда нельзя. В Dockerfile через ENV или ARG — значение сохраняется в слое образа и видно любому, кто выполнит docker history. В COPY .env . — файл остаётся в слое, даже если следующей строкой сделать RUN rm .env: слои неизменяемы, удаление в следующем слое лишь прячет файл. В git — включая приватные репозитории, потому что история хранится вечно и разлетается по форкам и CI-кэшам. Подробнее про слои образа и секреты в Docker.

    Как можно.

    • Локально и в Compose: docker run --env-file, env_file: или Docker secrets (файл монтируется в /run/secrets/...).
    • На этапе сборки, если секрет действительно нужен (например, токен приватного PyPI): BuildKit-механизм RUN --mount=type=secret,id=pip — секрет доступен только внутри одной инструкции RUN и в слой не попадает.
    • В Kubernetes: объект Secret, смонтированный как файл (том), а не как переменная окружения; либо CSI Secrets Store Driver / External Secrets Operator, которые тянут значения напрямую из внешнего менеджера.
    • В проде: источник истины — secret manager (Vault, AWS Secrets Manager, GCP Secret Manager), а Kubernetes-объекты синхронизируются с ним.

    Что требуется вокруг. Secret в Kubernetes хранит значение в base64, а не в шифре — это кодирование, не защита; нужно включать encryption at rest в etcd. Плюс RBAC (кто вообще может читать секреты в namespace), ротация без пересборки образа, аудит доступа и запрет логировать конфиг целиком.

    Переменные окружения удобны, но протекают: они видны в /proc/<pid>/environ любому процессу с теми же правами, попадают в дампы падений, в вывод docker inspect и в отладочные хендлеры, печатающие os.environ. Дочерние процессы наследуют их автоматически.

    Смонтированный файл лучше по трём причинам: права доступа задаются на уровне файловой системы (0400 и нужный runAsUser), значение не наследуется дочерними процессами и — главное — Kubernetes обновляет содержимое тома при изменении Secret, тогда как переменная окружения фиксируется на момент старта пода. Поэтому приложение, умеющее перечитывать файл, поддерживает ротацию без рестарта.

    .dockerignore — обязателен: без него COPY . . затянет в образ .env, .git, ~/.aws, kaggle.json и локальные чекпоинты. См. .dockerignore.

    Второе: контейнер не должен работать от root. Секрет с правами 0400, принадлежащий root, читается любым процессом внутри контейнера, если тот тоже root; см. запуск не от root.

    Третье, специфичное для ML: токены Hugging Face, W&B и ключи облачных хранилищ часто оседают в артефактах экспериментов — в логах wandb, в сохранённом config.yaml, в ноутбуках. Проверять надо не только образ, но и то, что вы публикуете как результат обучения. Полезно поставить сканер (gitleaks, trufflehog) в CI.

  33. Когда доступ к dict в Python превращается из $O(1)$ в $O(n)$?

    $O(1)$ у dict — это средняя амортизированная оценка, а не гарантия. Она держится на двух допущениях: хеши распределены равномерно и таблица заполнена не более чем на 2/3. Когда допущения ломаются, сложность деградирует.

    Реальные сценарии деградации:

    Плохой пользовательский __hash__. Если метод возвращает константу или значение с малым числом различных исходов (hash(self.status) для поля из трёх значений), все ключи выстраиваются в одну последовательность проб. Поиск превращается в линейный перебор, причём с вызовом __eq__ на каждом шаге — то есть $O(n)$ с большой константой.

    Дорогой __eq__. Даже при нормальном распределении хешей: если сравнение ключей само по себе стоит $O(k)$ (длинные строки с общим префиксом, вложенные кортежи), итоговая стоимость операции умножается на $k$.

    Resize. При заполнении примерно на 2/3 таблица перестраивается и все элементы перехешируются — эта конкретная вставка стоит $O(n)$. Амортизированно это по-прежнему $O(1)$, потому что размер удваивается, но отдельный вызов может «затормозить», и в latency-чувствительном сервисе это видно в хвосте распределения.

    Целенаправленная атака (hash flooding). Злоумышленник подбирает ключи с одинаковым хешем и отправляет их в сервис, который складывает их в словарь, — получается $O(n^2)$ на обработке запроса. Именно от этого защищает hash randomization для строк и bytes: соль генерируется при старте процесса, поэтому заранее подобрать коллизии нельзя.

    Для встроенных типов на практике проблема почти не встречается; она приходит вместе с собственными классами. Подробнее — хеш-таблица и алгоритмическая сложность.

    class BadKey: def __init__(self, v): self.v = v def __hash__(self): return 42 # все ключи в одну цепочку проб def __eq__(self, o): return self.v == o.v d = {BadKey(i): i for i in range(20_000)} # вставка стала квадратичной

    Простой диагностический приём: посчитать len({hash(k) for k in keys}) и сравнить с len(keys). Если различных хешей ощутимо меньше, чем ключей, — распределение плохое.

    Второй приём — сравнить время на одном и том же наборе, обернув ключи в tuple из тех же полей. Если словарь с кортежами работает быстро, а с вашим классом медленно, виноват __hash__.

    Правильная реализация почти всегда одна и та же: def __hash__(self): return hash((self.a, self.b)) по тому же набору полей, что и в __eq__. Хеш кортежа в CPython качественный, изобретать своё смешивание битов не нужно.

    «Коллизии в dict разрешаются цепочками» — нет, в CPython это открытая адресация с псевдослучайной последовательностью проб, использующей все биты хеша.

    «Из-за коллизий dict часто работает за $O(n)$» — нет, для встроенных типов это исключительная ситуация; амортизированное $O(1)$ выполняется на практике очень надёжно.

    И обратное заблуждение: «in для списка тоже быстрый». x in list — всегда $O(n)$; замена списка на set/dict в проверке вхождения внутри цикла — самая частая и самая дешёвая оптимизация в Python-коде.

  34. Контейнер остановили или удалили: потеряются ли код и данные?

    Ответ зависит от того, что именно произошло, и от того, где лежат данные.

    Контейнер — это образ (неизменяемые слои, read-only) плюс тонкий writable-слой поверх них. Всё, что процесс внутри записал в файловую систему контейнера, попадает в этот writable-слой. См. слои образа.

    • docker stop / docker start. Останавливается только процесс. Writable-слой остаётся на диске, после start все файлы на месте. Теряется лишь то, что жило в оперативной памяти: кэши в процессе, незаписанные буферы, состояние соединений.
    • docker rm (или docker run --rm). Writable-слой удаляется вместе с контейнером — всё, что было записано внутрь и не вынесено наружу, исчезает безвозвратно.
    • Код из образа не теряется никогда. Он лежит в read-only слоях образа; docker run из того же образа поднимет новый контейнер с тем же кодом. Именно поэтому контейнеры считают одноразовыми (cattle, а не pets).

    Отсюда правило: всё, что должно пережить контейнер, хранится вне его файловой системы — в volume, bind mount или внешнем хранилище (S3, БД). Volume существует независимо от жизненного цикла контейнера и не удаляется вместе с ним (для удаления нужен docker volume rm или docker rm -v). Bind mount — это просто каталог хоста, с ним ничего не случится в принципе.

    docker stop app && docker start app # данные writable-слоя на месте docker rm app # writable-слой удалён docker run -v mydata:/app/data image # named volume: переживёт контейнер docker run -v $(pwd)/data:/app/data i # bind mount: каталог хоста docker run --rm image # контейнер удалится сразу после выхода

    Writable-слой реализован через copy-on-write (overlay2): изменение одного байта в файле из образа копирует весь файл в верхний слой. Для больших файлов — чекпоинтов, датасетов, индексов — это дорого и по времени, и по диску.

    Дальше: этот слой не переносится между хостами, не резервируется штатными средствами и не масштабируется — при трёх репликах сервиса будет три расходящихся состояния. В Kubernetes всё то же самое, но острее: под может быть пересоздан планировщиком в любой момент, и его файловая система исчезнет вместе с ним. Данные там живут в PersistentVolume или во внешнем хранилище.

    Практическое следствие для ML: датасеты, чекпоинты, кэши весов (HF_HOME, TORCH_HOME) и логи выносят в volume или в объектное хранилище. Иначе каждый рестарт заново скачивает несколько гигабайт весов.

    Удалённые контейнеры не всегда освобождают место: остаются образы, dangling-слои, тома и кэш сборки. На машине для обучения это регулярно приводит к «No space left on device» посреди эпохи.

    Диагностика — docker system df; уборка — docker system prune (безопасно) и docker system prune -a --volumes (удалит и неиспользуемые тома — перед запуском убедитесь, что в них нет нужных данных). Отдельно стоит помнить, что docker builder prune чистит кэш сборки, который на ML-образах легко занимает десятки гигабайт.

  35. Как отсортировать файл на 100 ГБ из символов ограниченного алфавита?

    Ключ к задаче — ограниченный алфавит. Как только это сказано, сортировка сравнениями не нужна вовсе: отсортированный результат полностью определяется тем, сколько раз встретился каждый символ.

    Алгоритм — counting sort в два прохода:

    1. Читаем файл чанками (например, по 8–64 МБ) и накапливаем счётчики в массиве размера $|\Sigma|$. Ни одна часть файла в памяти не задерживается.
    2. Пишем выходной файл: для каждого символа в порядке возрастания выводим его count[c] раз, тоже блоками.

    Сложность: время $O(n + |\Sigma|)$, дополнительная память $O(|\Sigma|)$ — то есть константа, не зависящая от 100 ГБ. Для сравнения, внешняя сортировка слиянием дала бы $O(n \log n)$ сравнений плюс запись и чтение промежуточных отрезков — несколько лишних проходов по 100 ГБ диска.

    Практически всё упирается в I/O: 100 ГБ читаются один раз и 100 ГБ пишутся один раз, поэтому нижняя граница времени — это скорость диска. Оптимизировать имеет смысл размер буфера и, при чтении по байтам, — использование bytes.count() или collections.Counter над bytes, а не цикл на чистом Python.

    from collections import Counter def counting_sort_file(src: str, dst: str, chunk: int = 1 << 24) -> None: counts = Counter() with open(src, "rb") as f: # проход 1: только счётчики while block := f.read(chunk): counts.update(block) # C-уровень, без Python-цикла with open(dst, "wb") as out: # проход 2: запись блоками for code in sorted(counts): left = counts[code] piece = bytes([code]) * min(left, chunk) while left > 0: n = min(left, chunk) out.write(piece[:n]) left -= n

    Counting sort работает не только с символами. Он применим всегда, когда ключ — целое число из небольшого известного диапазона: возрасты, оценки от 1 до 5, дни года, идентификаторы категорий, квантованные значения.

    Два родственных приёма из того же семейства «сортировок без сравнений»: bucket sort (разложить по корзинам по старшим разрядам, отсортировать каждую отдельно — так устроена и внешняя сортировка по ключу) и radix sort (последовательные counting sort по разрядам, $O(d \cdot n)$ для $d$-разрядных ключей).

    Если бы алфавит был не ограничен — например, файл из строк переменной длины, — правильным ответом стала бы внешняя сортировка слиянием: читаем куски, помещающиеся в RAM, сортируем их в памяти, пишем на диск, затем сливаем $k$ отсортированных потоков через heapq.merge. Стоит упомянуть это как альтернативу: интервьюер обычно проверяет, понимаете ли вы, почему в данном случае она не нужна.

    Первое, что стоит спросить вслух: «символы — это байты или Unicode-кодпоинты?». Для байтов $|\Sigma| = 256$ и всё тривиально; для UTF-8 придётся декодировать чанки с учётом того, что символ может быть разрезан границей блока (лечится io.TextIOWrapper или codecs.iterdecode).

    Второе: не пытайтесь строить строку в памяти. "".join(...) на 100 ГБ — мгновенный OOM; выход пишется потоково.

    Третье, про «сортировку строк» и «сортировку символов»: если требуется отсортировать строки файла, а не символы, задача другая — это внешняя сортировка слиянием. Уточнить постановку до начала решения здесь ценится выше, чем скорость кодирования.

  36. Какие delivery semantics есть в Kafka?

    Три уровня гарантий доставки, и различаются они, по сути, моментом фиксации offset относительно обработки сообщения.

    At-most-once («не более одного раза»). Consumer коммитит offset до обработки. Если он упадёт между коммитом и обработкой, сообщение потеряно — повторно оно не придёт. Дублей не бывает. Уместно там, где потеря дешевле дубля: метрики, телеметрия, некритичные логи.

    At-least-once («не менее одного раза»). Offset коммитится после успешной обработки. Падение между обработкой и коммитом приводит к повторной доставке — возможны дубли, но потерь нет. Это режим по умолчанию и правильный выбор для большинства задач.

    Exactly-once. Kafka обеспечивает его через idempotent producer (enable.idempotence=true: брокер отбрасывает повторы по producer ID и sequence number) и транзакции, которые атомарно объединяют запись в топики и коммит offset'ов. Consumer читает с isolation.level=read_committed. Важное ограничение: гарантия действует внутри Kafka — в схеме «прочитал из топика → обработал → записал в топик».

    Подробнее — гарантии доставки и retention и основные понятия Kafka.

    Как только результат обработки уходит наружу — в PostgreSQL, в S3, в HTTP-вызов, — транзакция Kafka его не покрывает: нет распределённого коммита между Kafka и чужой системой. Между записью в БД и коммитом offset остаётся окно, в котором падение даёт повтор.

    Поэтому «exactly once» на практике почти всегда строится как at-least-once + идемпотентность на стороне потребителя:

    • у каждого события есть устойчивый event_id (или ключ + offset), по которому запись дедуплицируется;
    • вместо INSERT используется UPSERT / INSERT ... ON CONFLICT DO NOTHING;
    • либо применяется transactional outbox: обработка и запись offset попадают в одну транзакцию БД, и она же становится источником истины;
    • либо операция по природе идемпотентна (перезапись значения, SET, а не INCREMENT).

    Формулировка, которую ждут на собеседовании: «effectively once = at-least-once доставка плюс идемпотентная обработка».

    Автокоммит. enable.auto.commit=true коммитит offset по таймеру, независимо от того, обработано сообщение или нет. Это не at-least-once и не at-most-once, а «как повезёт». Для контролируемых гарантий его выключают и коммитят вручную.

    Настройки producer. acks=1 (по умолчанию в старых клиентах) подтверждает запись, как только её принял лидер партиции; при падении лидера до репликации данные теряются. Для «без потерь» нужны acks=all, min.insync.replicas >= 2 и retries вместе с включённой идемпотентностью — иначе повторы producer'а сами создадут дубли и могут переставить порядок.

    Ребаланс. Долгая обработка сообщения дольше max.poll.interval.ms приводит к исключению consumer'а из группы, ребалансу и повторной выдаче тех же сообщений другому инстансу — типичный источник «внезапных» дублей в ML-пайплайнах, где инференс на батче занимает минуты. Лечится уменьшением max.poll.records, вынесением тяжёлой работы в отдельный пул и увеличением интервала.

    Порядок. Kafka гарантирует порядок только внутри партиции. Если для сущности важна последовательность событий, все её события должны идти с одним ключом.

  37. Почему нельзя использовать изменяемый объект как значение по умолчанию в функции?

    Потому что значения по умолчанию вычисляются один раз — в момент определения функции, а не при каждом вызове. Результат сохраняется в атрибуте func.__defaults__ и переиспользуется всеми вызовами, где аргумент не передан явно.

    Для неизменяемых значений (0, None, "abc") это незаметно. Но если по умолчанию стоит список или словарь, все вызовы работают с одним и тем же объектом, и мутации накапливаются между ними: функция «помнит» предыдущие вызовы, чего никто не ожидает.

    Стандартное решение — часовой None: в качестве значения по умолчанию ставится None, а новый объект создаётся внутри тела функции. Тогда каждый вызов получает свой контейнер.

    Проблема касается всех изменяемых объектов: list, dict, set, экземпляров классов с изменяемым состоянием, а также объектов, которые вычисляются при определении (datetime.now() в аргументе по умолчанию зафиксируется на момент импорта модуля — ещё одна разновидность той же ошибки).

    def add_item(x, items=[]): # ловушка items.append(x) return items print(add_item(1)) # [1] print(add_item(2)) # [1, 2] — а ожидали [2] print(add_item.__defaults__) # ([1, 2],) — объект живёт в самой функции
    def add_item(x, items=None): # правильный паттерн if items is None: items = [] items.append(x) return items print(add_item(1)) # [1] print(add_item(2)) # [2]

    Это прямое следствие того, что def — исполняемая инструкция: при её выполнении создаётся объект функции, и выражения из сигнатуры вычисляются тут же. Альтернатива (вычислять умолчания при каждом вызове, как в Ruby) стоила бы производительности и породила бы вопрос, в каком пространстве имён их вычислять.

    У поведения есть и полезная сторона — им намеренно пользуются для кэша, привязанного к функции, и для «замораживания» значения из замыкания:

    def fib(n, _cache={0: 0, 1: 1}): # мемоизация без внешнего состояния if n not in _cache: _cache[n] = fib(n - 1) + fib(n - 2) return _cache[n] fns = [lambda x, k=k: x * k for k in range(3)] # k фиксируется, а не берётся из замыкания

    Первый приём сегодня лучше писать через functools.lru_cache, но понимать механику всё равно нужно — на собеседовании про неё спрашивают.

    Проверять надо именно if items is None, а не if not items: пустой список, переданный явно, — валидный аргумент, и not [] истинно, так что второй вариант молча подменит переданный объект новым. См. None: почему проверять через is.

    В @dataclass эта ошибка запрещена на уровне языка: tags: list = [] бросит ValueError при определении класса, нужно field(default_factory=list).

    Линтеры ловят проблему автоматически: правило B006 в flake8-bugbear и ruff (mutable-argument-default). Включить его — дешевле, чем полагаться на внимательность; см. линтеры.

    И отдельная разновидность: def f(ts=datetime.now()) — время зафиксируется на момент импорта. Нужен либо None-часовой, либо default_factory.

  38. Чем отличается shallow copy от deep copy в Python?

    Shallow copy (copy.copy, list(x), x[:], dict(x), x.copy()) создаёт новый внешний контейнер, но кладёт в него те же самые ссылки на вложенные объекты. Внешний уровень независим, внутренние — общие.

    Deep copy (copy.deepcopy) рекурсивно копирует и контейнер, и всё, на что он ссылается, на любую глубину. Результат полностью независим от оригинала.

    Разница видна только на вложенных изменяемых объектах. Для плоского списка чисел или строк оба варианта дают одно и то же, потому что копировать неизменяемые элементы бессмысленно — deepcopy их и не копирует, а переиспользует.

    Правило выбора: shallow copy достаточно, когда вложенные объекты неизменяемы или вы точно не собираетесь их менять; deepcopy нужен, когда копия должна жить своей жизнью, — например, снимок конфига перед экспериментом, откат состояния, изоляция аргумента от вызывающего кода.

    См. копирование изменяемых объектов: copy и deepcopy.

    import copy a = [[1, 2], [3, 4]] b = copy.copy(a) # shallow: b — новый список, но элементы те же объекты c = copy.deepcopy(a) # deep: всё скопировано a[0].append(99) print(b) # [[1, 2, 99], [3, 4]] — изменение "просочилось" print(c) # [[1, 2], [3, 4]] a.append([5]) print(len(b), len(c)) # 2 2 — внешний уровень у копий независим

    deepcopy ведёт словарь memo уже скопированных объектов по их id. Благодаря этому он корректно обрабатывает циклические ссылки (a.append(a)) и сохраняет разделяемость: если один и тот же объект встречается в структуре дважды, в копии он тоже будет одним объектом, а не двумя.

    Поведение можно настроить: класс может определить __deepcopy__(self, memo) и __copy__(self), а __reduce__ / __getstate__ влияют и на копирование, и на pickle. По умолчанию deepcopy копирует объект по __dict__, что для многих объектов бессмысленно или разрушительно:

    • открытые файлы, сокеты, соединения с БД — скопировать нельзя, будет ошибка или нерабочий дубликат;
    • блокировки (threading.Lock) — TypeError: cannot pickle '_thread.lock' object;
    • модели PyTorch на GPU — скопируются вместе с весами и займут ещё столько же видеопамяти;
    • объекты с кэшами и обратными ссылками на родителя — потянут за собой половину графа объектов приложения.

    x[:] и list(x) — это shallow copy, а не «настоящая» копия. Самая частая ошибка: скопировали список списков срезом, поменяли вложенный элемент — изменился и оригинал.

    [[0] * 3] * 3 — не матрица. Внешнее умножение размножает одну и ту же ссылку на внутренний список: m[0][0] = 1 изменит первый элемент всех трёх строк. Правильно — [[0] * 3 for _ in range(3)].

    Цена. deepcopy рекурсивен и медленный (он идёт через механику pickle-протокола); на больших структурах — секунды и удвоенная память. В горячем цикле его быть не должно.

    Альтернативы deepcopy. Часто задача решается дешевле: json.loads(json.dumps(obj)) для простых данных (быстрее, но теряет типы), pickle.loads(pickle.dumps(obj)) (быстрее deepcopy на больших однородных структурах), а лучше всего — не мутировать входные данные, тогда копия не нужна вовсе. Неизменяемые структуры (tuple, frozenset, @dataclass(frozen=True)) снимают проблему на корню.

    NumPy и pandas живут по своим правилам: arr.copy() копирует данные массива, а срез arr[1:5] — это представление, не копия; df.copy() по умолчанию делает глубокую копию, df.copy(deep=False) — поверхностную.
