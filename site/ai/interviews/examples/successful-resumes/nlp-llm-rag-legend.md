#### Проект 1 — RAG-система для операционной документации и диалогов

##### Постановка задачи и цель бизнеса

Аэропорт — это очень регламентированная среда. Там тысячи страниц операционной документации: стандарты обслуживания, инструкции по безопасности, процедуры для разных служб, регуляторные требования. Плюс постоянно накапливаются диалоги служб — транскрипции переговоров, заявки, отчёты об инцидентах.

Проблема: сотрудник не может оперативно найти нужную информацию в огромном массиве документов. Поиск по ключевым словам — неточный, читать всё вручную — долго. Нужен был интерфейс на естественном языке: задал вопрос → получил ответ из нужного документа.

##### Архитектура RAG-системы

**RAG (Retrieval-Augmented Generation)** — это подход, при котором языковая модель не отвечает «из памяти», а сначала находит релевантные фрагменты в базе знаний и генерирует ответ на их основе. Это решает проблему галлюцинаций и позволяет работать с актуальными корпоративными данными.

**Этап 1 — Индексирование документов:**

Все документы разбивались на чанки. Стратегия чанкинга была нетривиальной: для операционных инструкций важно не разрезать логические блоки. Использовал семантический чанкинг, то есть разбиение по смысловым границам, а не просто по числу токенов.

Каждый чанк преобразовывался в embedding через embedding-модель. Векторы хранились в **Qdrant**: это векторная база данных с поддержкой фильтрации, масштабирования и REST API.

**Этап 2 — Retrieval:**

1. Запрос пользователя превращался в embedding той же моделью.
2. В Qdrant выполнялся поиск по cosine similarity.
3. Возвращались top-K наиболее релевантных чанков.

Дополнительно применялся **re-ranking**: cross-encoder уточнял порядок результатов перед подачей в генерацию.

**Этап 3 — Generation:**

Найденные чанки и исходный вопрос подавались в LLM как контекст. Модель генерировала ответ строго на основе предоставленного контекста. Системный промпт явно запрещал модели отвечать на вопросы, которые не покрываются контекстом.

**Обработка диалогов:**

Помимо статических документов, система работала и с диалогами служб: транскрипции переговоров индексировались так же, что позволяло задавать вопросы по событиям, сменам и инцидентам.

##### Возможные вопросы

- **Почему Qdrant, а не FAISS?** FAISS — это библиотека: нет REST API, нет persistence «из коробки», нет удобной фильтрации по метаданным. Qdrant — полноценная база данных: API, payload-фильтры, горизонтальное масштабирование.
- **Что такое re-ranking и зачем он нужен?** Bi-encoder быстрый, но не всегда точный. Cross-encoder рассматривает пару «запрос + документ» совместно и даёт более точный score, но медленнее. Поэтому bi-encoder быстро отбирает top-50, а cross-encoder точно ранжирует top-10.
- **Что такое галлюцинации и как вы с ними боролись?** В RAG снижаем их через строгий системный промпт, citations и fallback: если retrieval не нашёл ничего релевантного, модель говорит «не нашёл информации», а не придумывает.
- **Как выбирали размер чанка?** Экспериментально. Для операционных документов оптимум был около 300–500 токенов с overlap, чтобы не разрывать логику на границах.

#### Проект 2 — LLM-агенты для анализа переговоров

##### Постановка задачи

Операционные службы ведут много переговоров: диспетчеры, операционный центр, наземные службы, безопасность. Всё это транскрибируется. Раньше аналитики вручную просматривали часы транскриптов, чтобы выявить инциденты, извлечь ключевые события и составить отчёты.

Задача: автоматизировать анализ — извлекать события, классифицировать инциденты, генерировать структурированные отчёты.

##### Архитектура агентов

Использовал **LLM-агентный подход** с tool-calling и multi-step reasoning.

**Инструменты, доступные агенту:**

1. `extract_events(text)` — извлечение событий из транскрипта: временные метки, участники, суть события.
2. `classify_incident(event)` — классификация инцидента по типу и приоритету.
3. `retrieve_context(query)` — обращение к RAG-системе для получения релевантной информации из документации.
4. `generate_report(events, classifications, context)` — генерация структурированного отчёта.

**Как работает агент:**

1. Агент получает транскрипт переговоров.
2. Вызывает `extract_events` и получает список событий.
3. Для каждого события вызывает `classify_incident`.
4. При необходимости вызывает `retrieve_context` для подтверждения классификации.
5. Вызывает `generate_report` и получает структурированный отчёт.

Оркестрация workflows реализована через **LangGraph**: он позволяет описывать пайплайн как граф состояний с явными переходами, ветвлениями и возможностью возвращаться на предыдущие шаги.

**Результат:** время ручного анализа переговоров сокращено на **60%**.

##### Возможные вопросы

- **Что такое tool-calling и чем отличается от обычного промпта?** В tool-calling модель выдаёт структурированный вызов функции, реальная функция выполняется в коде, а результат возвращается обратно в модель как часть контекста.
- **Почему LangGraph, а не просто LangChain?** LangChain удобен для линейных цепочек. LangGraph нужен, когда логика нелинейная: агент может ветвиться, возвращаться к предыдущим шагам и уточнять результат.
- **Как обеспечивали надёжность агента?** Через Pydantic-схемы, валидацию аргументов инструментов и лимиты на количество шагов, чтобы агент не зацикливался.

#### Оптимизация инференса — p95 latency < 700 мс

##### Проблема

При выходе в production latency была слишком высокой. Для операционного персонала, который использует систему в напряжённых ситуациях, это критично.

Цель: обеспечить **p95 latency < 700 мс**.

##### Что делал

**Batching:** вместо обработки каждого запроса отдельно накапливаем несколько запросов и обрабатываем их одним forward pass через модель.

**Async processing:** использовал Python asyncio и FastAPI async endpoints, чтобы параллельно обрабатывать другие запросы, пока одна задача ждёт ответа от LLM.

**Caching:**

- Embedding cache: если фрагмент документа уже был закодирован в embedding, не пересчитываем его.
- Semantic cache: если новый запрос семантически близок к уже отвеченному, возвращаем кэшированный ответ.

**Результат:** p95 latency < **700 мс** при production-нагрузке.

#### Деплой в production

Система развёрнута в **Docker**-контейнерах: embedding-сервис, inference-сервис, Qdrant, API gateway на FastAPI.

**FastAPI** выбран как inference API: поддерживает async из коробки, автогенерацию OpenAPI-документации и высокую производительность.

Интеграция с внутренними системами — через REST API.

### Университетская NLP-лаборатория

Работал NLP Engineer в исследовательской лаборатории. Основная задача — разработка мультиязычных NLP-моделей для научных и прикладных задач на английском и турецком языках.

---

#### Задачи и языковая специфика

Работал с тремя типами задач:

- **Text classification** — отнесение текста к одной или нескольким категориям.
- **Semantic similarity** — насколько два текста близки по смыслу.
- **Information extraction** — нахождение в тексте конкретных сущностей и отношений.

Мультиязычный сценарий создавал дополнительные сложности: турецкий язык агглютинативный, поэтому токенизация и обработка нетривиальны.

---

#### Модели и архитектуры

Работал с семейством BERT-моделей:

- **BERT** — двунаправленная transformer-модель, предобученная на Masked Language Modeling.
- **RoBERTa** — улучшенная версия BERT, обученная дольше, на большем корпусе и без задачи Next Sentence Prediction.
- **mBERT** — multilingual BERT, предобученный на 104 языках одновременно.

---

#### Fine-tuning и domain adaptation

**Fine-tuning** — дообучение предобученной модели на специфическом датасете задачи. Архитектура: BERT → [CLS] токен → классификационная голова.

**Domain adaptation** — дополнительное pretraining на domain-специфичном корпусе перед fine-tuning, чтобы модель лучше понимала терминологию домена.

**Transfer learning** — использование знаний, полученных на одной задаче или домене, для другой.

**Результат:** F1-score на domain-специфичных задачах вырос на **+15–20%** по сравнению с baseline.

##### Возможные вопросы

- **В чём разница BERT и RoBERTa?** RoBERTa обучалась дольше, на большем корпусе, без NSP и с динамической маскировкой.
- **Почему mBERT, а не отдельная монолингвальная модель?** mBERT удобен для cross-lingual задач. Если задача только на одном языке, монолингвальная модель часто лучше.
- **Что такое catastrophic forgetting и как с ним бороться?** Это ситуация, когда при fine-tuning модель забывает общие знания. Борются через маленький learning rate, weight decay, gradual unfreezing и early stopping.

### IT-компания

До университетской лаборатории я год работал в IT-компании, где строил RAG-пайплайн для корпоративной базы знаний и запускал AI-ассистента для сотрудников и клиентов.

---

#### E2E RAG-пайплайн для корпоративной базы знаний

##### Постановка задачи

Компания накопила большой массив документации: технические руководства, API-документация, процедуры, FAQ. Инженеры и клиенты тратили в среднем **~6 минут** на поиск нужной информации.

Нужно было построить систему, которая отвечает на вопросы по документации на естественном языке.

##### Архитектура и ключевые решения

**Индексирование:**

- Парсинг документов разных форматов: PDF, Confluence, Markdown.
- Чанкинг с overlap.
- Embedding через sentence-transformer модели.
- Хранение в **FAISS** как MVP-решение без отдельного сервера.

**Retrieval:**

- Dense retrieval как основной канал.
- BM25 как дополнение для точных совпадений терминов.
- Гибрид через Reciprocal Rank Fusion.

**Generation:**

LLM с RAG-промптом: «Ответь на вопрос, используя только предоставленный контекст».

**Результаты retrieval:**

- Recall@5: **+13%**.
- NDCG@10: **+6%**.

**Результат для пользователей:** среднее время получения ответа сократилось с **~6 минут до < 2 минут**.

---

#### Offline-метрики качества и мониторинг

Чтобы контролировать качество системы в production, внедрил offline evaluation pipeline:

- **Retrieval метрики:** Recall@K, NDCG@K.
- **Generation метрики:** faithfulness, answer relevancy.
- **Мониторинг:** логирование запросов, latency, процент запросов без ответа, дрейф качества во времени.

CI/CD запускал тесты на evaluation set при изменении промпта или компонента системы и блокировал деплой при деградации метрик ниже порога.

---

#### Оптимизация инференса

Для embedding-модели применял:

- **Batching:** группировка нескольких текстов в один батч для повышения throughput.
- **Quantization:** снижение точности весов FP32 → INT8 для ускорения и уменьшения памяти.

##### Возможные вопросы

- **Что такое Recall@5 и как его считали?** Доля запросов, для которых хотя бы один релевантный документ попал в top-5 результатов retrieval.
- **Почему гибрид dense + sparse retrieval?** Dense хорошо ловит смысл, sparse точно работает по ключевым словам. Гибрид перекрывает оба сценария.
- **Что такое Reciprocal Rank Fusion?** Метод объединения нескольких ранжированных списков по рангам без необходимости нормировать абсолютные скоры.

### Конфликт

На одном из проектов при проектировании системы для анализа переговоров возник конфликт с менеджером проекта. Он настаивал на простом пайплайне: транскрипт → один LLM-вызов → «вытащи все инциденты и напиши отчёт».

Я видел проблему: один большой промпт для нескольких разных задач давал нестабильный результат. LLM путалась между задачами, пропускала события или неверно классифицировала.

Предложил компромисс: сделал прототип обоих подходов на одном и том же тестовом наборе, посчитал точность извлечения событий и правильность классификации. Агентный подход с разделёнными инструментами дал точность на 23% выше. После этого вопрос решился данными, а не спором.

---

### Факап

В RAG-проекте, когда система уже несколько месяцев работала в production, начали поступать жалобы от пользователей: система стала выдавать странные ответы и находить нерелевантные документы.

Начал разбираться. Метрики retrieval постепенно деградировали, начиная с конкретной даты. Оказалось: зависимость `sentence-transformers` автоматически обновилась через `pip install --upgrade` в CI/CD пайплайне. Новая версия подтянула обновлённую embedding-модель с другими весами.

Embedding-пространство изменилось: запросы кодировались новой моделью, а в индексе лежали embeddings от старой. Cosine similarity между ними не имела смысла.

Быстрое решение: откатил зависимость и пересобрал FAISS-индекс с нужной версией модели.

Долгосрочное решение:

1. Зафиксировал версии зависимостей в `requirements.txt`.
2. Добавил версию embedding-модели как метаданные индекса.
3. В CI/CD запретил автоматические `--upgrade` без явного изменения `requirements.txt`.

Вывод: версионирование в ML-системах — это не только код, но и модели, и индексы.
