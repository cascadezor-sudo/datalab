### International Energy Company

В международной энергетической компании я работал на проекте по обработке финансовых PDF-документов в большом масштабе. Из PDF извлекался контент-> как текст, так и таблицы. Далее извлеченная информация трансформировалась в структурированные транзакции, после этого мы проводили нормализацию значений и очистку ошибок. Далее добавляли проверки на корректность. И на выходе у нас был надёжный датасет для дальнейшей аналитики и проверки QA командой  
  
Сейчас расскажу как было все устроено по этапам:  
  
#### Платформа и окружение

- Система работала на Azure Databricks (managed Spark-платформа — кластер для распределённой обработки больших объёмов данных).
- Для автоматизации и оркестрации ETL-процессов использовались Databricks Workflows / Jobs (встроенный планировщик задач с поддержкой расписаний, ретраев и зависимостей между задачами).
- Для ускорения выполнения типовых SQL и Spark-операций применялся Photon (ускоренный runtime движок Databricks).

Такой стек позволял надежно обрабатывать тысячи PDF-документов одновременно и масштабировать систему под большие объёмы данных.

#### Хранилище и управление данными

- Данные хранились в Delta Lake / Delta tables (таблицы поверх файлов в data lake с поддержкой ACID-транзакций — atomicity, consistency, isolation, durability — версиями данных и возможностью merge/upsert).
- Для управления доступами и метаданными использовался Unity Catalog (каталог с ролями и правами на чтение/запись).
- Для ускорения аналитики создавались:

	- Views (логические представления данных, удобные для запросов, но иногда медленные),
	- Cache tables (физические копии Views для быстрого чтения и обхода ограничений доступа).

Такой подход позволял безопасно хранить данные и обеспечивать быстрый доступ для downstream процессов.

#### Хранение PDF-документов

- PDF-документы хранились в Volumes (объёмы Databricks с управлением правами доступа как у обычных таблиц).
- Для конфигураций, ручных оверрайдов и списков исключений использовалась смонтированная папка SharePoint volume.

Таким образом, все входные файлы и вспомогательные данные были централизованы и доступны для ETL-процессов.

#### Подготовка данных
- Сначала из метаданных инвойсов и документов формировались кэш-таблицы:
1) фильтровались только документы в “scope” проекта,
2) сохранялись как Delta tables для дальнейшей обработки.  
	
- После этого выполнялись оптимизации хранения:

1) VACUUM (удаление старых файлов и версий),
2) OPTIMIZE (объединение маленьких файлов в крупные для ускорения чтения),
3) ZORDER (ко-локализация данных по часто фильтруемым колонкам).

Эти шаги обеспечивали быструю и стабильную работу всех downstream задач.

#### Сбор заявок на обработку

Далее формировался список документов для обработки:

1) выбирались записи по статусу, дате и другим условиям,
2) исключались уже обработанные документы (incremental run),
3) добавлялись ручные исключения из конфигурации.

Результатом был точный список документов, которые нужно было обработать на текущей итерации.

#### Привязка записей к PDF

- По ключам метаданных подтягивались физические пути к PDF в Volumes.
- Для каждой записи формировалась структура: «одна запись → список PDF (основной + supporting)».
- При необходимости собирались zip-архивы для ручной проверки QA.

#### Извлечение контента из PDF

Для извлечения текста и таблиц использовались:

- Azure Document Intelligence / Document AI (сервис, который извлекает layout, текст и таблицы из PDF, полезно для сканов и сложных документов),
- PyMuPDF (библиотека для быстрого парсинга цифровых PDF, извлекает текст и таблицы через эвристики),
- AWS Textract (резервный OCR сервис на случай нестандартных PDF).

На этом шаге каждая PDF превращалась в машинно-читаемый контент.

#### Extraction и структурирование транзакций

Далее извлечённые данные трансформировались в структурированные транзакции:

1) выбирались релевантные файлы и страницы,
2) текст и таблицы преобразовывались в поля и строки,
3) в сложных случаях использовалась LLM (Large Language Model — крупная языковая модель) для структурирования данных,
4) результаты валидировались через Pydantic схемы (инструмент для проверки правильности формата данных на Python).

Цель — получить корректные транзакции для downstream аналитики.

#### Conform + Harmonize

- Conform: приведение всех транзакций к единой канонической схеме (форматы дат и чисел, обязательные поля, нормализация знаков).
- Harmonize: очистка межинвойсных артефактов, унификация справочных значений.

Эти шаги выполнялись с использованием pandas/polars (для быстрых трансформаций) и Spark (для массовой обработки).

#### Запись результатов и downstream-слои

Результаты писались в Delta tables: сырые извлечения, чистые транзакции (clean views), служебные таблицы с ошибками, метриками и версиями прогонов.

Благодаря Delta tables можно было безопасно переобрабатывать данные и выполнять merge/upsert без потери целостности.

#### Правила и контроль качества

1) Проверка данных через конфиги YAML rulesets и движок правил
2) Результат — выявление аномалий и проверка связей между транзакциями,
3) Все таблицы доступны для QA и аналитиков без повторных пересчётов.

#### Эксплуатация, расписание и деплой

1) Регулярные запуски через Databricks Jobs (параметры, ретраи, лимиты параллельности),
2) Деплой и обновление workflow через Azure DevOps pipeline (изменения в репозитории → обновление конфигов → автоматический прогон).

Такой подход обеспечивал стабильную обработку больших объёмов документов и минимизировал ручную работу.

### Outsourcing ML Company  
  
Это аутсорс компания, где я работал на проекте по разработке системы для анализа отзывов пользователей для одного из американских маркетплейсов. Основная цель бизнеса была в том, чтобы сделать рекомендательную систему в будущем и повысить посещаемость и доверие пользователей за счёт рекомендации только проверенных продавцов.  
Основной фокус у нас был на классификации по темам и тональности(семантика текста).

Я занимался сбором данных, ресёрчем SOTA-моделей, оборачивал наши модели в FastAPI, fine-tuning'ом под реальные ошибки, а также CI/CD и последующим мониторингом качества и метрик.

Сейчас расскажу как было все устроено по этапам:

#### Сбор и подготовка данных

Отзывы у нас собирались напрямую с сайта заказчика через парсинг HTML-страниц с использованием BeautifulSoup (Python-библиотека для извлечения данных из HTML) и Selenium (инструмент для автоматизации браузера, нужен для динамических страниц с JS). 

Из страниц вытаскивались тексты отзывов и метаданные — категории товаров, рейтинги, даты публикации и идентификаторы.

Данные проходили очистку (data cleaning — удаление шума) ->  удаление HTML-артефактов,нормализация текста, фильтрация дублей и пустых отзывов

Далее формировали размеченный датасет для обучения модели. Часть данных размечали вручную и часть модель помогала автоматически размечать, а сложные и сомнительные случаи проверяли вручную.

#### Исследование моделей (Research)

На этапе ресёрча, я сравнивал разные SOTA-модели (State-of-the-Art — лучшие доступные архитектуры на текущий момент) для текстовой классификации ->  
BERT (Bidirectional Encoder Representations from Transformers),  
RoBERTa (Robustly Optimized BERT Approach),  
DeBERTa (Decoding-enhanced BERT with disentangled attention).  
В оценке моделей главными критериями были -> качество классификации, устойчивость к шумным и коротким отзывам, скорость инференса и потребление памяти

Задача была найти баланс между точностью и продакшен-ограничениями по ресурсам.

В итоге остановились на RoBERTa, так как модель показала лучшее качество и стабильность на реальных данных при приемлемой скорости.

Дополнительно тестировалась оптимизация через квантование (quantization — снижение точности весов модели для ускорения вычислений): fp16 (16-bit floating point) и int8 (8-bit integer). На практике fp16 дала прирост скорости без заметной потери качества

  
#### Архитектура проекта

Вся система была развернута в контейнерах с использованием Docker (платформа для изоляции и упаковки сервисов).

Она состояла из трёх основных контейнеров:

1) фронтенд,
2) backend-сервис на FastAPI (высокопроизводительный Python-фреймворк для построения REST API),
3) отдельный сервис инференса модели также на FastAPI.

Все три контейнера запускались на одной ноде и управлялись через Docker Compose (инструмент для совместного управления несколькими контейнерами).

#### Роль backend-сервиса

Backend выступал в роли API-шлюза и слоя бизнес-логики.

Он отвечал за: приём пользовательских запросов, валидацию входных данных, обработку крайних случаев (пустые тексты, слишком длинные отзывы, некорректные символы), предобработку текста (очистка, нормализация, подготовка входа для модели)  
После этого backend отправлял подготовленные данные в сервис инференса по внутреннему HTTP API.

#### Роль сервиса инференса

Нейросеть была вынесена в отдельный контейнер и работала как самостоятельный сервис инференса с API на FastAPI.

При старте контейнера модель загружалась в память один раз и постоянно находилась в готовом состоянии для обработки запросов, что снижало задержки на инференс.

Сервис принимал уже подготовленный текст и возвращал либо вероятности по классам, либо финальное предсказание в структурированном формате.

#### Обработка ответа

После получения результата от модели backend выполнял постобработку: выбирал итоговую категорию, применял пороги уверенности при необходимости, формировал финальный JSON-ответ для пользователя

#### Почему такая архитектура

Такое разделение позволяло:

1) изолировать ML-зависимости и тяжёлые вычисления от основного приложения,

2) обновлять или переобучать модель без влияния на backend,

3) контролировать нагрузку на инференс-сервис,

4) упростить масштабирование в будущем.

  

#### Fine-tuning на реальных ошибках

Зачем понадобился fine-tuning? Реальные пользовательские отзывы сильно отличались от «чистых» датасетов, они были: короткими, содержали ошибки, сленг и опечатки, часто включали сарказм или неявный смысл. И без адаптации модель показывала заметную деградацию качества в продакшене.

#### Формирование обучающего датасета

В основе использовался кастомный датасет отзывов от заказчика, максимально отражающий реальные боевые данные.

Дополнительно подключался крупный открытый датасет от Яндекса (около 500 000 отзывов) для увеличения объёма данных и повышения устойчивости модели.

Обучение шло в несколько этапов:

1) начальное дообучение на открытых данных,
2) адаптация под отзывы заказчика,
3) регулярное дообучение на новых продакшен-примерах.

#### Работа с ошибками модели

После запуска инференса собирались сложные кейсы (hard cases — примеры, где модель ошибалась или была неуверенной).

Эти примеры вручную проверялись, добавлялись в тренировочный датасет и использовались для последующих итераций обучения.

Также экспериментировали с hard negative mining (подбор похожих, но ошибочных примеров для повышения устойчивости классификации).

  
#### Оптимизация и ускорение inference

Для дообучения использовались PEFT-подходы (Parameter-Efficient Fine-Tuning — обучение только небольшой части параметров модели вместо всей сети).

Основным методом был LoRA (Low-Rank Adaptation — добавление небольших обучаемых матриц к весам модели вместо полного обновления параметров).

Это позволяло значительно снизить потребление памяти и ускорить обучение без потери качества.

Для ускорения вывода модели применялся DeepSpeed (фреймворк для оптимизации инференса и управления памятью больших нейросетей).

Это уменьшало задержки ответа и позволяло стабильнее держать нагрузку в продакшене.

  

#### Пайплайн инференса (что происходит при запросе пользователя)

##### Входные данные

- Пользователь отправлял текст отзыва в backend-сервис через REST API на FastAPI.
- Запрос содержал: текст отзыва, при необходимости — дополнительные метаданные (например язык или категория).

##### Предобработка

Backend выполнял preprocessing (подготовку текста): очистку от лишних символов, нормализацию регистра и пробелов, токенизацию или приведение формата под вход модели, контроль длины текста (обрезка или паддинг)  

Цель — привести сырой пользовательский текст к стабильному входу для нейросети.

##### Инференс

- Подготовленные данные отправлялись во внутренний сервис инференса.
- Модель возвращала: вероятности по классам или сразу финальную категорию отзыва

##### Постобработка

Backend выполнял postprocessing (формирование финального результата): выбор итогового класса, логирование сложных или неуверенных примеров для будущего обучения.

##### Ответ 

Получали структурированный JSON-ответ, например:категорию отзыва («положительный», «отрицательный», «нейтральный») Чтобы в последующем проводить АБ тесты и аналитику

#### Мониторинг и контроль качества

Для ML-части использовался MLflow (платформа трекинга экспериментов, моделей и метрик).

Продакшен-метрики отслеживались через Prometheus (сбор показателей) и Grafana (визуализация и алерты): скорость ответа сервиса, ошибки инференса, признаки деградации качества модели.

#### Метрики

F1-score(micro f1) — основная метрика была, так как это гармоническое среднее между precision и recall. Мы решали задачу, где важно было не пропустить целевой класс (1), но и не плодить лишние срабатывания, поэтому accuracy не отражало сути задачи. F1 хорошо показывал общее качество классификации, особенно в условиях дисбаланса

Micro F1- Считаем общее количество TP, FP, FN по всем классам, потом считаем F1.  

Подходит, когда важно общее качество предсказания, а не поведение по каждому классу. Мы можем использовать когда: классы сбалансированы по важности, не важна отдельная точность по каждому классу.  
  
Macro F1 - Считаем F1 отдельно по каждому классу, потом берём среднее арифметическое.Мы можем использовать когда: нужно оценить качество модели одинаково по всем классам, особенно если классы несбалансированы, интересно, как модель работает на редких классах.  

Weighted F1 - Тоже считает F1 по каждому классу, но берёт среднее с весами, пропорциональными количеству примеров в классе. Мы можем использовать когда хотим учитывать и дисбаланс классов, и разницу в качестве по ним.  
  
Precision и Recall — использовались для анализа баланса между ложными срабатываниями и пропущенными случаями;

ROC-AUC — использовалась на этапе сравнения моделей, особенно при сильной дисбалансировке классов.

#### Чего удалось достичь
F1-score на тестовой выборке: 0.84, Precision: ~0.87, Recall: ~0.81

#### Возможные вопросы

- Что такое слои докера?(каждая строчка это и есть слой)
    
- Зачем там кэширование?(для ускорения сборки)
    
- Как оптимизировать слои?(писать зависимости вначале а код позже, т.к код часто изменяется, а зависимости нет, так же докеригнор и объединять слои в один)
    
- Почему именно ECR кластер (формально, но там была 1 нода) 
    
- Какое RPS было на проде и чего требовал заказчик. Ответ: заявлено, чтоб сетка имела RPS до 50, хотя на практике было 10-25. Инферили батчами
    
- А как вы достигали RPS 50, если бы использовали BERT, а он не самый легкий. Ответ: квантование + onnx + vLLM (+ DeepSpeed)
    
- Вытекающий вопрос: чего вы достигли квантованием? Ответ: уменьшили latency.
    
- Вытекающий вопрос: почему FastAPI, ведь кластер у вас, и там нужна параллельная асинхронная история. Ответ: было достаточно FastAPI, потому что rps не большой и хватало однопоточности
    

  

### QA Platform Company 

До этого я два года работал в QA Platform Company, Делал два продакшн-проекта — один по компьютерному зрению, второй по временным рядам.

#### CV проект
##### Постановка задачи и цель бизнеса

В компании стояла задача в будущем построить рекомендательную систему продавцов, где продавцы с лучшими отзывами показываются пользователям чаще, чем продавцы с плохими отзывами (это напрямую влияет на конверсию и удержание пользователей, а также на ranking продавцов внутри маркетплейса — такие системы обычно используют сигналы качества товара и пользовательского опыта).

Однако анализ отзывов показал важную проблему: пользователи часто прикладывают фотографии товаров, и именно они содержат ключевую информацию о продукте, но:

1) текст в отзыве может отсутствовать (в таких случаях классические NLP-подходы не работают),
2) текст может быть нерелевантным (часто люди пишут про доставку или сервис, а не про сам товар),
3) фотографии часто noisy (плохое освещение, часть товара, похожие упаковки, domain shift относительно обучающих датасетов CV моделей).

Поэтому мы решили построить систему, которая будет определять категорию товара по фотографии (чтобы понимать, о каком типе товара идет речь даже без текста), находить похожие товары (важно для будущего retrieval и рекомендаций), формировать представление товара, которое можно использовать в будущей рекомендательной системе (embedding можно использовать как feature в ranking модели рекомендаций).

##### Первый вариант —  модель для анализа изображений

На первом этапе мы решили попробовать решить задачу только через компьютерное зрение.

Использовали архитектуру Vision Transformer (ViT) с предобученными весами DINOv2 (self-supervised модель — она уже умеет извлекать сильные визуальные признаки без разметки, что хорошо работает на noisy данных и лучше переносится на пользовательские фото, чем классические supervised модели).

Модель использовалась для генерации embedding-векторов изображений товаров (векторное представление изображения — компактное описание того, что изображено на картинке; такие embedding обычно нормализуются, чтобы их можно было сравнивать через cosine similarity).

ViT работает через механизм patch embedding (изображение делится на маленькие части — патчи, например 16×16 пикселей, каждый превращается в вектор; это позволяет модели анализировать структуру изображения и глобальные зависимости между объектами на картинке, а не только локальные признаки как в CNN).

Мы экспериментировали с размером патчей, потому что меньшие патчи дают больше деталей, но увеличивают вычислительную нагрузку и размер sequence для трансформера; большие патчи ускоряют инференс, но могут терять мелкие признаки, важные для похожих упаковок

Также проверяли стабильность embedding на augmentation (чтобы похожие изображения давали близкие embedding — это важно для retrieval систем).

##### Построение системы поиска похожих товаров

Полученные embedding-векторы изображений сохранялись в векторную базу FAISS (библиотека для быстрого поиска ближайших векторов — используется в системах рекомендаций и поиска, реализует approximate nearest neighbor алгоритмы).

Мы выбрали именно FAISS вместо облачных решений вроде Pinecone или Qdrant, так как это было дешевле, быстрее в нашей инфраструктуре и позволяло запускать систему on-premise без зависимости от внешних сервисов, а также давало больше контроля над типами индексов и параметрами поиска

Для индекса использовали: HNSW (графовый индекс — улучшает точность ближайших соседей и хорошо работает на больших embedding-пространствах).

IVF (кластеризация векторов — ускоряет поиск за счёт предварительного разбиения пространства embedding на кластеры),

Мы использовали HNSW (графовый индекс — улучшает точность ближайших соседей и хорошо работает на больших embedding-пространствах).

Дополнительно подбирали параметры индекса  
(nlist, efSearch, efConstruction — чтобы балансировать скорость поиска и recall).

Это позволило быстро находить похожие товары по изображению, по сути это был прототип рекомендательной системы на уровне визуального сходства и кандидатов для ранжирования.

Основной метрикой retrieval была:  
Recall@5 ≈ 0.89  
(насколько часто правильный похожий товар попадает в топ-5 результатов; эта метрика важна для систем candidate generation в рекомендациях).

##### Попытка классификации только по изображению

Далее мы попробовали решать задачу классификации:

embedding изображения → классификатор категории товара  
(простая и масштабируемая архитектура, потому что embedding можно кэшировать и использовать повторно).

Однако на продакшен данных появились проблемы:

1) много визуально похожих товаров (например разные бренды с одинаковыми упаковками),
2) одинаковые упаковки у разных категорий (визуальная неоднозначность класса),
3) noisy фотографии пользователей (обрезанные объекты, blur, фон, частичные объекты).

Также проявился эффект visual ambiguity  
(когда визуально разные категории находятся близко в embedding пространстве).

Из-за этого качество было нестабильным.

Основная метрика:  
ROC AUC ≈ 0.85.

Это было недостаточно для системы рекомендаций (потому что ошибки категории могут ухудшать ranking продавцов).

##### Переход к мультимодальной архитектуре

После анализа ошибок стало понятно, что часто текст из отзыва помогает понять товар лучше, чем изображение (например фото банки + текст "протеин" или "витамины").

Я инициировал переход к мультимодальному подходу (объединение нескольких типов данных — изображения и текста, чтобы модель принимала более точные решения и уменьшить неоднозначность визуальных признаков).

Мы начали использовать:

- ViT (изображение),
- BERT для обработки текста (модель извлекает семантические признаки из пользовательских отзывов, даже если текст короткий или неструктурированный),
- CLIP для совместных embedding изображений и текста (модель обучена понимать соответствие картинки и текста на огромных датасетах).

CLIP обучается через contrastive learning (модель сближает правильные пары изображение-текст и отдаляет неправильные — фактически учится выравнивать два embedding-пространства: текстовое и визуальное).

Это позволило лучше работать в задачах similarity и retrieval.

##### Объединение изображения и текста

Мы протестировали несколько вариантов объединения модальностей и в итоге использовали:

late fusion + объединение embedding-векторов (concat) перед классификацией, этот подход оказался более стабильным на noisy данных и проще масштабировался в продакшене, потому что можно независимо обновлять модели изображения и текста.

Перед объединением embedding нормализовали, чтобы разные модели давали сопоставимые масштабы признаков и не происходило доминирования одной модальности.

Более сложные архитектуры с cross-attention тоже тестировали, но отказались от них они увеличивали latency, требовали больше GPU и усложняли inference pipeline без заметного прироста метрик.

Также пришлось решать проблему alignment между текстом и изображением, иногда текст не описывает товар или вообще не связан с изображением — поэтому добавили фильтрацию текста и confidence-оценку, чтобы динамически определять вес модальностей.

##### Улучшение retrieval системы

После перехода к мультимодальным embedding система поиска похожих товаров стала заметно точнее (теперь учитывался не только внешний вид, но и смысл товара, что важно для похожих категорий).

Для similarity использовали cosine similarity (важно направление embedding-вектора, а не его длина — это лучше работает для моделей вроде CLIP, где embedding обычно L2-нормализованы).

Также добавили re-ranking этап  
(после поиска через FAISS дополнительная модель уточняла порядок результатов, делали на top-N кандидатах, чтобы улучшить precision).

В re-ranking учитывались: мультимодальные признаки, категория товара, дополнительные текстовые сигналы.

Это помогло решить одну из ключевых проблем, мы перестали путать визуально похожие, но семантически разные товары.

##### Оптимизация инференса модели

Когда система начала использоваться в продакшене, появилась проблема latency (время ответа модели критично для пользовательских сервисов и масштабируемости системы).

Мы провели оптимизацию inference для CLIP:

Квантование модели  
FP32 → FP16 / INT8 (уменьшение точности чисел — ускоряет вычисления, снижает использование памяти и позволяет лучше использовать GPU/CPU).

Разница:  
FP32 — максимальная точность  
FP16 — быстрее и дешевле  
INT8 — ещё быстрее, но может слегка снижать качество (из-за потери точности в представлении весов).

Также применили дистилляцию модели  
(обучили более маленькую модель повторять поведение большой — student модель обучается на soft predictions teacher модели, что сохраняет структуру embedding пространства).

После оптимизации, инференс ускорился примерно в 2 раза.

При этом деградация качества составила всего 2–4%  
(это проверяли через офлайн тесты и продакшен метрики, включая ROC AUC и retrieval recall).

##### Итоговые метрики системы

После перехода к мультимодальной архитектуре и оптимизации мы получили:

ROC AUC  
0.85 → 0.94  
(основная метрика классификации категории товара — значительное улучшение за счёт мультимодального сигнала).

F1-score (macro)  
≈ 0.72–0.76 на noisy продакшен данных  
(важно для сбалансированности качества между категориями).

Recall@5 (поиск похожих товаров)  
≈ 0.89  
(метрика candidate generation для retrieval системы).

Latency inference  
уменьшена примерно в 2 раза после оптимизаций  
(что позволило масштабировать систему на поток отзывов).

##### Рефакторинг продакшен-кода

После стабилизации модели я провел рефакторинг продакшен системы.

Код был переработан так, чтобы:

1) было проще добавлять новые модели (например можно было подключить новую embedding модель без изменения всей системы),
2) быстрее ориентироваться в проекте,
3) снизить технический долг.

Что сделали:

Разделение системы на модули, логика моделей, инференса и retrieval была вынесена в отдельные компоненты так как это упрощает поддержку и масштабирование сервисов независимо.  
Добавили автоматическую документацию через FastAPI Swagger (позволяет быстро тестировать и интегрировать сервис, а также удобно для внутренних команд).

#### Задача 2 (временные ряды):

Цель бизнеса была в прогнозировании скачивания приложения, для того чтобы делать промоакции для пользователей в нужный момент. У нас были данные за 3 года скачиваемости приложения.

##### Подход:

на этом проекте мы использовали классические методы: Prophet от Facebook (который удобен для сезонности, трендов, праздников), Модели из statsmodels (ARIMA, SARIMAX и пр.).

Мы выбрали Prophet от фейсбука, так как устроило качество предсказаний и простота, в отличии от ARIMA.

##### Как решали : 

Мы делали SQL запросы в базу данных и получали информацию о скачивании приложения. Далее готовили датасет, для Prophet подходит датасет из двух колонок, поэтому выстраивали датесет именно таким образом. Затем готовили модель, передавали туда данные о сезонности, трендах, и исключениях, потому что там именно надо было указывать инфу о неделе, годах, днях, праздников. В библиотеке holiday, который советовали скачать в официальной доке к Prophet, не оказалось наших нормальных праздников, поэтому пришлось написать их вручную и подать в модель обновленный список холидей.

##### Метрики:  

- MAE (Mean Absolute Error) — основная метрика (чувствительна к масштабу): до оптимизации: ~12.4 -> после улучшений: ~8.1
- MAPE (Mean Absolute Percentage Error) — для бизнес-интерпретации: после адаптации моделей: ~6–9% на основных метриках

##### Достижения:

- ускорил инференс (CLIP) (мультимодалка) в 2 раза (квантование\дистилляция) (качество упало на 2-4%)
- CV-подход (ViT DinoV2): строить эмбеддинги карточек товар и пытьася по векторной бд (faiss) рекомендовать похожие товары    
- рефакторингом повысил поддерживаемость и читаемость продуктового кода, а также упростил порядок введения новых фичей
- менторил джунов\стажеров, которые только устроились в команду    
- сначала пытались только за счет CV (стротиь эмбеддинги карточек нтоваров и по ним классифицировать) строить таргетированные рекомендации. Понял, что этого недостаточно, и предложил комбинированный подход: cv + llm => мультимодальность.
