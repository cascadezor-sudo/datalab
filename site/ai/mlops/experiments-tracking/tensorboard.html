TensorBoard

Материалы по TensorBoard и визуализации экспериментов.

    Блок 1

  1. Что такое TensorBoard?↗

    TensorBoard — инструмент визуализации экспериментов, изначально созданный для TensorFlow. Он читает event-файлы и показывает графики метрик, изображения, гистограммы, computation graph, embeddings и профилирование.

    TensorBoard не является полноценной MLOps-платформой с registry и управлением моделями. Его сильная сторона — быстрый локальный или серверный просмотр логов обучения: loss по эпохам, learning rate, изображения, распределения весов, profiler traces.

    TensorBoard особенно полезен в deep learning:

    • смотреть кривые train/validation loss
    • находить переобучение и нестабильность обучения
    • сравнивать несколько запусков
    • визуализировать изображения и маски в CV-задачах
    • анализировать время операций через profiler
    • проверять гистограммы весов и градиентов

    Код обучения записывает события в директорию вроде runs/experiment_001/. TensorBoard сканирует эту директорию и строит UI:

    tensorboard --logdir runs --port 6006

    1. Что читает TensorBoard?

      Event-файлы, которые создаются во время обучения через TensorFlow summary writer или совместимые writer-ы.

    2. Для чего TensorBoard подходит лучше всего?

      Для визуализации процесса обучения: метрик, изображений, гистограмм, графов и профилирования.

    3. Чем TensorBoard отличается от MLflow или W&B?

      TensorBoard проще и ближе к визуализации логов обучения. MLflow и W&B шире: tracking, collaboration, artifacts, reports, registry или model-management flow.

  2. Scalars: loss, accuracy и learning rate↗

    Scalars в TensorBoard — численные значения, записанные по шагам: train/loss, valid/loss, accuracy, learning_rate, grad_norm и любые другие метрики обучения.

    from torch.utils.tensorboard import SummaryWriter writer = SummaryWriter(log_dir="runs/resnet50_lr_1e-3") for epoch in range(num_epochs): train_loss = train_one_epoch(model, train_loader) valid_loss, valid_acc = evaluate(model, valid_loader) writer.add_scalar("loss/train", train_loss, epoch) writer.add_scalar("loss/valid", valid_loss, epoch) writer.add_scalar("accuracy/valid", valid_acc, epoch) writer.add_scalar("lr", optimizer.param_groups[0]["lr"], epoch) writer.close()
    СимптомВозможная причина
    Train loss падает, valid loss растётПереобучение
    Обе кривые почти не падаютСлишком слабая модель, плохой learning rate, ошибка в данных
    Loss скачетLearning rate слишком большой, нестабильные батчи, проблемы с нормализацией
    Accuracy высокая, loss плохойНужна проверка calibration, class imbalance или метрики задачи

    Кривые имеют смысл только при одинаковом split, preprocessing, seed policy и метрике. Если один run обучался на другой версии данных, визуальное сравнение loss может вводить в заблуждение.

    1. Что такое scalar в TensorBoard?

      Численная метрика, записанная на конкретном шаге или эпохе.

    2. Какие scalars стоит логировать почти всегда?

      Train/validation loss, основную validation-метрику, learning rate и при необходимости gradient norm.

    3. Как по кривым увидеть переобучение?

      Train loss продолжает падать, а validation loss перестаёт улучшаться или растёт.

  3. Images, histograms и embeddings↗

    TensorBoard полезен не только для scalar-метрик. В CV, NLP и recommender systems часто нужно смотреть сами данные, промежуточные результаты и представления модели.

    ТипПример применения
    ImagesВходные изображения, segmentation masks, предсказанные bbox
    HistogramsРаспределения весов, bias, activations, gradients
    EmbeddingsВизуализация признаков через projector
    TextПримеры генерации, decoded predictions, ошибки классификации
    AudioРезультаты speech-моделей
    from torchvision.utils import make_grid images, masks = next(iter(valid_loader)) preds = model(images.to(device)).argmax(dim=1).cpu() writer.add_image("valid/images", make_grid(images[:8]), global_step=epoch) writer.add_images("valid/pred_masks", preds[:8].unsqueeze(1), global_step=epoch)

    Если TensorBoard доступен команде или развёрнут на сервере, нельзя бездумно логировать персональные данные, медицинские снимки, документы, лица, тексты пользователей и другие чувствительные объекты. Event-файлы — это тоже артефакты, которые нужно защищать.

    1. Зачем логировать изображения в TensorBoard?

      Чтобы проверять качество данных, аугментации и визуальные ошибки модели, которые не видны по одной метрике.

    2. Что показывают histograms?

      Распределения весов, активаций или градиентов по шагам обучения.

    3. Какая главная опасность media-логов?

      Утечка чувствительных данных через event-файлы или открытый TensorBoard UI.

  4. TensorBoard Profiler↗

    TensorBoard Profiler — набор представлений для анализа производительности обучения: время операций, загрузка GPU/CPU, input pipeline, memory и bottleneck-и.

    Profiler нужен, когда модель обучается медленно, GPU простаивает или батчи долго готовятся на CPU. Он помогает отличить проблемы модели от проблем data pipeline.

    СимптомЧто проверить
    GPU utilization низкийDataLoader, чтение с диска, аугментации на CPU
    Step time сильно плаваетНестабильный input pipeline, разные размеры батчей
    Много времени в host-to-device copypin_memory, num_workers, перенос данных на GPU
    Memory близко к лимитуBatch size, activation checkpointing, mixed precision
    import torch from torch.profiler import profile, ProfilerActivity, tensorboard_trace_handler with profile( activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA], on_trace_ready=tensorboard_trace_handler("runs/profiler"), record_shapes=True, profile_memory=True, ) as prof: for step, batch in enumerate(train_loader): train_step(batch) prof.step() if step >= 20: break

    1. Когда нужен TensorBoard Profiler?

      Когда обучение медленное, GPU простаивает, много времени уходит на загрузку данных или нужно понять стоимость операций.

    2. Что такое input pipeline bottleneck?

      Ситуация, когда модель ждёт данные: чтение, декодирование, аугментации или перенос на GPU занимают слишком много времени.

    3. Почему profiler запускают на коротком участке?

      Профилирование создаёт overhead и большие trace-файлы, поэтому обычно достаточно десятков шагов.
