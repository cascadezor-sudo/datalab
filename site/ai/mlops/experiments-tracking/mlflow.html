  1. Что такое MLflow?↗

    MLflow — open-source платформа для управления жизненным циклом ML-моделей: эксперименты, метрики, параметры, артефакты, модели, model registry и деплой. В контексте experiment tracking чаще всего используют модуль MLflow Tracking.

    MLflow решает проблему «какой код, данные и гиперпараметры дали этот результат». Каждый запуск обучения сохраняется как run внутри experiment. В run обычно попадают:

    • параметры: learning_rate, batch_size, model_name
    • метрики: loss, accuracy, f1, roc_auc
    • артефакты: графики, confusion matrix, веса модели, отчёты
    • теги: автор, git commit, dataset version, окружение

    Без трекинга эксперименты быстро превращаются в набор ноутбуков и файлов model_final_v7.pkl. MLflow делает историю воспроизводимой: можно сравнить запуски, понять, почему один run лучше другого, восстановить модель и передать её дальше в production-процесс.

    КомпонентЗачем нужен
    TrackingЛогирование параметров, метрик, артефактов и моделей
    ProjectsУпаковка запуска эксперимента с окружением и entry point
    ModelsЕдиный формат сохранения моделей разных фреймворков
    Model RegistryВерсионирование моделей, стадии, approval flow
    DeploymentsИнтеграция с serving-платформами и провайдерами

    1. Что такое experiment и run в MLflow?

      Experiment — логическая группа запусков. Run — один конкретный запуск обучения или оценки с параметрами, метриками и артефактами.

    2. Что обычно логируют в MLflow Tracking?

      Гиперпараметры, метрики, артефакты, модель, теги окружения, версию данных и git commit.

    3. Почему MLflow важен для MLOps?

      Он связывает эксперимент, модель и артефакты в воспроизводимую историю, которую можно сравнивать, ревьюить и передавать в registry.

  2. MLflow Tracking Server↗

    MLflow Tracking Server — HTTP-сервис, через который клиенты логируют runs, параметры, метрики и артефакты. Он отделяет код обучения от места хранения metadata и файлов.

    Типичная production-схема MLflow состоит из двух хранилищ:

    • Backend store — metadata: experiments, runs, params, metrics, tags. Обычно PostgreSQL или MySQL.
    • Artifact store — файлы: модели, графики, отчёты, датасеты-семплы. Обычно S3, MinIO, GCS, Azure Blob или файловая система.
    Training job -> MLflow Tracking Server -> PostgreSQL | v S3 / MinIO
    mlflow server \ --backend-store-uri postgresql://mlflow:mlflow@postgres:5432/mlflow \ --artifacts-destination s3://mlflow-artifacts \ --host 0.0.0.0 \ --port 5000

    Для локальной разработки можно использовать mlruns/ на диске. Для команды так делать нельзя: runs будут жить на машине одного человека, артефакты легко потерять, а доступы и бэкапы станут неуправляемыми. Командный MLflow почти всегда требует отдельный tracking server, БД и object storage.

    1. Зачем нужен MLflow Tracking Server?

      Чтобы несколько пользователей и пайплайнов логировали эксперименты в одно централизованное место через HTTP API.

    2. Чем backend store отличается от artifact store?

      Backend store хранит metadata runs. Artifact store хранит файлы: модели, изображения, отчёты и другие артефакты.

    3. Почему SQLite или локальный mlruns/ плохи для команды?

      Они плохо подходят для совместного доступа, бэкапов, прав, масштабирования и надёжного хранения артефактов.

  3. Логирование экспериментов в MLflow↗

    В MLflow логирование обычно происходит прямо в training script. Код явно создаёт run, записывает параметры до обучения, метрики во время обучения, а в конце сохраняет модель и артефакты.

    import mlflow from sklearn.ensemble import RandomForestClassifier from sklearn.metrics import f1_score mlflow.set_tracking_uri("http://localhost:5000") mlflow.set_experiment("churn-classification") params = {"n_estimators": 300, "max_depth": 8, "random_state": 42} with mlflow.start_run(): mlflow.log_params(params) model = RandomForestClassifier(**params) model.fit(X_train, y_train) preds = model.predict(X_valid) mlflow.log_metric("valid_f1", f1_score(y_valid, preds)) mlflow.sklearn.log_model(model, name="model")

    MLflow умеет autologging для популярных библиотек: scikit-learn, XGBoost, LightGBM, PyTorch, TensorFlow, Keras и других. Это удобно для быстрого старта, но в production лучше явно логировать ключевые параметры, бизнес-метрики и артефакты, потому что autologging не знает контекст задачи.

    Метрика без контекста почти бесполезна. accuracy=0.91 нужно связывать с версией датасета, split-ом, кодом, seed, preprocessing pipeline и business cutoff. Иначе лучший run невозможно честно воспроизвести.

    1. Какая минимальная единица логирования в MLflow?

      Run. Внутри него сохраняются параметры, метрики, теги, артефакты и модель.

    2. Чем log_param отличается от log_metric?

      Param — фиксированная настройка запуска. Metric — численное значение результата, часто меняется по шагам или эпохам.

    3. Почему autologging не заменяет явное логирование?

      Autologging не знает бизнес-контекст, версию данных, дополнительные графики, правила отбора модели и специфичные метрики проекта.

  4. MLflow Model Registry↗

    MLflow Model Registry — хранилище версий моделей поверх MLflow Tracking. Оно позволяет зарегистрировать модель из run, назначить версию, описать изменения и управлять жизненным циклом модели.

    Experiment tracking отвечает на вопрос «что происходило во время эксперимента». Model Registry отвечает на вопрос «какую модель можно использовать дальше». Обычно flow выглядит так:

    1. training job логирует run
    2. модель сохраняется как artifact
    3. лучший run регистрируется как новая model version
    4. модель проходит ревью
    5. serving или batch inference забирает утверждённую версию

    Для каждой версии модели полезно фиксировать:

    • ссылку на run
    • версию данных и период обучения
    • метрики offline-валидации
    • результаты shadow/A/B-теста, если они есть
    • ограничения применения модели
    • changelog: что поменялось относительно прошлой версии

    Registry хранит версии и metadata, но сам по себе не гарантирует качество модели. Нужны правила: кто может переводить модель в production, какие проверки обязательны, где лежит отчёт валидации, как откатываться на прошлую версию.

    1. Чем Model Registry отличается от Tracking?

      Tracking хранит историю экспериментов. Registry хранит версии моделей, которые рассматриваются для дальнейшего использования.

    2. Что такое model version?

      Конкретная зарегистрированная версия модели, обычно связанная с run и его артефактами.

    3. Почему registry важен перед production?

      Он создаёт управляемую точку передачи модели из экспериментов в inference, ревью, тестирование и откат.
