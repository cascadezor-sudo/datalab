  1. Что такое Cloud Computing?↗

    Cloud Computing — модель, в которой мы арендуем вычислительные ресурсы и готовые сервисы у облачного провайдера: виртуальные машины, GPU, хранилища, базы данных, Kubernetes, serverless, сети, мониторинг и другие компоненты инфраструктуры.

    В целом есть два пути:

    1. держать свои серверы дома, в офисе или в ЦОДе
    2. арендовать инфраструктуру у провайдера

    Cloud Computing — это второй вариант, но в более гибкой форме, чем классическая аренда одного VPS. Облако обычно даёт API, панель управления, автоматизацию, оплату по потреблению и набор managed-сервисов, которые можно создать за минуты.

    VPS — это чаще всего просто виртуальная машина. Облако шире: можно создать managed PostgreSQL, объектное хранилище, Kubernetes-кластер, очередь сообщений, балансировщик, IAM-права, serverless-функцию, secret manager и мониторинг без ручной сборки всего с нуля.

    ML Engineer использует облако не ради самого облака, а чтобы быстрее запускать ML-системы:

    • обучать модели на CPU/GPU/TPU
    • хранить датасеты, модели и артефакты
    • запускать batch inference и online inference
    • поднимать MLflow, Airflow, Kafka, Kubernetes, feature store
    • строить RAG-сервисы с managed DB и object storage
    • масштабировать inference под нагрузку
    • контролировать стоимость экспериментов

    После 2022 года у пользователей из России могут быть ограничения при регистрации и оплате иностранных облаков: часто нужны нероссийский IP, иностранная платёжная карта или юридическая схема доступа. На практике поэтому используют российские облака, self-hosted-инфраструктуру или гибридные варианты.

    1. Что такое облако?

      Это аренда вычислительных ресурсов и сервисов через API/панель управления с быстрым выделением, масштабированием и оплатой по потреблению.

    2. Чем облако отличается от VPS?

      VPS даёт виртуальную машину. Облако даёт экосистему: сети, IAM, managed DB, object storage, Kubernetes, serverless, мониторинг, бэкапы и автоматизацию.

    3. Зачем облако ML Engineer?

      Чтобы быстро получать вычисления, GPU, хранилища и managed-сервисы для обучения, экспериментов, inference и MLOps-пайплайнов.

  2. Какие бывают модели облачных сервисов?↗

    Облачные сервисы часто делят на IaaS, PaaS, SaaS, CaaS, FaaS и managed-сервисы. Разница в том, сколько инфраструктуры провайдер берёт на себя, а сколько остаётся на команде.

    МодельЧто арендуемПример для ML
    IaaSВиртуальные машины, диски, сетиGPU VM для обучения модели
    PaaSПлатформу для запуска приложенияmanaged runtime для API модели
    CaaSКонтейнерную платформуmanaged Kubernetes для inference
    FaaS / ServerlessФункции по событиюобработка загруженного файла или webhook
    Managed DBБД как сервисPostgreSQL для метаданных экспериментов
    SaaSГотовое приложениеhosted MLflow, monitoring, BI

    Чем выше уровень сервиса, тем меньше операционной работы, но тем сильнее vendor lock-in. Виртуальная машина переносится проще, чем serverless-функция с привязкой к IAM, очередям, логам и storage конкретного облака.

    Для MVP ML-сервиса можно начать с managed-сервисов:

    • контейнер с FastAPI inference
    • managed PostgreSQL для метаданных
    • object storage для моделей и файлов
    • managed Kubernetes или serverless containers для запуска
    • managed monitoring для метрик

    Так команда быстрее проверит продуктовую гипотезу, не собирая инфраструктуру вручную.

    2. Что такое managed service?

      Сервис, где провайдер берёт на себя часть эксплуатации: обновления, бэкапы, отказоустойчивость, мониторинг и масштабирование.

      ML-пайплайны могут зависеть от конкретных API облака: storage, IAM, очередей, managed training, registry. Чем больше таких зависимостей, тем дороже миграция.

  3. Какие бывают облачные провайдеры?↗

    Облачный провайдер — компания, которая предоставляет вычислительные ресурсы и managed-сервисы через интернет: AWS, Google Cloud, Microsoft Azure, Yandex Cloud, Selectel, VK Cloud, Sber Cloud, DigitalOcean, Heroku и другие.

    Крупные провайдеры похожи базовыми слоями, но отличаются деталями, зрелостью сервисов, ценами, регионами, доступностью GPU, документацией и ограничениями.

    Google Cloudсильные data/ML-сервисы, BigQuery, GKE, Vertex AI
    Microsoft Azureсильная интеграция с Microsoft-экосистемой и enterprise
    Yandex Cloudроссийский провайдер с managed-сервисами, документацией и сертификацией

    DigitalOcean / Herokuпроще стартовать, меньше enterprise-сложности

    Для ML Engineer выбор облака обычно зависит от:

    • доступности GPU и нужных типов инстансов
    • стоимости хранения и сетевого трафика
    • managed Kubernetes и контейнерного registry
    • object storage и совместимости с S3 API
    • managed DB и очередей
    • требований к персональным данным и региону хранения
    • того, где уже живёт продуктовая инфраструктура

  4. Какие облачные сервисы нужны ML Engineer?↗

    Для ML Engineer облако — это набор строительных блоков для обучения, хранения данных, оркестрации пайплайнов, inference и наблюдаемости.

    Базовый cloud-набор для ML:

    КатегорияЗачем нужна
    Computeобучение, preprocessing, batch jobs, inference
    GPU/TPUобучение и ускоренный inference глубоких моделей
    Object Storageдатасеты, модели, логи, артефакты
    Managed DBметаданные экспериментов, статусы задач, продуктовые данные
    Kubernetes / Containersвоспроизводимый запуск сервисов и пайплайнов
    Queue / Streamingасинхронные задачи, events, real-time inference
    IAM / Secretsдоступы к данным, сервисам и секретам
    Monitoring / Logginglatency, ошибки, ресурсы, метрики модели
    Container Registryхранение Docker-образов

    Типичный cloud-пайплайн:

    1. сырые данные лежат в object storage
    2. preprocessing запускается как batch job
    3. признаки пишутся в feature store или БД
    4. обучение запускается на GPU VM или managed training
    5. модель сохраняется в registry/object storage
    6. inference-сервис разворачивается в Kubernetes
    7. метрики и логи уходят в monitoring

    Самая частая ошибка в ML-облаке — думать только про GPU. На практике стоимость и надёжность часто определяются storage, network egress, простаивающими инстансами, невыключенными notebooks, логами, снапшотами и неверно выбранным классом хранилища.

  5. Как думать о стоимости и безопасности облака?↗

    Cloud cost & security management — это практики, которые помогают не тратить лишнее, не открывать данные наружу и не давать сервисам больше прав, чем нужно.

    Для ML Engineer два главных риска в облаке:

    1. Деньги: GPU, большие диски, egress, невыключенные notebooks, снапшоты, логи и масштабирование.
    2. Данные: публичные buckets, лишние IAM-права, секреты в коде, неразделённые окружения, доступ к персональным данным.
    • включить budgets и billing alerts
    • ставить теги/labels на ресурсы
    • выключать экспериментальные VM и notebooks
    • использовать spot/preemptible-инстансы там, где можно
    • хранить датасеты в подходящем классе storage
    • чистить старые checkpoints, logs и snapshots
    • контролировать network egress
    • least privilege для IAM
    • отдельные service accounts для пайплайнов и сервисов
    • секреты в secret manager
    • private networks для БД и внутренних сервисов
    • шифрование данных at rest и in transit
    • аудит действий
    • запрет публичных buckets без явной причины
    • разделение dev/stage/prod

    Плохой ML-cloud сценарий: ноутбук с ключом администратора запускает обучение на дорогой GPU, пишет временные данные в публичный bucket, забывает выключить инстанс и оставляет месяцы логов.

    Хороший сценарий: отдельный service account, ограниченный bucket, budget alert, lifecycle policy для артефактов, автоматическое выключение idle compute и отдельный project/account для экспериментов.

      Budget alerts, IAM least privilege, отдельный project/account, private storage, secret manager и правила остановки дорогих ресурсов.

      Они дорогие и часто простаивают между экспериментами. Один забытый инстанс может стоить больше, чем вся остальная инфраструктура.

      Ноутбуки легко попадают в git, шарятся и запускаются в разных окружениях. Лучше использовать roles/service accounts/secret manager.

  6. Что важно знать про AWS?↗

    AWS (Amazon Web Services) — крупнейшая облачная платформа с большим набором сервисов для compute, storage, networking, databases, analytics, ML, security и developer tools.

    Для ML Engineer в AWS особенно часто встречаются:

    ЗадачаСервисы
    Виртуальные машиныEC2
    Объектное хранилищеS3
    КонтейнерыECR, ECS, EKS
    Базы данныхRDS, Aurora, DynamoDB
    Очереди и событияSQS, SNS, EventBridge
    ServerlessLambda
    ML-платформаSageMaker
    IAM и секретыIAM, KMS, Secrets Manager
    IaCCloudFormation, Terraform AWS Provider

    AWS очень мощный, но требует дисциплины: IAM least privilege, бюджеты и алерты, tagging ресурсов, отдельные аккаунты/environments, выключение экспериментальных GPU, контроль публичных bucket-ов и понимание сетей VPC.

    Минимальная AWS-архитектура для ML API:

    • модель и артефакты лежат в S3
    • Docker-образ лежит в ECR
    • inference-сервис работает в ECS или EKS
    • метаданные лежат в RDS PostgreSQL
    • секреты хранятся в Secrets Manager
    • логи и метрики уходят в CloudWatch

  7. Что важно знать про Google Cloud Platform?↗

    Google Cloud Platform (GCP) — облачная платформа Google с сильными сервисами для данных, аналитики, контейнеров и ML.

    Для ML Engineer в GCP часто важны:

    ЗадачаСервисы
    Виртуальные машиныCompute Engine
    КонтейнерыArtifact Registry, GKE, Cloud Run
    Объектное хранилищеCloud Storage
    АналитикаBigQuery
    ML-платформаVertex AI
    ServerlessCloud Functions, Cloud Run
    Секреты и доступыIAM, Secret Manager
    MonitoringCloud Monitoring, Cloud Logging

    GCP часто удобен для data/ML-сценариев из-за BigQuery, Vertex AI, GKE и Cloud Storage. Но billing тоже требует внимания: ошибка в коде, масштабировании или лимитах может быстро привести к большой сумме.

    Для batch scoring можно хранить данные в BigQuery или Cloud Storage, запускать job в Vertex AI или GKE, складывать результаты обратно в BigQuery, а API-слой держать в Cloud Run.

  8. Что важно знать про Microsoft Azure?↗

    ML API в Azure можно собрать так:

    • модель и данные лежат в Blob Storage
    • контейнер хранится в Azure Container Registry
    • сервис развёрнут в AKS или Container Apps
    • секреты лежат в Key Vault
    • метрики и ошибки собираются в Azure Monitor/Application Insights

  10. Что такое OpenStack?↗

    OpenStack — open-source платформа для построения private cloud: виртуальные машины, сети, хранилища, образы, identity, API и дополнительные сервисы.

    OpenStack нужен, когда компания хочет облачную модель управления ресурсами, но на своей инфраструктуре: в собственном ЦОДе, у локального провайдера или в контролируемом контуре.

    Типичные компоненты:

    КомпонентРоль
    Novacompute и управление VM
    Neutronсети
    Cinderблочные диски
    Swiftobject storage
    Glanceобразы VM
    Keystoneidentity и access management
    Horizonweb-панель
    Heatorchestration

    OpenStack — мощная, но сложная платформа. Для ML Engineer обычно важно не администрировать OpenStack, а понимать, что private cloud может давать VM/GPU/storage/API как внутренний аналог публичного облака. Если команда маленькая, OpenStack может быть слишком тяжёлым решением.

    В компании с ограничениями на публичные облака ML-платформа может жить поверх OpenStack:

    • GPU VM выдаются через Nova
    • образы окружений хранятся в Glance
    • данные лежат в object/block storage
    • доступы управляются через Keystone
    • Kubernetes поднимается поверх выделенных VM

    1. Что такое OpenStack?

      Open-source платформа для построения private cloud с API для compute, storage, network и identity.

    2. Чем OpenStack отличается от Proxmox?

      OpenStack больше похож на конструктор облачного провайдера с большим числом компонентов и API. Proxmox проще и ближе к управлению виртуализацией/кластерами.

    3. Когда OpenStack уместен?

      Когда нужна private cloud-модель, много команд, автоматизация через API, изоляция tenants и есть компетенции для эксплуатации.

  11. Что такое Proxmox?↗

    Proxmox VE — open-source платформа виртуализации на базе Debian, KVM и LXC для управления виртуальными машинами, контейнерами, кластером, хранилищами, бэкапами и high availability.

    Proxmox часто выбирают для homelab, небольших компаний, внутренних стендов и self-hosted-инфраструктуры, где OpenStack слишком тяжёлый, а одного сервера уже мало.

    Что обычно даёт Proxmox:

    • Web UI для управления VM и контейнерами
    • KVM-виртуализация
    • LXC-контейнеры
    • кластер из нескольких нод
    • live migration для VM
    • централизованные бэкапы
    • storage-интеграции
    • HA-сценарии

    Для ML Engineer Proxmox полезен как способ получить внутреннюю лабораторию: VM с GPU passthrough, self-hosted MLflow, Airflow, MinIO, GitLab Runner, Kubernetes-кластер или тестовые inference-сервисы. Но эксплуатация железа, сети, бэкапов и отказов остаётся на команде.

    Self-hosted MLOps-стенд на Proxmox:

    • VM под Kubernetes control plane и worker-ноды
    • отдельная VM под MLflow/PostgreSQL/MinIO
    • GPU VM для обучения
    • Proxmox Backup Server для бэкапов
    • мониторинг через Prometheus/Grafana
