Databases

Материалы по базам данных и хранилищам.

    Блок 1

  1. Что такое база данных?↗

    База данных (Database, DB) — это организованное хранилище данных, к которому можно обращаться из приложения: читать, изменять, удалять и добавлять записи.

    Если у интернет-магазина есть личный кабинет, корзина, история заказов и адрес доставки, эти данные должны переживать перезапуск backend-сервиса. Поэтому их хранят не в памяти приложения, а в базе данных.

    Типичная веб-система часто состоит из трёх частей:

    • Frontend — интерфейс пользователя
    • Backend — серверная логика и API
    • DB — долговременное хранилище данных

    Backend обычно выступает посредником: проверяет запрос, обращается к БД, преобразует ответ и возвращает его клиенту.

    Не каждому сайту нужна БД. Например, лендинг с перечнем услуг может быть статической страницей. Но если есть регистрация, платежи, история действий, персональные настройки, очереди задач или результаты экспериментов, без долговременного хранилища уже сложно.

    ML Engineer редко администрирует БД как DBA, но постоянно взаимодействует с данными:

    • хранит метаданные экспериментов и артефактов
    • читает обучающие датасеты и витрины признаков
    • пишет результаты batch inference
    • проектирует схемы для feature store
    • использует векторные БД или поисковые индексы в RAG-системах
    • разбирается, почему inference-сервис стал медленным из-за запросов к БД

    Поэтому важно понимать не только SELECT *, но и ограничения транзакций, индексы, репликацию, мониторинг и безопасность.

    1. Что такое база данных?

      Организованное долговременное хранилище данных, к которому приложение обращается через СУБД или специализированный движок.

    2. Чем БД отличается от файла на диске?

      Файл тоже хранит данные, но СУБД добавляет язык запросов, индексы, транзакции, права доступа, конкурентную работу нескольких клиентов, резервное копирование и механизмы восстановления.

    3. Зачем ML Engineer знать базы данных?

      Чтобы корректно доставать данные для обучения, хранить результаты пайплайнов, понимать задержки inference-сервисов, проектировать feature store и не ломать продуктовые данные неудачными запросами.

  2. Какие бывают виды СУБД?↗

    СУБД — система управления базами данных. Это программный слой, который отвечает за хранение, запросы, права доступа, конкурентную работу, восстановление и оптимизацию обращения к данным.

    Базы данных различаются не только синтаксисом запросов, но и тем, под какую модель данных и нагрузку они оптимизированы.

    ТипКак хранит данныеГде полезно
    РеляционнаяТаблицы, строки, связи, SQLПользователи, заказы, транзакции, метаданные ML-пайплайнов
    Ключ-значениеБыстрый доступ по ключуКэш, сессии, rate limit, быстрые lookup-таблицы
    ДокументнаяJSON/BSON-документыГибкие сущности, события, конфиги, профили
    КолоночнаяДанные по столбцамАналитика, агрегации, большие таблицы признаков
    Time-seriesЗначения с временной меткойМетрики, мониторинг, телеметрия, логи
    ГрафоваяУзлы и связиСоциальные графы, knowledge graph, рекомендации
    ПоисковаяИнвертированные индексыFull-text search, логи, поиск по документам
    ВекторнаяВекторы эмбеддингов и ANN-индексыRAG, semantic search, поиск похожих объектов

    Выбор БД — это выбор компромиссов. PostgreSQL удобен как универсальная реляционная БД, Redis хорош для кэша, ClickHouse — для аналитических агрегаций, Elasticsearch/OpenSearch — для поиска, а векторные хранилища — для поиска по эмбеддингам. Один проект может использовать сразу несколько БД, если нагрузки действительно разные.

    В ML-продукте может быть такая связка:

    • PostgreSQL хранит пользователей, задания и статусы пайплайнов
    • S3/MinIO хранит большие датасеты и модели
    • ClickHouse хранит события и метрики
    • Redis кэширует признаки для online inference
    • Vector DB хранит эмбеддинги документов для RAG

    1. Почему нет одной идеальной БД для всего?

      Разные БД оптимизированы под разные запросы: транзакции, кэш, аналитику, поиск, графы, временные ряды или векторы. Универсальность обычно означает компромиссы по скорости, простоте и масштабу.

    2. Когда лучше начать с PostgreSQL?

      Когда данные хорошо описываются таблицами, важны транзакции, SQL, целостность и умеренная универсальность. Для многих ML-сервисов PostgreSQL хватает для метаданных, задач, пользователей и результатов.

    3. Когда нужна отдельная аналитическая или векторная БД?

      Когда запросы становятся специализированными: большие агрегации по событиям, поиск по текстам, ANN-поиск по эмбеддингам или поток метрик с временными метками.

  3. Что такое SQL?↗

    SQL (Structured Query Language) — декларативный язык для работы с реляционными базами данных. На SQL описывают, какие данные нужны, а СУБД сама выбирает план выполнения запроса.

    Реляционная БД хранит данные в таблицах. Таблица состоит из строк и столбцов, а связи между таблицами задаются ключами.

    Основные группы SQL-команд:

    ГруппаЧто делаетПримеры
    DDLОписывает структуруCREATE TABLE, ALTER TABLE, DROP TABLE
    DMLМеняет данныеINSERT, UPDATE, DELETE
    DQLЧитает данныеSELECT
    DCLУправляет доступомGRANT, REVOKE
    TCLУправляет транзакциямиBEGIN, COMMIT, ROLLBACK

    В ML-задаче можно собрать обучающую выборку SQL-запросом:

    SELECT u.user_id, u.country, COUNT(o.order_id) AS orders_count, AVG(o.amount) AS avg_order_amount, MAX(o.created_at) AS last_order_at FROM users AS u LEFT JOIN orders AS o ON u.user_id = o.user_id WHERE u.created_at >= DATE '2025-01-01' GROUP BY u.user_id, u.country;

    Для ML Engineer SQL важен не только как способ "достать табличку". Ошибочный JOIN, утечка таргета через будущие данные или неверный фильтр по времени могут испортить датасет сильнее, чем неудачный выбор модели.

    1. Почему SQL называют декларативным языком?

      Потому что мы описываем желаемый результат, а не пошаговый алгоритм получения данных. Оптимизатор СУБД сам выбирает порядок чтения таблиц, использование индексов и стратегию соединений.

    2. Какие SQL-операции чаще всего нужны ML Engineer?

      SELECT, WHERE, JOIN, GROUP BY, оконные функции, CTE, агрегации, фильтры по времени и создание витрин признаков.

    3. Какая частая ML-ошибка связана с SQL?

      Data leakage: например, когда признаки считаются с использованием событий, которые произошли после момента предсказания.

  4. Что такое NoSQL?↗

    NoSQL — семейство нереляционных подходов к хранению данных. Это не одна технология, а общий ярлык для key-value, документных, wide-column, графовых, time-series, поисковых и других хранилищ.

    NoSQL часто выбирают, когда реляционная модель неудобна или нагрузка требует другой архитектуры:

    • нужен очень быстрый доступ по ключу
    • схема данных часто меняется
    • данные естественно выглядят как документы или граф
    • нужно горизонтально масштабировать запись
    • важнее доступность и скорость, чем строгие транзакции на много таблиц

    NoSQL не означает "SQL больше не нужен". В реальных системах SQL и NoSQL часто живут вместе. Например, PostgreSQL хранит критичные сущности, Redis кэширует online features, MongoDB хранит гибкие документы, а Elasticsearch/OpenSearch используется для поиска по логам или текстам.

    Для RAG-сервиса можно хранить:

    • исходные документы в объектном хранилище
    • метаданные документов в PostgreSQL
    • эмбеддинги чанков в векторной БД
    • временный кэш ответов и rate limit в Redis

    Это не "зоопарк ради зоопарка", если у каждого хранилища есть понятная роль.

      Key-value, документные, wide-column, графовые, time-series, поисковые и векторные хранилища.

    2. Когда NoSQL может быть лучше SQL?

      Когда данные плохо ложатся в таблицы, нужна гибкая схема, быстрый доступ по ключу, специализированный поиск или горизонтальное масштабирование под конкретный паттерн нагрузки.

    3. Какой главный риск у NoSQL для ML-продукта?

      Риск выбрать хранилище по моде, а не по запросам. Потом сложные аналитические выборки, консистентность и миграции данных становятся дороже, чем ожидалось.

  5. Что такое транзакции и ACID?↗

    Транзакция — логическая единица работы с БД, которая должна выполниться целиком или не выполниться вовсе.

    ACID — набор свойств транзакций: Atomicity, Consistency, Isolation, Durability.

    Свойства ACID:

    СвойствоСмысл
    AtomicityВсе операции транзакции применяются целиком или откатываются
    ConsistencyПосле транзакции данные остаются в допустимом состоянии
    IsolationПараллельные транзакции не должны некорректно мешать друг другу
    DurabilityЗафиксированные изменения не теряются при сбое

    Если ML-пайплайн записывает результат batch inference, удобно делать это транзакционно:

    1. записать новую версию предсказаний
    2. записать метаданные запуска
    3. обновить статус пайплайна
    4. зафиксировать изменения

    Если на третьем шаге всё упало, лучше откатить всё, чем оставить систему в состоянии "предсказания есть, но статус запуска неизвестен".

    Isolation важен для аналитики и обучения. Если во время построения датасета часть таблиц читается до обновления, а часть после, можно получить неконсистентную выборку. Для больших offline-выгрузок часто используют снапшоты, версионирование данных или отдельные аналитические реплики.

    1. Что такое транзакция?

      Набор операций с БД, который рассматривается как единая операция: либо все изменения применяются, либо все откатываются.

    2. Расшифруй ACID.

      Atomicity — атомарность, Consistency — согласованность, Isolation — изолированность, Durability — долговечность.

    3. Почему ACID важен для ML Engineer?

      Потому что пайплайны часто записывают несколько связанных сущностей: статусы, метрики, версии датасетов, предсказания и артефакты. Без транзакций легко получить неполное или противоречивое состояние.

  6. Что такое CAP-теорема?↗

    CAP-теорема говорит, что в распределённой системе при сетевом разделении нельзя одновременно гарантировать все три свойства: Consistency, Availability и Partition tolerance.

    Три буквы CAP:

    СвойствоСмысл
    ConsistencyВсе клиенты видят согласованное состояние данных
    AvailabilityКаждый корректный запрос получает ответ
    Partition toleranceСистема продолжает работать при сетевых разрывах между узлами

    В распределённой системе сетевые проблемы считаются неизбежными. Поэтому практический выбор чаще звучит так: что делать при partition — сохранять строгую согласованность или доступность?

    CAP часто упрощают до "выбери любые две буквы", но это грубая формулировка. В реальности системы настраивают компромиссы: кворумы чтения/записи, уровни консистентности, задержки репликации, eventual consistency, read-your-writes и другие гарантии.

    Для ML Engineer компромисс зависит от сценария:

    • Feature lookup для online inference: лучше не отдавать противоречивые критичные признаки, но иногда допустим слегка устаревший кэш.
    • Лента рекомендаций: eventual consistency часто приемлема.
    • Списание денег за платную генерацию: нужна строгая согласованность.
    • Метрики мониторинга: можно потерпеть задержку или небольшую неточность, зато система должна оставаться доступной.

  7. Что такое индексы в БД?↗

    Индекс в БД — дополнительная структура данных, которая ускоряет поиск строк по одному или нескольким столбцам. Индекс похож на оглавление книги: вместо полного просмотра таблицы СУБД может быстрее найти нужные записи.

    Индексы ускоряют чтение, но не бесплатны:

    • занимают место на диске
    • замедляют INSERT, UPDATE, DELETE
    • требуют обслуживания и статистики
    • могут не использоваться, если запрос написан неудачно или фильтр слишком широкий

    Частые типы индексов:

    ТипГде полезен
    B-Treeравенство, диапазоны, сортировка, самый частый выбор
    Hashточный поиск по равенству
    GIN / invertedмассивы, JSONB, full-text search
    GiST / spatialгеоданные, диапазоны, специальные типы
    Partialиндекс только на часть строк
    Functionalиндекс по выражению, например lower(email)

    Если online inference читает последние признаки пользователя, запрос вида:

    SELECT * FROM user_features WHERE user_id = 42 ORDER BY event_time DESC LIMIT 1;

    может выиграть от составного индекса:

    CREATE INDEX user_features_user_time_idx ON user_features (user_id, event_time DESC);

    Индексы нужно подбирать под реальные запросы, а не "на всякий случай". Для этого смотрят EXPLAIN, EXPLAIN ANALYZE, slow query logs, Query Analytics в PMM или аналоги в конкретной СУБД.

      Чтобы ускорять чтение и поиск строк, избегая полного просмотра больших таблиц.

      Индексы занимают место, замедляют запись и усложняют обслуживание. Лишний индекс может вредить.

      Понимать, почему фича-сервис или выгрузка датасета стали медленными, читать план запроса на базовом уровне и обсуждать индекс с backend/data-инженерами.

  8. Что такое sharding и replication?↗

    Replication — копирование данных между несколькими узлами БД.

    Sharding — горизонтальное разбиение данных на части, где разные шарды хранят разные строки или ключи.

    Репликация и шардинг решают разные задачи.

    МеханизмЧто даётТипичный риск
    ReplicationОтказоустойчивость, read replicas, резервные копиизадержка репликации, split-brain, сложный failover
    ShardingМасштабирование объёма данных и записисложные JOIN, ребалансировка, выбор shard key

    Если inference-сервис много читает справочник признаков, можно добавить read-replica и разгрузить primary. Если же таблица событий выросла до терабайтов и запись упирается в один узел, может понадобиться шардинг или перенос аналитической нагрузки в ClickHouse/BigQuery/Snowflake.

    Шардинг почти всегда дороже, чем кажется. До него часто пробуют:

    • правильные индексы
    • партиционирование
    • read replicas
    • кэширование
    • перенос аналитики из OLTP-БД
    • архивирование старых данных

    1. Чем репликация отличается от шардинга?

      Репликация создаёт копии одних и тех же данных. Шардинг делит разные части данных между узлами.

    2. Что такое lag репликации?

      Задержка между записью на primary и появлением этих данных на replica. Из-за lag можно прочитать устаревшее состояние.

    3. Почему shard key важен?

      От него зависит равномерность распределения данных и запросов. Плохой ключ приводит к горячим шардам и сложным запросам между шардами.

  9. Что мониторить в базе данных?↗

    DB monitoring — наблюдение за состоянием БД, запросами и инфраструктурой вокруг неё: CPU, RAM, диск, соединения, задержки, ошибки, репликация, slow queries и алерты.

    Для ML Engineer мониторинг БД важен, потому что деградация БД часто выглядит как "модель стала медленной", хотя проблема находится в чтении признаков, записи предсказаний или перегруженной аналитической витрине.

    Базовые группы метрик:

    ГруппаЧто смотреть
    ИнфраструктураCPU, RAM, disk I/O, свободное место, network
    Подключениячисло соединений, idle connections, pool saturation
    ЗапросыQPS, latency, slow queries, locks, ошибки
    Хранилищеразмер таблиц и индексов, bloat, рост данных
    Репликацияlag, состояние replica, failover
    Бэкапыуспешность, длительность, возможность восстановления

    Часто встречаются:

    • PMM (Percona Monitoring and Management) — мониторинг, алерты и query analytics для БД
    • Prometheus + Grafana — сбор метрик и дашборды
    • Zabbix — классический мониторинг инфраструктуры и сервисов
    • postgres_exporter / mysqld_exporter / mongodb_exporter — экспортеры метрик для Prometheus

    Если latency inference выросла, полезно проверить:

    1. не вырос ли p95/p99 запросов к feature store
    2. не закончились ли соединения в pool
    3. нет ли долгих блокировок
    4. не читает ли пайплайн обучения тяжёлую таблицу с primary
    5. не отстаёт ли реплика, из которой читается offline-аналитика

      Даже хорошая модель будет отвечать медленно, если признаки или метаданные достаются неэффективным запросом.

    3. Что такое query analytics?

      Анализ запросов к БД: какие запросы выполняются чаще всего, сколько занимают времени и какую нагрузку создают.

  10. Как думать о безопасности БД?↗

    Безопасность БД — набор практик, которые защищают данные от несанкционированного доступа, утечек, случайного удаления, подмены и нарушения доступности.

    Для ML Engineer безопасность БД особенно важна из-за данных. Обучающие выборки часто содержат персональные данные, бизнес-события, финансовые признаки или чувствительные тексты. Ошибка в доступах или выгрузке может быть дороже ошибки модели.

    Базовый минимум:

    • принцип наименьших привилегий
    • отдельные пользователи для приложения, аналитики, мониторинга и пайплайнов
    • запрет shared-аккаунтов
    • секреты в secret manager, а не в коде и ноутбуках
    • TLS для соединений
    • сетевые ограничения: private network, firewall, allowlist
    • регулярные бэкапы и проверка восстановления
    • аудит действий и логирование подозрительных запросов
    • маскирование или обезличивание чувствительных данных

    Для пайплайна обучения лучше создать отдельного пользователя с SELECT только на нужные витрины, а не выдавать права администратора на всю БД. Если пайплайн должен писать результаты, запись можно ограничить конкретной схемой или таблицами.

    Мониторинг безопасности — это не только "поймать взлом". Полезно видеть:

    • неудачные попытки логина
    • обращения к системным таблицам
    • массовые выгрузки
    • изменение ролей и паролей
    • создание дампов
    • доступ с непривычных адресов

    1. Что такое принцип наименьших привилегий?

      Пользователь или сервис получает только те права, которые нужны для работы, и ничего сверх этого.

    2. Почему нельзя хранить пароли от БД в ноутбуках?

      Ноутбуки часто попадают в git, шарятся между людьми и запускаются в разных окружениях. Секреты должны жить в secret manager или переменных окружения, управляемых платформой.

    3. Что особенно важно для ML-данных?

      Контроль доступа, обезличивание, аудит выгрузок, корректная работа с персональными данными и отделение production-данных от исследовательских окружений.
