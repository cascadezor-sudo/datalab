Материалы по метрикам, scraping и alerting.

    Блок 1

  1. Что такое Prometheus?↗

    Prometheus — open-source система мониторинга и алертинга, которая собирает метрики путём периодического опроса (scraping) HTTP-эндпоинтов. Хранит метрики в собственной time-series БД (TSDB) и предоставляет язык запросов PromQL.

    Модель работы Prometheus принципиально отличается от push-based систем: сервисы не отправляют метрики сами, а предоставляют endpoint /metrics, который Prometheus опрашивает по расписанию (обычно каждые 15–30 секунд).

    Service ──-> /metrics endpoint ←──(scrape)── Prometheus TSDB │ PromQL queries │ AlertManager │ Grafana

    Это упрощает архитектуру: каждый сервис просто выставляет метрики, а Prometheus сам решает, как часто их собирать.

    ML-сервисы в production нужно мониторить иначе, чем обычные API:

    • Latency inference — время ответа модели по перцентилям (p50, p95, p99)
    • Throughput — сколько запросов в секунду обрабатывает inference-сервис
    • Дрейф данных — метрики распределения входящих признаков и предсказаний
    • Качество модели — точность на свежей разметке, A/B-метрики
    • Ресурсы — GPU memory utilization, CPU, RAM во время обучения и inference
    • Feature pipeline — consumer lag, время обновления признаков в feature store
    • Батчевые пайплайны — время выполнения, количество обработанных записей, ошибки

    Prometheus + Grafana — стандартный стек для всего этого в большинстве ML-команд.

    Prometheus — self-hosted. В облачных стеках есть managed-аналоги:

    ИнструментСуть
    Grafana CloudManaged Prometheus + Grafana
    AWS CloudWatchМетрики в AWS (не Prometheus-совместимый, но Prometheus Remote Write поддерживается)
    Google Cloud MonitoringPrometheus-совместимый managed
    DatadogПолностью managed, Prometheus-метрики импортируются
    VictoriaMetricsSelf-hosted, Prometheus-совместимый, эффективнее при большом объёме

    Многие компании начинают с self-hosted Prometheus, а потом переходят на Grafana Cloud или VictoriaMetrics при росте нагрузки.

    1. Как Prometheus собирает метрики?

      По модели pull: сам опрашивает /metrics endpoint-ы сервисов по расписанию (scraping). Сервисы не отправляют данные сами.

    2. Что хранит Prometheus?

      Time-series данные: каждая метрика — последовательность пар (timestamp, значение), идентифицированная именем и набором labels.

    3. Какие метрики ML-сервиса важно мониторить через Prometheus?

      Latency inference (p95/p99), throughput (RPS), ошибки, распределение предсказаний, GPU utilization, consumer lag feature pipeline, время выполнения батчевых пайплайнов.

  2. Типы метрик в Prometheus

    Prometheus поддерживает четыре типа метрик:

    ТипСутьПример
    CounterМонотонно возрастающий счётчик, только увеличиваетсячисло запросов, число ошибок
    GaugeПроизвольное значение, может расти и падатьGPU memory, queue size, температура
    HistogramРаспределение значений по бакетам + сумма + countlatency запросов, размер батча
    SummaryКвантили на стороне клиента + сумма + countp50/p95/p99 latency

    Counter — только растёт (сброс при рестарте). В PromQL используют rate() или increase() для получения скорости роста:

    rate(http_requests_total[5m]) -> запросов в секунду за последние 5 минут

    Gauge — мгновенное значение. Можно брать напрямую или с агрегацией:

    gpu_memory_used_bytes / gpu_memory_total_bytes * 100 -> % GPU памяти

    Histogram — записывает распределение. Автоматически создаёт три временных ряда:

    • _bucket{le="0.1"} — сколько наблюдений $\leq 0.1$ сек
    • _sum — сумма всех значений
    • _count — число наблюдений

    В PromQL: histogram_quantile(0.95, rate(latency_seconds_bucket[5m])) — p95 latency.

    Summary vs Histogram: Summary считает квантили на клиенте (нельзя агрегировать по нескольким инстансам). Histogram считает квантили на сервере через PromQL, поэтому предпочтительнее для inference-сервисов с несколькими репликами.

    Что измеряемТипПочему
    Число inference-запросовCounterТолько растёт, нужна скорость
    Число ошибокCounterТолько растёт
    GPU memory utilizationGaugeМожет падать и расти
    Размер очереди задачGaugeТекущее значение
    Latency предсказанияHistogramНужны перцентили по нескольким репликам
    Распределение предсказаний моделиHistogramНужны бакеты для дрейф-мониторинга
    Значение признака (для дрейфа)HistogramОтслеживаем сдвиг распределения

    Prometheus-конвенция: <namespace>_<subsystem>_<name>_<unit>.

    inference_requests_total # Counter: всего запросов inference_errors_total # Counter: всего ошибок inference_latency_seconds # Histogram: latency inference_prediction_score # Histogram: распределение score модели feature_store_lookup_latency_seconds # Histogram: latency обращения к feature store model_gpu_memory_bytes # Gauge: GPU memory batch_job_processed_records_total # Counter: обработано записей в batch pipeline

    1. Чем Counter отличается от Gauge?

      Counter только растёт (сброс при рестарте), Gauge может принимать любое значение. Counter используют для подсчёта событий (запросы, ошибки), Gauge — для состояния (память, очередь).

    2. Почему для latency нужен Histogram, а не Gauge?

      Gauge показал бы только последнее значение. Histogram фиксирует распределение всех измерений и позволяет вычислить перцентили (p95, p99) через histogram_quantile().

    3. Чем Histogram лучше Summary для inference-сервиса с несколькими репликами?

      Summary считает квантили локально на каждом инстансе, их нельзя агрегировать. Histogram хранит бакеты, которые можно суммировать по всем репликам и считать единый p95.

    4. Как называть метрики по конвенции Prometheus?

      <namespace>_<subsystem>_<name>_<unit>, единицы измерения в конце (_seconds, _bytes, _total). _total — суффикс для Counter.

  3. Инструментирование Python-сервисов

    prometheus_client — официальная Python-библиотека для инструментирования сервисов. Позволяет объявить метрики в коде и автоматически экспортировать их через HTTP-эндпоинт /metrics.

    Минимальный workflow:

    1. Объявить метрики как глобальные объекты
    2. В нужных местах кода обновлять метрики (.inc(), .set(), .observe())
    3. Запустить HTTP-сервер метрик или подключить middleware к FastAPI/Flask
    4. Добавить сервис в prometheus.yml (scrape config)
    pip install prometheus-client

    Инструментирование FastAPI inference-сервиса

    from fastapi import FastAPI, Request from prometheus_client import Counter, Histogram, Gauge, make_asgi_app import time app = FastAPI() # --- Метрики --- REQUEST_COUNT = Counter( "inference_requests_total", "Всего inference-запросов", ["model_name", "status"], # labels ) REQUEST_LATENCY = Histogram( "inference_latency_seconds", "Latency inference в секундах", ["model_name"], buckets=[0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5], ) PREDICTION_SCORE = Histogram( "inference_prediction_score", "Распределение предсказаний модели", ["model_name"], buckets=[0.1 * i for i in range(11)], ) MODEL_LOADED = Gauge( "inference_model_loaded", "1 если модель загружена, 0 если нет", ["model_name"], ) # Экспортируем /metrics как ASGI-приложение metrics_app = make_asgi_app() app.mount("/metrics", metrics_app) # --- Inference endpoint --- @app.post("/predict") async def predict(request: Request): model_name = "recommender_v3" start = time.time() try: body = await request.json() score = model.predict(body["features"]) # ваша модель REQUEST_COUNT.labels(model_name=model_name, status="ok").inc() PREDICTION_SCORE.labels(model_name=model_name).observe(score) return {"score": score} except Exception as e: REQUEST_COUNT.labels(model_name=model_name, status="error").inc() raise finally: REQUEST_LATENCY.labels(model_name=model_name).observe(time.time() - start) # При старте сервиса MODEL_LOADED.labels(model_name="recommender_v3").set(1)

    Scrape-конфигурация Prometheus

    # prometheus.yml global: scrape_interval: 15s scrape_configs: - job_name: "inference-service" static_configs: - targets: ["inference-service:8000"] metrics_path: "/metrics" - job_name: "feature-pipeline" static_configs: - targets: ["feature-pipeline:8001"] # В Kubernetes — через service discovery - job_name: "kubernetes-pods" kubernetes_sd_configs: - role: pod relabel_configs: - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape] action: keep regex: "true"

    Context manager для автоматического измерения latency:

    with REQUEST_LATENCY.labels(model_name="v3").time(): score = model.predict(features)

    Декоратор для счётчика вызовов функции:

    @REQUEST_COUNT.labels(model_name="v3", status="ok").count_exceptions() def predict(features): return model.predict(features)

    1. Что нужно сделать, чтобы Prometheus начал собирать метрики с Python-сервиса?

      Объявить метрики через prometheus_client, обновлять их в коде, выставить endpoint /metrics и добавить сервис в scrape_configs в prometheus.yml.

    2. Зачем нужны labels в метриках?

      Labels позволяют разбить метрику по измерениям (модель, статус, регион) без создания отдельных метрик. В PromQL потом можно фильтровать и агрегировать по любому label.

    3. Почему важно не злоупотреблять количеством уникальных значений labels?

      Каждая уникальная комбинация labels создаёт отдельный time series. Высокая cardinality (user_id, request_id как labels) быстро переполняет Prometheus TSDB — это называется «кардинальность взрывается».

  4. PromQL: запросы к метрикам

    PromQL (Prometheus Query Language) — язык запросов к time-series данным Prometheus. Возвращает instant vector (значения в момент времени), range vector (значения за период) или scalar.

    Базовая структура: metric_name{label="value"}[duration]

    КонструкцияПримерЧто возвращает
    Instant vectorinference_requests_totalтекущее значение по каждому label-набору
    Label filterinference_requests_total{status="error"}только ошибки
    Range vectorinference_requests_total[5m]все значения за 5 минут
    rate()rate(inference_requests_total[5m])запросов/сек (по range vector Counter)
    increase()increase(inference_requests_total[1h])абсолютный прирост за час
    histogram_quantile()histogram_quantile(0.95, rate(inference_latency_seconds_bucket[5m]))p95 latency
    Агрегацияsum by (model_name) (rate(...))суммирует по model_name
    Делениеerrors / total * 100error rate в %

    Throughput (RPS):

    sum by (model_name) ( rate(inference_requests_total[5m]) )

    Error rate (%):

    100 * sum by (model_name) ( rate(inference_requests_total{status="error"}[5m]) ) / sum by (model_name) ( rate(inference_requests_total[5m]) )

    p95 latency:

    histogram_quantile( 0.95, sum by (model_name, le) ( rate(inference_latency_seconds_bucket[5m]) ) )

    GPU memory utilization (%):

    100 * model_gpu_memory_bytes{type="used"} / model_gpu_memory_bytes{type="total"}

    Kafka consumer lag (для feature pipeline):

    sum by (consumergroup, topic) ( kafka_consumergroup_lag )

    Среднее время batch job за последние 24 часа:

    increase(batch_job_duration_seconds_sum[24h]) / increase(batch_job_duration_seconds_count[24h])
    ФункцияПрименение
    rate(v[d])скорость роста Counter за период d
    increase(v[d])абсолютный прирост Counter за период
    histogram_quantile(φ, v)перцентиль из Histogram
    sum by (labels) (v)агрегация суммой по label
    avg by (labels) (v)среднее по label
    max by (labels) (v)максимум по label
    topk(n, v)n наибольших значений
    absent(v)возвращает 1, если метрика отсутствует (алерт на пропавший сервис)
    predict_linear(v[d], t)линейный прогноз значения через t секунд

    1. Зачем нужен rate() для Counter, а не просто сырое значение?

      Counter только растёт — сырое значение показывает общее накопленное число. rate() даёт скорость изменения (событий в секунду), что практически полезнее и правильно обрабатывает сброс при рестарте.

    2. Как получить p95 latency из Histogram?

      histogram_quantile(0.95, rate(latency_seconds_bucket[5m])) — берёт бакеты Histogram за последние 5 минут и вычисляет 95-й перцентиль.

    3. Что делает sum by (model_name) и зачем это нужно?

      Агрегирует метрику, суммируя по всем инстансам/репликам, оставляя разбивку только по model_name. Позволяет видеть суммарный RPS сервиса, а не отдельно по каждой реплике.

    4. Как написать запрос, который сработает, когда сервис перестал слать метрики?

      absent(up{job="inference-service"} == 1) — вернёт значение, если метрика up для нужного job-а отсутствует или равна 0.

  5. Алертинг: Alerting Rules и AlertManager

    Alerting Rules — PromQL-выражения в Prometheus, которые при выполнении условия генерируют алерт. AlertManager — отдельный компонент, получающий алерты от Prometheus и направляющий уведомления в Slack, PagerDuty, email, Telegram и другие каналы.

    Цепочка алертинга:

    Prometheus evaluates rules every 15s ↓ rule fires Prometheus sends alert to AlertManager ↓ routing + grouping + silencing AlertManager sends notification ↓ Slack / PagerDuty / Email / Telegram

    Alerting Rule имеет три состояния:

    • inactive — условие не выполняется
    • pending — условие выполняется, но ещё не прошёл for (grace period)
    • firing — условие выполняется дольше for — алерт активен

    Alerting Rules для ML-сервисов

    # alerts/inference.yml groups: - name: inference rules: # Сервис недоступен - alert: InferenceServiceDown expr: absent(up{job="inference-service"} == 1) for: 1m labels: severity: critical annotations: summary: "Inference-сервис недоступен" description: "Job {{ $labels.job }} не отвечает более 1 минуты." # Высокий error rate - alert: InferenceHighErrorRate expr: | 100 * sum by (model_name) ( rate(inference_requests_total{status="error"}[5m]) ) / sum by (model_name) ( rate(inference_requests_total[5m]) ) > 5 for: 5m labels: severity: warning annotations: summary: "Высокий error rate inference" description: "Модель {{ $labels.model_name }}: error rate {{ $value | humanize }}% > 5%" # p95 latency выше порога - alert: InferenceHighLatency expr: | histogram_quantile(0.95, sum by (model_name, le) ( rate(inference_latency_seconds_bucket[5m]) ) ) > 0.5 for: 5m labels: severity: warning annotations: summary: "p95 latency inference > 500ms" description: "Модель {{ $labels.model_name }}: p95={{ $value | humanizeDuration }}" # Kafka consumer lag растёт - alert: FeaturePipelineLagHigh expr: | sum by (consumergroup, topic) (kafka_consumergroup_lag) > 100000 for: 10m labels: severity: warning annotations: summary: "Consumer lag feature pipeline слишком высок" description: "Group={{ $labels.consumergroup }}, lag={{ $value }}"

    AlertManager routing

    # alertmanager.yml global: slack_api_url: "https://hooks.slack.com/services/..." route: receiver: "slack-ml-team" group_by: ["alertname", "model_name"] group_wait: 30s group_interval: 5m repeat_interval: 4h routes: - match: severity: critical receiver: "pagerduty-oncall" - match: severity: warning receiver: "slack-ml-team" receivers: - name: "slack-ml-team" slack_configs: - channel: "#ml-alerts" title: "{{ .GroupLabels.alertname }}" text: "{{ range .Alerts }}{{ .Annotations.description }}\n{{ end }}" - name: "pagerduty-oncall" pagerduty_configs: - service_key: "<key>"

    Практики хорошего алертинга:

    • Алерт должен требовать действия человека — не плоди алерты на всё подряд
    • Используй for: 5m чтобы не получать шум от временных всплесков
    • Severity: critical — будит ночью, warning — в Slack днём
    • Алертируй на симптомы (error rate, latency, lag), а не только на причины (CPU, disk)
    • Используй group_by и group_interval чтобы не получать шторм из 100 одинаковых уведомлений

    1. Что такое for: 5m в alerting rule?

      Grace period: алерт переходит в firing только если условие выполняется непрерывно 5 минут. Это защищает от шума при кратковременных всплесках.

    2. Чем отличается Prometheus Alerting Rules от AlertManager?

      Prometheus evaluates rules и генерирует алерты. AlertManager получает алерты и решает, куда отправить уведомление (Slack, PagerDuty), с учётом routing, grouping и silencing.

    3. На что правильно алертировать в ML-сервисе?

      На симптомы, которые влияют на пользователей: высокий error rate, p95 latency > порога, недоступность сервиса, рост consumer lag. Не стоит алертировать напрямую на CPU/RAM без корреляции с деградацией сервиса.

  6. Экспортёры: инфраструктурные метрики

    Exporter — отдельный процесс, который читает метрики из системы, не поддерживающей Prometheus нативно, и переводит их в Prometheus-формат. Prometheus scrape-ит exporter так же, как и любой другой сервис.

    Большинство инфраструктурных компонентов не умеют экспортировать метрики в Prometheus. Для них существуют готовые экспортёры:

    ЭкспортёрЧто мониторитКлючевые метрики для ML
    node_exporterLinux-узел (CPU, RAM, disk, network)CPU во время обучения, disk I/O датасетов
    nvidia_gpu_exporterGPU NVIDIAGPU utilization, memory, temperature
    kafka_exporterApache Kafkaconsumer lag, messages/s, under-replicated partitions
    postgres_exporterPostgreSQLconnections, query latency, replication lag
    redis_exporterRedismemory, hit rate, latency (для feature store)
    kube-state-metricsKubernetes объектыpod restart count, deployment status
    blackbox_exporterHTTP/TCP probeдоступность inference endpoint снаружи

    1. Зачем нужен exporter, если сервис сам не поддерживает Prometheus?

      Exporter читает метрики через нативный API системы (NVIDIA SMI, Kafka JMX, postgres stats) и транслирует их в Prometheus text format. Prometheus scrape-ит exporter, не зная ничего об оригинальном протоколе.

    2. Какой exporter важен для мониторинга обучения моделей на GPU?

      nvidia_gpu_exporter — показывает utilization, memory, температуру. Полезно убедиться, что GPU действительно загружен на 80–100% во время обучения, а не простаивает из-за узкого места в data loading.

    3. Что мониторит blackbox_exporter и зачем он нужен?

      Выполняет HTTP/TCP probe на эндпоинт снаружи и измеряет доступность и latency. Это «взгляд пользователя» — позволяет обнаружить недоступность сервиса до того, как пожалуются пользователи.
