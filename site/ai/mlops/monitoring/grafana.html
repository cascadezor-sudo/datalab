Grafana

Материалы по дашбордам и визуализации метрик.

    Блок 1

  1. Что такое Grafana?↗

    Grafana — open-source платформа для визуализации и мониторинга метрик, логов и трейсов. Подключается к различным источникам данных (Prometheus, Loki, ClickHouse, Elasticsearch, PostgreSQL и десяткам других) и строит интерактивные дашборды.

    Grafana — «стекло» над данными. Она сама не хранит метрики, а только визуализирует их из источников. Типичный стек:

    Сервисы -> Prometheus (хранение метрик) -> Grafana (визуализация) Сервисы -> Loki (хранение логов) -> Grafana (визуализация) Сервисы -> Tempo (хранение трейсов) -> Grafana (визуализация)

    Весь этот стек (Prometheus + Loki + Tempo + Grafana) называется Grafana OSS stack или PLG stack (Prometheus, Loki, Grafana).

    ML Engineer работает с Grafana как потребитель и строитель дашбордов:

    • Мониторинг inference-сервисов — latency, throughput, error rate в разбивке по моделям
    • Мониторинг обучения — GPU utilization, loss curve (если логируется в метрики), время эпох
    • Дрейф данных — распределение входящих признаков и предсказаний в динамике
    • Качество модели — A/B-метрики, точность на свежей разметке
    • Feature pipeline — consumer lag, задержка обновления признаков
    • Батчевые пайплайны — время выполнения, SLA, количество ошибок
    • Бизнес-метрики — CTR, конверсия, revenue per request — рядом с техническими

    Видеть всё это на одном дашборде помогает быстро находить деградацию модели и понимать её причины.

    Grafana умеет подключаться к множеству источников данных:

    Data SourceЧто даёт
    PrometheusМетрики сервисов, инфраструктуры, ML-пайплайнов
    LokiЛоги (структурированные и неструктурированные)
    ClickHouseАналитика, бизнес-метрики, events
    PostgreSQL / MySQLПроизвольные SQL-запросы к prod-данным
    ElasticsearchЛоги и полнотекстовый поиск
    Tempo / JaegerDistributed tracing
    AWS CloudWatchМетрики и логи AWS-сервисов
    BigQueryАналитика в GCP

    1. Что такое Grafana и что она хранит?

      Grafana — инструмент визуализации. Она не хранит данные, а подключается к источникам (Prometheus, Loki и др.) и строит дашборды поверх них.

    2. Что входит в стандартный OSS-стек мониторинга с Grafana?

      Prometheus (метрики) + Loki (логи) + Grafana (визуализация). Опционально Tempo или Jaeger для distributed tracing.

    3. Какие дашборды нужны ML Engineer?

      Inference latency/throughput/errors, GPU utilization, Kafka consumer lag, распределение предсказаний для drift-мониторинга, A/B-метрики, бизнес-метрики.

  2. Дашборды: структура и лучшие практики

    Dashboard — набор панелей (panels), организованных по строкам (rows), отображающих метрики за выбранный временной диапазон. Дашборд сохраняется как JSON и может быть выгружен, импортирован и версионирован в Git.

    Структура дашборда:

    Dashboard ├── Variables (переключатели: environment, model_name, region) ├── Row: "Service Health" │ ├── Panel: RPS (time series) │ ├── Panel: Error rate % (time series) │ └── Panel: p95 Latency (time series) ├── Row: "Model Quality" │ ├── Panel: Prediction score distribution (histogram) │ ├── Panel: Drift score (gauge) │ └── Panel: A/B CTR (bar chart) └── Row: "Infrastructure" ├── Panel: GPU utilization (time series) └── Panel: Consumer lag (time series)

    Типы панелей:

    ПанельКогда использовать
    Time seriesМетрики во времени (latency, RPS, lag)
    Stat / Big numberОдно текущее значение (uptime, error count)
    GaugeЗначение на шкале (GPU utilization %, error rate %)
    Bar chartСравнение по категориям (модели, регионы)
    HistogramРаспределение (score distribution)
    TableТабличные данные (топ медленных запросов)
    HeatmapРаспределение по времени (request latency heatmap)
    LogsСтроки логов из Loki

    Хорошая практика — один дашборд на «область ответственности»:

    ДашбордАудиторияСодержимое
    Inference SLOML + SRERPS, latency p50/p95/p99, error rate, uptime
    Model HealthML EngineerScore distribution, drift score, prediction volume
    Feature PipelineML + Data EngConsumer lag, признаки freshness, ошибки pipeline
    Training JobsML EngineerGPU util, epoch time, loss (если в метриках)
    A/B ExperimentsML + ProductCTR, conversion, revenue по группам

    2. Найти нужный дашборд (например, Node Exporter Full, ID: 1860)
    3. В Grafana: Dashboards $\to$ Import $\to$ Dashboard ID
    4. Указать Prometheus data source

    Популярные ID для ML/MLOps:

    IDНазвание

    Дашборды хранятся как JSON и должны быть в Git:

    # Экспорт через Grafana API curl -H "Authorization: Bearer $GRAFANA_TOKEN" \ http://grafana:3000/api/dashboards/uid/inference-slo \ | jq '.dashboard' > dashboards/inference-slo.json

    Grafana поддерживает provisioning: при старте автоматически загружает дашборды из папки — удобно для GitOps.

    1. Что такое row в Grafana-дашборде и зачем он нужен?

      Row — строка-группировщик для панелей. Позволяет логически разделить дашборд по областям (Service Health, Model Quality, Infrastructure) и сворачивать разделы.

    2. Почему дашборды нужно хранить в Git?

      Чтобы версионировать изменения, делать code review, восстанавливать дашборды после пересоздания Grafana и применять их через provisioning в GitOps-стиле.

    3. Какой тип панели выбрать для мониторинга распределения предсказаний?

      Histogram panel — показывает распределение значений. Для дрейф-мониторинга важно видеть форму распределения score, а не только среднее.

  3. Построение панелей: PromQL в Grafana

    В Grafana каждая панель содержит один или несколько запросов к data source. Для Prometheus это PromQL-запросы. Grafana автоматически подставляет временной диапазон ($__range) и интервал ($__rate_interval).

    $__rate_interval — специальная переменная Grafana: автоматически выбирает правильный интервал для rate() в зависимости от zoom уровня. Всегда используйте её вместо фиксированного [5m]:

    rate(inference_requests_total[$__rate_interval])

    $__range — текущий временной диапазон дашборда (например, 6h). Удобен для increase():

    increase(inference_requests_total[$__range])

    Legend format — шаблон легенды: {{model_name}} {{status}} автоматически заполняется значениями labels.

    RPS (запросов в секунду):

    # Query A sum by (model_name) ( rate(inference_requests_total[$__rate_interval]) ) # Legend: {{model_name}} # Visualization: Time series

    Error rate (%):

    # Query A 100 * sum by (model_name) ( rate(inference_requests_total{status="error"}[$__rate_interval]) ) / sum by (model_name) ( rate(inference_requests_total[$__rate_interval]) ) # Thresholds: 1% = yellow, 5% = red # Visualization: Time series

    Latency p50 / p95 / p99 (3 запроса на одной панели):

    # Query A — p50 histogram_quantile(0.50, sum by (model_name, le) ( rate(inference_latency_seconds_bucket[$__rate_interval]) )) # Query B — p95 histogram_quantile(0.95, sum by (model_name, le) ( rate(inference_latency_seconds_bucket[$__rate_interval]) )) # Query C — p99 histogram_quantile(0.99, sum by (model_name, le) ( rate(inference_latency_seconds_bucket[$__rate_interval]) )) # Legend: p{{quantile}} {{model_name}} # Unit: seconds

    GPU utilization (время обучения):

    avg by (gpu, instance) ( nvidia_gpu_duty_cycle ) # Unit: percent (0-100) # Thresholds: < 50% = yellow (GPU простаивает)

    Распределение предсказаний (дрейф-мониторинг):

    sum by (le) ( rate(inference_prediction_score_bucket[$__rate_interval]) ) # Visualization: Heatmap (ось Y = бакеты, цвет = плотность)

    Grafana умеет автоматически форматировать числа — выбирается в поле Unit панели:

    UnitПрименение
    secondslatency (показывает ms/µs автоматически)
    percent (0-100)utilization, error rate
    shortRPS, lag
    bytesmemory, disk
    reqpsrequests per second

    1. Почему в Grafana для rate() нужно использовать $__rate_interval вместо фиксированного [5m]?

      $__rate_interval автоматически масштабируется под текущий zoom дашборда. Фиксированный [5m] может давать неверные результаты при просмотре данных за часы или дни.

    2. Как на одной панели показать p50, p95 и p99 latency?

      Добавить три запроса A/B/C с histogram_quantile(0.50/0.95/0.99, ...), настроить Legend format для каждого.

    3. Какая визуализация подходит для мониторинга дрейфа распределения предсказаний?

      Heatmap — ось Y это бакеты Histogram, цвет = плотность. Позволяет визуально заметить сдвиг распределения предсказаний во времени.

  4. Template Variables: многоуровневые дашборды

    Template Variables — переменные в Grafana, которые позволяют динамически менять параметры запросов через dropdown-меню вверху дашборда. Переменная подставляется в PromQL-запросы как $variable_name.

    Без переменных нужен отдельный дашборд для каждой модели, окружения или региона. С переменными один дашборд работает для всех:

    ┌──────────────────────────────────────────────────────┐ │ environment: [production ▼] model: [recommender ▼] │ ├──────────────────────────────────────────────────────┤ │ RPS for recommender in production... │ │ p95 latency for recommender in production... │ └──────────────────────────────────────────────────────┘

    Типы переменных:

    ТипОписание
    QueryЗначения берутся из Prometheus (label values)
    CustomФиксированный список значений
    ConstantОдно фиксированное значение (datasource URL, prefix)
    IntervalВременной интервал ($__auto_interval)
    Data sourceВыбор data source из списка

    Переменная environment (из Prometheus label):

    Type: Query Data source: Prometheus Query: label_values(inference_requests_total, environment) Refresh: On dashboard load Multi-value: false Include All: false

    Переменная model_name (зависит от environment):

    Type: Query Query: label_values(inference_requests_total{environment="$environment"}, model_name) Refresh: On time range change Multi-value: true ← можно выбрать несколько моделей Include All: true ← опция "All models"

    Использование в PromQL:

    sum by (model_name) ( rate(inference_requests_total{ environment="$environment", model_name=~"$model_name" ← =~ для multi-value (regex) }[$__rate_interval]) )
    ПеременнаяLabelЗачем
    $environmentenvironmentproduction / staging / canary
    $model_namemodel_nameверсии и типы моделей
    $regionregionмультирегиональный деплой
    $instanceinstanceконкретный pod / сервер
    $interval—Interval variable для агрегации

    Interval variable — позволяет переключать шаг агрегации (1m / 5m / 1h):

    Type: Interval Values: 1m,5m,15m,1h,6h,1d Auto option: on

    Использование в запросе:

    avg_over_time(inference_latency_p95[$__rate_interval])

    1. Зачем нужны template variables в дашборде?

      Чтобы один дашборд работал для любой комбинации environment, модели, региона — через dropdown вместо дублирования дашбордов.

    2. Как использовать multi-value переменную в PromQL?

      С оператором regex match =~: {model_name=~"$model_name"}. При выборе нескольких значений Grafana автоматически формирует model_name=~"v1|v2|v3".

    3. Что делает параметр Refresh: On dashboard load у переменной?

      Grafana обновляет список значений из Prometheus при каждой загрузке дашборда. Это важно для переменных типа model_name — когда деплоится новая модель, она сразу появляется в dropdown.

  5. Алертинг в Grafana

    Grafana Alerting (Unified Alerting, начиная с Grafana 8+) — встроенная система алертинга, которая работает параллельно с Prometheus Alerting Rules. Grafana сама evaluates PromQL-правила и отправляет уведомления через Contact Points (Slack, PagerDuty, email и др.).

    Grafana Alerting vs Prometheus AlertManager:

    Prometheus Alerting RulesGrafana Alerting
    Где живут правилаalerts/*.yml в PrometheusGrafana UI / provisioning
    Источники данныхТолько PrometheusPrometheus, Loki, ClickHouse, SQL, ...
    ВизуализацияНетПрямо на дашборде
    Силencing / routingAlertManagerGrafana Alerting
    GitOpsЛучшеЧерез provisioning

    Для ML-команд удобно, когда алерт видно прямо на дашборде в виде аннотации — сразу понятно, при каком значении метрики он сработал.

    Пример: алерт на высокий p95 latency inference-сервиса.

    Alert rule:

    # Grafana provisioning: alerts/inference.yaml apiVersion: 1 groups: - orgId: 1 name: "ML Inference Alerts" folder: "ML Monitoring" interval: 1m rules: - uid: inference-latency-high title: "Inference p95 Latency High" condition: C data: - refId: A datasourceUid: prometheus model: expr: | histogram_quantile(0.95, sum by (model_name, le)( rate(inference_latency_seconds_bucket[5m]) ) ) - refId: C datasourceUid: "__expr__" model: type: threshold conditions: - evaluator: type: gt params: [0.5] # > 500ms for: 5m labels: severity: warning annotations: summary: "p95 latency > 500ms для {{ $labels.model_name }}"

    Contact Point — куда отправлять (Slack, PagerDuty, Telegram, email).

    Notification Policy — правила маршрутизации: какие алерты куда идут.

    Default policy -> slack-ml-team ├── severity=critical -> pagerduty-oncall └── team=ml -> slack-ml-alerts

    Grafana поддерживает silences — временное отключение алертов (например, во время планового maintenance или A/B-эксперимента, который намеренно меняет метрики).

    Алерты Grafana можно показывать как аннотации на time series панелях — вертикальная полоса в момент срабатывания. Это мощный инструмент для root cause analysis: видно, что именно произошло с метрикой при алерте.

    Настройка: панель $\to$ Alert tab $\to$ включить аннотации.

    1. В чём преимущество Grafana Alerting перед Prometheus Alerting Rules?

      Grafana Alerting работает с любыми data sources (не только Prometheus), алерты видны прямо на дашборде как аннотации, и логика routing/silencing встроена без отдельного AlertManager.

    2. Когда лучше использовать Prometheus Alerting Rules?

      Когда важна GitOps-чистота (YAML в репозитории), все данные только в Prometheus, и уже используется AlertManager для routing. Для Kubernetes-среды это часто предпочтительнее.

    3. Что такое silence и когда его применяют?

      Временное отключение алертов по условию (label match). Применяется при плановом maintenance, деплое новой версии модели, или намеренном A/B-эксперименте, который меняет метрики.

  6. Loki: логи в Grafana

    Grafana Loki — система агрегации логов, оптимизированная для работы с Grafana. В отличие от Elasticsearch, Loki не индексирует содержимое логов — только метаданные (labels). Это делает его дешевле в хранении, но быстрее при поиске по labels.

    Язык запросов — LogQL.

    Архитектура PLG-стека с Loki:

    Сервис пишет логи в stdout/stderr ↓ Promtail / Grafana Alloy (агент) читает логи, добавляет labels, отправляет в Loki ↓ Loki (хранение логов с индексом по labels) ↓ Grafana (панели с логами, корреляция с метриками)

    Loki vs Elasticsearch:

    LokiElasticsearch
    ИндексированиеТолько labelsПолный текст
    Стоимость храненияНизкаяВысокая
    Поиск по текстуМедленнее (grep по сжатым чанкам)Быстрее
    Интеграция с GrafanaНативнаяЧерез plugin
    Типичное применениеCloud-native, KubernetesБольшие объёмы, full-text

    Базовый синтаксис: {selector} |= "filter" | parser | метрика

    # Все логи inference-сервиса с ошибками {job="inference-service", environment="production"} |= "ERROR" # Логи с парсингом JSON и фильтром по полю {job="inference-service"} | json | model_name="recommender_v3" | duration > 500ms # Количество ошибок в минуту (метрика из логов) sum by (model_name) ( rate({job="inference-service"} |= "ERROR" | json | __error__="" [1m]) )

    Promtail-конфигурация для ML-сервисов

    # promtail.yml server: http_listen_port: 9080 clients: - url: http://loki:3100/loki/api/v1/push scrape_configs: - job_name: inference-service static_configs: - targets: - localhost labels: job: inference-service environment: production __path__: /var/log/inference/*.log - job_name: feature-pipeline static_configs: - targets: - localhost labels: job: feature-pipeline __path__: /var/log/pipeline/*.log # Kubernetes pods - job_name: kubernetes-pods kubernetes_sd_configs: - role: pod pipeline_stages: - json: expressions: level: level model_name: model_name latency_ms: latency_ms - labels: level: model_name:

    Самая мощная возможность Loki в Grafana — переход от метрики к логу в один клик. При высоком p95 latency на Prometheus-панели можно открыть логи inference-сервиса за тот же период прямо в Grafana через Explore или Logs panel.

    Настраивается через Data Links в панели:

    Title: View logs URL: /explore?datasource=loki&queries=[{...filters from labels...}]

    1. Чем Loki отличается от Elasticsearch в подходе к индексированию?

      Loki индексирует только labels (метаданные), а не содержимое логов. Это дешевле по хранению и памяти, но поиск по тексту медленнее — Loki грепает по сжатым чанкам.

    2. Что такое LogQL и как он связан с PromQL?

      LogQL — язык запросов Loki, синтаксически похожий на PromQL. Позволяет фильтровать логи по labels и тексту, а также строить метрики из логов (rate ошибок, count событий).

    3. Как использовать Loki совместно с Prometheus в Grafana?

      Панели с метриками (Prometheus) и логами (Loki) живут на одном дашборде. Через Data Links можно переходить от всплеска метрики прямо к логам за тот же промежуток — это ускоряет root cause analysis.
