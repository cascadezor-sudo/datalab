Практика: Продуктовые метрики и SQL

Практикум по расчету ключевых продуктовых показателей на реальных данных: SQL-запросы для DAU/MAU, воронок, когортного Retention в Pandas, юнит-экономики и анализа просадок.

  1. Практика: Расчет DAU и MAU в SQL

    Практическая задача: Написание высокопроизводительного SQL-запроса для расчета суточной аудитории (DAU), скользящей 30-дневной месячной аудитории (Rolling MAU) и коэффициента Stickiness Ratio ($\frac{\mathrm{DAU}}{\mathrm{MAU}} \times 100\%$) на базе ClickHouse / PostgreSQL без полных блокировок таблиц.

    Если совсем простыми словами: это классическая задача с технического собеседования на позицию Product Data Analyst. Никаких «календарных» месяцев: строгий расчет скользящего 30-дневного окна для каждой даты.

    Архитектурный подход к оптимизации SQL:

    1. Шаг 1 (Предагрегация): Сначала сворачиваем миллиарды сырых событий в уникальные пары (event_date, user_id). Это сокращает объем обрабатываемых строк в 100 раз.
    2. Шаг 2 (Самообъединение или оконная агрегация): Для каждой даты $D$ находим количество уникальных пользователей в интервале $[D - 29, D]$. В ClickHouse для этого идеально подходит массив дат или оконная функция.
    3. Шаг 3: Расчет отношения $\mathrm{Stickiness} = \mathrm{round}(\mathrm{DAU} / \mathrm{MAU} \times 100, 2)$.

    Условие кейса: Дана таблица событий app_events (event_time DateTime, user_id UInt64, event_name String). Целевые активные события: app_open, send_message, make_transfer. Период: последние 60 дней. Требуется рассчитать ежедневный DAU, 30-дневный Rolling MAU и Stickiness.

    -- Высокопроизводительный расчет в ClickHouse
WITH daily_users AS (
    -- Шаг 1: Уникальные пользователи по дням
    SELECT
        toDate(event_time) AS report_date,
        user_id
    FROM app_events
    WHERE event_name IN ('app_open', 'send_message', 'make_transfer')
      AND event_time >= today() - 90
    GROUP BY report_date, user_id
),
daily_dau AS (
    SELECT
        report_date,
        count(user_id) AS dau
    FROM daily_users
    GROUP BY report_date
)
SELECT
    d.report_date,
    d.dau,
    -- Шаг 2: Скользящий 30-дневный MAU
    (
        SELECT uniqExact(sub.user_id)
        FROM daily_users AS sub
        WHERE sub.report_date BETWEEN d.report_date - 29 AND d.report_date
    ) AS rolling_mau,
    -- Шаг 3: Stickiness
    round(d.dau / rolling_mau * 100, 2) AS stickiness_pct
FROM daily_dau AS d
WHERE d.report_date >= today() - 60
ORDER BY d.report_date DESC;
    • Использование COUNT(DISTINCT) по сырым логам внутри скользящего окна. Приводит к квадратичной сложности и OOM (Out Of Memory) на больших объемах данных.
    • Забывание о фильтрации по типу событий. Включение технических фоновых событий (background_sync) искусственно раздувает аудиторию.
    • Использование календарного месяца вместо скользящего окна 30 дней. Календарный месяц скачет в зависимости от длины месяца (28-31 день).
    • Ошибочное деление на ноль в первый день запуска продукта. Необходима защита через nullif(rolling_mau, 0).

    На собеседовании: «Как оптимизировать этот запрос в ClickHouse, если таблица содержит 10 миллиардов строк?» Ответ: «Создать Materialized View с движком AggregatingMergeTree и типом колонки AggregateFunction(uniq, UInt64) по группировке (event_date). При выборке скользящего окна мы мгновенно объединяем 30 HLL-состояний через uniqMerge() за доли секунды без сканирования сырых строк».

    1. Что такое скользящий MAU (Rolling MAU)?

      Количество уникальных активных пользователей за последние 30 дней относительно каждой точки времени.

    2. Что измеряет показатель Stickiness Ratio?

      Регулярность использования продукта пользователями: отношение суточной активности к месячной.

    3. Какая агрегатная функция ClickHouse обеспечивает максимальную точность дедупликации?

      uniqExact() (или приближенная сверхбыстрая uniq() на базе HyperLogLog).

    4. Почему сначала нужно сделать GROUP BY (date, user_id)?

      Для схлопывания дубликатов действий одного человека внутри суток до выполнения тяжелых скользящих агрегаций.

    5. Какой бенчмарк Stickiness характерен для успешных социальных сетей?

      Выше 50%.

  2. Практика: Построение продуктовой воронки в SQL

    Практическая задача: Написание SQL-запроса для построения 4-шаговой продуктовой воронки чекаута e-commerce: Каталог $\to$ Корзина $\to$ Чекаут $\to$ Оплата с ограничением по времени прохождения (конверсионное окно 2 часа). Расчет абсолютного числа пользователей, конверсии к первому шагу и конверсии между соседними шагами.

    Если совсем простыми словами: это скрипт, находящий место максимальной потери клиентов в процессе покупки.

    Два подхода к расчету воронок в SQL:

    1. Стандартный SQL (Self-Joins / Conditional Aggregation): Соединение шагов по пользователю с условием t2.event_time > t1.event_time AND t2.event_time <= t1.event_time + INTERVAL 2 HOUR.
    2. ClickHouse-way (windowFunnel): Нативная векторизованная функция, работающая в десятки раз быстрее:

      windowFunnel(7200)(event_time, cond1, cond2, cond3, cond4)

    Условие кейса: Таблица events (user_id, event_name, event_time). Шаги воронки: 1. view_catalog 2. add_to_cart 3. start_checkout 4. purchase_success Окно конверсии: 7200 секунд (2 часа). Период: за последние 7 дней.

    -- Решение в ClickHouse через специализированный windowFunnel
WITH funnel_levels AS (
    SELECT
        user_id,
        windowFunnel(7200)( -- 2 часа в секундах
            event_time,
            event_name = 'view_catalog',
            event_name = 'add_to_cart',
            event_name = 'start_checkout',
            event_name = 'purchase_success'
        ) AS max_step
    FROM events
    WHERE event_time >= now() - INTERVAL 7 DAY
    GROUP BY user_id
)
SELECT
    step_name,
    users_reached,
    -- Конверсия к первому шагу (Overall Conversion)
    round(users_reached / (SELECT count() FROM funnel_levels WHERE max_step >= 1) * 100, 2) AS cr_to_first_step,
    -- Конверсия к предыдущему шагу (Step-by-Step Conversion)
    round(users_reached / nullif(lagInFrame(users_reached) OVER (), 0) * 100, 2) AS step_cr
FROM (
    SELECT '1_view_catalog'    AS step_name, countIf(max_step >= 1) AS users_reached FROM funnel_levels
    UNION ALL
    SELECT '2_add_to_cart'     AS step_name, countIf(max_step >= 2) AS users_reached FROM funnel_levels
    UNION ALL
    SELECT '3_start_checkout'  AS step_name, countIf(max_step >= 3) AS users_reached FROM funnel_levels
    UNION ALL
    SELECT '4_purchase_success' AS step_name, countIf(max_step >= 4) AS users_reached FROM funnel_levels
)
ORDER BY step_name ASC;
    • Использование строгого знака равенства (max_step = 2) вместо (max_step >= 2). Пользователь, дошедший до 4-го шага, обязан учитываться на всех предшествующих шагах (1, 2 и 3).
    • Отсутствие ограничения временного окна. Без окна покупка через 3 месяца после просмотра каталога ошибочно свяжется в одну воронку.
    • Игнорирование хронологии шагов. Покупка не может засчитываться, если она произошла раньше добавления в корзину.
    • Забывание о NULL при делении на предыдущий шаг. В первом шаге предыдущего значения нет, требуется обработка через nullif().

    На собеседовании: «Как посчитать воронку в стандартном PostgreSQL без функции windowFunnel?» Ответ: «Через условную агрегацию: находим время первого шага $t_1$, затем время второго шага $t_2 > t_1$, затем $t_3 > t_2$ внутри CTE по каждому пользователю. Затем суммируем флаги COUNT(user_id) FILTER (WHERE t1 IS NOT NULL), FILTER (WHERE t2 IS NOT NULL) и т.д.».

    1. Что возвращает функция windowFunnel в ClickHouse?

      Максимальный достигнутый индекс шага воронки (от 0 до числа условий), уложившийся в заданный временной тайм-аут.

    2. Почему при подсчете воронки используется условие max_step >= N, а не max_step = N?

      Потому что воронка кумулятивна: пользователь, завершивший 3-й шаг, физически прошел 1-й и 2-й шаги.

    3. Что такое Step-by-Step Conversion Rate?

      Отношение числа пользователей на текущем шаге к числу пользователей строго на предыдущем шаге.

    4. Какое окно конверсии принято считать стандартным для e-commerce сессий?

      От 1 до 24 часов в зависимости от специфики покупки.

    5. Как найти главное «узкое место» воронки?

      По минимальному значению Step-by-Step конверсии вдоль воронки.

  3. Практика: Когортный Retention в Pandas

    Практическая задача: Построение классической когортной матрицы удержания (Retention Table) с нуля на языке Python с использованием библиотеки Pandas. Группировка пользователей по месяцу первой активности, расчет жизненного цикла (Lifetime Period) и вывод процентной тепловой матрицы.

    Если совсем простыми словами: это скрипт, строящий красивую треугольную таблицу удержания клиентов для продуктового отчета.

    Пошаговый алгоритм на Pandas:

    1. Преобразуем даты в месячные периоды: df['order_period'] = df['order_date'].dt.to_period('M').
    2. Определяем дату когорты каждого пользователя: df['cohort_group'] = df.groupby('user_id')['order_period'].transform('min').
    3. Вычисляем возраст когорты в месяцах: df['cohort_lifetime'] = (df['order_period'] - df['cohort_group']).apply(lambda x: x.n).
    4. Строим сводную таблицу (pivot table): строки — когорты, столбцы — возраст когорты, значения — nunique('user_id').
    5. Делим каждую строку на размер нулевого месяца: retention_matrix.divide(cohort_sizes, axis=0) * 100.

    Условие кейса: Дан датасет транзакций пользователей e-commerce с января по июнь 2026 года. Требуется рассчитать процентный Retention первого, второго, третьего и последующих месяцев для каждой когорты и вывести матрицу.

    import pandas as pd
import numpy as np

# 1. Генерация реалистичного датасета активности
np.random.seed(42)
n_orders = 100000

user_ids = np.random.randint(1000, 5000, size=n_orders)
dates = pd.date_range("2026-01-01", "2026-06-30", freq="h")
order_dates = np.random.choice(dates, size=n_orders)

df = pd.DataFrame({"user_id": user_ids, "order_date": order_dates})

# 2. Определение когорты и периодов
df["period"] = df["order_date"].dt.to_period("M")
df["cohort"] = df.groupby("user_id")["period"].transform("min")
df["lifetime_month"] = (df["period"] - df["cohort"]).apply(lambda x: x.n)

# 3. Построение когортной матрицы
cohort_pivot = df.pivot_table(
    index="cohort",
    columns="lifetime_month",
    values="user_id",
    aggfunc="nunique"
)

# 4. Нормализация в проценты
cohort_size = cohort_pivot[0]
retention_matrix = cohort_pivot.divide(cohort_size, axis=0) * 100

print("КОГОРТНАЯ МАТРИЦА УДЕРЖАНИЯ RETENTION (%):")
print(retention_matrix.round(1))
    • Использование разности обычных дат вместо периодов. Вычитание дат 31 января и 1 февраля даст разницу в 1 день, хотя это разные календарные месяцы. Использование Period('M') решает проблему идеально.
    • Забывание об удалении дубликатов визитов. Один пользователь совершает 10 заказов в месяц. Функция агрегации обязана быть nunique, а не count.
    • Включение неполных текущих месяцев без предупреждения. Текущий незавершенный месяц исказит показатели удержания.
    • Деление не на ту ось. Деление axis=1 вместо axis=0 приведет к делению по колонкам вместо размера когорты.

    На собеседовании: «Как на собеседовании быстро написать когортный анализ в 3 строки Pandas?» Ответ: «1) Считаем когорту: df['c'] = df.groupby('u')['d'].transform('min').dt.to_period('M'); 2) Считаем лаг: df['l'] = (df['d'].dt.to_period('M') - df['c']).apply(lambda x: x.n); 3) Сводная таблица с делением: p = df.pivot_table(index='c', columns='l', values='u', aggfunc='nunique'); p.div(p[0], axis=0) * 100».

    1. Что является строками, а что столбцами в когортной матрице удержания?

      Строки — когорты по времени первого действия; столбцы — возраст когорты (Lifetime) в днях, неделях или месяцах.

    2. Почему нулевой столбец (Lifetime = 0) всегда равен 100%?

      Потому что это базовый размер когорты: все пользователи когорты были активны в период своего прихода.

    3. Как интерпретировать падение значений по диагонали матрицы?

      Падение по диагонали отражает влияние конкретного календарного месяца (например, сезонный спад или авария серверов).

    4. Какая агрегатная функция применяется к ID пользователей при построении когортной таблицы?

      nunique() для исключения повторных действий одного и того же клиента.

    5. Как визуализировать полученную матрицу в отчете?

      С помощью тепловой карты sns.heatmap(retention_matrix, annot=True, cmap='Blues').

  4. Практика: Расчет ARPU и когортного LTV в Pandas

    Практическая задача: Расчет монетизационных метрик продукта на языке Python: вычисление ARPU, ARPPU и Paying Share по месяцам, а также построение когортного накопительного LTV (Cumulative LTV) по поколениям пользователей.

    Если совсем простыми словами: это скрипт, показывающий, сколько чистых денег накапливает каждый привлеченный клиент к 1, 3, 6 и 12 месяцу жизни в сервисе.

    Математика расчета накопительного LTV:

    1. Для каждой когорты определяем исходный размер аудитории в месяц 0: $N_{\text{cohort}}$.
    2. Для каждого месяца жизни $t \ge 0$ суммируем выручку когорты: $\mathrm{Rev}_{\text{cohort}}(t)$.
    3. Накопительный LTV к возрасту $T$:

      $$\mathrm{LTV}(T) = \sum_{t=0}^T \frac{\mathrm{Rev}_{\text{cohort}}(t)}{N_{\text{cohort}}}$$

    Условие кейса: Дан датасет транзакций пользователей с суммой revenue_rub и датой оплаты. Требуется рассчитать: 1. ARPU и ARPPU за последний месяц. 2. Матрицу кумулятивного LTV по месяцам жизненного цикла когорт.

    import pandas as pd
import numpy as np

# 1. Генерация транзакционных данных
np.random.seed(42)
n_tx = 50000

user_ids = np.random.randint(100, 2000, size=n_tx)
dates = pd.date_range("2026-01-01", "2026-06-30", freq="h")
tx_dates = np.random.choice(dates, size=n_tx)
revenue = np.random.exponential(scale=1200, size=n_tx) + 100

df = pd.DataFrame({"user_id": user_ids, "tx_date": tx_dates, "revenue": revenue})

# 2. Расчет когорт
df["period"] = df["tx_date"].dt.to_period("M")
df["cohort"] = df.groupby("user_id")["period"].transform("min")
df["lifetime"] = (df["period"] - df["cohort"]).apply(lambda x: x.n)

# 3. Исходный размер когорты (покупатели в M0)
cohort_sizes = df[df["lifetime"] == 0].groupby("cohort")["user_id"].nunique()

# 4. Сводная выручка по когорте и возрасту
revenue_pivot = df.pivot_table(
    index="cohort",
    columns="lifetime",
    values="revenue",
    aggfunc="sum"
).fillna(0)

# 5. Средняя выручка на одного пользователя когорты в месяц t
arpu_cohort = revenue_pivot.divide(cohort_sizes, axis=0)

# 6. Кумулятивный накопительный LTV
cumulative_ltv = arpu_cohort.cumsum(axis=1)

print("КУМУЛЯТИВНЫЙ КОГОРТНЫЙ LTV (РУБ.):")
print(cumulative_ltv.round(1))
    • Деление выручки месяца t на активных пользователей месяца t вместо исходного размера когорты. Это дает ARPU активных пользователей, а не накопительный LTV когорты! Знаменатель LTV обязан быть зафиксирован на размере когорты в день $0$.
    • Забывание о нулях для месяцев без покупок. Пропуски в сводной таблице обязаны заполняться нулями через fillna(0) перед кумулятивным суммированием cumsum().
    • Игнорирование себестоимости. LTV по выручке без умножения на Gross Margin завышает реальную ценность клиента.
    • Сравнение когорт разного возраста. Когорта января прожила 6 месяцев, а когорта мая — только 2 месяца. Сравнивать их можно только на одинаковом срезе (напр., LTV M2).

    На собеседовании: «В чем разница между кривой удержания (Retention) и кривой когортного LTV во времени?» Ответ: «Кривая Retention — монотонно убывающая (доля активных пользователей со временем падает или выходит на плато). Кривая кумулятивного LTV — строго монотонно возрастающая (выручка только накапливается с каждой новой покупкой). Наклон кривой LTV отражает текущую силу монетизации старых клиентов».

    1. Что показывает кумулятивный когортный LTV?

      Накопленную среднюю сумму выручки (или валовой прибыли), принесенную одним пользователем когорты к возрасту N месяцев.

    2. Какая функция Pandas используется для расчета накопительного итога вдоль строки?

      Метод .cumsum(axis=1).

    3. Почему знаменатель при расчете LTV когорты фиксируется на размере когорты в период 0?

      Чтобы учесть вклад всей первоначальной когорты, включая тех пользователей, кто уже оттек.

    4. Как с помощью матрицы кумулятивного LTV определить точку окупаемости CAC?

      Найти месяц Lifetime, в котором значение ячейки LTV впервые превышает стоимость привлечения CAC.

    5. Что означает, если кривая кумулятивного LTV становится совершенно плоской?

      Это означает, что пользователи когорты полностью прекратили совершать повторные покупки (100% Churn).

  5. Практика: Анализ узких мест в воронке

    Практическая задача: Аналитический разбор воронки мобильного приложения с расчетом потенциального прироста выручки при устранении «узкого горлышка» (Bottleneck). Оценка эластичности макроконверсии к изменениям микроконверсий отдельных шагов.

    Если совсем простыми словами: это математический расчет ответа на вопрос: «Сколько миллионов рублей заработает компания, если починить один кривой шаг в приложении?»

    Математика расчета потенциала воронки:

    1. Сквозная конверсия воронки из $K$ шагов равна произведению поэтапных конверсий:

      $$\mathrm{CR}_{\text{total}} = \prod_{i=1}^{K-1} \mathrm{CR}_{i \to i+1}$$

    2. Если конверсия шага $j$ вырастет в $1 + \delta$ раз, вся сквозная конверсия вырастет ровно в $1 + \delta$ раз:

      $$\Delta \mathrm{Revenue} = \mathrm{Revenue}_{\text{base}} \times \delta_j$$

    3. Правило максимального рычага: Повысить конверсию слабого шага с 10% до 15% ($+50\%$ относительного роста) в разы проще и прибыльнее, чем выжимать крохи из шага с конверсией 95%.

    Условие кейса: Входной трафик: $200\,000$ пользователей в месяц. Шаг 1 (Установка $\to$ Регистрация): $60\%$ ($120\,000$). Шаг 2 (Регистрация $\to$ Просмотр каталога): $80\%$ ($96\,000$). Шаг 3 (Каталог $\to$ Корзина): $15\%$ ($14\,400$). Шаг 4 (Корзина $\to$ Оплата): $25\%$ ($3\,600$). Средний чек: $3\,000$ руб. Текущая месячная выручка: $10.8$ млн руб. Аналитик предлагает оптимизировать Шаг 3 (поиск и фильтры) и поднять его конверсию с $15\%$ до $20\%$. Требуется рассчитать новый объем заказов и финансовый инкремент выручки.

    # Моделирование влияния оптимизации шага воронки на выручку
traffic = 200000
cr_1_2 = 0.60
cr_2_3 = 0.80
cr_3_4_base = 0.15 # шаг Каталог -> Корзина (база)
cr_3_4_opt  = 0.20 # оптимизированный вариант
cr_4_5 = 0.25
aov = 3000.0 # руб.

# Базовый сценарий
orders_base = traffic * cr_1_2 * cr_2_3 * cr_3_4_base * cr_4_5
revenue_base = orders_base * aov

# Оптимизированный сценарий
orders_opt = traffic * cr_1_2 * cr_2_3 * cr_3_4_opt * cr_4_5
revenue_opt = orders_opt * aov

increment_orders = orders_opt - orders_base
increment_revenue = revenue_opt - revenue_base
relative_growth = increment_revenue / revenue_base

print(f"Базовые заказы:   {orders_base:8,.0f} | Выручка: {revenue_base:12,.0f} руб.")
print(f"Новые заказы:     {orders_opt:8,.0f} | Выручка: {revenue_opt:12,.0f} руб.")
print(f"Прирост заказов:  {increment_orders:+8,.0f} заказов/мес.")
print(f"Инкремент выручки:{increment_revenue:+12,.0f} руб./мес. ({relative_growth:+.1%})")
    • Оптимизация шагов с высокой базовой конверсией. Пытаться поднять конверсию с 95% до 98% требует колоссальных сил при минимальном финансовом выхлопе.
    • Игнорирование снижения среднего чека. Упрощение добавления в корзину может привлечь мелкие покупки, снизив средний чек AOV.
    • Игнорирование качества аудитории. Привлечение неплатежеспособного трафика раздует верх воронки, но срежет конверсию на этапе оплаты.
    • Забывание о capacity инфраструктуры. Резкий рост заказов может парализовать складскую логистику.

    На собеседовании: «Если мы улучшим конверсию шага воронки с 20% до 25%, как изменится итоговая выручка сервиса при неизменном среднем чеке?» Ответ: «Так как итоговая конверсия мультипликативна, она вырастет ровно пропорционально относительному росту шага: $(25 - 20) / 20 = +25\%$. Следовательно, число заказов и общая выручка сервиса увеличатся ровно на $+25\%$».

    1. Каково математическое свойство мультипликативности продуктовой воронки?

      Сквозная конверсия равна произведению конверсий всех промежуточных шагов воронки.

    2. Что такое эффект узкого горлышка (Bottleneck)?

      Этап воронки с наименьшей относительной конверсией или наибольшим абсолютным оттоком пользователей.

    3. Как относительный прирост конверсии одного шага влияет на сквозную конверсию?

      Сквозная конверсия увеличивается строго на тот же относительный процент.

    4. Почему оптимизация слабого звена воронки эффективнее оптимизации сильного?

      Потому что слабый шаг имеет наибольший потенциал роста при равных трудозатратах.

    5. Какие факторы могут компенсировать рост конверсии воронки в реальном бизнесе?

      Падение среднего чека (AOV) или рост возвратов товара (Refund Rate).

  6. Практика: Интерпретация когортной матрицы

    Практическая задача: Проведение аналитического аудита когортной матрицы продукта. Анализ динамики удержания по трем направлениям (горизонталь, вертикаль, диагональ), выявление эффекта релиза и локализация сезонных шоков.

    Если совсем простыми словами: это навык чтения когортной таблицы как открытой книги.

    Правила аналитического чтения когортной матрицы:

    1. Горизонтальный анализ (Lifetime Trend): Скорость затухания кривой удержания конкретной когорты. Ищем наличие горизонтального плато.
    2. Вертикальный анализ (Release Impact): Сравнение ячеек одинакового возраста ($M_1$) между разными когортами. Рост $M_1$ по вертикали вниз означает, что новые релизы улучшают продукт для новичков.
    3. Диагональный анализ (Calendar Shock): Ячейки с одинаковой календарной датой ($i + t = \text{const}$). Если просадка видна на всей диагонали — в этот календарный месяц произошел внешний сбой (баг, санкции, падение серверов).

    Условие кейса: Дана матрица Retention (%) по месяцам:

    КогортаM0M1M2M3
    Январь100%25%18%15%
    Февраль100%26%19%—
    Март (Релиз V2)100%38%29%—
    Апрель100%39%——
    Требуется сделать строгие аналитические выводы.

    # Интерпретация когортной динамики
matrix_data = {
    "Jan": [100.0, 25.0, 18.0, 15.0],
    "Feb": [100.0, 26.0, 19.0, None],
    "Mar": [100.0, 38.0, 29.0, None],
    "Apr": [100.0, 39.0, None, None]
}

m1_jan = matrix_data["Jan"][1]
m1_mar = matrix_data["Mar"][1]
relative_m1_lift = (m1_mar - m1_jan) / m1_jan

print("=== АНАЛИТИЧЕСКИЙ АУДИТ КОГОРТНОЙ МАТРИЦЫ ===")
print(f"1. Вертикальный срез M1: рост с {m1_jan:.1f}% до {m1_mar:.1f}% (относительно {relative_m1_lift:+.1%})")
print("   ВЫВОД: Релиз V2 в марте совершил качественный прорыв в активации новичков.")
print("2. Горизонтальный срез Марта: M2 удерживается на уровне 29.0% (против 18-19% у старых).")
print("   ВЫВОД: Рост удержания устойчив во времени и формирует новое высокое плато ценности.")
    • Игнорирование незаполненных диагоналей. Попытка усреднять столбцы матрицы с включением еще не наступивших месяцев.
    • Путаница между абсолютными процентными пунктами и относительным ростом. Рост с 25% до 38% — это +13 п.п., но +52% относительного роста!
    • Ошибочное приписывание диагонального шока качеству продукта. Если в апреле просели все когорты разом, виноват не мартовский релиз, а внешний апрельский инцидент.
    • Игнорирование изменений маркетингового микса. Рост Retention может быть вызван не релизом, а переходом маркетинга на более дорогую качественную аудиторию.

    На собеседовании: «Если в когортной таблице все ячейки на одной диагонали внезапно покраснели (упали на 10%), что произошло?» Ответ: «Это классический календарный шок. В конкретный календарный месяц произошло общее внешнее или инфраструктурное событие, затронувшее всех пользователей независимо от их возраста в продукте (например, массовый сбой платежей, блокировка приложения в App Store или сезонный майский спад)».

    1. Что означает анализ когортной матрицы по вертикали?

      Сравнение метрик пользователей разных поколений в одном и том же возрасте их жизненного цикла.

    2. Что отражает диагональ в когортной таблице?

      Показатели активности разных когорт в один и тот же календарный временной промежуток.

    3. Как обнаружить успешный продуктовый релиз на когортной матрице?

      По резкому ступенчатому росту показателей по вертикали вниз, начиная с когорты месяца релиза.

    4. В чем различие между процентными пунктами (п.п.) и процентами прироста?

      п.п. — абсолютная разность долей ($P_2 - P_1$); проценты — относительное изменение ($(P_2 - P_1) / P_1 imes 100\%$).

    5. Почему когортная матрица всегда имеет треугольную форму?

      Потому что более молодые когорты физически прожили меньше временных интервалов, чем старые.

  7. Практика: Расчет юнит-экономики и окупаемости

    Практическая задача: Полный расчет финансовой юнит-экономики подписочного B2C продукта: расчет Fully Loaded CAC, валовой маржи (Gross Margin), Lifetime в месяцах, LTV, соотношения LTV/CAC и точного срока окупаемости в месяцах (Payback Period).

    Если совсем простыми словами: это скрипт инвестиционного аудита стартапа. Мы проверяем, сойдется ли бизнес, если влить в рекламу 100 млн рублей.

    Формулы юнит-экономики:

    1. $\mathrm{CAC} = \frac{\text{Бюджет маркетинга} + \text{ФОТ маркетинга}}{\text{Новые платящие клиенты}}$.
    2. $\mathrm{Monthly\ Gross\ Profit} = \mathrm{ARPU} \times \mathrm{Margin\ \%}$.
    3. $\mathrm{Customer\ Lifetime} = \frac{1}{\mathrm{Monthly\ Churn\ Rate}}$.
    4. $\mathrm{LTV} = \mathrm{Monthly\ Gross\ Profit} \times \mathrm{Lifetime}$.
    5. $\mathrm{Payback\ Period} = \frac{\mathrm{CAC}}{\mathrm{Monthly\ Gross\ Profit}}$.

    Условие кейса: Маркетинговый бюджет: $12\,000\,000$ руб./мес. ФОТ команды привлечения: $3\,000\,000$ руб./мес. Привлечено новых платящих клиентов: $5\,000$ человек. Стоимость месячной подписки: $1\,500$ руб. Переменные расходы (эквайринг, сервера, лицензии): $450$ руб. на пользователя в месяц ($\text{Margin} = 70\%$). Месячный отток клиентов (Monthly Churn): $5.0\%$. Требуется рассчитать все ключевые показатели и вынести вердикт об инвестиционной привлекательности.

    # Полный финансовый расчет юнит-экономики
marketing_budget = 12000000.0
marketing_salaries = 3000000.0
new_paying_users = 5000

subscription_price = 1500.0
variable_costs = 450.0
monthly_churn = 0.05

# 1. Fully Loaded CAC
total_acquisition_cost = marketing_budget + marketing_salaries
cac = total_acquisition_cost / new_paying_users

# 2. Маржинальность и валовая прибыль
gross_profit_per_user_monthly = subscription_price - variable_costs
margin_pct = gross_profit_per_user_monthly / subscription_price

# 3. Lifetime и LTV
lifetime_months = 1.0 / monthly_churn
ltv = gross_profit_per_user_monthly * lifetime_months

# 4. Метрики окупаемости
ltv_to_cac = ltv / cac
payback_months = cac / gross_profit_per_user_monthly

print("=== РЕЗУЛЬТАТЫ АУДИТА ЮНИТ-ЭКОНОМИКИ ===")
print(f"CAC (Fully Loaded):     {cac:8,.0f} руб.")
print(f"Валовая маржа (Margin): {margin_pct:8.1%}")
print(f"Срок жизни клиента:     {lifetime_months:8.1f} месяцев")
print(f"LTV клиента:            {ltv:8,.0f} руб.")
print(f"Отношение LTV / CAC:    {ltv_to_cac:8.2f}x (Бенчмарк: >= 3.0x)")
print(f"Срок окупаемости:       {payback_months:8.1f} месяцев (Бенчмарк: <= 12 мес.)")
print("---------------------------------------")
if ltv_to_cac >= 3.0 and payback_months <= 12:
    print("ВЕРДИКТ: Бизнес-модель здорова и готова к масштабированию!")
else:
    print("ВЕРДИКТ: Экономика сходится со скрипом, высокий риск.")
    • Расчет CAC только по рекламному бюджету без ФОТ. Занижает реальный CAC на 20-40%.
    • Игнорирование себестоимости подписки. Расчет окупаемости по выручке вместо валовой прибыли приводит к кассовым разрывам.
    • Предположение о нулевом оттоке. Ни один продукт не имеет нулевой Churn Rate в долгосрочной перспективе.
    • Забывание о налогах и комиссиях магазинов (Apple / Google 15-30%). Комиссии сторов обязаны вычитаться из чистой выручки.

    На собеседовании: «Что лучше для инвестора: LTV/CAC = 2.5x при окупаемости 4 месяца или LTV/CAC = 5.0x при окупаемости 24 месяца?» Ответ: «В большинстве случаев предпочтительнее первый вариант (окупаемость за 4 месяца). Быстрая оборачиваемость капитала позволяет реинвестировать прибыль 3 раза за год, обеспечивая экспоненциальный рост. Окупаемость в 24 месяца создает гигантский кассовый разрыв и риск банкротства до возврата инвестиций».

    1. Как рассчитывается Fully Loaded CAC?

      Делением всех расходов на привлечение (рекламный бюджет, зарплаты маркетологов, комиссии агентств, софт) на число новых привлеченных клиентов.

    2. Что такое Gross Margin в юнит-экономике?

      Доля выручки, остающаяся после вычета прямых переменных расходов на оказание услуги (эквайринг, сервера, саппорт).

    3. Какое значение LTV/CAC считается порогом безубыточности с учетом накладных расходов?

      Не менее 3.0x.

    4. Как рассчитать срок окупаемости (Payback Period)?

      CAC разделить на ежемесячную валовую прибыль с одного клиента.

    5. Почему быстрый Payback важнее высокого теоретического LTV?

      Потому что он снижает требования к объему оборотного капитала и риски изменения рыночной конъюнктуры.

  8. Практика: Моделирование оттока и LTV

    Практическая задача: Математическое моделирование динамики клиентской базы подписочного сервиса во времени. Расчет точки равновесия (Equilibrium / Plateau), при которой приток новых пользователей полностью уравновешивается оттоком старых, и расчет упущенной выручки от Churn.

    Если совсем простыми словами: это скрипт, показывающий, когда ваш продукт упрется в «стеклянный потолок» и перестанет расти.

    Математика динамического равновесия:

    Пусть ежемесячно в продукт приходит $N_{\text{new}}$ новых клиентов, а ежемесячный отток составляет долю $c$. Размер активной базы в месяц $t$ описывается разностным уравнением:

    $$S_t = S_{t-1} \cdot (1 - c) + N_{\text{new}}$$

    В точке динамического равновесия ($S_t = S_{t-1} = S^*$):

    $$S^* = \frac{N_{\text{new}}}{c}$$

    Снижение оттока в 2 раза увеличивает максимальный размер бизнеса ровно в 2 раза при том же рекламном бюджете!

    Условие кейса: Ежемесячный приток: $2\,000$ новых подписчиков. Тариф: $1\,000$ руб./мес. Сценарий A: отток $8\%$ в месяц. Сценарий B: снизили отток до $4\%$ в месяц за счет улучшений онбординга. Требуется рассчитать потолок базы подписчиков и годовую выручку в обоих сценариях.

    # Моделирование равновесия базы подписчиков
inflow = 2000
price = 1000.0

churn_a = 0.08
churn_b = 0.04

# Потолок базы пользователей
ceiling_a = inflow / churn_a
ceiling_b = inflow / churn_b

mrr_a = ceiling_a * price
mrr_b = ceiling_b * price

arr_a = mrr_a * 12
arr_b = mrr_b * 12

print(f"Сценарий A (Churn = {churn_a:.0%}): Потолок = {ceiling_a:8,0f} юзеров | Годовая выручка: {arr_a:13,.0f} руб.")
print(f"Сценарий B (Churn = {churn_b:.0%}): Потолок = {ceiling_b:8,0f} юзеров | Годовая выручка: {arr_b:13,.0f} руб.")
print(f"Инкремент от снижения оттока:     +{ceiling_b - ceiling_a:8,0f} юзеров | +{arr_b - arr_a:13,.0f} руб./год!")
    • Ожидание бесконечного линейного роста при постоянном маркетинге. Любой продукт с ненулевым оттоком асимптотически упирается в потолок $N_{\text{new}} / c$.
    • Игнорирование когортной вариации оттока. В реальности отток первого месяца в 3-4 раза выше оттока десятого месяца.
    • Попытка компенсировать растущий отток увеличением рекламного бюджета. Приводит к резкому росту CAC и ускорению банкротства.
    • Путаница между абсолютным числом ушедших и процентом оттока. При росте базы число уходящих клиентов неизбежно растет даже при стабильном проценте оттока.

    На собеседовании: «Мы привлекаем 10 000 пользователей в месяц, наш отток 5% в месяц. Каков максимальный размер нашей аудитории?» Ответ: «Максимальный размер аудитории в точке равновесия равен $S^* = N_{\text{new}} / c = 10\,000 / 0.05 = 200\,000$ активных пользователей. Достигнув 200 тысяч, продукт полностью прекратит расти, так как каждый месяц 10 000 ушедших будут в точности равны 10 000 пришедших».

    1. Как рассчитать максимальный размер активной базы пользователей при постоянном притоке?

      По формуле динамического равновесия: $S^* = \mathrm{Inflow} / \mathrm{Churn}$.

    2. Во сколько раз вырастет потолок базы клиентов при снижении месячного оттока с 10% до 2%?

      В $10 / 2 = 5$ раз.

    3. Что происходит с бизнесом, когда объем оттока сравнивается с объемом нового привлечения?

      Рост полностью останавливается, наступает плато зрелости базы.

    4. Почему удержание существующих клиентов считается главным драйвером роста подписок?

      Потому что оно экспоненциально расширяет емкость базы без роста маркетинговых затрат.

    5. Что такое Revenue Churn в отличие от User Churn?

      Процент потерянной регулярной выручки (MRR) с учетом даунгрейдов и потерь тарифов.

  9. Практика: Разбор инцидента падения конверсии

    Практическая задача: Решение реального инцидент-кейса с собеседования: общая конверсия маркетплейса внезапно упала с $5.0\%$ до $3.8\%$. При этом конверсия внутри мобильного приложения выросла, и конверсия на десктопе тоже выросла! Требуется объяснить парадокс Симпсона (Simpson's Paradox) и локализовать причину сдвига микса трафика.

    Если совсем простыми словами: это разбор математической загадки, когда на каждом отдельном устройстве всё стало лучше, а общий график в дашборде обвалился.

    Математика эффекта изменения структуры (Mix Shift / Simpson's Paradox):

    Общая конверсия является средневзвешенной суммой конверсий по сегментам:

    $$\mathrm{CR}_{\text{total}} = w_{\text{desktop}} \cdot \mathrm{CR}_{\text{desktop}} + w_{\text{mobile}} \cdot \mathrm{CR}_{\text{mobile}}$$

    Если доля мобильного трафика $w_{\text{mobile}}$ (у которого конверсия исторически ниже) резко возрастает (например, маркетинг запустил рекламу в TikTok), общая конверсия падает, даже если $\mathrm{CR}_{\text{desktop}}$ и $\mathrm{CR}_{\text{mobile}}$ по отдельности выросли!

    Условие кейса: Прошлая неделя: - Desktop: $100\,000$ визитов, $8\,000$ заказов ($\mathrm{CR} = 8.0\%$). - Mobile: $100\,000$ визитов, $2\,000$ заказов ($\mathrm{CR} = 2.0\%$). - Итого: $200\,000$ визитов, $10\,000$ заказов ($\mathrm{CR}_{\text{total}} = 5.0\%$). Текущая неделя (маркетинг запустил TikTok): - Desktop: $50\,000$ визитов, $4\,250$ заказов ($\mathrm{CR} = 8.5\%$, рост!). - Mobile: $250\,000$ визитов, $6\,250$ заказов ($\mathrm{CR} = 2.5\%$, рост!). - Итого: $300\,000$ визитов, $10\,500$ заказов ($\mathrm{CR}_{\text{total}} = 3.5\%$, обвал на 1.5 п.п.!).

    import pandas as pd

# Демонстрация Парадокса Симпсона (Mix Shift) в коде
data_prev = {"channel": ["Desktop", "Mobile"], "visits": [100000, 100000], "orders": [8000, 2000]}
data_curr = {"channel": ["Desktop", "Mobile"], "visits": [50000, 250000],  "orders": [4250, 6250]}

df_prev = pd.DataFrame(data_prev)
df_prev["cr"] = df_prev["orders"] / df_prev["visits"]

df_curr = pd.DataFrame(data_curr)
df_curr["cr"] = df_curr["orders"] / df_curr["visits"]

total_cr_prev = df_prev["orders"].sum() / df_prev["visits"].sum()
total_cr_curr = df_curr["orders"].sum() / df_curr["visits"].sum()

print("Прошлая неделя:")
print(df_prev[["channel", "visits", "orders", "cr"]])
print(f"ОБЩАЯ КОНВЕРСИЯ: {total_cr_prev:.2%}\n")

print("Текущая неделя:")
print(df_curr[["channel", "visits", "orders", "cr"]])
print(f"ОБЩАЯ КОНВЕРСИЯ: {total_cr_curr:.2%}\n")
print(f"ПАРАДОКС: На Desktop CR вырос на {(df_curr.loc[0,'cr'] - df_prev.loc[0,'cr']):+.2%}")
print(f"          На Mobile  CR вырос на {(df_curr.loc[1,'cr'] - df_prev.loc[1,'cr']):+.2%}")
print(f"          А ОБЩИЙ CR ОБВАЛИЛСЯ НА {(total_cr_curr - total_cr_prev):+.2%} из-за сдвига долей трафика!")
    • Попытка чинить продукт, когда проблема лежит в маркетинговом миксе. Продукт стал работать лучше на обеих платформах, а падение вызвано притоком мобильного трафика.
    • Анализ только агрегированных показателей без разрезов. Агрегированные дашборды скрывают противоположные тренды внутри страт.
    • Обвинение разработчиков в падении конверсии. Разработчики подняли конверсию кода, но изменение весов перекрыло этот успех.
    • Игнорирование абсолютного числа заказов. Несмотря на падение общего процента, число заказов выросло с 10 000 до 10 500.

    На собеседовании: «Как называется этот парадокс и как провести факторный анализ, чтобы доказать его руководству?» Ответ: «Это парадокс Симпсона (Mix Shift effect). Для доказательства мы проводим факторный анализ отклонений: декомпозируем изменение общей конверсии на два слагаемых: 1) Вклад изменения конверсий внутри сегментов при фиксированных старых долях; 2) Вклад изменения структуры долей сегментов при фиксированных старых конверсиях. Мы наглядно покажем, что продуктовый вклад строго положителен, а весь минус обусловлен перекосом долей трафика маркетинга».

    1. Что такое парадокс Симпсона в продуктовой аналитике?

      Ситуация, при которой тренд в агрегированных данных противоположен трендам в каждой отдельной подгруппе из-за изменения весовых долей этих подгрупп.

    2. Что такое Mix Shift (сдвиг структуры трафика)?

      Изменение пропорций различных каналов или сегментов аудитории в общем объеме трафика.

    3. Как математически декомпозировать изменение агрегированной метрики?

      На эффект изменения внутренних ставок (Rate Effect) и эффект изменения весов (Weight / Mix Effect).

    4. Означает ли падение общей конверсии с 5% до 3.5% падение бизнеса в данном кейсе?

      Нет, абсолютное число заказов выросло с 10 000 до 10 500, бизнес вырос в объеме.

    5. Какой вывод должен сделать продуктовый аналитик из кейса с Mix Shift?

      Всегда сегментировать ключевые метрики по платформам и источникам до вынесения вердикта о деградации продукта.

  10. Практика: Аудит качества данных DAU

    Практическая задача: Проведение аналитического расследования аномального скачка суточной аудитории (DAU $+40\%$ за 1 день) на предмет выявления дефектов логирования, спам-ботов, фоновых пушей или ошибок дедупликации первичных ключей.

    Если совсем простыми словами: это скрипт детекции фейкового трафика. Мы проверяем, действительно ли в продукт пришли живые люди или аналитику надули сломанные логи.

    Диагностический чек-лист валидации скачка DAU:

    1. Проверка сессионности: Сколько событий приходится на одного «нового» пользователя? (Если у 100 000 пользователей ровно по 1 событию — признак фонового пинга).
    2. Проверка User-Agent и версий ОС: Нет ли концентрации трафика на одной устаревшей версии браузера или дата-центра (IP-пулы AWS/DigitalOcean — признак краулера).
    3. Проверка целевых действий: Совершают ли эти пользователи глубокие события (просмотр каталога, скролл, добавление в корзину)? Если конверсия в шаг 2 равна нулю — трафик мертв.
    4. Проверка первичных ключей на NULL: Не схлопнулись ли миллионы анонимов в один user_id = NULL или user_id = 'undefined'.

    Условие кейса: В среду DAU подскочил со $150\,000$ до $210\,000$ ($+40\%$). Маркетинг празднует победу. Аналитик выполнил аудит и выгрузил распределение: - $60\,000$ добавленных пользователей сгенерировали ровно 1 событие app_open в 04:00 утра. - У всех $60\,000$ пользователей отсутствуют клики и просмотры экранов. - Версия ОС: Android, свойство is_background_launch = true. Инцидент раскрыт: ночной маркетинговый пуш разбудил приложение в фоне без согласия пользователя. Люди даже не брали телефон в руки. Настоящий DAU не изменился.

    # Скрипт аудита качества данных активности DAU
def audit_traffic_surge(df_events):
    print("=== АУДИТ КАЧЕСТВА ДАННЫХ ВСПЛЕСКА DAU ===")
    
    # 1. Проверка на NULL и undefined идентификаторы
    null_users = df_events["user_id"].isnull().sum()
    undef_users = (df_events["user_id"] == "undefined").sum()
    print(f"1. Мусорные ID: NULL = {null_users}, 'undefined' = {undef_users}")
    
    # 2. Среднее число событий на пользователя
    events_per_user = df_events.groupby("user_id").size()
    single_event_users_pct = (events_per_user == 1).mean() * 100
    print(f"2. Доля пользователей с ровно 1 событием: {single_event_users_pct:.1f}% (Норма: < 15%)")
    
    # 3. Доля фоновых запусков
    bg_share = df_events["is_background"].mean() * 100
    print(f"3. Доля фоновых событий: {bg_share:.1f}%")
    
    # Вердикт
    if single_event_users_pct > 50 or bg_share > 40:
        print("ВЕРДИКТ: Всплеск фейковый! Вызван техническими фоновыми пингами или ботами.")
    else:
        print("ВЕРДИКТ: Трафик похож на органический всплеск живых людей.")

# Пример вызова с подозрительными данными
import pandas as pd
df_suspicious = pd.DataFrame({
    "user_id": [f"u_{i}" for i in range(1000)],
    "is_background": [True] * 800 + [False] * 200
})

    • Признание фонового пробуждения за активного пользователя. Пользователь не видел экран, ценность не получена.
    • Отсутствие фильтрации внутренних IP-адресов компании и нагрузочных тестов. QA-инженеры перед релизом запустили нагрузочный тест на 50 000 виртуальных ботов, исказив суточный отчет.
    • Игнорирование идентификатора '0' или 'null'. Если неавторизованные пользователи логируются с user_id = 0, COUNT(DISTINCT user_id) посчитает их за одного человека.
    • Празднование роста без проверки конверсий. Рост трафика без роста целевых действий всегда подозрителен.

    На собеседовании: «Как отличить живой всплеск аудитории от наплыва ботов или бага логирования?» Ответ: «Живой всплеск сопровождается естественным распределением глубины сессий (люди кликают, скроллят, переходят по страницам) и ростом конверсий по воронке. Аномалия ботов или логов характеризуется аномальной концентрацией: 90%+ пользователей совершают ровно 1 событие, приходят с одного User-Agent или пула IP, имеют is_background = true и показывают нулевую конверсию в следующий шаг».

    1. Что такое фантомный DAU (Ghost DAU)?

      Искусственно завышенное число активных пользователей, вызванное фоновыми системными процессами, спам-ботами или ошибками сбора логов.

    2. Какое событие должно служить критерием активного пользователя?

      Осознанное взаимодействие человека с интерфейсом на переднем плане (Foreground interaction).

    3. Почему пользователи с ровно одним событием в логах вызывают подозрение?

      Потому что живой человек при использовании приложения почти всегда генерирует цепочку из нескольких последовательных действий.

    4. Что происходит, если в поле user_id попадает значение 'null' как строка?

      Все такие пользователи объединяются в один профиль, занижая реальную аудиторию.

    5. Какие метаданные устройства помогают выявить ботов?

      User-Agent, разрешение экрана, наличие WebGL/Canvas и принадлежность IP-адреса к диапазонам хостинг-провайдеров.
