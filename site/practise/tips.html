    Оформление Python кода

  1. Как оформлять Google-style docstrings?

    Docstring — строка документации сразу после объявления модуля, класса, метода или функции. В Google style информация разбивается на понятные секции: Args, Returns, Raises, Yields, Attributes и Examples.

    Docstring объясняет контракт кода: что он делает, какие данные ожидает, что возвращает и в каких случаях завершается ошибкой. Он не должен пересказывать реализацию построчно.

    Базовая структура

    Начни с короткого описания в повелительной форме. Если одной строки недостаточно, после пустой строки добавь подробности, а затем нужные секции. Название секции заканчивается двоеточием, её содержимое оформляется с отступом в четыре пробела.

    def calculate_discount(price: float, percent: float) -> float: """Рассчитай цену товара после применения скидки. Args: price: Исходная цена товара в рублях. Должна быть неотрицательной. percent: Размер скидки от 0 до 100 включительно. Returns: Цена после применения скидки, округлённая до двух знаков. Raises: ValueError: Если цена отрицательная или скидка находится вне диапазона. Examples: >>> calculate_discount(1_000.0, 15.0) 850.0 """ if price < 0: raise ValueError("price must be non-negative") if not 0 <= percent <= 100: raise ValueError("percent must be between 0 and 100") return round(price * (1 - percent / 100), 2)

    Что писать в секциях

    • Args: назначение каждого аргумента, единицы измерения, допустимые диапазоны и особые значения. Не повторяй очевидное вроде «name — имя».
    • Returns: смысл результата и его формат. Если функция всегда возвращает None, секцию обычно можно опустить.
    • Raises: только исключения, которые являются частью ожидаемого поведения функции и которые важно знать вызывающему коду.
    • Yields: используй вместо Returns для генераторов и опиши каждый выдаваемый элемент.
    • Examples: добавляй небольшой запускаемый пример для нетривиального поведения или пограничного случая.

    Если типы уже указаны в сигнатуре, не дублируй их в Args и Returns. Аннотация отвечает на вопрос «какого типа значение», а docstring — «что оно означает и какие ограничения действуют».

    Пример генератора

    from collections.abc import Iterator def iter_batches(items: list[str], batch_size: int) -> Iterator[list[str]]: """Раздели последовательность строк на пакеты заданного размера. Последний пакет может содержать меньше элементов, чем остальные. Исходный список не изменяется. Args: items: Строки, которые нужно объединить в пакеты. batch_size: Максимальное число элементов в одном пакете. Yields: Очередной пакет строк с сохранением исходного порядка. Raises: ValueError: Если размер пакета меньше единицы. Examples: >>> list(iter_batches(["a", "b", "c"], 2)) [['a', 'b'], ['c']] """ if batch_size < 1: raise ValueError("batch_size must be positive") for start in range(0, len(items), batch_size): yield items[start : start + batch_size]

    Пример класса

    У класса опиши его назначение и публичные атрибуты. Методы документируй отдельно, если их поведение не очевидно из названия и сигнатуры.

    class TemperatureSensor: """Храни показания датчика температуры. Attributes: sensor_id: Уникальный идентификатор физического датчика. unit: Единица измерения: ``"celsius"`` или ``"fahrenheit"``. """ def __init__(self, sensor_id: str, unit: str = "celsius") -> None: """Инициализируй датчик. Args: sensor_id: Непустой идентификатор датчика. unit: Единица измерения возвращаемых значений. Raises: ValueError: Если идентификатор пуст или единица измерения неизвестна. """ if not sensor_id: raise ValueError("sensor_id must not be empty") if unit not in {"celsius", "fahrenheit"}: raise ValueError("unsupported temperature unit") self.sensor_id = sensor_id self.unit = unit

    Частые ошибки

    Проверка перед сдачей
    • Docstring стоит первой инструкцией внутри функции, метода или класса.
    • Первая строка коротко и точно описывает действие.
    • Все параметры из сигнатуры перечислены в Args в том же порядке.
    • Указаны важные ограничения: диапазоны, форматы, единицы измерения и допустимость None.
    • Returns описывает значение, а не повторяет его тип.
    • Raises соответствует реальным исключениям в коде.
    • Пример можно скопировать и запустить без скрытых переменных.

    2. Загрузка кода в GitHub-репозиторий

  2. Как сдавать задания? (Pull Request)

    PR (Pull Request) — запрос на перенос изменений из твоей ветки в основную ветку main. В PR видны все изменённые файлы, история коммитов, результаты автоматических проверок и комментарии ревьюера.

    Одно задание оформляй одним небольшим PR. Так изменения легче проверить, обсудить и при необходимости исправить.

    Почитать про основы Git можно здесь.

    Перед началом работы

    Убедись, что Git настроен, репозиторий склонирован, а команда git status не показывает случайных незакоммиченных изменений. Команды ниже выполняются из папки проекта.

    git status git remote -v
    Пошаговая сдача задания
    • 1. Переключись на main и получи свежие изменения:
      git switch main git pull origin main
    • 2. Создай отдельную ветку от обновлённой main:

      Имя должно кратко отражать задачу. Используй латиницу, строчные буквы и дефисы.

      git switch -c practice/titanic-model
    • 3. Выполни задание и проверь результат:

      Например, помести решение задачи Titanic в отдельную папку, добавь инструкцию запуска и убедись, что код выполняется на чистых входных данных.

      python -m pytest python src/train.py --help
    • 4. Проверь состав изменений:
      git status git diff

      Не добавляй секреты, датасеты большого размера, .venv/, кэш, логи и временные файлы. Для них настрой .gitignore.

    • 5. Добавь только нужные файлы и создай понятный коммит:
      git add titanic/ README.md git commit -m "Add Titanic classification solution"
    • 6. Отправь ветку на GitHub:
      git push -u origin practice/titanic-model

      Флаг -u связывает локальную ветку с удалённой. Следующие обновления можно отправлять обычной командой git push.

    • 7. Открой Pull Request:
      • Открой вкладку Pull requests и нажми New pull request.
      • В base выбери main, в compare — practice/titanic-model.
      • Проверь вкладку Files changed: там не должно быть посторонних файлов.
      • Дай PR конкретное название, например Add Titanic classification solution.
      • Опиши результат, способ проверки и известные ограничения.
      • Нажми Create pull request и дождись автоматических проверок.

    Пример описания Pull Request

    ## Что сделано - добавлена подготовка данных Titanic; - обучена модель LogisticRegression; - добавлены тесты для обработки пропусков. ## Как проверить 1. Установить зависимости: `pip install -r requirements.txt`. 2. Запустить тесты: `pytest`. 3. Запустить обучение: `python src/train.py`. ## Результат Accuracy на validation-выборке: 0.81. ## Ограничения - модель пока не сохраняется в отдельный файл.

    Как внести исправления после ревью

    Не закрывай PR и не создавай новый. Исправь код в той же ветке, сделай ещё один коммит и отправь его — PR обновится автоматически.

    git switch practice/titanic-model # внеси исправления git add titanic/ git commit -m "Address review comments" git push
    Финальная проверка
    • PR посвящён одному заданию и создан из отдельной ветки.
    • В репозитории нет паролей, токенов, виртуального окружения и тяжёлых временных файлов.
    • Код запускается, тесты проходят, а способ проверки описан в PR.
    • Вкладка Files changed содержит только относящиеся к заданию изменения.
    • На все комментарии ревьюера дан ответ, а исправления отправлены в ту же ветку.
  3. Видео: Git и Pull Request

    Эти видео показывают полный путь задания: от создания ветки и коммита до открытия Pull Request. Смотри их вместе с терминалом — после каждого смыслового блока ставь видео на паузу и повторяй команды в учебном репозитории.

    Нажми на карточку, чтобы открыть видео.

    4. Python

  4. Полноценный Python-проект

    Собрать не просто файл main.py, а нормальный Python-проект: с pyproject.toml, виртуальным окружением .venv, структурой src/, тестами, линтером, type checker, Docker, docker-compose, GitHub Actions и бейджами в README.md.

    Инструменты
    uv Ruff ty pytest Docker GitHub Actions

    В конце должен получиться примерно такой проект:

    awesome-weather/ ├── .github/ │ └── workflows/ │ └── ci.yml ├── src/ │ └── awesome_weather/ │ ├── __init__.py │ ├── cli.py ... │ └── core.py ├── tests/ │ └── test_core.py ... │ └── ... ├── .dockerignore ├── .gitignore ├── .python-version ├── Dockerfile ├── README.md ├── docker-compose.yml ├── pyproject.toml └── uv.lock

    Сначала создай папку проекта и главный конфигурационный файл pyproject.toml. В нём описываются имя проекта, версия Python, зависимости, CLI-команда, build backend, настройки тестов, линтера и type checker.

    Минимальный pyproject.toml для приложения с CLI, тестами, Ruff и ty:

    [project] name = "awesome-weather" version = "0.1.0" description = "Small example Python project with uv, tests, linting, typing and Docker." readme = "README.md" # можно не указывать requires-python = ">=3.12" dependencies = [ "pydantic>=2.0", ] [project.scripts] awesome-weather = "awesome_weather.cli:main" [dependency-groups] dev = [ "pytest>=8.0", "pytest-cov>=5.0", "ruff>=0.8", "ty>=0.0.1a1", ] [tool.ruff] line-length = 100 target-version = "py312" src = ["src", "tests"] [tool.ruff.lint] select = [ "E", "F", "I", "B", "UP", "SIM", ] [tool.ty.environment] python-version = "3.12" root = ["./src"]

    Если используешь uv init awesome-weather --package, pyproject.toml будет создан автоматически. Но полезно понимать его структуру вручную: именно этот файл является центром проекта.

    Теперь привяжи версию Python, создай lock-файл и синхронизируй окружение. uv sync создаст .venv рядом с pyproject.toml и установит обычные и dev-зависимости.

    uv python pin 3.12 uv lock uv sync

    После синхронизации появятся:

    • .python-version — выбранная версия Python;
    • .venv/ — локальное виртуальное окружение;
    • uv.lock — зафиксированное дерево зависимостей.

    Команды проекта запускай через uv run, чтобы не активировать окружение вручную.

    uv run python --version uv run ruff check . uv run ruff format . uv run ty check uv run pytest

    src/-layout защищает от случайного импорта кода прямо из корня репозитория. Это ближе к тому, как пакет будет работать после установки.

    mkdir -p src/awesome_weather tests # создать папки из терминала touch src/awesome_weather/__init__.py # создать файл из терминала touch src/awesome_weather/core.py # создать файл из терминала touch src/awesome_weather/cli.py # создать файл из терминала touch tests/test_core.py # создать файл из терминала

    Основная бизнес-логика должна лежать отдельно от CLI, API и тестов.

    from __future__ import annotations from pydantic import BaseModel, Field class WeatherReport(BaseModel): city: str = Field(min_length=1) temperature_c: float wind_mps: float = Field(ge=0) @property def feels_cold(self) -> bool: return self.temperature_c < 5 or self.wind_mps >= 10 def format_report(report: WeatherReport) -> str: status = "cold" if report.feels_cold else "ok" return f"{report.city}: {report.temperature_c:.1f} C, wind {report.wind_mps:.1f} m/s, {status}"

    CLI-слой только парсит аргументы, вызывает бизнес-логику и печатает результат.

    from __future__ import annotations import argparse from awesome_weather.core import WeatherReport, format_report def build_parser() -> argparse.ArgumentParser: parser = argparse.ArgumentParser(description="Print a small weather report.") parser.add_argument("--city", required=True) parser.add_argument("--temperature", required=True, type=float) parser.add_argument("--wind", required=True, type=float) return parser def main() -> None: args = build_parser().parse_args() report = WeatherReport( city=args.city, temperature_c=args.temperature, wind_mps=args.wind, ) print(format_report(report)) if __name__ == "__main__": main()

    После uv sync команда из [project.scripts] должна запускаться через uv run.

    uv run awesome-weather --city Moscow --temperature -3 --wind 4

    Тесты кладём в tests/. Они должны проверять не только happy path, но и ошибки валидации, граничные случаи и несколько вариантов входных данных.

    import pytest from pydantic import ValidationError from awesome_weather.core import WeatherReport, format_report def test_format_report_for_normal_weather() -> None: report = WeatherReport(city="Tbilisi", temperature_c=18.2, wind_mps=2.5) assert format_report(report) == "Tbilisi: 18.2 C, wind 2.5 m/s, ok" @pytest.mark.parametrize( ("temperature_c", "wind_mps"), [ (0.0, 2.0), (12.0, 11.0), ], ) def test_cold_weather_detection(temperature_c: float, wind_mps: float) -> None: report = WeatherReport(city="Oslo", temperature_c=temperature_c, wind_mps=wind_mps) assert report.feels_cold is True def test_city_must_not_be_empty() -> None: with pytest.raises(ValidationError): WeatherReport(city="", temperature_c=10.0, wind_mps=1.0)

    Запускай тесты той же командой локально и в CI.

    uv run pytest

    Ruff отвечает за линтинг, порядок импортов и форматирование. В pyproject.toml уже есть базовая конфигурация.

    uv run ruff check . uv run ruff format .

    В CI лучше проверять форматирование без изменения файлов.

    uv run ruff format --check .
    • E, F — базовые ошибки стиля и неиспользуемые импорты;
    • I — сортировка импортов;
    • B — частые баги из flake8-bugbear;
    • UP — обновление синтаксиса под современный Python;
    • SIM — упрощение кода.

    ty проверяет типы и быстро ловит несовместимые аргументы, неправильные возвращаемые значения и ошибки в аннотациях.

    uv run ty check

    Такой код должен быть подозрительным для type checker: temperature_c ожидает число, а не строку.

    from awesome_weather.core import WeatherReport report = WeatherReport(city="Berlin", temperature_c="warm", wind_mps=3.0)

    В git не должны попадать виртуальные окружения, кеши, coverage-отчёты и сборочные артефакты.

    .venv/ .pytest_cache/ .ruff_cache/ .coverage htmlcov/ dist/ build/ *.egg-info/ __pycache__/ *.py[cod]

    В Docker build context не нужно отправлять .git, .venv, кеши и артефакты сборки.

    .git .github .venv .pytest_cache .ruff_cache htmlcov dist build *.egg-info __pycache__ *.pyc

    Dockerfile должен ставить зависимости из uv.lock, копировать код и запускать CLI. Для приложения важны воспроизводимость и отсутствие лишних dev-зависимостей в runtime-образе.

    FROM python:3.12-slim AS runtime ENV PYTHONDONTWRITEBYTECODE=1 ENV PYTHONUNBUFFERED=1 ENV UV_SYSTEM_PYTHON=1 WORKDIR /app COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv COPY .python-version pyproject.toml uv.lock README.md ./ COPY src ./src RUN uv sync --frozen --no-dev ENTRYPOINT ["uv", "run", "awesome-weather"] CMD ["--city", "Moscow", "--temperature", "-3", "--wind", "4"]

    Проверь, что образ собирается и CLI запускается внутри контейнера.

    docker build -t awesome-weather:local . docker run --rm awesome-weather:local --city Kazan --temperature 7 --wind 3

    docker-compose удобен, когда сервисов становится больше: API + база данных + кеш + worker. Даже для маленького CLI можно показать стандартный каркас.

    services: app: build: context: . dockerfile: Dockerfile command: ["--city", "Moscow", "--temperature", "-3", "--wind", "4"]

    Команда ниже пересоберёт образ и запустит сервис.

    docker compose up --build

    Если позже появится FastAPI-сервис, command обычно заменяют на запуск сервера, а наружу пробрасывают порт.

    services: api: build: . ports: - "8000:8000" command: ["uv", "run", "uvicorn", "awesome_weather.api:app", "--host", "0.0.0.0", "--port", "8000"]

    CI должен повторять локальные проверки: установка зависимостей, Ruff, форматирование, type checking, тесты и сборка Docker-образа.

    name: CI on: push: branches: ["main"] pull_request: jobs: test: runs-on: ubuntu-latest steps: - name: Checkout uses: actions/checkout@v4 - name: Install uv uses: astral-sh/setup-uv@v5 with: enable-cache: true - name: Set up Python run: uv python install 3.12 - name: Install dependencies run: uv sync --frozen - name: Ruff lint run: uv run ruff check . - name: Ruff format check run: uv run ruff format --check . - name: Type check run: uv run ty check - name: Tests run: uv run pytest docker: runs-on: ubuntu-latest needs: test steps: - name: Checkout uses: actions/checkout@v4 - name: Build Docker image run: docker build -t awesome-weather:ci .

    В README.md должны быть бейдж CI, версия Python, используемые инструменты и команды для запуска проекта.

    Перед тем как считать проект собранным, проверь:

    • uv sync --frozen проходит на чистой машине;
    • .venv/ не попадает в git;
    • uv.lock лежит в git;
    • весь код приложения лежит в src/<package_name>/;
    • тесты лежат в tests/;
    • uv run pytest проходит;
    • uv run ruff check . проходит;
    • uv run ruff format --check . проходит;
    • uv run ty check проходит;
    • Docker-образ собирается;

    • в README.md есть команды запуска, тестов и бейдж CI.

    Да, информации много, но именно так или очень похоже выглядит настоящий проект: продуктовый репозиторий, где людям не всё равно на качество и воспроизводимость кода. Бывает и иначе: в репозитории может быть бардак без всего перечисленного выше, но это уже редфлаг

    Старайся следовать хотя бы базовому минимуму: uv, pyproject.toml, ruff. Так ты сразу будешь восприниматься как более компетентный инженер. А если умеешь собирать docker-compose и разворачивать сервис, это ещё сильнее повышает уровень проекта.
