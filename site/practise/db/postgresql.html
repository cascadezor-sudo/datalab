  1. Выручка по кампаниям без размножения строк

    Научиться соединять таблицу с двумя таблицами «один-ко-многим» так, чтобы агрегаты не раздувались, и корректно заполнять нулями отсутствующие значения.

    Решение — это SQL-запрос в строке QUERY. Тесты создают базу SQLite в памяти, заливают туда данные и сравнивают результат запроса с эталоном. Используй стандартный SQL: JOIN, GROUP BY, COALESCE, CTE (WITH) работают одинаково в SQLite и PostgreSQL. Запрос из этой задачи без изменений запустится и в Postgres.

    Методы
    LEFT JOIN GROUP BY COALESCE CTE (WITH)

    Маркетинг хочет табличку для модели атрибуции: сколько кликов и сколько выручки принесла каждая рекламная кампания.

    Таблицы:

    • campaigns(campaign_id INTEGER, name TEXT) — справочник кампаний;
    • clicks(click_id INTEGER, campaign_id INTEGER) — клики, у кампании их может быть много;
    • orders(order_id INTEGER, campaign_id INTEGER, amount REAL) — заказы, у кампании их тоже может быть много.

    Верни по одной строке на каждую кампанию из campaigns: campaign_id, name, clicks (число кликов), revenue (сумма заказов, округлённая ROUND(..., 2)). Если кликов или заказов нет — там должен быть 0, а не NULL. Сортировка по campaign_id.

    Ловушка: если сделать campaigns LEFT JOIN clicks LEFT JOIN orders и потом GROUP BY, каждый клик умножится на каждый заказ. У кампании с 3 кликами и 2 заказами на 10 и 20 получится clicks = 6 и revenue = 90 вместо 3 и 30.

    Пример: для кампании 1 с 3 кликами и заказами на 10 и 20 ожидается строка (1, 'spring', 3, 30.0); для кампании без заказов — (2, 'summer', 1, 0.0).

    1. Почему JOIN одной таблицы с двумя таблицами «один-ко-многим» раздувает агрегаты?

      Каждая строка первой дочерней таблицы соединяется с каждой строкой второй по тому же ключу. У кампании с 3 кликами и 2 заказами получится 3 × 2 = 6 строк, поэтому COUNT и SUM считают каждое значение по несколько раз.

    2. Как избежать размножения строк при сборе агрегатов из нескольких таблиц?

      Агрегировать каждую дочернюю таблицу отдельно до ключа (в подзапросе или CTE), чтобы на ключ осталась одна строка, и только потом соединять результаты с основной таблицей.

    3. Почему здесь нужен LEFT JOIN, а не INNER JOIN?

      INNER JOIN выбросит кампании, у которых нет кликов или заказов. LEFT JOIN сохраняет все строки левой таблицы, а на месте отсутствующих данных оставляет NULL.

    4. Зачем COALESCE после LEFT JOIN?

      Для кампании без заказов агрегат из присоединённой таблицы приходит как NULL. Для фичи «выручка» это на самом деле 0, поэтому COALESCE(x, 0) заменяет NULL на ноль. Иначе модель или отчёт получат пропуск вместо нуля.

    5. Как быстро проверить, что JOIN не размножил строки?

      Сравнить COUNT(*) до и после JOIN и убедиться, что ключ в присоединяемой таблице уникален: GROUP BY key HAVING COUNT(*) > 1 должен вернуть пустой результат.

  2. Топ-N товаров в каждой категории

    Отработать классическую задачу с собеседований «top-N на группу» через ROW_NUMBER() и понять, почему результат оконной функции нельзя отфильтровать прямо в WHERE.

    Решение — SQL-запрос в строке QUERY. Тесты создают базу SQLite в памяти и сравнивают результат с эталоном. Оконные функции (ROW_NUMBER, RANK, PARTITION BY) в SQLite и PostgreSQL пишутся одинаково, так что запрос без правок перенесётся в Postgres. В Postgres у этой задачи есть и короткий вариант для N = 1: DISTINCT ON (category). Для N = 2 он уже не подходит.

    Методы
    ROW_NUMBER() PARTITION BY Подзапрос / CTE

    Рекомендательный блок «хиты категории» показывает по два самых прибыльных товара из каждой категории.

    Таблица products(product_id INTEGER, category TEXT, revenue REAL).

    Верни для каждой категории ровно два товара с наибольшей revenue (или один, если в категории всего один товар). Колонки: category, product_id, revenue, rn, где rn — место внутри категории (1 или 2). Если выручка одинаковая, выше стоит товар с меньшим product_id. Отсортируй по category, затем по rn.

    Обрати внимание: при равной выручке RANK() выдаст двум товарам одно место, и в «топ-2» может попасть три строки. Нужно ровно две, поэтому бери ROW_NUMBER() с явным тай-брейком, то есть дополнительным ключом сортировки для случая равенства.

    Пример: в категории books товары (1, 500), (2, 900), (3, 700). Ответ: ('books', 2, 900.0, 1) и ('books', 3, 700.0, 2).

    1. Чем ROW_NUMBER отличается от RANK и DENSE_RANK?

      ROW_NUMBER выдаёт уникальные номера 1, 2, 3 даже при равных значениях. RANK даёт равным значениям одно место и пропускает следующие (1, 1, 3). DENSE_RANK даёт одно место без пропусков (1, 1, 2).

    2. Почему для «ровно N на группу» нужен тай-брейк в ORDER BY?

      Без дополнительного ключа порядок строк с равными значениями не определён, и результат может меняться от запуска к запуску. Уникальный второй ключ (например, id) делает нумерацию детерминированной.

    3. Почему результат оконной функции нельзя отфильтровать в WHERE того же запроса?

      WHERE выполняется раньше, чем вычисляются оконные функции. Поэтому номер строки сначала считают во внутреннем подзапросе или CTE, а фильтруют уже во внешнем запросе.

    4. Что делает PARTITION BY?

      Разбивает строки на независимые группы: нумерация и любые оконные вычисления начинаются заново в каждой группе, при этом строки, в отличие от GROUP BY, не схлопываются.

    5. Какой короткий вариант top-1 на группу есть в PostgreSQL?

      DISTINCT ON (group_col) ... ORDER BY group_col, sort_col DESC оставляет первую строку каждой группы в заданном порядке. Для N > 1 он не подходит, там нужен ROW_NUMBER или LATERAL.

  3. Дедупликация: последняя версия записи

    Научиться оставлять из истории изменений только актуальную версию записи. Это ежедневная задача при сборке датасета из сырых логов и CDC-выгрузок (Change Data Capture, поток всех изменений строк из базы-источника).

    Решение — SQL-запрос в строке QUERY. Проверка идёт в SQLite, даты хранятся строками 'YYYY-MM-DD HH:MM:SS': в таком формате строки сортируются так же, как даты. В PostgreSQL эта задача обычно решается через DISTINCT ON (user_id) ... ORDER BY user_id, updated_at DESC. В SQLite DISTINCT ON нет, поэтому здесь используй переносимый вариант с ROW_NUMBER(): он работает в обеих СУБД.

    Методы
    ROW_NUMBER() DISTINCT ON Тай-брейк при равных ключах

    В хранилище каждый час приезжает выгрузка профилей пользователей. Одна и та же версия профиля может приехать дважды, а старые версии не удаляются.

    Таблица profiles_raw(user_id INTEGER, city TEXT, updated_at TEXT, loaded_at TEXT):

    • updated_at — когда профиль изменился в системе-источнике;
    • loaded_at — когда эта строка была загружена в хранилище.

    Верни по одной строке на пользователя с самой свежей версией профиля: колонки user_id, city, updated_at, сортировка по user_id. Свежесть определяется по updated_at. Если у двух строк updated_at совпадает (источник прислал исправление с той же меткой), побеждает строка с более поздним loaded_at.

    Пример: у пользователя 1 строки ('Москва', '2026-01-01 10:00:00', ...) и ('Казань', '2026-02-01 09:00:00', ...). Ответ: (1, 'Казань', '2026-02-01 09:00:00').

    Подход через GROUP BY user_id с MAX(updated_at) не подходит: он вернёт дату, но не город из той же строки.

    QUERY = """ -- напиши запрос здесь """

    1. Почему GROUP BY с MAX(updated_at) не решает задачу «последняя версия записи»?

      Он вернёт максимальную дату по ключу, но другие колонки нельзя взять «из той же строки»: их пришлось бы агрегировать отдельно, и значения могли бы прийти из разных версий записи.

    2. Как ROW_NUMBER помогает дедуплицировать данные?

      Внутри каждого ключа строки нумеруются по убыванию свежести. Строка с номером 1 и есть актуальная версия, остальные отбрасываются фильтром во внешнем запросе.

    3. Зачем второй ключ сортировки, например loaded_at?

      Если у двух версий совпадает основная метка времени, без тай-брейка выбор между ними случаен. Второй ключ делает выбор детерминированным и отражает бизнес-правило, например «побеждает более поздняя загрузка».

    4. Чем updated_at отличается от loaded_at и почему сортировать нужно в первую очередь по updated_at?

      updated_at — когда запись изменилась в источнике, loaded_at — когда она доехала до хранилища. Старая версия может загрузиться позже новой (переотправка, backfill), поэтому свежесть определяется временем изменения, а время загрузки служит только тай-брейком.

    5. Как такую задачу обычно решают в PostgreSQL?

      Через DISTINCT ON (key) ... ORDER BY key, updated_at DESC, loaded_at DESC: коротко и эффективно. Вариант с ROW_NUMBER переносим между СУБД.

  4. Лаговые фичи и скользящее среднее по пользователю

    Собрать поведенческие фичи для модели прямо в SQL: значение предыдущего события (LAG), интервал между событиями и скользящее среднее по последним заказам с явно заданной рамкой окна.

    Решение — SQL-запрос в строке QUERY. Проверка идёт в SQLite, даты хранятся строками 'YYYY-MM-DD'.

    Отличия от PostgreSQL в этой задаче:

    • разница дат: в Postgres для колонок типа date это просто order_date - LAG(order_date) OVER (...), результат — целое число дней. В SQLite считай через julianday(a) - julianday(b) и приводи к целому: CAST(... AS INTEGER);
    • LAG, AVG(...) OVER (... ROWS BETWEEN ...), WINDOW w AS (...) работают одинаково.
    Методы
    LAG / LEAD ROWS BETWEEN 2 PRECEDING AND CURRENT ROW WINDOW-клауза NULL у первой строки

    Таблица orders(user_id INTEGER, order_date TEXT, amount REAL). У одного пользователя в один день бывает не больше одного заказа.

    Для каждого заказа верни колонки:

    • user_id, order_date, amount;
    • prev_amount — сумма предыдущего заказа этого пользователя (NULL у первого заказа);
    • days_since_prev — сколько дней прошло с предыдущего заказа, целое число (NULL у первого);
    • avg_last_3 — среднее amount по текущему и двум предыдущим заказам пользователя, ROUND(..., 2). Если заказов раньше меньше двух, усредняй по тем, что есть.

    Сортировка: user_id, order_date.

    Пример для пользователя с заказами 2026-01-01: 100, 2026-01-04: 200, 2026-01-05: 60, 2026-01-15: 40:

    order_dateamountprev_amountdays_since_prevavg_last_3
    2026-01-01100NULLNULL100.0
    2026-01-042001003150.0
    2026-01-05602001120.0
    2026-01-15406010100.0

    Не забудь PARTITION BY user_id: без него LAG возьмёт заказ другого пользователя, и фича тихо протечёт между клиентами.

    QUERY = """ -- напиши запрос здесь """

    1. Что возвращают LAG и LEAD?

      LAG(x) — значение x из предыдущей строки окна, LEAD(x) — из следующей, в порядке ORDER BY окна. Для первой (или последней) строки результат NULL, если не задано значение по умолчанию.

    2. Почему для лаговых фичей обязателен PARTITION BY user_id?

      Без разбиения окно идёт по всей таблице, и у первого заказа пользователя «предыдущим» окажется заказ другого клиента. Фича тихо протечёт между пользователями, и ошибки не будет.

    3. Чем ROWS BETWEEN 2 PRECEDING AND CURRENT ROW отличается от рамки по умолчанию?

      При ORDER BY рамка по умолчанию — RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, то есть накопительное среднее с начала истории. ROWS BETWEEN 2 PRECEDING AND CURRENT ROW берёт ровно текущую и две предыдущие строки, это и есть скользящее окно.

    4. Почему у первых строк скользящее среднее считается по меньшему числу значений?

      Рамка обрезается границей партиции: если предыдущих строк меньше двух, AVG усредняет только те, что есть. Если нужна полная история, такие строки фильтруют или помечают отдельно.

    5. Как посчитать разницу дат в PostgreSQL и в SQLite?

      В PostgreSQL для типа date вычитание сразу даёт целое число дней: d2 - d1. В SQLite даты хранятся строками, поэтому считают julianday(d2) - julianday(d1) и приводят к целому.

  5. Retention 7-го дня по когортам

    Посчитать продуктовую метрику, которую часто используют и как таргет, и как фичу: долю пользователей когорты, вернувшихся в течение недели после регистрации. По пути разобрать три ловушки: дубли от JOIN, потерю пользователей без событий и целочисленное деление.

    Решение — SQL-запрос в строке QUERY. Проверка идёт в SQLite, даты хранятся строками 'YYYY-MM-DD'.

    Как то же самое пишется в PostgreSQL:

    • месяц когорты — to_char(date_trunc('month', signup_date), 'YYYY-MM'). В SQLite: strftime('%Y-%m', signup_date);
    • дата через 7 дней — signup_date + 7 (или + INTERVAL '7 days'). В SQLite: date(signup_date, '+7 days');
    • целочисленное деление ведёт себя одинаково: 3 / 4 = 0 в обеих СУБД, поэтому одно из чисел нужно привести к дробному (1.0 * x / y или x::numeric / y в Postgres).
    Методы
    GROUP BY EXISTS / CTE LEFT JOIN + COUNT(DISTINCT)

    Таблицы:

    • users(user_id INTEGER, signup_date TEXT) — дата регистрации;
    • events(user_id INTEGER, event_date TEXT) — активность, у одного пользователя может быть много событий, в том числе несколько в один день.

    Пользователь считается удержанным (retained D7), если у него есть хотя бы одно событие в дни с 1-го по 7-й после регистрации включительно: signup_date < event_date <= signup_date + 7 дней. Активность в день регистрации не считается.

    Когорта — месяц регистрации в формате 'YYYY-MM'. Верни по строке на когорту: cohort, cohort_size (сколько пользователей зарегистрировалось), retained (сколько из них удержались), retention (= retained / cohort_size, ROUND(..., 2)). Сортировка по cohort.

    Пример: в январе зарегистрировались 3 человека. Первый заходил на 2-й и 3-й день, второй только в день регистрации, третий не заходил вообще. Ответ: ('2026-01', 3, 1, 0.33).

    Проверь себя: пользователь без единого события должен попасть в cohort_size, а пять событий одного пользователя должны дать в retained единицу, а не пятёрку.

    QUERY = """ -- напиши запрос здесь """

    1. Почему при подсчёте удержанных пользователей нельзя просто COUNT(*) после JOIN с событиями?

      У одного пользователя много событий, и JOIN размножит его строки. Нужно считать пользователей, а не события: через COUNT(DISTINCT user_id) или через EXISTS, который даёт по одному флагу на пользователя.

    2. Почему пользователь без событий должен попасть в знаменатель и как этого добиться?

      Retention — доля от всей когорты, включая тех, кто не вернулся. INNER JOIN с событиями потеряет таких пользователей, поэтому основой берут таблицу пользователей и используют LEFT JOIN или EXISTS.

    3. Чем опасно целочисленное деление в метриках-долях?

      В SQL 3 / 4 для целых даёт 0. Одно из чисел приводят к дробному типу: 1.0 * a / b или a::numeric / b в PostgreSQL.

    4. Как аккуратно задать окно «с 1-го по 7-й день после регистрации»?

      Строгим неравенством слева и нестрогим справа: signup < event_date <= signup + 7 дней. Границы окна — частый источник ошибки на единицу, поэтому их проверяют на краевых датах.

    5. Как выделить месяц когорты в PostgreSQL?

      date_trunc('month', signup_date) возвращает начало месяца, а для строки вида 'YYYY-MM' результат форматируют через to_char(..., 'YYYY-MM').

  6. Point-in-time join фичей к таргету без утечки

    Собрать обучающую выборку так, как это делает feature store: к каждому моменту предсказания подтянуть только те значения фичей, которые были известны до этого момента. Отдельно посчитать агрегат за скользящее окно, которое заканчивается в момент предсказания.

    Решение — SQL-запрос в строке QUERY. Проверка идёт в SQLite, моменты времени хранятся строками 'YYYY-MM-DD HH:MM:SS', такие строки корректно сравниваются через < и >=.

    Как то же самое пишется в PostgreSQL:

    • «последний снимок до момента» — обычно LEFT JOIN LATERAL (SELECT ... ORDER BY computed_at DESC LIMIT 1) ON true. В SQLite нет LATERAL, но сработает коррелированный подзапрос в SELECT с тем же ORDER BY ... LIMIT 1, и в Postgres он тоже валиден;
    • граница окна — prediction_time - INTERVAL '30 days'. В SQLite: datetime(prediction_time, '-30 days').
    Методы
    Point-in-time join Коррелированный подзапрос / LATERAL Полуинтервал [t - 30d, t)

    Модель оттока делает прогноз в момент prediction_time. Таблицы:

    • labels(user_id INTEGER, prediction_time TEXT, target INTEGER) — моменты прогноза и истинный ответ;
    • snapshots(user_id INTEGER, computed_at TEXT, avg_check REAL) — фича «средний чек», которую пересчитывает ночная джоба; computed_at — момент, когда значение стало доступно;
    • orders(user_id INTEGER, order_ts TEXT, amount REAL) — заказы.

    Для каждой строки labels верни: user_id, prediction_time, target,

    • avg_check — значение из последнего снимка с computed_at строго раньше prediction_time. Если такого снимка нет, NULL;
    • orders_30d — число заказов пользователя в полуинтервале [prediction_time - 30 дней, prediction_time): левая граница включена, правая нет. Если заказов нет, 0.

    Сортировка: user_id, prediction_time.

    Почему «строго раньше»: снимок, посчитанный ровно в момент прогноза, в проде ещё не успел бы доехать до модели. Взять его — значит заглянуть в будущее, и офлайн-метрика окажется лучше продовой.

    Пример: прогноз в 2026-03-10 12:00:00, снимки от 2026-03-01 00:00:00 (чек 500) и 2026-03-11 00:00:00 (чек 900). Правильный avg_check = 500. Если взять просто последний снимок пользователя, получится 900, то есть утечка.

    1. Что такое point-in-time join?

      Соединение, при котором к каждой строке таргета подтягиваются значения фичей, известные на момент прогноза, то есть последние с временем доступности раньше этого момента. Так обучающая выборка воспроизводит то, что модель реально видела бы в проде.

    2. Почему условие «строго раньше момента прогноза», а не «не позже»?

      Значение, посчитанное ровно в момент прогноза, в проде ещё не успело бы дойти до модели. Нестрогое условие добавляет в обучение информацию из будущего, и офлайн-метрики получаются завышенными.

    3. Почему окно агрегата задают полуинтервалом [t − 30 дней, t)?

      Правая граница исключает события в момент прогноза и после него, это защита от утечки. Левая граница включена, чтобы соседние окна не теряли и не дублировали события на стыке.

    4. Как в PostgreSQL взять последнее значение фичи до момента прогноза для каждой строки?

      Через LEFT JOIN LATERAL (SELECT ... WHERE ... < t ORDER BY time DESC LIMIT 1) ON true или коррелированный подзапрос с тем же ORDER BY ... LIMIT 1. Индекс (user_id, time) делает такой поиск быстрым.

    5. Почему нельзя просто взять последний снимок фичи для пользователя?

      Последний снимок в таблице посчитан уже после многих прогнозов. Он содержит информацию о будущем относительно этих прогнозов, поэтому модель на обучении «подсматривает» ответ, а в проде качество падает.

  7. Поиск пропущенных дней во временном ряду

    Найти дыры в ежедневных данных до того, как на них обучится модель временных рядов. Пропущенный день — частая причина странных лагов и «прыгающих» скользящих средних: LAG(1) незаметно превращается в «значение неделю назад».

    Решение — SQL-запрос в строке QUERY. Проверка идёт в SQLite, даты хранятся строками 'YYYY-MM-DD'.

    Как то же самое пишется в PostgreSQL:

    • сдвиг даты на день — sale_date + 1 для типа date. В SQLite: date(sale_date, '+1 day');
    • разница дат в днях — sale_date - prev_date. В SQLite: julianday(a) - julianday(b);
    • в Postgres есть и второй способ: построить полный календарь через generate_series(min_date, max_date, INTERVAL '1 day') и найти дни без данных через anti-join (LEFT JOIN ... WHERE ... IS NULL). Здесь ответ нужен интервалами, поэтому удобнее LAG.
    Методы
    LAG CTE Gaps and islands

    Таблица daily_sales(sale_date TEXT, revenue REAL), по одной строке на день, даты уникальны. Некоторые дни пропущены: джоба выгрузки падала.

    Верни интервалы пропусков: gap_start (первый пропущенный день), gap_end (последний пропущенный день), missing_days (сколько дней пропущено подряд, целое число). Сортировка по gap_start. Если пропусков нет, результат пустой.

    Пропуски до первой и после последней даты в таблице не ищем: только дыры между существующими датами.

    Пример: даты 2026-01-01, 2026-01-02, 2026-01-05, 2026-01-06, 2026-01-08. Ответ:

    gap_startgap_endmissing_days
    2026-01-032026-01-042
    2026-01-072026-01-071

    Идея: сравни каждую дату с предыдущей через LAG. Если разница больше одного дня, между ними дыра.

    QUERY = """ -- напиши запрос здесь """

    1. Почему пропущенные дни опасны для фичей временного ряда?

      Лаги и скользящие окна по строкам (LAG(1), ROWS BETWEEN 6 PRECEDING) считают строки, а не дни. Если дня нет, «вчера» незаметно становится «три дня назад», и фича меняет смысл.

    2. Как с помощью LAG найти дыры в последовательности дат?

      Для каждой даты берут предыдущую дату в сортировке и считают разницу. Если она больше одного дня, между ними пропуск, а его границы — предыдущая дата + 1 и текущая − 1.

    3. Как найти пропущенные дни в PostgreSQL другим способом?

      Построить полный календарь через generate_series(min_date, max_date, INTERVAL '1 day') и найти дни без данных anti-join'ом: LEFT JOIN ... WHERE t.date IS NULL.

    4. Что такое задача gaps and islands?

      Класс задач про поиск непрерывных отрезков («островов») и промежутков между ними («дыр») в упорядоченной последовательности: сессии пользователей, серии дней активности, простои сервиса. Решают их через оконные функции LAG и ROW_NUMBER.

    5. Зачем ORDER BY внутри OVER, если строки в таблице уже лежат по порядку?

      Порядок хранения строк в SQL не гарантирован. Без ORDER BY в окне «предыдущая строка» не определена, и результат может зависеть от порядка вставки.
