  1. Ключ кэша для предсказаний модели

    Научиться строить ключ кэша предсказаний, который одинаков для одинаковых входов, различается для разных версий модели и не раскрывает данные пользователя.

    Методы
    Кэш предсказаний Версионирование ключей SHA-256

    Напиши prediction_key(model, version, features), который возвращает строку вида

    pred:<model>:<version>:<sha256-хэш входа>

    Правила:

    • хэш считается от канонической формы словаря features: json.dumps с sort_keys=True, separators=(",", ":") и ensure_ascii=False, закодированной в UTF-8;
    • перед сериализацией значения типа float округляются до 6 знаков после запятой (round(v, 6)) — чтобы 0.1 + 0.2 и 0.3 давали один ключ; остальные значения не меняются;
    • порядок полей в features не должен влиять на ключ, а смена version — должна.

    Например, prediction_key("churn", "v7", {"age": 31}) начинается с pred:churn:v7:, а за ним идут 64 шестнадцатеричных символа.

    Вопрос «как вы кэшируете предсказания» почти всегда упирается в ключ: что будет после выкатки новой модели, почему hit rate неожиданно низкий, не лежат ли в Redis email-адреса в открытом виде. Эта функция отвечает на все три вопроса.

    import hashlib import json def prediction_key(model: str, version: str, features: dict) -> str: pass

    1. Зачем в ключе кэша предсказания версия модели?

      Ответ модели зависит и от входа, и от весов. С версией в ключе после выкатки новая модель читает и пишет свои ключи, а старые ответы уходят по TTL — инвалидация получается бесплатно.

    2. Зачем приводить вход к канонической форме?

      Одинаковые по смыслу входы должны давать одинаковую строку: иначе порядок полей или форматирование чисел дробят один вход на много ключей, и hit rate падает.

    3. Почему вход хэшируют, а не кладут в ключ целиком?

      Хэш фиксированной длины экономит память на длинных входах и не раскрывает персональные данные в именах ключей, которые видны в SCAN и логах.

    4. Какая проблема с числами с плавающей точкой?

      0.1 + 0.2 и 0.3 сериализуются в разные строки. Округление до разумной точности перед хэшированием склеивает такие входы в один ключ.

  2. Cache-aside декоратор с TTL для модели

    Реализовать паттерн cache-aside в виде декоратора: при попадании отдать результат из Redis, при промахе посчитать, сохранить с TTL и вернуть.

    Методы
    Cache-aside TTL Сериализация JSON

    Напиши фабрику декораторов cached(r, ttl). Здесь r — клиент с интерфейсом как у redis-py:

    • r.get(key) — строка или None, если ключа нет или он истёк;
    • r.set(key, value, ex=None) — записать строку value, ex — TTL в секундах.

    Декорированная функция должна:

    1. построить ключ из имени функции и аргументов: f"cache:{func.__name__}:" + json.dumps({"args": list(args), "kwargs": kwargs}, sort_keys=True);
    2. если r.get(key) вернул значение — вернуть json.loads(value), не вызывая исходную функцию;
    3. иначе вызвать функцию, записать результат как JSON-строку с ex=ttl и вернуть результат.

    Благодаря sort_keys=True вызовы predict(a=1, b=2) и predict(b=2, a=1) попадают в один ключ. Результат None считай некэшируемым для простоты — в тестах его не будет.

    Ровно так оборачивают model.predict или вызов эмбеддера в сервисе инференса. В тестах вместо настоящего Redis используется FakeRedis с управляемыми часами r.now, чтобы проверить истечение TTL без реального ожидания.

    import json def cached(r, ttl: int): def decorator(func): pass return decorator

    1. Как работает чтение в паттерне cache-aside?

      Сначала проверяется кэш; при попадании значение возвращается сразу, при промахе вычисляется или читается из БД, кладётся в кэш с TTL и возвращается.

    2. Почему значение в Redis кладут JSON-строкой?

      Redis хранит только строки байтов и ничего не знает о Python-объектах. Словарь нужно сериализовать при записи и десериализовать при чтении.

    3. Зачем передавать TTL при записи в кэш?

      Без TTL ключ живёт вечно: память растёт, а значение устаревает. TTL ограничивает время жизни любой ошибки инвалидации.

    4. Почему в ключе сортируют kwargs?

      Вызовы с одинаковыми именованными аргументами в разном порядке должны попадать в один ключ, иначе кэш дробится и hit rate падает.

    5. Какая проблема у такого декоратора при высокой нагрузке?

      Когда горячий ключ истекает, все одновременные запросы получают промах и параллельно запускают модель — cache stampede. От него защищает блокировка на пересчёт.

  3. Защита от cache stampede через SET NX EX

    Сделать так, чтобы при истечении горячего ключа дорогой пересчёт запускал только один процесс, а остальные не шли в модель параллельно.

    Методы
    Cache stampede SET NX EX Распределённая блокировка

    Напиши get_or_compute(r, key, compute, ttl, lock_ttl). Клиент r умеет:

    • r.get(key) — строка или None;
    • r.set(key, value, ex=None, nx=False) — при nx=True пишет, только если ключа нет, и возвращает True; если ключ уже есть — возвращает None (как redis-py);
    • r.delete(key).

    Логика:

    1. Если в key есть значение — вернуть json.loads(value).
    2. Иначе попытаться взять замок: r.set(f"lock:{key}", "1", ex=lock_ttl, nx=True).
    3. Замок не взят — кто-то уже считает: вернуть None, не вызывая compute (вызывающий код отдаст заглушку или повторит позже).
    4. Замок взят — вызвать compute(), записать результат JSON-строкой в key с ex=ttl, вернуть результат.
    5. Замок нужно снять (r.delete) в любом случае, даже если compute() выбросил исключение, — исключение при этом пробрасывается дальше.

    Если процесс, взявший замок, упадёт посреди расчёта, finally не выполнится, и без ex=lock_ttl замок остался бы навсегда. TTL замка — страховка: через lock_ttl секунд пересчёт сможет начать другой процесс. В тестах это проверяется через управляемые часы r.now.

    import json def get_or_compute(r, key: str, compute, ttl: int, lock_ttl: int): pass

    1. Что такое cache stampede?

      Истекает горячий ключ, и множество одновременных запросов получают промах и параллельно запускают один и тот же дорогой пересчёт, перегружая модель или БД.

    2. Почему SET ... NX EX подходит для замка?

      NX атомарно записывает ключ, только если его нет, — замок достаётся ровно одному процессу. EX гарантирует, что замок исчезнет сам, если владелец упал.

    3. Зачем снимать замок в finally?

      Иначе при ошибке в расчёте замок провисит до истечения TTL, и всё это время ключ никто не пересчитает.

    4. Что делать процессам, которые не получили замок?

      Не запускать пересчёт: отдать устаревшее значение или заглушку, либо подождать и перечитать кэш.

    5. Чем опасно освобождение замка простым DEL в проде?

      Если расчёт длился дольше TTL замка, замок уже мог взять другой процесс, и DEL удалит чужой замок. Надёжно — хранить в замке уникальный токен и удалять Lua-скриптом, только если токен совпадает.

  4. Rate limiter: фиксированное окно на INCR + EXPIRE

    Реализовать самый частый на собеседованиях rate limiter — «не больше limit запросов за окно в window секунд» — на атомарном счётчике Redis.

    Методы
    INCR EXPIRE Fixed window

    Напиши allow(r, user_id, limit, window, now) -> bool. Клиент r умеет:

    • r.incr(key) — атомарно увеличить счётчик на 1 и вернуть новое значение (несуществующий ключ считается нулём);
    • r.expire(key, seconds) — поставить ключу TTL;
    • r.ttl(key) — оставшийся TTL (нужен тестам).

    Алгоритм фиксированного окна:

    1. номер окна — int(now // window), ключ — f"rl:{user_id}:{номер окна}";
    2. count = r.incr(key);
    3. если count == 1 (первый запрос в окне) — поставить r.expire(key, window), чтобы счётчик не жил вечно;
    4. вернуть count <= limit.

    Например, при limit=3, window=60 запросы в секунды 0, 1, 2 пропускаются, в секунду 3 — нет, а в секунду 60 начинается новое окно.

    Шаги 2–3 в проде выполняют в MULTI/EXEC или Lua-скрипте: если процесс упадёт между INCR и EXPIRE, ключ останется без TTL. Здесь, в однопоточной эмуляции, это не проявится, но на собеседовании об этом стоит сказать.

    def allow(r, user_id: str, limit: int, window: int, now: float) -> bool: pass

    1. Почему для счётчика используют INCR, а не GET + SET?

      INCR атомарен: сервер читает, увеличивает и записывает значение одной операцией. При GET + SET параллельные запросы теряют инкременты.

    2. Зачем ставить TTL на ключ окна?

      Иначе ключи всех прошедших окон копятся в памяти бесконечно. TTL, равный длине окна, удаляет счётчик, когда окно закончилось.

    3. Почему INCR и EXPIRE в проде выполняют атомарно?

      Если процесс упадёт между ними, ключ останется без TTL. Поэтому их объединяют в MULTI/EXEC или Lua-скрипт.

    4. В чём главный недостаток фиксированного окна?

      На стыке двух окон можно за очень короткое время пропустить до двух лимитов запросов: конец одного окна и начало следующего. Это исправляет скользящее окно.

  5. Rate limiter: скользящее окно на sorted set

    Исправить недостаток фиксированного окна: считать запросы за последние window секунд от текущего момента, храня время каждого запроса в sorted set.

    Методы
    Sorted Set Sliding window log ZREMRANGEBYSCORE

    Напиши allow_sliding(r, user_id, limit, window, now, request_id) -> bool. Клиент r эмулирует команды sorted set:

    • r.zremrangebyscore(key, min, max) — удалить элементы со score в отрезке [min, max] (границы включительно);
    • r.zcard(key) — число элементов;
    • r.zadd(key, {member: score}) — добавить элемент со score;
    • r.expire(key, seconds) — TTL на весь ключ.

    Алгоритм для ключа f"rl:sliding:{user_id}":

    1. удалить запросы, которые старше окна: score от 0 до now - window включительно — в окне остаются запросы из полуинтервала $(now - window,\ now]$;
    2. если zcard меньше limit — добавить текущий запрос (request_id со score now), продлить TTL ключа на window и вернуть True;
    3. иначе вернуть False, не добавляя запрос.

    Например, при limit=3, window=60 и запросах в 0, 10, 20 запрос в 30 отклоняется, а в 60 проходит: запрос из секунды 0 уже выпал из окна.

    Эти три команды в проде выполняют одним Lua-скриптом: иначе два параллельных запроса одновременно увидят zcard = 2 и оба добавят себя, превысив лимит. Плата за точность — память: sorted set хранит каждый запрос в окне, а не один счётчик.

    def allow_sliding(r, user_id: str, limit: int, window: int, now: float, request_id: str) -> bool: pass

    1. Почему для скользящего окна подходит sorted set?

      Score хранит время запроса, поэтому старые запросы удаляются одной командой по диапазону score, а число запросов в окне даёт ZCARD — всё на сервере, без выгрузки данных.

    2. Чем скользящее окно лучше фиксированного?

      Окно отсчитывается от текущего момента, а не от начала минуты, поэтому на стыке окон нельзя пропустить удвоенный лимит.

    3. Зачем выполнять команды лимитера одним Lua-скриптом?

      Иначе два параллельных запроса одновременно прочитают одинаковое число элементов и оба добавят себя, превысив лимит. Скрипт выполняется атомарно.

    4. Какая цена у точности скользящего окна?

      Память: хранится каждый запрос в окне, а не один счётчик. Для больших лимитов используют приближение — взвешенную сумму счётчиков текущего и предыдущего фиксированных окон.

  6. Лидерборд: семантика sorted set

    Разобраться, почему лидерборд в Redis делают на sorted set, реализовав его команды ZINCRBY, ZRANGE ... REV WITHSCORES и ZREVRANK на обычном Python.

    Методы
    Sorted Set ZINCRBY ZREVRANK

    Напиши класс Leaderboard с методами:

    • add(player, points) -> float — прибавить очки игроку (новый игрок начинает с 0) и вернуть его новый счёт, как ZINCRBY;
    • top(n) -> list[tuple[str, float]] — первые n игроков по убыванию счёта в виде пар (игрок, счёт), как ZRANGE key 0 n-1 REV WITHSCORES;
    • rank(player) -> int | None — место игрока в том же порядке, с нуля, или None, если игрока нет, как ZREVRANK.

    Порядок при равном счёте — как в Redis для REV: имена игроков в обратном лексикографическом порядке ("bob" выше "alice").

    Например, после add("alice", 50), add("bob", 80), add("alice", 40) вызов top(2) вернёт [("alice", 90.0), ("bob", 80.0)], а rank("bob") — 1.

    Простая реализация со словарём и сортировкой на каждый top работает за $O(N \log N)$ — для задачи это нормально. В Redis sorted set хранит элементы в skip list, поэтому ZINCRBY и ZREVRANK стоят $O(\log N)$, а топ-$n$ — $O(\log N + n)$ на миллионах игроков.

    class Leaderboard: def __init__(self): pass def add(self, player: str, points: float) -> float: pass def top(self, n: int) -> list: pass def rank(self, player: str): pass

    1. Почему лидерборд в Redis делают на sorted set?

      Sorted set всегда хранит элементы отсортированными по score, поэтому добавление очков, место игрока и топ-N выполняются одной командой за логарифмическое время прямо на сервере.

    2. Какие команды нужны для лидерборда?

      ZINCRBY для начисления очков, ZRANGE ... REV WITHSCORES для топа, ZREVRANK для места игрока и ZSCORE для его счёта.

    3. Как устроен sorted set внутри?

      Skip list, упорядоченный по score, плюс хэш-таблица «элемент → score». Первое даёт диапазоны и ранги за $O(\log N)$, второе — поиск счёта за $O(1)$.

    4. Как упорядочены элементы с одинаковым score?

      Лексикографически по имени элемента; в обратных командах (REV, ZREVRANK) — в обратном лексикографическом порядке.

    5. Где ещё в ML пригодится sorted set?

      Скользящие окна событий по времени, топ популярных товаров за период, очереди с приоритетом, хранение кандидатов для рекомендаций со скорами.

  7. LRU-кэш: как работает allkeys-lru

    Реализовать классический LRU-кэш с операциями за $O(1)$ — ту самую политику вытеснения, которую Redis применяет при maxmemory-policy allkeys-lru.

    Методы
    Политики вытеснения LRU OrderedDict

    Напиши класс LRUCache(capacity) с методами:

    • get(key) — значение по ключу или None, если ключа нет. Успешное чтение делает ключ самым свежим;
    • put(key, value) — записать значение. Запись тоже делает ключ самым свежим. Если после добавления нового ключа их стало больше capacity, удалить ключ, к которому дольше всего не обращались, и вернуть его; иначе вернуть None.

    Обе операции должны работать за $O(1)$: подойдёт collections.OrderedDict с методами move_to_end и popitem(last=False).

    Например, при capacity=2: put("a", 1), put("b", 2), get("a"), put("c", 3) — вытесняется "b", потому что "a" только что читали.

    Здесь LRU точный. Redis экономит память и делает приближённый LRU: берёт случайную выборку из maxmemory-samples ключей и вытесняет самый давний из неё. И вытесняет он по объёму памяти, а не по числу ключей.

    from collections import OrderedDict class LRUCache: def __init__(self, capacity: int): pass def get(self, key): pass def put(self, key, value): pass

    1. Какой ключ вытесняет LRU?

      Тот, к которому дольше всего не обращались: ни чтением, ни записью.

    2. Как получить LRU с операциями за O(1)?

      Хэш-таблица для поиска плюс двусвязный список для порядка обращений; в Python это OrderedDict с move_to_end и popitem(last=False).

    3. Почему LRU в Redis приближённый?

      Точный порядок обращений требует дополнительной памяти на каждый ключ. Redis берёт случайную выборку ключей и вытесняет самый давний из неё, что почти не уступает точному LRU.

    4. Когда LRU работает плохо и что взять вместо него?

      При разовых сканах большого числа ключей: они становятся «свежими» и вымывают действительно горячие ключи. В таких случаях лучше LFU, который учитывает частоту обращений.
