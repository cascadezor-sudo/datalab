Короткий справочник по окружению, секретам, параметризованному SQL, конфигурации, импорту и идемпотентности — с упражнениями на примерах из архива.

Зачем этот материал

Небольшие привычки снижают риск утечки доступа и помогают другому человеку запустить проект так же, как у тебя.

Зависимости и секреты

Фиксируй зависимости проекта в файле требований или используйте менеджер зависимостей с lock-файлом. Передавай пароли через окружение или локальный .env, который не коммитится.

# .env.example — шаблон без реальных значений
DATABASE_URL=your-local-connection-string

# .gitignore
.env
.venv/
__pycache__/
*.py[cod]

Секреты не должны появляться в исходниках, notebook, скриншотах и логах. Для общего репозитория оставь только шаблон с пустыми значениями.

Безопасный SQL: значения передавай параметрами

Не вставляй ввод пользователя в запрос через f-строку. Параметры защищают значения; имена таблиц и колонок нельзя передать как обычный параметр — для них нужны фиксированный список допустимых вариантов или безопасное построение выражений.

# psycopg2
cur.execute(
    "SELECT id, topic FROM post WHERE topic = %s LIMIT %s",
    (topic, limit),
)

Проверь также диапазон limit и возвращаемые поля. Ошибка параметризации особенно важна в API, где значения приходят от клиента.

Вынеси меняющиеся настройки

Пороговые даты, лимиты и параметры поведения удобно хранить в конфигурации; секреты — отдельно. Для YAML используй safe_load, проверь наличие обязательных ключей и типы значений при старте.

from pathlib import Path
import yaml

config_path = Path(__file__).resolve().parents[1] / "params.yaml"
with config_path.open(encoding="utf-8") as file:
    config = yaml.safe_load(file) or {}

feed_start_date = config["feed_start_date"]

Один параметр должен иметь одно место-источник. Не копируй один и тот же порог в API, notebook и DAG.

Проектируй повторяемый запуск

Идемпотентная операция при одинаковом входе приводит систему к одному и тому же результату. Это критично для Airflow retries и повторного запуска ноутбука.

Неудачный подход

При каждом повторе безусловно добавлять все строки ещё раз.

Лучше

Формировать данные для конкретного интервала и выполнять upsert по ключу или заменять только целевой раздел.

Определи ключ идемпотентности, интервал обработки и ожидаемое поведение при частичном сбое. В notebook избегай скрытой зависимости от уже исполненных ячеек: сделай перезапуск сверху вниз воспроизводимым.

Структура, логи и изменения

  • Запускай пакетный модуль из корня проекта через python -m package.module; избегай постоянного sys.path.append().
  • Оставляй бизнес-логику в импортируемых функциях, а входную точку — тонкой.
  • Пиши в лог ключевые параметры запуска, число обработанных строк и ошибки; пароли и персональные данные не логируй.
  • Делай небольшие коммиты с понятным глаголом и областью изменения, например fix: validate report date.

Структура демо из архива полезна как идея: приложение, SQL-функции и параметры разнесены по модулям. Пример из архива содержит учебные упрощения; переносить его целиком в рабочий проект не требуется.

Упражнения

  1. Найди и вынеси все секреты из учебного проекта в переменные окружения; добавь безопасный .env.example.
  2. Замени динамическую SQL-строку параметризованным запросом и добавь проверку диапазона лимита.
  3. Вынеси дату начала выборки в YAML и проверь ошибку при отсутствующем ключе.
  4. Запусти обработку одного и того же периода дважды и докажи, что дублей не возникло.
  5. Удали ручной sys.path.append() и проверь запуск через модуль из корня.
  6. Добавь логирование количества обработанных записей без вывода самих секретов.

Перед коммитом проверь diff и статус репозитория: секреты, локальные окружения, кэш Python и временные файлы не должны попасть в историю.
